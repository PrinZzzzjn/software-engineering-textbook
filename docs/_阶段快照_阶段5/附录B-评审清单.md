# 附录 B 评审清单（可复印）

评审不是「找茬」，是用同一把尺子检查交付物是否可交接。每张表逐项打勾；有一项说不清，就退回补充，不靠口头承诺。

## B.1 需求文档评审（第 3 章用）

| # | 检查项 | 通过判据 | ✓ |
| --- | --- | --- | --- |
| 1 | 角色与场景 | 写清「谁、在什么情况下、要做什么」 | ☐ |
| 2 | 功能清单 | 每条有编号、有优先级（MoSCoW） | ☐ |
| 3 | 用户故事 | 含角色、目标、价值三部分 | ☐ |
| 4 | 验收标准 | 每条可判定真假，有具体数值或状态 | ☐ |
| 5 | 非功能需求 | 性能、安全、易用性给出可测指标 | ☐ |
| 6 | 边界与异常 | 空值、重复、越权、失败路径都写明 | ☐ |
| 7 | 术语一致 | 同一对象全书同名，无「部门/单位」混用 | ☐ |
| 8 | 数据口径 | 明确为教学模拟数据，不含真实业务数据 | ☐ |

## B.2 接口设计评审（第 4、10 章用）

| # | 检查项 | 通过判据 | ✓ |
| --- | --- | --- | --- |
| 1 | 路径与方法 | 资源名用复数、方法语义与操作一致 | ☐ |
| 2 | 参数 | 路径 / 查询 / 请求体三类放对位置 | ☐ |
| 3 | 请求与响应模型 | 字段、类型、必填项都声明 | ☐ |
| 4 | 状态码 | 成功与各类失败分别约定，含 4xx 语义 | ☐ |
| 5 | 错误体 | 结构统一，能定位到字段 | ☐ |
| 6 | 文档 | 接口在 `/docs` 中可见且可试调 | ☐ |

## B.3 代码评审（第 15 章用）

| # | 检查项 | 通过判据 | ✓ |
| --- | --- | --- | --- |
| 1 | 可运行 | 干净环境按 README 能跑起来 | ☐ |
| 2 | 命名 | 见名知意，无魔法数字散落 | ☐ |
| 3 | 分层 | 路由 / 服务 / 模型职责不混写 | ☐ |
| 4 | 复用 | 重复 CRUD 已抽取，无整段复制 | ☐ |
| 5 | 异常 | 统一异常处理，事务边界清楚 | ☐ |
| 6 | 安全 | 密码不明文、令牌校验、越权被拦截 | ☐ |
| 7 | 测试 | 关键路径有测试，含一个失败用例 | ☐ |
| 8 | 配置 | 密钥与地址走环境变量，不写死在代码 | ☐ |

## B.4 交付清单（第 15、26 章用）

- ☐ 源代码与 `requirements.txt` / 依赖锁定文件
- ☐ `README.md`：环境、启动步骤、端口、默认账号说明
- ☐ `.env.example`（只给键名与示例值，不含真实密钥）
- ☐ 接口文档或 `/docs` 截图说明
- ☐ 测试执行结果说明
- ☐ 变更记录：本轮改了什么、为什么、影响哪些模块
- ☐ 已知问题与后续建议

> 一票否决（沿用课程教学计划）：涉密信息未脱敏、安全漏洞不处理、提交记录造假。书中数据为教学模拟数据，但保密意识与诚信要求不因此放宽。
