# 第 3 章 需求文档编写

> **节首信息条**｜对应课次 3 · 2 学时 · 实践｜前置：第 2 章的用户故事、验收标准与优先级；能使用 Markdown 或 Word 写结构化文档｜章末有质量评价量表、AI 了解性侧栏与本章提示页

上一章解决的是“一条需求怎么写”。但一个系统有几十条需求，分散在访谈记录、聊天消息和几个人脑子里，开发、测试和验收三方各拿一份不同的理解，问题就会在联调时集中爆发。需求文档（Requirements Document）的作用，是把这些条目组织成一份可评审、可交接、可追溯的契约。

本章把上一章的方法用一遍：从访谈记录整理功能清单（Function List），用 MoSCoW 排优先级，为用户故事补验收标准，再补非功能需求与约束，最后通过评审和修订落稿。重点不是再讲一遍概念，而是把文档真正写出来。

## 本章学习目标

读完第 3 章并完成实训后，你应该能：

1. 按“背景与目标、角色与职责、功能清单、优先级、用户故事与验收标准、非功能需求与约束”六块结构组织需求文档。
2. 把一条业务描述写成“动词 + 对象”的功能条目，并标注 Must / Should / Could / Won’t。
3. 为关键功能写出“给定—当—则（Given-When-Then）”形式的验收标准。
4. 检查需求文档内部的术语、字段与优先级是否一致，并组织一次可执行的评审。
5. 识别文档中的敏感信息并按教学模拟数据口径处理。

## 3.1 概念讲解

### 3.1.1 文档不是聊天记录的汇总

聊天记录回答“谁在什么时候说了什么”，需求文档回答“系统要做什么、做到什么程度算完成、依据是什么”。前者是过程材料，后者是契约。契约要能被不同角色使用：开发据此设计，测试据此写用例，验收据此判断是否通过。

因此，需求文档至少要做到三件事：说清边界，说清条目，说清验收。边界回答“做什么、不做什么”；条目回答“每一项功能是什么、优先级如何”；验收回答“怎样算完成”。缺了任何一件，文档就会退化成一份愿望清单。

### 3.1.2 需求文档的六块结构

一份可评审的需求文档通常包含六块内容。结构不必死板，但这六块对应的信息不能缺。

| 章节 | 写什么 | 合格标准 |
| --- | --- | --- |
| 文档信息 | 版本、日期、编写人、修订说明 | 能追溯每一版改了什么 |
| 背景与目标 | 系统解决什么问题、给谁用、不做什么 | 能说清系统边界 |
| 角色与职责 | 谁使用、谁被管理、各自能做什么、能看哪些数据 | 区分系统用户与业务人员 |
| 功能需求 | 功能清单、优先级、用户故事与验收标准 | 覆盖主要业务流程，条目可验证 |
| 非功能需求 | 性能、安全与保密、可用性、兼容性、可靠性 | 每条可度量 |
| 约束与假设 | 技术栈、部署环境、时间人员限制、前提条件 | 能判断方案是否可行 |

### 3.1.3 背景与目标：先划边界

背景与目标不是“项目简介”，而是边界的声明。它要回答三个问题：这个系统解决什么业务问题；给哪些角色使用；本期明确不做什么。

“不做什么”尤其重要。没有它，评审时每个人都按自己的想象补充范围，开发到后期才发现做多了或做偏了。把 Won't 写进文档，等于提前把范围争议摆到桌面上。

### 3.1.4 角色与职责：系统用户不等于业务人员

角色表要区分两类人：一类是系统的使用者，例如值班员、管理员；另一类是业务中被管理或记录的对象，例如被排班的人员。两者可能重叠，但职责不同。

每个角色至少写清三件事：主要操作、数据权限、不能做什么。数据权限是需求文档里最容易被漏掉的一栏，却直接决定后面的认证与授权设计。例如“普通用户只能查看本部门数据”就是一条必须写进需求、并在测试中验证的约束。

### 3.1.5 功能清单：动词加对象

功能清单的写法是“动词 + 对象”，例如“新增值班记录”“查询部门列表”“校验时间冲突”。这样写有两个好处：一是能直接对应到接口或操作，二是能暴露“页面清单”式的伪需求。

按业务域（Business Domain）分组，可以让读者看出主流程是否完整。一个值班系统的业务域通常包括登录与账号、部门、人员、工位、值班、查班、统计。分组之后逐域检查：每个域的主要操作是否都有对应条目？有没有把“页面”当成“功能”？

> 💡 **常见坑**：功能清单写成“部门管理、人员管理、值班管理”。这不是功能，是模块名。读的人不知道“管理”具体包含哪些操作，也无法判断做到什么程度算完成。

### 3.1.6 优先级：Must 不是“我觉得重要”

MoSCoW 的判定标准要具体。Must 的含义是“没有它，业务流程走不通”，不是“我觉得重要”。如果一份文档里一半以上都是 Must，等于没有排序。

一个实用的检查法是逐条问：如果本期不做这一条，哪条业务流程会断？会断的才是 Must；能用人工或现有工具替代的，通常是 Should 或 Could；本期明确不做的，写进 Won't 并说明原因。每条优先级后面写一句理由，评审时才有讨论依据。

### 3.1.7 用户故事与验收标准：给定、当、则

文档里的用户故事沿用上一章的格式，但验收标准可以写得更结构化，常用“给定—当—则”：

- **给定**某个前置条件；
- **当**执行某个操作；
- **则**系统产生某个可观察的结果。

例如：“给定部门与起止日期，当值班管理员查询值班记录，则列表返回该范围内的记录，并显示日期、时段、值班人员与工位。”这条标准可以被测试直接执行，也可以被验收人员直接判断。

验收标准要覆盖三类情况：正常流程、边界情况、异常情况。正常流程证明功能可用；边界情况证明规则完整；异常情况证明系统不会在错误输入下失控。INVEST 清单则用来检查故事本身是否独立、可协商、有价值、可估算、足够小、可测试。

### 3.1.8 非功能需求与约束：可度量才算需求

非功能需求覆盖性能、安全与保密、可用性、兼容性和可靠性。它们的共同要求是“可度量”。

| 类别 | 要写什么 | 示例 |
| --- | --- | --- |
| 性能 | 响应时间、数据量、并发 | 1000 条值班记录下列表查询 2 秒内返回 |
| 安全与保密 | 认证、授权、审计、脱敏 | 未登录不能访问；普通用户只能看本部门数据；联系方式脱敏 |
| 可用性 | 操作步骤、错误提示、学习成本 | 常用操作不超过 3 步；错误提示说明原因和处理办法 |
| 兼容性 | 浏览器、分辨率、网络环境 | 支持 Chrome/Edge 最新版；内网环境可离线部署 |
| 可靠性 | 数据备份、故障恢复 | 每日自动备份；异常退出后数据不丢失 |

约束与假设则记录外部条件：必须使用的技术栈、部署环境、时间与人员限制、必须遵守的规范；以及“部门与人员的基础数据由管理员提前维护”这类前提。假设一旦不成立，方案就要重评，所以它必须写出来。

### 3.1.9 一致性与评审：文档自己也要能对上

需求文档最常见的质量问题不是“写少了”，而是“前后对不上”：角色表里有“查班人员”，用户故事里却把查班操作写给了管理员；功能清单里有“导入导出”，却找不到对应的用户故事；正文叫“值班记录”，图表里叫“值班单”。

因此，落稿前要做四项一致性检查：角色名全文一致；功能清单与用户故事能一一对应；术语与字段名一致；交叉引用（编号、章节）指向真实存在的条目。评审清单就是把这四项检查固定下来，让不同的人按同一套标准看文档。

评审意见要具体、可执行。“写得不错”“再完善一下”不是评审意见；“功能清单未使用动词加对象，建议把‘部门管理’拆成查询、新增、修改、删除四条”才是。每条意见都要有处理结果：采纳、不采纳及理由，形成闭环。

### 3.1.10 涉密信息必须脱敏

本书面向部队院校场景，需求文档可能涉及人员、部门、值班安排等内部信息。文档中不得出现真实番号、人员姓名、具体驻地和敏感数据；示例数据要脱敏（De-identification），截图要打码。脱敏不是文档写完后的补救，而是从访谈记录开始就要遵守的纪律。

## 3.2 示范例题

#### 例 3-1：把访谈记录整理成功能清单与优先级【Bloom：应用】

**题目**：下面是某值班系统的访谈记录片段。请据此写出“功能清单与优先级”一节，列出 5 条功能，标注 MoSCoW 并各写一句理由。

> 值班管理员每天要排班，最怕两个人排到同一时段；值班记录现在记在纸上，月底统计要靠人翻；查班记录也分散；人员调动后，联系方式经常对不上。

**解**：

| 编号 | 业务域 | 功能 | 优先级 | 理由 |
| --- | --- | --- | --- | --- |
| F-01 | 值班 | 新增值班记录 | Must | 没有它无法记录值班，主流程走不通 |
| F-02 | 值班 | 查询值班记录 | Must | 排班核对与月底统计都依赖查询 |
| F-03 | 值班 | 校验同一人员同一时段重复值班 | Should | 很重要，但首期可先人工核对 |
| F-04 | 统计 | 按月份统计值班次数 | Should | 替代手工翻纸，首期可先导出后人工汇总 |
| F-05 | 查班 | 新增查班记录 | Could | 有更好；首期可沿用纸质记录，上线后再迁移 |

理由说明：每条功能都写成“动词 + 对象”；Must 只保留不写就无法走通主流程的两条；Should 与 Could 都给出了首期的替代办法，符合 MoSCoW 的判定标准。访谈记录中的“联系方式对不上”暂不进入本期功能，可在背景与目标中记为已知问题，避免范围膨胀。

#### 例 3-2：评审一份需求文档片段【Bloom：分析】

**题目**：下面是某需求文档片段。请按评审清单指出至少三处问题，并说明每条对应评审清单的哪一项。

> **3 功能需求**
>
> 系统要有部门管理、人员管理、工位管理、值班管理、查班管理、统计、登录、权限、导入导出、消息提醒。
>
> **用户故事**
>
> 作为管理员，我想要管理所有数据，以便系统正常运行。
>
> 验收标准：系统要好用、响应快。

**解**：

1. **功能清单写成名词清单**：没有使用“动词 + 对象”，也没有按业务域分组和标注优先级。对应清单项“功能清单按动词加对象编写，覆盖主要业务流程”。
2. **用户故事缺角色、功能与价值**：“管理员”过于宽泛，“管理所有数据”没有边界，“系统正常运行”不是价值。对应清单项“用户故事有明确的角色、功能与价值”。
3. **验收标准不可验证**：“好用、响应快”没有条件、没有指标，无法判断通过与否。对应清单项“验收标准可验证，覆盖正常、边界、异常”。
4. **缺少优先级**：十项功能没有 MoSCoW，无法判断本期范围。对应清单项“MoSCoW 划分合理，Must 有理由”。
5. **范围可能膨胀**：“消息提醒”未说明是否属于本期，背景与目标也未写“不做什么”。对应清单项“背景与目标说清了系统边界（System Boundary）”。

答出其中任意三处即可；每处都要指出问题与对应清单项，不能只写“写得不清楚”。

## ◆ 实训 3-1：需求文档编写（对应课次 3 · 2 学时）

### 一、任务目标与验收

| 目标 | 验收标志 |
| --- | --- |
| 文档六块结构齐全 | 六节标题齐备，每节有实质内容 |
| 功能清单可执行 | 每条为“动词+对象”，带优先级 |
| 关键功能有验收标准 | 至少 5 条“给定—当—则” |
| 文档内部一致 | 角色、字段、优先级无冲突 |
| 评审记录完整 | 列出问题、责任人与修改结论 |

### 二、课前准备

- 第 2 章产出的用户故事与利益相关者清单
- duty 系统的业务背景材料（教学模拟数据）
- 一份空白评审记录表

### 三、操作步骤

1. **搭文档骨架**
   - 做什么：搭文档骨架
   - 操作：新建 `需求文档.md`，按六块结构写标题
   - 预期输出：→ 六个二级标题齐备
   - 做错会看到什么：只有功能清单，缺背景与约束；回到本节结构表补齐
2. **写功能与优先级**
   - 做什么：写功能与优先级
   - 操作：`把功能逐条写成“动词+对象”，标 MoSCoW`
   - 预期输出：→ 每条一行，优先级可解释
   - 做错会看到什么：把“要好看”写成功能；改为可验收的非功能需求
3. **写验收标准**
   - 做什么：写验收标准
   - 操作：`给 5 条关键功能写“给定—当—则”`
   - 预期输出：→ 验收人能据此判断通过/不通过
   - 做错会看到什么：只写“正常显示”；补输入、动作与可观察结果
4. **评审与修订**
   - 做什么：评审与修订
   - 操作：`两人交换文档，按清单找问题并记录`
   - 预期输出：→ 评审记录含问题、责任人、结论
   - 做错会看到什么：评审变成互相夸奖；按“缺失、冲突、不可验证”三类找问题

### 四、排错清单

| 现象 | 先查什么 |
| --- | --- |
| 功能条目无法验收 | 缺少对象、条件或结果，改成“动词+对象+可观察结果” |
| 优先级全是 Must | 回到 MoSCoW 定义，Must 只留“不做就不能上线”的 |
| 验收标准写成实现步骤 | 写外部可观察行为，不写内部函数调用 |
| 文档前后字段名不一致 | 用全文搜索统一术语，必要时建术语表 |

### 五、提交与验收

## 本章小结

**核心结论**：

1. 需求文档是开发、测试与验收三方共用的契约，必须说清边界、条目和验收。
2. 结构上至少覆盖文档信息、背景与目标、角色与职责、功能需求、非功能需求、约束与假设。
3. 功能清单用“动词 + 对象”写，按业务域分组；Must 的判定标准是“不做则主流程走不通”。
4. 用户故事要写清角色、功能、价值；验收标准用“给定—当—则”，覆盖正常、边界与异常。
5. 非功能需求必须可度量；文档落稿前要做术语、角色、功能与交叉引用（Cross Reference）的一致性检查，并完成涉密信息脱敏。

**学完本章，你可以体会到**：需求文档不是写给老师看的作业，而是让开发、测试、业务三方少吵几次架的共用底稿。

## 本章提示页

> 先自己做，卡住了再看。提示按“方向 → 关键步骤 → 完整解答”排列。

**例 3-3（引导练习）：补全非功能需求【Bloom：应用】**

**提示 1（方向）**

安全要落到“谁能做什么、数据怎么保护”；好用要落到“几步完成、错误怎么提示”。

**提示 2（关键步骤）**

每条都要有可观察的条件和判断方式，例如“用不同角色账号尝试越权访问”。

**完整解答**

1. **安全与保密**：未登录不能访问任何业务页面；普通用户只能查看本部门数据；人员联系方式脱敏显示。度量方式：用不同角色账号尝试越权访问，均应被拒绝；检查列表页是否只显示脱敏后的号码。
2. **可用性**：新增值班记录的常用流程不超过 3 步；必填项缺失时提示缺哪一项以及如何补。度量方式：按流程走查并记录步骤数；逐项触发校验，检查提示内容。

**例 3-4（引导练习）：改写模糊条目【Bloom：应用】**

**提示 1（方向）**

第一条要拆成角色、操作对象、操作范围；第二条要落到认证、授权、审计或脱敏。

**提示 2（关键步骤）**

每条改写后应能直接写出验收标准；写不出验收标准的改写还不算完成。

**完整解答**

1. 作为系统管理员，我想要新增、修改和停用部门与人员账号，以便组织结构变化时系统数据保持准确；管理员不能查看值班人员的联系方式明文。
2. 未登录用户不能访问业务接口；普通用户只能访问本部门数据；所有新增、修改、删除操作记录操作人、时间与对象；联系方式在列表页脱敏显示。
