# 第 15 章 后端开发综合实践（二）

前面各章分别完成了用户、部门、人员、执勤记录和统计。每个模块单独看都能跑，但真实使用是把它们串起来：管理员先登录，创建普通用户，再建部门和人员，然后录入执勤记录，最后查统计，并验证普通用户看不到管理数据。任何一步的字段、权限或数据依赖对不上，整条链路就会断。

本章不写新功能，做三件事：按清单跑通全流程，整理可交接的成果，做一次三分钟展示。目标是把“代码写完了”变成“系统真的能用，而且能说清哪里还不能用”。

## 本章学习目标

读完本章，你应该能：

1. 把重复的 CRUD 抽取为通用基类或服务层，说明路由/服务/模型的职责边界，并在新模块中复用。
2. 能为后端模块编写 pytest 单元测试与接口测试，覆盖正常、边界与异常路径，并据失败信息定位缺陷。

## 15.1 概念讲解

### 15.1.1 联调：按真实使用顺序串接口

单元测试验证“一个接口对不对”，联调验证“一串接口能不能配合”。联调的顺序应当接近真实使用：登录 → 建用户 → 建部门/人员 → 建执勤记录 → 查统计 → 验证权限。

```mermaid
flowchart LR
    A[管理员登录] --> B[创建普通用户]
    B --> C[创建部门与人员]
    C --> D[创建执勤记录]
    D --> E[查询统计]
    E --> F[验证普通用户 403]
```

*图 15-1：后端主流程的联调顺序*

每一步都要记录“请求 → 期望结果 → 实际结果”。失败时不要从头重来，先定位是哪一步断的。

### 15.1.2 全流程清单

| 步骤 | 请求 | 期望 |
| --- | --- | --- |
| 1 | 管理员登录 | 200，拿到令牌 |
| 2 | 创建普通用户 | 201 |
| 3 | 普通用户登录 | 200 |
| 4 | 普通用户查用户列表 | 403 |
| 5 | 管理员建部门 | 201 |
| 6 | 管理员建人员（带 `dept_code`） | 201 |
| 7 | 管理员建执勤记录 | 201 |
| 8 | 再建一条时间重叠的记录 | 400 |
| 9 | 查年度统计 | 200，数字正确 |
| 10 | 查时段分布 | 200，24 项 |
| 11 | 不带令牌访问 `/users/me` | 401 |
| 12 | 缺字段新增部门 | 422 |

清单的价值在于“可证明”：每一步都有明确的期望，通过与否不靠感觉。至少跑通主流程，失败步骤要写清原因。

### 15.1.3 排查顺序：状态码 → detail → 日志 → 定位 → 重跑

联调失败时，按这个顺序排查：

1. 看状态码：401 是身份、403 是权限、404 是路径或资源、422 是参数、400 是业务规则、500 是代码或环境。
2. 看 `detail`：它通常已经指出具体原因。
3. 看服务日志：500 的堆栈在日志里，不在响应里。
4. 定位到具体接口与字段：是哪一步、哪个参数、哪张表。
5. 改完重跑清单，而不是只重跑失败的那一步。

不要一上来就改代码。先确认“哪一步、什么错”，再决定改哪里。

### 15.1.4 常见卡点

| 卡点 | 可能原因 |
| --- | --- |
| 普通用户登录失败 | 账号被禁用（`is_active` 为 0） |
| 普通用户能看管理列表 | 管理接口没挂管理员依赖 |
| 建人员失败 | `dept_code` 不存在，或字段名与接口不一致 |
| 重叠记录没有被拒绝 | 重叠条件写错，或只查了部分记录 |
| 统计全是 0 | 年份或人员参数不对，或记录确实为空 |
| 联调 404 | URL 前缀、尾斜杠或路径参数不一致 |

### 15.1.5 契约不一致：文档、代码、调用方三处对账

联调中最常见的问题不是“代码坏了”，而是“三处说法不一致”：设计文档写 `sort_order`，代码用 `order`；文档写 `dept_id`，代码用 `dept_code`；前端按旧字段名传参，后端已经改了。

处理原则：以实际代码与 `/docs` 为准，把文档改过来；前端按 `/docs` 调整。三处必须收敛到同一个说法，否则每次联调都要重新猜。

### 15.1.6 成果清单：交付不只是代码

一份可交接的成果至少包括：代码在 Git 仓库且提交记录完整；接口文档（`/docs` 或 Markdown）；能运行的测试；一份“做了什么”的清单；一份“已知问题”列表。已知问题要写出来，不要藏；藏起来的问题会在验收时集中爆发。

### 15.1.7 三分钟展示：做了什么、能跑什么、还有什么问题

展示按四段组织：做了哪些模块；演示 1–2 个能跑的接口；遇到的最大问题与解决办法；还有什么没做完。展示的重点不是“功能多”，而是“能说清边界”：能跑什么、不能跑什么、为什么。

### 15.1.8 专题二的知识地图

用户模块解决“你是谁”；部门与人员模块解决“数据怎么管”；执勤记录模块解决“业务规则怎么落”；统计模块解决“多条记录怎么汇总”。四层依次依赖：没有用户就没有权限；没有部门与人员，执勤记录没有关联对象；没有记录，统计没有数据。

## 15.2 示范例题

#### 例 15-1：实现执勤记录列表接口【Bloom：应用】

**题目**：实现 `GET /duty-records`，支持按人员证件号过滤与分页，返回 `items` 与 `total`。说明参数来源与返回字段。

**解**：

```python
@router.get("/duty-records")
def list_duty_records(
    personnel_certificate_number: str | None = None,
    page: int = Query(1, ge=1),
    page_size: int = Query(10, ge=1, le=100),
    db: Session = Depends(get_db),
):
    query = db.query(DutyRecord)
    if personnel_certificate_number:
        query = query.filter(
            DutyRecord.personnel_certificate_number == personnel_certificate_number
        )
    total = query.count()
    items = query.order_by(DutyRecord.start_time.desc()).offset((page - 1) * page_size).limit(page_size).all()
    return {
        "items": [
            {
                "id": r.id,
                "personnel_certificate_number": r.personnel_certificate_number,
                "workstation_id": r.workstation_id,
                "start_time": r.start_time,
                "end_time": r.end_time,
            }
            for r in items
        ],
        "total": total,
    }
```

参数来源：人员证件号是筛选条件，放查询参数；分页也是查询参数；路径里没有单个资源标识。返回只包含列表需要的字段，不返回内部备注等无关内容。

#### 例 15-2：定位联调中的 403【Bloom：分析】

**题目**：联调第 4 步“普通用户查用户列表”期望 403，实际返回 200。请分析最可能的原因，并给出排查与修正步骤。

**解**：

1. 200 说明请求成功，身份已通过认证；问题不在登录，而在授权。
2. 最可能的原因：用户列表接口没有挂管理员依赖，普通用户也能访问。
3. 排查：打开该接口的路由定义，看是否有 `Depends(get_current_admin_user)`；再看依赖内部是否真的检查了 `role`。
4. 修正：在路由或函数参数上挂管理员依赖；用管理员、普通用户、未登录三种请求分别验证 200、403、401。
5. 回归：跑权限相关测试，确认没有把普通接口也误加管理员限制。

## 15.3 引导练习

#### 例 15-3（引导练习）：串起创建部门到创建执勤记录的链路【Bloom：应用】

**题目**：按“建部门 → 建人员 → 建执勤记录”的顺序，写出三步请求的关键字段与期望状态码，并说明每一步依赖前一步的哪个值。

<details><summary>提示 1（方向）</summary>

人员需要 `dept_code`；执勤记录需要人员证件号与工位编号。

</details>

<details><summary>提示 2（关键步骤）</summary>

先建部门拿到 `dept_code`，再用它建人员；先确认人员与工位存在，再建执勤记录。

</details>

<details><summary>完整解答</summary>

1. 建部门：`POST /departments`，请求含 `dept_code`、`full_name`，期望 201；产出 `dept_code`。
2. 建人员：`POST /personnel`，请求含 `certificate_number`、`name`、`dept_code`（来自第 1 步），期望 201；产出 `certificate_number`。
3. 建执勤记录：`POST /duty-records`，请求含 `personnel_certificate_number`（来自第 2 步）、`workstation_id`、开始与结束时间，期望 201。

依赖关系：人员依赖部门的 `dept_code`；执勤记录依赖人员的 `certificate_number` 与已存在的工位。

</details>

## 本章小结

**核心结论**：

1. 联调按真实使用顺序串接口：登录 → 用户 → 部门/人员 → 执勤记录 → 统计 → 权限验证。
2. 排查按“状态码 → detail → 日志 → 定位 → 重跑”的顺序，先确认哪一步、什么错，再改代码。
3. 契约不一致是联调的高频问题；以实际代码与 `/docs` 为准，把文档、代码、调用方收敛到同一个说法。
4. 交付不只是代码：Git 记录、接口文档、可运行测试、成果清单、已知问题，缺一不可。
5. 展示要说清边界：做了什么、能跑什么、还有什么问题；能解释比功能多更重要。

**与持久理解的呼应**：本章推进了「软件工程的价值不在于多写代码，而在于用可验证的过程把不确定性逐步收敛为可交付的系统」与「接口契约是前后端并行开发的共同语言」——通过全流程清单与契约对账，读者看到“能跑”如何被证明为“可交付”。
