## 一、总体判断

计划把重排主要理解为「内容跟着原章走、章号跟着新位置改」（第四节改法规则）。这个规则对**带章号的引用**是有效且必要的，但恰好覆盖不到用户担心的两件事：

- **承接关系**的大部分是**不带章号**的句子（「下一章」「上一章」「接下来」「本章的作用」），计划第四节的 63 行清单是按章号检索得到的，天然漏掉这一类；
- **行文可读性**根本不是章号问题，而是「删掉的论述用什么补回来」的问题，计划 3.1–3.4 的操作列几乎全是「保留 / 删除 / 改号 / 重编号」，没有一条规定改写后的论述按什么口径写、按什么判据验。

一句话：**计划是一份合格的「搬迁方案」，还不是一份合格的「重写方案」。**

## 二、焦点一：逻辑设置与前后承接

### 2.2 P0-2（必补，最严重）：数据接口裸奔 × 新 09 章的最小权限

这是重排后**唯一会让教材自相矛盾**的地方，现计划完全没有讨论。

- 实测：原 08 章 `/departments` 的新增/详情/删除/分页列表（L354–398、L455–463、L543–549）与原 09 章列表接口（L232–235）**只挂 `Depends(get_db)`，没有任何认证/授权依赖**；原书里 dept 接口从第 4 章起全程裸奔，因为认证（原 06）在数据章（原 08）之前，教材也没回头补。
- 重排后顺序反了：新 06/07 **大张旗鼓地建出** dept 的完整 CRUD、分页、过滤、排序（接口规模远大于 05 章那五个），新 08 讲认证，新 09 讲「越权要挡在接口入口」「前端隐藏按钮只改变看不看得见，不改变接口是否执行」「最小权限」。学生合上书会发现：自己刚写完的两章数据接口，正好是本章定义的越权敞口。
- 计划第二节第 4 条称「依赖链仍然正向，没有回指的环」，**这句结论不成立**：章号上无环，但机制上存在明确的回头应用——新 08/09 的权限依赖必须套回新 06/07 已建的接口。

三种处理，建议取 A：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）显式前向声明 + 章末回收** | 新 06 章首声明「本章接口先开放，身份与权限在第 8、9 章统一加」；新 09 章末给一个明确动作：把 `Depends(get_current_admin_user)` 挂到已建的数据接口上，并说明这一步为何不能省 | 只加两段论述 + 一处代码，不动 06/07 主体 |
| B 回头改代码 | 新 08 加认证时把 06/07 的 controller 一并改 | 06/07 正文与实训全部返工，违背「重排不是整章搬家」的初衷 |
| C 权限提前到数据章 | 06/07 就讲授权 | 违反用户「只调顺序、内容随章走」的裁决 |

### 2.3 P0-3（必补）：实训 6-1 的唯一参考工程仍是内存版

实测 `实训手册/实训6-1/项目/` 共 19 个 `.py`：`department/model.py` 与 `user/model.py` 均为 `@dataclass` + `TABLE: list[...] = []`，`user/crud.py` 注释还写着「第 8 章换库时五个函数都会多出 db: Session 参数」，**没有 `database.py`、没有 SQLAlchemy、没有 Session**。

而计划 3.3 已把新 08 认证章定为「落库版起步」，3.1 把新 06 定为「dept 落库」。计划第五节对这套工程的处理只有 `git mv` 改名 + 更新 README/指南/验收记录/注释，**没有改工程代码**。结果是：教材第 6 章已建库、第 8 章 user 已落库，学生照着实训手册做出来的仍是无库的内存工程，且 `department` 也是内存版（与新 06 冲突）。

这是「前后承接」里最刺眼的一处，因为实训手册是唯一带四件套与可运行参考工程的材料。必须把「参考工程改造」列为独立 Task：加 `database.py` + 依赖、`department` 与 `user` 两模块落库、注释去内存，并跑通注册/登录/受保护接口。计划第八节第 6 条「参考工程（若改名后）可启动」应改为「落库版参考工程可启动且接口全通」。

> 附注：计划第六节写「参考工程代码不动」，指的是 `项目参考/duty-simplified/`，措辞上容易被实施者误读成实训手册的 `项目/` 也不动，建议加括号澄清。

### 2.4 P1-4（建议补）：新 07 的第二示例前提不成立

计划 3.2 判定「原 09 章正文内容无需改写」，依据是第二示例已换成 personnel、与 user 位置无关。这个判断只解决了一半。

实测 09 章 9.1 原文：「**比较单位模块与人员模块的列表查询**…**两个模块的 `crud.py` 并排放在一起**」，9.5「换一个模型仍一字不改」的复用判据也依赖两个真实模块。但重排后：dept 在**新 06 课内**完成，`users` 表在新 06 建而 user 的 crud 要到**新 08** 才写，**人员模块只是新 06 的 8.4 课后拓展**（计划 3.1 明确「保留」），既非课内必做，也无统一形态。课次 6→7 间隔又短。学生翻开新 07 时，手上大概率只有一份 `crud.py`。

计划应补一条衔接口径，二选一：①把 8.4 的人员模块从「课后拓展」提为课内必做并给出最小 `crud.py`（会动 4 学时负荷）；②把 9.1 改为「本章给出人员模块的列表查询代码，与第 6 章的 dept 并排比较」，并在 9.5 的回归判据里说明示例代码的出处。**「正文无需改写」这句应从计划中删掉。**

### 2.5 P1-5（建议补）：三处「改了数字，逻辑没改」

- `05 章 L69/L70/L78/L272/L302/L346/L347`：「`crud.py` 由 4-1 迁入（内存）→ 第 8 章换数据库」「`security.py` 在第 6 章，`database.py` 在第 8 章」「依赖清单里 sqlalchemy 第 8 章加入」。这些表的排列**体现「第一次需要」的先后**，重排后不只是 8→6、6→8，两行的**先后位置也要对调**，否则第 5 章会写成「先加 security 后加 database」，与新章序相反。

## 三、焦点二：论述的行文可读性

### 3.1 P0-4（必补）：最大的可读性塌陷点在 3.1 的 8.1 改写

计划 3.1 要求：「**删除整段 user 落库演示（原 8-1-3～8-1-6、对比表、L85–220，约 135 行）**，改为追加 departments 与 users 两个表模型，『一句带过：字段含义在用户模块章展开』」。

原 8.1 那 135 行不是冗余，它承担了本章唯一的推导链：**为什么要 engine / Session / Base / get_db 四件套、为什么换库只动 model 与 crud、为什么哈希与令牌一行不用改**。删掉后，章首一句「服务一停就清空」只回答了「为什么要落库」，没回答「为什么是这样一套东西」，8.1 就变成 `database.py` 代码块 + `create_all` 三行 + 两个模型定义——正是 **C22（2026-11-19 裁定）明令禁止的「先看这张表」式开篇甩结论**：表格/代码成了结论的替代，删掉代码后读者推不出它。

计划应把这一格改成「**删 user 落库演示，但把其中的推导链改写为 dept 落库的推导**」：从「内存表里同一编码能写两次、重启就没、多人读写各持一份」三个具体缺口，推出「需要一张表 + 一次连接 + 一次会话 + 一处声明」，再落到 `database.py` 的四件套，最后才给代码块。字数可比原段短，但**推导步骤一步不能省**。

同类风险还有 3.3 的「6.1 四核心字段表保留、删 TABLE 与 dataclass」：原 6.1 有「为什么先用内存版描述用户数据」的论述，删掉后字段表前面同样没有推导，须补「认证需要系统存什么」的反推。

### 3.2 P1-6（建议补）：悬空代码块，并反过来影响待裁决点 1

「一句带过『字段含义在用户模块章展开』」会造出一个**讲了表结构却不讲字段含义**的代码块：学生在新 06 看到 `users` 表的四个字段，却被告知两章后再解释。按现行「节标题＝功能化知识条目、按知识条目组织不按代码出现顺序」的口径，这一段的知识条目属于用户模块，硬塞进「让数据落地」节是错位的。

由此**从行文可读性反推待裁决点 1，结论与计划的推荐项相反**：

| | 计划推荐：users 表在新 06 建 | 备选：users 表留到新 08 建 |
| --- | --- | --- |
| 改动量 | 较小（计划原判据） | 新 08 多一个建表代码块 |
| 推导链 | 06 章同时讲 dept + users 两个业务对象，单一主线被打断，且 users 字段含义悬空 | 06 章只讲 dept，推导链完整闭合；08 章「认证需要存什么」与 users 建表在同一节，字段含义即时兑现 |
| 叙事 | 「地基先于用户」 | 用户要的「数据层地基」= engine/Session/Base/get_db + 落库范式 + CRUD + 查询复用，**users 表本身不是地基**；地基章讲完范式，认证章在同一范式下建自己的表，反而更能体现「地基可复用」 |

建议把待裁决点 1 的推荐项改为备选，并把「避免悬空代码块、保持章内单一主线」写成判据；若仍取推荐项，则必须在新 06 补一段 users 四字段的含义（不能只「一句带过」）。

### 3.3 P1-7（建议补）：现行行文硬口径没有进入改写红线

计划的改写指令里没有一处提到本项目已生效的行文约束。重排是**最容易触发这些红线**的操作，建议新增「改写红线」小节，明确以下条款只写给实施者、**不得进入学生稿**：

1. **C22 逻辑链**：概念讲解先提本节要回答的问题 → 拆解/归纳/反推 → 才得出表格或代码；判据是「删掉表格/代码块后，读者仍能顺着文字推出它」。不要用场景故事切入。
2. **正文禁作者口吻与修订逻辑**（2026-11-20 裁定）：严禁「本章按教学需要简化为…」「刻意只保留…」「目的是让学生看清…」「演示要点/前向指引」，以及内部编号（C13、K3/K7、待签/TODO）。**特别提醒**：计划里「删除整段 user 落库演示」「前移」「重编号」「习题随章对调」这类话，是改写指令，若被照抄进正文即违规；学生不该知道「书是怎么改的」。
3. **节标题＝功能化知识条目**，按知识条目组织、不按代码出现顺序；节标题编号 `N.k` 连续，示范例题/独立习题/小结无编号。
4. **三段式**、纯纸质（无二维码/数字挂载点/`<details>`）、示范例题解答随题印、独立习题答案入 98。
5. **代码块编号随节重编**：04 章曾留下指向已不存在小节的 `4-6-x`，本轮四章大改须按新节号逐个核对。

### 3.4 P1-8（建议补）：第八节验证方案缺行文验收判据

现有 6 条验证全是结构/编号/学时/门禁 + 第十节一句「人工精读一遍」。用户担心的行文可读性在验收环节**没有任何可检查项**。建议补 4 条：

1. **接力朗读**：按 2.1 表逐格读 05 末→06 首→…→09 末→10 首，每格能回答「上一章留下了什么、本章为什么接着做」，且无「下一章内容对不上」。
2. **推导链抽查**：新 06 的 8.1、新 08 的 6.1 两处，遮住代码块/表格后仍能复述出为什么需要这些对象；不满足即退回改写。
3. **修订口吻检索归零**：在新 06–09 章内检索「原第 / 前移 / 本次调整 / 改写 / 演示 / 按教学 / 留待 / 后续章再讲 / TODO / 待签」等词，命中即人工判定。
4. **代码事实对照**：四章与 `项目参考/duty-simplified/`、`实训手册/实训8-1/项目/` 的 model/crud/security/依赖清单逐项一致（尤其 user 落库、security 无 JWT、create_admin 为数据库脚本）。
