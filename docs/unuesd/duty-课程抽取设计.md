# duty 项目 → 课程内容抽取设计

> 以 `项目参考/duty`（值班数据统计服务）为单一主线项目，从中抽取模块填入现有课程体系。
> 课次标题不改，只把每个课次的通用主题锚定到 duty 的具体模块上。
>
> 本文档随讨论更新，记录已确定的设计决策；未定项见第 9 节。

## 1. 设计意图

- duty 是一个**真实、完整、可运行**的 FastAPI 后端项目，分层清晰、自带测试与部署配置，适合作为"示例代码库"。
- 课程原有教学计划是**通用骨架**（用户管理 / 数据管理 / 业务逻辑 / 前端 / 部署），场景待定。duty 提供具体场景：**值班数据统计（军事信息管理系统方向）**。
- 学生在 26 个课次中**沿着 duty 逐步构建**，到课程结束时得到一个前后端完整、可部署的系统。
- **不必覆盖全部模块**，也**不必每个模块都在课上完成**；未覆盖的模块作为扩展任务，由学生自选完成并计入考核。
- **进度即完成**：随着课程推进，duty 的功能逐步完整，学生"体会"项目的逐步完成。

## 2. 抽取原则

1. **不改课次标题** —— 保持现有教学计划结构不变。
2. **从项目中抽取模块填入课程** —— 每个课次的通用主题用 duty 的具体模块实例化。
3. **不全覆盖** —— duty 的 10 个业务模块中，只选一部分作为课上主线。
4. **不必每模块课上完成** —— 课上讲授 + 学生动手做一部分，其余作为扩展。
5. **进度即完成** —— 随着课程推进，duty 的功能逐步完整。

## 3. AI 使用约束（时有时无环境）

> 已确认：上课环境的 AI 情况为**时有时无、不可预期**。已存在派生文件
> `课程教学计划_院校版-1117-弱化AI.md`，政策口径已处理，本设计以其为基线。

**硬规则：任何一个课次，没有 AI 也必须能完整达成教学目标；有 AI 时只是更快、更好，而不是"能多做一截"。**

落地为三条：

1. **基线采用弱化 AI 版**：AI 不进考核、不做强制产出；教材保留 AI 内容，教学口径按环境可选处理。
2. **双层任务设计**：每个课次设"无 AI 核心任务"（必做、可完成）+ "AI 加速层"（可选，有则用）。两种环境共用同一份教案，只差第二层。
3. **产出标准从"写得多"改为"读懂—改对—讲清"**：用 duty 当脚手架，学生在其上修改、扩展；以"解释你改了什么、为什么"防复制粘贴，考核补答辩/解释环节。

**基础教学形态（已定 C：前期自己敲、后期改脚手架）：**

- 前期（auth / dept 等模式样板模块）：学生对着 duty 参考自己敲，建立手感；user 作为复制 dept 的练习（读改）。
- 后期（personnel / workstation / duty_record 等复杂模块）：转为在 duty 脚手架上"读 → 改 → 扩"。
- 与教学计划已有的"教师示范 → 学生模仿 → 独立探索"渐进模式一致。

**课程定位不变**：课名"AI 时代的软件工程实践"保留，AI 从"工具操作"转为"认知与审查能力"——知道 AI 会生成什么、怎么验证、哪里会错，无需真用也能讲、也能考。

## 5. 专题一重新设计（6 学时，保持 4 理论 + 2 实践）

### 5.1 诊断

1. **概念没有锚点**：学生没做过项目，生命周期、敏捷落不到具体物上。
2. **需求分析是"软技能"**：不好演示，也不好像代码那样即时验证对错。
3. **课次 2 / 3 内容模糊**：两节都在讲"需求获取 + 文档 + 用户故事 + 优先级"，边界不清，学生感觉听了两遍。
4. **案例虚构**：装备管理、训练计划系统学生既没接触过，也没法对照答案。

### 5.2 总思路

从"讲概念"改为**"拆一个真实系统"**：学生面对 duty 这个真实系统，**先猜 → 再拆 → 后对照**，从用户视角反推需求。核心手法是"**先猜后对照**"——猜在前、答案是后给的，既让需求分析可验证、有即时反馈，又避免照着文档抄。

### 5.3 课次 1：「先经历、后命名」

概念不当作起点，当作学生自己推出来的结论。定义出现在第 3–4 步，不是第 1 步。

1. **开场制造问题（10 分钟）**：跑起 duty 或放操作截图。问"如果明天让你做一个一模一样的，你第一步做什么？"小组写前三步。
2. **暴露混乱（20 分钟）**：展示"想到哪写到哪"的小功能 vs duty 中同一功能的分层写法。问"哪个以后改起来更痛苦？"——工程化的价值由学生自己说出口。
3. **对照真实开发顺序（15 分钟）**：翻开 `开发步骤.md` 章节顺序，和学生写的前三步对照，问"你们差在哪？"
4. **概念命名（15 分钟）**：此时才讲生命周期五阶段、敏捷迭代，用 `开发步骤.md` 的分阶段推进当例子。
5. **小组归类（20 分钟）**：把 duty 的文件归到生命周期各阶段——`app/`→编码，`tests/`→测试，`Dockerfile`→部署，`api说明.md`→设计，`开发步骤.md`→？讨论"文档属于哪个阶段"这类无标准答案的问题。
6. **收束（10 分钟）**：软件工程不是"多写文档"，是"让复杂的东西可控"。

### 5.4 课次 2 与课次 3 的边界

一句话：**课次 2 讲"怎么问、怎么写"，课次 3 是"真的问、真的写"。**

**课次 2（理论，2 学时）— 只教方法，不产出文档**
- 用 duty 的**用户视角**（菜单、操作流程）让学生猜"后台得有哪些功能"。
- 亮出 `api说明.md` 的接口清单对照："你漏了什么？为什么漏？"→ 引出访谈 / 观察 / 文档分析三种方法各能补什么。
- 讲用户故事格式，用"烂故事 vs 好故事"对比。
- 讲 MoSCoW 优先级。产出：每人给一个模块写 3–5 条用户故事。

**课次 3（实践，2 学时）— 真的做一遍**
- 分组角色扮演：一方演"值班业务骨干"，一方演"开发"。
- 写功能清单 + MoSCoW + 用户故事与验收标准 + 非功能需求。
- 对照 duty 真实模块评审：抓准了什么、漏了什么、多想了什么。
- 产出：需求文档 v1，作为专题二的设计输入。

### 5.5 课时

保持 **4 理论 + 2 实践**，不改学时结构；概念讲不动靠改讲法解决。若课次 3 评审做不完，再从专题三借 2 学时（Streamlit 26 学时有余量）。

## 7. 前端补充计划（专题三）

**定位已定 A：教师参考实现。** 教师写一份完整、规范的 Streamlit 前端，学生照此构建；学生版以后按需删减。这与"自己先写一个前端，再给课程作参考"一致。

**范围：先做一条最小垂直切片，不按模块铺开。**

1. **登录页** —— 对接 `auth`，重点演示 JWT 存入 `session_state`、按登录态切换页面。这是 Streamlit 最易翻车、最需要参考实现的地方。
2. **一个通用 CRUD 页** —— 以 `dept` 为样板：列表 + 筛选 + 分页 + 新增/编辑表单。**做成可复用模式**，课上 7 个模块的界面本质都是它的实例，这本身就是"抽象与复用"的教学点。
3. **一个数据仪表盘** —— 读 `duty_record` 或 `analytics`，画 1–2 张图，覆盖课次 21。

这套内容覆盖专题三完整教学弧线（组件 → 布局 → 联调 → 仪表盘），无多余代码。

**实现顺序：先纵向打通，再横向铺开。** 先跑通"登录 → 调 dept 列表 → 显示"，再补表单、分页、仪表盘。因为专题三最难教的是联调（课次 19/20），一条链路通了，后面都是复制扩展。先能跑，再好看——视觉优化是课次 21 的事，案例第一版不追求。

### 7.1 已完成的参考实现

位置：`项目参考/duty_frontend/`（美化版）；`项目参考/duty_frontend_basic/`（基础版，课次 21 对比用）。

两个版本功能完全相同，差异只在视觉与页面组织：基础版展示"能用"的界面；
美化版加入青绿主题、Hero 横幅、卡片化、tabs 分区、column_config 中文表头、
KPI 卡片与 toast 提示。

美化版结构：

```
duty_frontend/
├── .streamlit/config.toml # 青绿主题
├── Dockerfile             # 前端容器化（专题四）
├── .dockerignore
├── app.py                 # 入口：登录门禁 + 首页（Hero + 功能卡片）
├── config.py              # 后端地址、分页、超时
├── api_client.py          # 统一请求封装（Bearer、统一错误、401 处理）
├── auth.py                # 登录（居中卡片）/ 登出 / 页面访问守卫
├── ui.py                  # 主题色、CSS、Hero、卡片、flash
├── components/table.py    # 表格 + 分页 + column_config
├── pages/1_部门管理.py     # tabs：列表 / 新增 / 编辑删除
├── pages/2_数据统计.py     # 筛选卡片 + 4 个 KPI + 两张图表卡片
├── requirements.txt
└── README.md
```

部署参考：顶层 `项目参考/docker-compose.yml` 编排 `duty`（后端，8000）与
`duty_frontend`（前端，8501）；后端沿用既有 `duty/Dockerfile`，前端新增
`duty_frontend/Dockerfile`。前端容器通过 `DUTY_API_BASE_URL=http://backend:8000`
访问后端，后端日志通过 `./duty/logs` 映射出来。`docker compose config` 已校验通过；
镜像构建需要本机 Docker Desktop 的 Linux 引擎已启动。

视觉参数（已校验）：主题色 `#0F766E`（teal-700），页面底色 `#F8FAFC`，卡片白色；
图表系列色 `#0D9488`（teal-600），在白底与 `#F8FAFC` 底上亮度带、色度、对比度均通过；
第二系列备用色 `#EB6834`（橙），配对校验通过。

已验证：后端 `duty` 启动后，三个页面均可无异常渲染；登录流程、
部门 CRUD（含中文）、三个 analytics 接口均实测通过。

**接口契约要点**（`duty/api说明.md` 已于 2026-10-26 按实际代码校正，以下仍作为课堂强调点）：
- 部门列表是 `/api/v1/departments/`（复数、带尾斜杠）；
- 部门列表排序参数是 `sort_order`，人员列表才是 `order`；
- 创建部门的 `DepartmentCreate` **要求 `dept_code` 必填**；
- 站点维度统计只有 `/analytics/workstation-duty-yearly`（按工位），
  没有"某人员跨站点分布"的接口；统计页第二张图因此使用
  `staff-duty-yearly` 返回的**月度值班分布**，与第一张"24 小时时间分布"形成两个维度。
