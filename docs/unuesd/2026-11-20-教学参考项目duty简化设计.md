# 教学参考项目「执勤排班 duty-simplified」设计

- 日期：2026-11-20
- 状态：已签字（2026-11-20 用户裁决：新建 duty-simplified/，旧 duty 改名历史基线；2026-11-20 第二轮：架构设计按"六文件+砍泛型、无 JWT、四依赖、最小烟测"落定）
- 上位依据：用户 2026-11-20 裁决——「建立一个教学参考项目替代目前的 duty 项目，把②和③融合成一层；保留 duty 业务语义但大幅简化；同步建参考工程」。第二轮用户补充：「原教材就是参考旧 duty 写的，正确起点是在执勤项目大背景下重新设计一个面向教学的简化工程，作为教材正文与参考实现的共同上游」。

## 一、要解决什么问题

教材三段式的「概念讲解」段，讲一个新概念时若一上来就用完整 duty 项目的业务代码承载，学员第一次接触"主键/外键""业务规则分类""统计口径"等抽象概念时，会同时消化"抽象概念 + 执勤业务背景 + 具体实现细节"三层信息，认知负担过重。

旧 duty 项目（`项目参考/duty/`，现已改名 `duty-historical/`）是**生产级重型实现**——字段多、表多（10 张表）、BaseCRUD 泛型、redis/loguru/pandas 依赖、JWT 认证、异常处理器、部门树自引用、级联删除，且主键定义与教材第 4 章 ER 图不一致。这套实现不是为教学设计的，教材正文长期背着它的包袱。

本设计的处理方式是：**在"执勤排班"业务背景不变的前提下，重新设计一个面向教学的简化工程 `duty-simplified`**，让它同时充当：

1. **教材正文与参考实现共同的"上游事实来源"**（教材代码 = 参考工程代码，不再有两套对不上的实现）；
2. **讲概念的最小实现**（示范/练习/实训里的真实工程背景）。

即把原方案里的②（教学承载）与③（项目背景）融合成一层。

## 二、核心决策

| 决策点 | 结论 |
| --- | --- |
| 业务语义 | **保留"执勤排班"**：单位 / 人员 / 哨位 / 执勤记录 |
| 表粒度 | **仅核心四表 + users**：dept、personnel、workstation、duty_record、users；其余全砍 |
| 主键策略 | **混合**：业务实体（dept/personnel/workstation）用业务编码做主键；关联记录（duty_record）用自增 id + 外键 |
| 分层结构 | **保留六文件 + 砍泛型**（详见第五节） |
| 认证 | **只做密码哈希，不做 JWT/会话**（详见第六节） |
| 依赖 | **四依赖**：fastapi、uvicorn[standard]、sqlalchemy、pydantic（详见第七节） |
| 测试 | **仅一个最小烟测** smoke test，测试教学另轮（详见第八节） |
| 数据库 | **SQLite 单文件 + `Base.metadata.create_all`**，无 redis/settings/迁移 |
| 参考工程位置 | 新建 `项目参考/duty-simplified/`；旧 `项目参考/duty/` 已 `git mv` 为 `duty-historical/` 留历史基线 |
| 替换范围 | 先定设计再逐章替换：先 03-13（后端，含第 12 章测试、第 13 章后端综合实践），再 14-24（前端与综合），配套材料另轮 |

## 三、简化后的数据模型（四表 + users）

与教材第 4 章 4.2 ER 图完全对齐。

```
department（单位）— 模块目录 `app/modules/department/`、类名 `Department`、表名 `departments`、URL `/departments`
  dept_code   String  主键（业务编码）
  full_name   String  必填
  address     String  可空

personnel（人员）
  certificate_number   String  主键（业务编码，证件号）
  name                 String  必填
  dept_code            String  外键 → department.dept_code
  rank                 String  可空（职级，如"一级值班员""二级值班员"；非键业务属性字段，供第 4 章讲"字段不都是主外键"做样例，保留）

workstation（哨位）
  workstation_id   String  主键（业务编码）
  name             String  必填
  dept_code        String  外键 → department.dept_code
  is_active        Integer 默认 1

duty_record（执勤记录）
  id                            Integer 主键（自增）
  personnel_certificate_number  String  外键 → personnel.certificate_number
  workstation_id                String  外键 → workstation.workstation_id
  start_time                    DateTime 必填
  end_time                      DateTime 必填
  status                        String  默认 normal

users（用户，认证模块）
  id            Integer 主键（自增）
  username      String  唯一
  password_hash String
  role          String  默认 normal
  is_active     Integer 默认 1
```

**命名口径（与教材正文统一，2026-11-20 修正）**：模块目录、类名、表名、URL 一律以教材正文为准——`department`（目录）/ `Department`（类）/ `departments`（表）/ `/departments`（URL），字段名 `dept_code` 保持不变。旧 duty 的 `dept` 表名、`app/api/v1/module_duty/dept/` 目录为历史写法，简化工程不再沿用。人员 `personnel`、哨位 `workstation`、执勤记录 `duty_record` 三者的目录/类/表/URL 命名与教材正文一致，无需改动。

关系：`department 1—N personnel`、`department 1—N workstation`、`personnel 1—N duty_record`、`workstation 1—N duty_record`。四个一对多，外键置于"多"的一方；`duty_record` 同时持有指向 personnel 与 workstation 的两个外键。

## 四、与旧 duty 的差异（砍掉了什么）

| 表 | 旧 duty 字段 | 简化后 | 砍掉 |
| --- | --- | --- | --- |
| department | dept_code/full_name/address/longitude/latitude/parent_dept_code | dept_code/full_name/address | longitude、latitude、parent_dept_code |
| personnel | certificate_number/name/id_card_number/dept_code/position/rank/hire_date | certificate_number/name/dept_code/rank | id_card_number、position、hire_date |
| workstation | id/workstation_id/workstation_name/dept_code/category_code/longitude/latitude/remark | workstation_id/name/dept_code/is_active | id 自增主键、category_code、longitude、latitude、remark；`workstation_name` 更名 `name` |
| duty_record | personnel_certificate_number/successor_certificate_number/start_time/end_time/workstation_id/status/remark/created_by | personnel_certificate_number/workstation_id/start_time/end_time/status | successor_certificate_number、remark、created_by |

**习题里"自选资源"的约束**：统一为——自选资源只能在四表范围内派生（例如"哨位类别""单位负责人"等仍属四表字段的扩展），不再引入四表之外的新实体；若习题本意是"脱离 duty 自由选资源"，则保留其"自选"性质、但不作为正文概念讲解的承载。

## 五、分层结构：六文件 + 砍泛型

### 5.1 目录树

```
duty-simplified/
├── main.py                          # FastAPI 实例 + 启动时建表/seed + 挂路由
├── requirements.txt                 # 四依赖
├── .gitignore
├── app/
│   ├── __init__.py
│   ├── core/
│   │   ├── __init__.py
│   │   ├── database.py              # engine / SessionLocal / Base / get_db
│   │   └── security.py              # hash_password / verify_password
│   └── modules/
│       ├── __init__.py
│       ├── dept/                    # 单位
│       │   ├── model.py
│       │   ├── schema.py
│       │   ├── param.py
│       │   ├── crud.py
│       │   ├── service.py
│       │   └── controller.py
│       ├── personnel/               # 人员
│       ├── workstation/             # 哨位
│       ├── duty_record/             # 执勤记录
│       └── user/                    # 用户（认证）
└── tests/
    └── test_smoke.py                # 最小烟测
```

每个业务模块严格六文件：`model` / `schema` / `param` / `crud` / `service` / `controller`。

### 5.2 与旧 duty 的分层差异

| 维度 | 旧 duty | duty-simplified |
| --- | --- | --- |
| CRUD 抽象 | 泛型 `CRUDBase[Model, Create, Update]` + 子类覆写 | 每模块手写朴素的 `crud.py`，函数名直白（`get_by_code` / `create` / `update` / `delete` / `list`） |
| Pydantic 基类 | `BaseModel` 带 create_time/update_time | schema/param 直接用 Pydantic `BaseModel`，无公共基类，无时间戳字段 |
| 配置 | `settings.py`（读 env） | 无 settings，`DATABASE_URL` 常量写在 `database.py` 里 |
| 异常 | 全局异常处理器 + 自定义业务异常 | 只在需要处 `raise HTTPException`，不建异常体系 |
| 中间件 | CORS 等 | 无 |

**砍泛型的理由**：旧 duty 的 `CRUDBase[Model, Create, Update]` 泛型对学生是认知黑洞——讲"这行代码在干嘛"时，要先解释泛型、TypeVar、继承、覆写，机制教学被 Python 高级特性淹没。手写朴素 `crud.py` 后，每个函数都能一步步讲清"查一条 / 插一条 / 改一条 / 删一条 / 列一页"。

## 六、认证：只做密码哈希，不做 JWT/会话

### 6.1 两层拆分

教材里"认证"实际讲两个不同层面的东西，旧 duty 用 JWT 把它们混在一起：

| 层面 | 教的是什么 | 参考工程提供什么 |
| --- | --- | --- |
| ① 密码的安全存储（第 6 章） | 密码不能明文存、要哈希、校验时比对哈希 | `users` 表 + `password_hash` 字段 + `hash_password()` / `verify_password()` |
| ② 登录态 / 会话（第 6/7 章） | 登录后怎么证明"我是谁"，令牌怎么发、怎么验 | **留空**，靠教材阶段递进来演，参考工程不预置 JWT |

### 6.2 `security.py` 的实现（标准库 hashlib + 盐）

```python
# app/core/security.py
import hashlib
import secrets

def hash_password(password: str) -> str:
    """随机盐 + SHA-256 哈希化（教学用，讲清"不能明文存"）"""
    salt = secrets.token_hex(16)
    digest = hashlib.sha256((salt + password).encode()).hexdigest()
    return f"{salt}${digest}"

def verify_password(password: str, stored: str) -> bool:
    salt, digest = stored.split("$", 1)
    return hashlib.sha256((salt + password).encode()).hexdigest() == digest
```

**为什么用 hashlib 而非旧 duty 的 passlib/bcrypt**：教学目标是"理解为什么要哈希、什么是盐、为什么不能存明文"，`hashlib` 是标准库、零依赖、学生能一步步看懂；`bcrypt` 是黑盒库，讲不清原理。**生产选最优，教学选最能讲清机制**。

### 6.3 登录态何时出现

- 第 6 章讲完哈希，示范例题里**临时演示**一个最简单的"内存 token"（`dataclass` + 一个字典存 `token → user_id`），讲清"登录后给个令牌"这个思想；
- 第 8 章落库时，`users` 表才正式进入参考工程；
- JWT 这个具体技术，若教材要讲，作为**进阶拓展**放第 7 章或附录，参考工程本体不承载。

`requirements.txt` 只有四行：

```
fastapi

```

| 依赖 | 对应教材主线 |
| --- | --- |

**被砍掉的那一串及理由**：

| 旧依赖 | 用途 | 砍的理由 |
| --- | --- | --- |
| redis | 缓存/会话 | SQLite 已够，多一个服务要装要配，纯负担 |
| loguru | 日志 | 标准库 `logging` 或 `print` 就够讲"日志"概念 |
| pandas | 统计 | 第 11 章统计用 SQL 聚合就能讲清，pandas 是另一个世界的知识 |
| passlib/bcrypt | 密码哈希 | 用标准库 `hashlib` 替代，原理可讲（见第六节） |
| python-jose | JWT | 认证会话后置，暂不需要 |
| email-validator | 邮箱校验 | 教学不涉及真实邮箱 |

## 八、测试：仅一个最小烟测

参考工程只带 `tests/test_smoke.py`，作用是"任何人 clone 下来、装好依赖，跑这一条就知道工程通不通"：

```python
# tests/test_smoke.py
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_health():
    r = client.get("/depts")
    assert r.status_code == 200
```

- **价值**：给老师和学生一个"工程能不能跑"的确定性信号，避免"装了半天跑不起来也不知道卡在哪"。
- **真正的测试教学**（第 12 章：断言、测试组织、TestClient）**不放进参考工程**，作为第 12 章教学内容让学生自己写。参考工程保持"最小可运行"，测试知识由教材递进地教，二者不打架。

## 九、`main.py` 启动逻辑与建表

- `DATABASE_URL = "sqlite:///./duty.db"` 常量写在 `database.py`；
- `main.py` 启动时：创建 engine → `Base.metadata.create_all(engine)` 建表 →（可选）seed 一条演示数据 → 挂载五个模块的 router → `app = FastAPI()`；
- 无 redis 连接、无 settings 读 env、无迁移工具（alembic）。建表即 `create_all`，删库即删 `duty.db` 文件，零配置。
