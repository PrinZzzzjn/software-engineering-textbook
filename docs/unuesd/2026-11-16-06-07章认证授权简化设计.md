# 06–07 章认证与授权简化设计

> 状态：已实施（2026-11-16）。实施结果见文末。
> 范围：`06-用户模块-登录认证.md`、`07-用户模块-账号管理.md` 及受影响的交叉引用。

## 一、要解决的问题

第 6 章 504 行、第 7 章 388 行。学生要在 6 学时内掌握登录与账号管理，当前正文把与登录闭环无关的结构决策一并展开：

1. 登录单建 `app/modules/auth/`，正文要解释“无表模块只放三个文件”，并产生跨模块 service 调用。
2. 06 章不建 `crud.py`，07 章又建 `crud.py`；同一六文件模板，两章两种用法。
3. `SECRET_KEY` 用 `os.getenv` 读取，但不会读 `.env`；正文、课前准备、排错清单三处都在解释环境变量。
4. 认证依赖建在 `app/core/dependencies.py`，而第 5 章的工程目录里没有这个文件；代码 6-1-10 把依赖函数与 `/me` 路由合写在一块，还要补一句“实际写在另一个文件”。
5. 权限依赖与 `/admin` 在 06 章先讲一遍，07 章 7.4 再讲一遍。
6. 07 章 7.5 用整节重讲第 3 章已讲过的 `Literal`/`Optional`，并重印第 6 章的表模型与输出模型。

## 二、目标与非目标

**目标**

- 06 只回答“你是谁”：注册、登录、令牌、`/me`，三个接口、五节。
- 07 只回答“你能做什么”：角色、管理员依赖、401/403、列表与启停，两个接口、四节。
- 不新增模块与分层：代码全部落在 `app/core/security.py` 与 `app/modules/user/` 的四个文件里。
- 每章 4 条学习目标、1 道示范例题、2–3 道独立习题，满足校验脚本下限。
- 两章语体按 03–05 章口径改为规范书面语；全部示例代码实际运行通过。

**非目标**

- 不改章号、章名、课次、学时与前言对照表。
- 不改第 3、4、5 章的六文件模板与工程目录。
- 不做刷新令牌、注册审核、分页、用户详情、密码重置。
- 不合并第 6、7 章。

**反目标（做成即失败）**

- 为了省代码而让令牌校验、密码哈希走捷径（例如明文比较、无签名令牌）。
- 为迁就简化而改动第 8 章以后已经定稿的模块结构与接口约定。

## 三、方案选择

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A 只删冗余 | 保留 auth 模块、`crud.py`、06 章的权限依赖 | 篇幅略降，结构深度未变 |
| **B 重切认证/授权边界（采用）** | 06 只做认证；07 做授权与最小账号管理；auth 并入 user 模块 | 结构少一层，需同步 12、17、98 等引用 |
| C 合并 6+7 | 一章两课次 | 章数 24→23，全书引用大改，与课次对应关系变复杂 |

采用 B。另定三项结构决定：

1. 登录路径改为 `POST /api/v1/users/login`，与注册、`/me` 同属 user 模块的一个 router。
2. 认证依赖与权限依赖写入 `app/core/security.py`，不建 `app/core/dependencies.py`。
3. `crud.py` 留到第 8 章部门 CRUD 时引入；06、07 章的查询直接写在 service。

## 五、第 6 章设计

**定位不变**：课次 7 · 4 学时 · 实践；实训 6-1；前置第 5 章骨架、第 3 章 3.5 与 3.6。

**学习目标（4 条）**

1. 说明认证回答什么问题，以及 401 表示什么。
2. 解释用户表四个字段的作用，说明密码为什么只存哈希。
3. 实现注册、登录与 `/me`，让“令牌签发—携带—校验”走通。
4. 用 `Depends` 挂认证依赖，说明未带令牌与令牌无效都返回 401。

**6.1 数据库基础设施**

- 无认证的接口示例与认证定义放在章首，不占小节。
- 从功能出发：服务重启后内存数据会丢，登录要能再次找到用户，因此需要数据库。
- 代码 6-1-1 `app/core/database.py`：逐条解释 `DATABASE_URL`、`create_engine`、`sessionmaker`、`declarative_base`、`get_db` 五行代码；补 `engine` / `SessionLocal` / `Base` / `get_db` 的职责表；说明 `main.py` 建表三行。

**6.2 用户表**

- 四字段表（`id`、`username`、`password_hash`、`role`、`is_active`）。`is_active` 只写一句“第 7 章启停使用”。
- 代码 6-1-2 `app/modules/user/model.py`：`User`，说明表名、主键与三类约束。
- `main.py` 导入模型才能建表；末尾把 `password_hash` 的处理指向 6.3。

**6.3 密码哈希与令牌**

- 只存哈希的两条理由（泄露后果、密码复用）。
- 代码 6-1-3 `app/core/security.py`：三项配置 + 哈希两函数 + 令牌两函数。
  - 配置沿用第 5 章 5.6 的变量名，保留 `os.getenv` 回退值；只写一句“生产环境必须设置 `SECRET_KEY`”。
  - 令牌只讲“载荷 + 过期 + 签名”“解析失败返回 `None`”，加一句 Bearer 头的写法。
- 删除：PBKDF2/JWT/RFC 编号、JWT 三段结构、无状态令牌的代价、安全习惯清单、`.env` 读取整段。

**6.4 注册与登录**

- 代码 6-1-4 `app/modules/user/schema.py`：`UserCreate`、`UserOut`、`LoginIn`、`TokenOut` 一次给全。
  - 注册只收 `username`、`password`；`role` 不由客户端决定，固定 `normal`。
  - 一句话说明输入校验失败返回 422；一句易错点说明输出模型挡住 `password_hash`。
- 代码 6-1-5 `app/modules/user/service.py`：`create_user`（查重 → 哈希 → 入库）、`login`（查用户 → 验密码 → 发令牌）。
- 代码 6-1-6 `app/modules/user/controller.py`：`POST ""`（201）与 `POST /login`（200）。
- 错误提示统一为“用户名或密码错误”，两句说明原因。
- `is_active` 的登录检查不在本章，留到 7.4。

**6.5 受保护接口**

- 代码 6-1-7 `app/core/security.py` 续写：`get_current_user`。返回 `{"id": int(...), "role": ...}`，`id` 直接是整数。
- 代码 6-1-8 `app/modules/user/controller.py` 续写：`GET /me`。
- 未带令牌、令牌无效或过期都返回 401，一句话。
- 易错点：令牌只签名不加密，不放敏感信息。

**例题与习题**

- 例 6-1（应用）：完成注册 → 登录 → `/me` 三次请求，写出请求体、请求头与状态码，说明 201/200/401 各由什么产生。
- 习题 6-1（理解）：用自己的话说明登录到访问受保护接口的完整流程，解释 401。
- 习题 6-2（分析）：三个 401 现象——密码正确仍 401、登录成功但 `/me` 401、令牌过期后 401——逐条给排查顺序。
- 删去原习题 6-3（部门权限场景），其内容并入第 7 章习题 7-3。

**实训 6-1（5 步，3 个接口）**

| 接口 | 方法 | 成功 | 失败 |
| --- | --- | --- | --- |
| `/api/v1/users` 注册 | POST | 201 + `UserOut` | 用户名重复 → 400 |
| `/api/v1/users/login` 登录 | POST | 200 + `{access_token, token_type}` | 密码错 → 401 |
| `/api/v1/users/me` 当前用户 | GET | 200 + `{id, role}` | 未带或无效令牌 → 401 |

步骤：建 `security.py` → 建模型与输入输出模型 → 注册与登录 → `/me` → `/docs` 全量验证。删去管理员接口步骤与环境变量准备项。
