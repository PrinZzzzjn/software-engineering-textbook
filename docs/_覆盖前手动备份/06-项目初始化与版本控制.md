# 第 6 章 项目初始化与版本控制

上一章画好了施工图：表怎么建、接口怎么定。现在要把图纸变成可以运行、可以继续开发的起点。这个起点不只是“新建一个文件夹”，它要满足三个条件：结构清楚，别人知道代码该放哪；环境可复现，换一台机器也能跑起来；提交有记录，改坏了可以回退。

本章从零搭一个 FastAPI 项目，完成第一次 Git 提交，再走一遍分支与合并。目标不是写完业务，而是建立一个“可复现、可提交、可继续开发”的起点。

## 本章学习目标

读完本章，你应该能：

1. 按标准目录结构初始化 FastAPI 项目并纳入 Git 版本控制，完成首个可运行接口。

## 6.1 概念讲解

### 6.1.1 标准目录结构解决什么问题

把所有代码写在一个文件里，短期能跑，长期会出三个问题：找不到代码、改一处牵动全身、别人无法接手。标准目录结构按职责分区，让每个文件有固定的位置，也让分层与模块化落到磁盘上。

一个可用的 FastAPI 项目骨架如下：

```text
duty/
├── main.py                 # 应用入口
├── requirements.txt        # 依赖清单
├── .env.example            # 环境变量示例
├── .gitignore              # 不提交的内容
├── app/
│   ├── api/
│   │   └── v1/
│   │       ├── module_system/   # 认证、用户
│   │       └── module_duty/     # 部门、人员、值班记录
│   ├── core/               # 数据库、基础模型、异常、日志、安全
│   └── config/             # 配置
├── tests/                  # 测试
├── alembic/                # 数据库迁移
└── logs/                   # 运行日志
```

`main.py` 负责创建应用、注册路由、启动服务；`app/api/` 按业务模块组织接口；`app/core/` 放跨模块的基础设施；`app/config/` 集中管理配置；`tests/` 与代码同仓；`alembic/` 管理数据库迁移；`logs/` 存运行日志。每个 Python 包目录都要有 `__init__.py`，否则导入时可能找不到模块。

### 6.1.2 虚拟环境与依赖清单

虚拟环境的作用是隔离依赖。系统 Python 里可能装着各种版本的库，项目 A 需要 FastAPI 0.110，项目 B 需要 0.139，装在一起就会冲突。虚拟环境给每个项目一套独立的库。

```bash
python -m venv venv
```

Windows 下激活：

```bash
venv\Scripts\activate
```

Linux 或 macOS 下激活：

```bash
source venv/bin/activate
```

激活后，命令提示符前通常会出现 `(venv)`。此时安装的依赖只进入这个环境。依赖清单 `requirements.txt` 记录项目需要哪些库及版本，别人拿到清单就能复现环境：

```bash
pip install -r requirements.txt
```

> 💡 **常见坑**：在系统 Python 里直接 `pip install`。项目换机器时依赖版本对不上，或者不同项目互相覆盖。看到命令提示符前没有 `(venv)`，先激活再装。

### 6.1.3 配置与环境变量

代码里不该写死数据库地址、密钥和调试开关。这些值随环境变化，应该放进环境变量。项目通常提供两个文件：`.env.example` 记录需要哪些变量、示例值是什么；`.env` 保存本机实际值。

```env
DATABASE_URL="sqlite:///./duty.db"
SECRET_KEY="change-me"
ALGORITHM="HS256"
ACCESS_TOKEN_EXPIRE_MINUTES=30
DEBUG=True
```

`.env.example` 进 Git，`.env` 不进 Git。原因是 `.env` 往往含真实密钥，提交上去等于泄露；而 `.env.example` 让新同事知道要配哪些项。生产环境必须替换默认 `SECRET_KEY`。

### 6.1.4 应用入口与健康检查

入口文件把应用创建起来，并注册一个最小的健康检查接口：

```python
from fastapi import FastAPI

app = FastAPI(title="Duty API", version="0.1.0")

@app.get("/health")
def health():
    return {"status": "healthy"}
```

运行 `uvicorn main:app --reload --port 8000` 后，访问 `/health` 应返回 `{"status":"healthy"}`，访问 `/docs` 应能打开接口文档。健康检查的意义不只是“证明服务活着”，它还是部署后判断服务是否可用的第一项证据。

### 6.1.5 Git 记录了什么

Git 把一次修改从“工作区”送到“本地仓库”，中间经过“暂存区”。

```mermaid
flowchart LR
    W[工作区<br/>修改文件] -->|git add| S[暂存区]
    S -->|git commit| R[本地仓库]
    R -->|git push| Remote[远程仓库]
    Remote -->|git pull| W
```

*图 6-1：Git 的工作区、暂存区、本地仓库与远程仓库*

三个动作要分清：`git add` 把改动放进暂存区，`git commit` 把暂存区的内容记录成一次提交，`git push` 把本地提交共享到远程仓库。`git status` 看当前有哪些改动，`git log` 看历史。

初始化仓库并完成第一次提交：

```bash
git init -b main
git add .
git commit -m "chore: init fastapi project"
```

如果 `git init` 的默认分支不是 `main`，可以用 `git branch -M main` 改名，或在初始化时加 `-b main`。

### 6.1.6 .gitignore：哪些东西不该进仓库

虚拟环境、数据库文件、日志和密钥都不应该提交。它们要么体积大，要么因机器而异，要么含敏感信息。`.gitignore` 把这些路径排除掉：

```gitignore
venv/
__pycache__/
*.pyc
.env
*.db
logs/
.pytest_cache/
```

`.gitignore` 必须在第一次提交前写好。如果已经误提交了 `venv/`，先把它加进 `.gitignore`，再用 `git rm -r --cached venv` 从索引中移除，然后提交这次移除。

### 6.1.7 分支与合并

分支让改动可以并行。主分支保持可用，新功能在独立分支上开发，完成后再合并回来。

```bash
git switch -c feature/hello
# 修改代码
git add main.py
git commit -m "feat: add hello endpoint"
git switch main
git merge feature/hello
```

如果主分支在分叉后没有新提交，合并通常是“快进”，历史是一条直线。如果两边都改了同一处，Git 无法自动决定保留哪一版，就会产生冲突。冲突文件里会出现三组标记：

```text
<<<<<<< HEAD
当前分支的内容
=======
要合并进来的内容
>>>>>>> feature/hello
```

处理方法是：打开文件，保留需要的内容，删掉三组标记，然后 `git add` 标记为已解决，再 `git commit` 完成合并。冲突不是错误，它只是提示“这里需要人做决定”。

### 6.1.8 提交信息与提交粒度

提交信息是给未来的自己和同伴看的。常用类型前缀有：`feat:` 新功能、`fix:` 修复、`docs:` 文档、`test:` 测试、`chore:` 构建或杂务。一个提交只做一件事，提交信息就能说清这件事。

“update”“修改一下”“最终版”这类提交信息，过两周连作者自己都看不懂改了什么。反过来，“feat: add hello endpoint”“fix: correct database path”能让历史自己讲故事。

### 6.1.9 常见故障排查

| 现象 | 先查什么 |
| --- | --- |
| 服务起不来 | 端口占用、依赖缺失、语法错误 |
| `/docs` 打不开 | 服务是否启动、路径是否正确 |
| 422 | 请求体字段、类型、必填 |
| 404 | 路径前缀、尾斜杠、方法 |
| 数据库为空 | `.env` 的 `DATABASE_URL`、启动目录 |
| 导入失败 | 虚拟环境是否激活、`__init__.py` 是否存在、包路径 |
| Git 提交为空 | `git status`、`.gitignore` 是否误伤 |

排查的顺序通常是：先看现象，再看日志或错误信息，最后才改代码。不要一上来就重装环境，那会把真正的原因一起覆盖掉。

#### 例 6-2：完成第一次 Git 提交【Bloom：应用】

**题目**：写出把一个已搭好骨架的 FastAPI 项目纳入 Git 的命令，要求：初始化主分支为 `main`、提交前排除虚拟环境与密钥、完成第一次提交。

**解**：

```bash
git init -b main
git add .gitignore
git commit -m "chore: add gitignore"
git add .
git commit -m "chore: init fastapi project"
```

其中 `.gitignore` 至少包含：

```gitignore
venv/
__pycache__/
.env
*.db
logs/
```

先单独提交 `.gitignore` 的好处是：后续 `git add .` 时，虚拟环境、`.env` 与数据库文件已经被排除，不会误入仓库。

**验证**：✅ 已验证（在临时仓库实际执行 `git init -b main`、`git add`、`git commit`，生成两次提交，`git ls-files` 只含 `main.py` 与 `.gitignore`）

```text
实际执行结果：
git log --oneline --graph：
* 08033fc (HEAD -> main) feat: add hello endpoint
* 2b628ed chore: init fastapi project
git ls-files：.gitignore、main.py
结论：命令可执行，提交与排除规则均符合预期，验证通过。
```

## 本章小结

**核心结论**：

1. 项目初始化要建立三件事：结构清楚、环境可复现、提交有记录。
2. 标准目录结构把分层与模块化落到磁盘；每个 Python 包目录要有 `__init__.py`。
3. 虚拟环境隔离依赖，`requirements.txt` 记录依赖，换机器时据此复现。
4. 配置放环境变量：`.env.example` 进 Git，`.env` 不进；密钥与数据库地址不写死在代码里。
5. Git 用暂存区组织提交；`.gitignore` 排除虚拟环境、数据库、日志与密钥；分支用于并行开发，冲突需要人工决定保留哪一版。

**与持久理解的呼应**：本章推进了「分层与接口契约使系统的各部分可以独立理解、替换和验证」——通过标准结构与版本控制，读者看到“可复现的起点”如何降低协作与变更的成本。
