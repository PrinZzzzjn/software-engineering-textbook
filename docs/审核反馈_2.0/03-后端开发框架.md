#### 二、3.1 概念补课（随记二、三、四）

- **联调**：在“三类失败”前补定义——前后端分别开发到能跑后，把两边接起来一起调试；前端发请求、后端返响应，逐项核对是否与约定一致。
- **地址 / 字段**：表格前补一句“地址是请求发往的 URL 路径，字段是响应 JSON 里的键名”，并给最小对照：`/department` vs `/departments` → 404；`deptName` vs `dept_name` → 页面有行无值。
- **OpenAPI**：首次出现处补一句——OpenAPI 是机器可读的接口描述规范，用一份结构化文档写清路径、方法、参数、请求体、响应、鉴权与版本；FastAPI 根据代码自动生成，`/docs` 看到的就是它。
- **契约与代码**：重写“以代码为准”一段：

  > 契约是双方约定的“应然”，代码是当前的“实然”。两者应当一致；不一致时，先记录差异（哪一项、期望什么、实际什么），再判断是改代码还是改契约。不能默认“以代码为准”：如果代码偏离了约定，改代码才对；如果约定本身写错了，就改契约并通知调用方。联调中出现的“数据不对”，可能来自契约不一致、数据状态不一致、权限或业务规则差异；先按契约逐项核对，再判断根因。

- 同步：课堂活动块听讲要点 6 的“代码是最终口径”改为“契约与实现要相互核对”；术语表“联调”“契约不一致”的出处改为第 3 章；登记表 C03-03 的表述同步。

#### 三、3.2 结构与顺序（随记五、六）

只保留一套请求分解：

> 按 RFC 9110，一次请求由请求行（方法、请求目标、HTTP 版本）、头部字段和一个可选的正文组成。初学阶段把请求目标理解为 URL、把正文理解为请求体；头部先只认识认证与内容类型两项。

表格改为“方法 / 请求目标 / 头部 / 正文”四行，并在表下明确：

> 参数不是请求的第五个部分，而是分布在请求目标和正文里的值：路径参数、查询参数在请求目标里，请求体字段在正文里。

小节顺序改为：方法 → 请求目标与 URL → 参数三位置 → 请求体与 JSON → 响应与状态码。这样与请求结构的顺序一致，也消除“方法、参数、JSON、状态码”与前面范畴对不上的问题。响应与状态码放在各请求部件之后讲，状态码责任表保留。

#### 四、3.3 接口组（随记七、八）

- 开头先给动机：一组反例（`GET /getDepartments`、`POST /departments/delete/1`、成功失败都返回 200、单复数混用），说明“每个接口各写各的”会让前端无法预测、联调难定位；再引出接口组与三条规则。
- 先定义“接口组”，再给五动作表；把现在放在表后的反例前移，避免重复。
- 解释 `/1`：

  > `1` 是资源标识（部门的主键 id），不是页码，也不是随便写的数字；`/departments/1` 读作“id 为 1 的部门”。REST 没规定标识必须是整数，也可以用业务编码（`/departments/D01`）或 UUID；选哪种取决于唯一、稳定、可读。本书用 id，因为它与数据库主键一致，后面查库最直接。

- 补一句集合与单个成员的写法约定（`/departments/` 与 `/departments/1`），以及项目内斜杠要一致。

#### 五、3.4 FastAPI（随记九）

建议把 3.4 改名为 **“FastAPI 与路由”**，节内加三个粗体小节：

1. **FastAPI 是什么**：不用框架时要自己解析 HTTP、做路由、校验、序列化、写文档；框架把这些做一次。FastAPI 的特点：类型注解校验、自动生成 OpenAPI 文档、依赖注入；本课程选它，是因为 `/docs` 让契约有共同参照。
2. **装饰器路由**：解释 `@app.get(...)` 是把函数登记到路由表；`name: str` 是类型注解，FastAPI 据此转换与校验。
3. **APIRouter：把路由拆到模块**：保留现有内容。

这样“先介绍 FastAPI，再讲装饰器与 APIRouter”，标题也与内容一致。若你不想改标题，也可以保留原标题、只加“FastAPI 是什么”粗体小节。

#### 六、3.5 Pydantic（随记十）

重排为“先问题、再工具、先最小例子、再回项目”：

1. **为什么需要输入模型**：请求体是结构化数据；手写 `if "dept_code" not in data` 这类检查重复且容易漏，模型把结构声明一次。
2. **Pydantic / BaseModel / Field 是什么**：Pydantic 是用 Python 类定义数据结构并自动校验的库；`BaseModel` 是提供校验与序列化的基类；`Field` 给字段加约束与文档信息（`min_length`、`max_length`、`examples`）；`...` 表示必填。
3. **最小例子**：用与 3.4 `hello` 呼应的中性例子，例如 `Greeting`（`name: str = Field(..., min_length=1, max_length=20)`）+ `POST /hello`；演示合法请求 200、空字符串 422，并指出 `detail.loc`。
4. **再回到项目**：用 `DepartmentCreate` 作为应用例子，指向 3.6 的完整三文件工程。
5. **422 发生在哪一层**：保留因果链，但放在最小例子之后讲。
6. **输入与输出分开**：先用 `GreetingOut` 说明输入/输出模型可以不同，再举 `password_hash` 的安全理由。
7. **Optional / Literal**：保留为“先导”一小段，说明含义与后续章节用点，不展开。
8. **HTTPException**：先用一个最小 404 例子，再讲“422 vs HTTPException”的分工，最后回到部门编码重复。
9. 每个子小节补一句“为什么这样设计”，不只给代码。
