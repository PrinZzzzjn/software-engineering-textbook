### 1.9 ARM Ubuntu 授课环境与 Docker 多架构（重点约束）

课堂实训在 **ARM64 Ubuntu** 上进行，Docker 相关实训（22-1～24-1）必须保证多架构兼容。仓库已有 [tools/offline-deps/README.md](file:///d:/Aproject/software-class-book/tools/offline-deps/README.md) 覆盖此场景，要点如下，实训工程参考必须遵守。

**Python 依赖层（已就绪）**：全部 56 个包有 `manylinux2014_aarch64` 预编译 wheel，逐包校验可用。ARM 授课机用 [requirements.linux-arm64.lock.txt](file:///d:/Aproject/software-class-book/tools/offline-deps/requirements.linux-arm64.lock.txt)（比 x86 多一个 `uvloop`）。**前提：授课机必须是 Python 3.12 + glibc ≥ 2.17**；若是 Alpine musl 需单独处理（当前未覆盖）。

**Docker 层（4 个必须处理的坑）**：

| 编号 | 坑 | 处理方式 |
| --- | --- | --- |
| A1 | 基础镜像 `swr.cn-north-4...python:3.12.9-slim` 是华为云代理，需确认提供 arm64 变体 | 在 ARM 机上 `docker pull --platform linux/arm64` 验证；报 `no matching manifest` 则改回官方 `python:3.12.9-slim` |
| A2 | `docker save` 的镜像 tar 绑架构，x86 build 的镜像在 ARM 上无法运行 | 必须在 ARM 机上直接 build，或用 `docker buildx build --platform linux/arm64 --load`（慢，需 QEMU）；工程参考的 Dockerfile 不得硬编码 x86 假设 |
| A3 | 内网无公网时 pip 拉不到包 | Dockerfile 写死了清华 pip 源，内网构建需删掉该行，改用本地 wheelhouse：`COPY wheelhouse/ /wheels/` + `pip install --no-index --find-links=/wheels`；镜像也需预先 `docker save` 后 `docker load` |
| A4 | 交叉构建慢且易失败 | 优先直接在 ARM 授课机上 build；只在必须产出 x86+arm 双镜像时才用 buildx |

**额外两个坑**：

- 内网 `/docs`（Swagger UI）空白（走公网 CDN），需用 `swagger-ui-bundle` 本地化；`/openapi.json` 不受影响（见 offline-deps README 第 6 节）。
- compose 的 healthcheck 用纯 Python urllib，arm 兼容，无需改动。

**实训工程参考的要求**：22-1～24-1 的 `项目/` 中，Dockerfile 不得硬编码 x86 假设；`验证记录.md` 必须记录构建架构（`docker inspect` 查 `Architecture`）。

**已确认约束（Q5/Q6）**：ARM64 验证环境**不可用**；课堂学生机**完全内网封闭**。由此产生两条硬要求：

1. **阶段 0 必须产出 ARM64 离线交付物**（见下方清单），学生机在内网无需公网即可完成 3-1～24-1 全部实训。
2. **22-1～24-1 无法在 ARM 实机验证**：在 x86 开发机上用 `docker buildx --platform linux/arm64 --load`（QEMU 模拟）验证 Dockerfile 可构建、镜像架构为 arm64；`验证记录.md` 必须标注「构建架构 arm64（buildx 交叉构建），未在 ARM 实机运行验证」。若开发机无法安装 Docker，则降级为纯静态校验 Dockerfile，并标注「未构建验证」。

**ARM64 离线交付物清单（阶段 0 产出，存 `实训工程参考/_offline/arm64/`）**：

| 交付物 | 内容 | 用途 | 准备方式 |
| --- | --- | --- | --- |
| `wheelhouse-arm64/` | 56 个 `manylinux2014_aarch64` + cp312 wheel | 学生机离线 `pip install --no-index --find-links` | x86 机 `pip download --platform manylinux2014_aarch64 ...`（纯下载，不需 ARM 机） |
| `python-images-arm64.tar` | `python:3.12.9-slim` 与官方 `python:3.12-slim` 的 arm64 变体 | 学生机 `docker load` 基础镜像，无需联网 pull | 需 Docker（x86 机 `docker pull --platform linux/arm64` + `docker save`） |
| `duty-images-arm64.tar` | 后端、前端业务镜像（arm64） | 学生机 `docker load` 后直接 `docker compose up -d`，无需 build | 需 Docker（buildx 交叉构建，或在 ARM 机 build） |
| `Dockerfile.offline`（后端/前端各一） | 删清华 pip 源，改 `COPY wheelhouse/ /wheels/` + `--no-index` | 学生机若需在内网 build 时用 | 从现有 Dockerfile 派生 |
| `docker-compose.offline.yml` | 服务用 `image:` 而非 `build:`，指向 load 进来的镜像 tag | 学生机一键启动，不触发 build | 从现有 compose 派生 |
| `离线安装说明.md` | wheelhouse 安装、镜像 load、compose 启动的内网命令 | 教师/管理员操作手册 | 基于 `tools/offline-deps/README.md` 裁剪 |

> 依赖关系：`wheelhouse-arm64/` 可在 x86 机纯下载完成；`python-images-arm64.tar` 和 `duty-images-arm64.tar` 需要开发机安装 Docker。若开发机也不能装 Docker，镜像 tar 需由用户在其他联网环境准备，工程参考只提供 Dockerfile.offline 与 compose.offline。

### 3.2 单个实训目录的七件套

```

├── README.md                12 节（与实训3-1对齐）：概览/目标/边界/准备/时间/步骤/文件/快速开始/验收/排错/提交/扩展
├── 分步实现指南.md          阶段 0..N，每阶段含代码、验证命令、常见错误
├── 项目/                    完成态工程快照，可独立启动
├── starter/                 学员起点；仅需要时提供（3-1、4-1、5-1、15-1、22-1）
├── 验证记录.md              命令、预期、实际、结论；含回归项
├── 难度评分.md              D/L 等级、代码量、文件数、新概念、预计分钟、文字结论
├── 接缝表.md                上一实训 → 本实训的新增/修改/删除文件与不兼容点
└── 学员版差异说明.md        完整版 → 学员版要删什么、留什么、替换什么
```

### 3.3 后端实训的快照策略

后端 3-1→13-1 是同一条 duty 主线的演进。每个 `项目/` 是**可独立启动的完整快照**，但内容从 `duty-simplified` 按阶段裁剪/派生：

| 实训 | 快照内容（相对 duty-simplified） | 说明 |
| --- | --- | --- |
| 3-1 | 单文件内存版，5 个端点 | 自包含，不依赖 app 结构 |
| 4-1 | 六文件内存版（自选对象示例用 department） | 无数据库、无 user |
| 5-1 | 4-1 六文件内存版 + 工程目录 + Git 提交记录（示例模块 department） | 以 4-1 产物为起点，不新建模块文件、不建 app/core 与 tests；路由 `include_router(..., prefix="")` |
| 6-1 | 5-1 + database.py + department 落库 + 分页 | users 表**不建**（第 8 章才建） |
| 7-1 | 6-1 + 查询复用（参数模型/过滤/固定排序） | 以 department 与 personnel 为示例 |
| 8-1 | 7-1 + users 表 + security.py + 注册/登录/me | 认证接入；main.py 补 user 模型导入 |
| 9-1 | 8-1 + 管理员依赖 + 用户列表(分页) + 修改/禁用 + 权限回收到 6/7 章接口 | create_admin 数据库脚本 |
| 10-1 | 9-1 + personnel + duty_record + 业务规则（时间冲突等） | 依赖 8-1 课后 personnel 完成 |
| 11-1 | 10-1 + analytics 统计聚合与校验 | staff-duty-yearly / duty-time-distribution |
| 12-1 | 11-1 + pytest 测试集（正常/边界/异常） | conftest 进程内 seed |

## 四、难度与合理性评估

### 4.1 代码量等级

| 等级 | 新增/修改有效代码 | 涉及文件 |
| --- | --- | ---: |
| D1 | ≤80 行 | ≤2 |
| D2 | 81–200 行 | 3–5 |
| D3 | 201–400 行 | 6–10 |
| D4 | 401–700 行 | 11–20 |
| D5 | >700 行 | >20 |

### 4.2 逻辑难度等级

| 等级 | 判据 |
| --- | --- |
| L1 | 单层直写，无跨文件调用 |
| L2 | 2–3 层调用，状态简单 |
| L3 | 跨层调用，含校验、状态或权限之一 |
| L4 | 多模块协同，含事务、异常、认证或统计口径 |
| L5 | 全链路联调，含故障定位、契约核对与交付判断 |

### 4.3 时间与节奏规则

| 规则 | 取值 |
| --- | --- |
| 每学时新增有效代码 | 40–60 行 |
| 单次实训引入新概念 | ≤2 个 |
| 相邻实训难度增幅 | ≤1 级 |
| 排错时间占比 | 20%–30% |
| 2 学时实训 | 只保留一个主目标 + 一个验证目标 |
| 4 学时实训 | 最多两个主目标 + 一个综合验证 |

### 4.4 合理性判定

一个实训判为「合理」需同时满足：

1. **时间可完成**：步骤合计 + 机动时间 ≤ 学时。
2. **前置齐全**：所需文件、接口、数据、账号在上一实训产物中存在。
3. **失败可定位**：每个主要失败现象在排错清单中有对应条目。
4. **验收可观测**：验收项能落到命令、状态码、页面行为或文件内容。
5. **教材可对应**：每个目标能指到教材节号与验收点。

## 五、教材对应与简化规则

### 5.1 映射矩阵

每个实训的 `README.md` 必须包含一张映射表：

| 教材位置 | 教材内容 | 工程参考落点 | 验收点 |
| --- | --- | --- | --- |
| 节号 | 该节核心概念/代码块 | 文件与函数 | 命令/状态码/页面行为 |

### 5.2 可简化清单

| 类型 | 可简化内容 | 上限 |
| --- | --- | --- |
| 业务字段 | 只保留核心字段 | 不改变接口契约 |
| 前端样式 | 颜色、间距、图标 | 不影响信息层级与三态 |
| 扩展功能 | 课后扩展项可不做 | 教材标为课后扩展的 |
| 异常分支 | 只保留教材点名的错误码 | 每种错误码至少一个用例 |
| 数据量 | 种子数据 3–5 条 | 覆盖正常、空、边界 |

### 5.3 不可简化清单

1. 六文件职责边界：controller / service / crud / model / schema / param
2. 状态码分工：200、201、204、400、401、403、404、422
3. 权限依赖：未登录 401、非管理员 403
4. 事务与回滚：批量写入失败无半批数据
5. 测试基线：12-1 的正常、边界、异常三类用例
6. 健康检查与交付清单：22-1～24-1
7. 认证机制：hashlib 盐哈希 + TOKEN_STORE（不得回退为 JWT/passlib）
8. 登录响应三字段：`{access_token, token_type, user}`

### 5.4 已知差异口径（统一以 duty-simplified 为准）

| 差异 | 统一口径 |
| --- | --- |
| 重复资源 | 400 |
| 删除 | 204 且无正文 |
| 资源名 | 名词复数（departments / personnel / workstations / duty-records） |
| 列表响应 | `{items, total}`，无 sort_by 参数 |
| 认证 | hashlib + TOKEN_STORE，无 JWT |
| 依赖 | 后端 4 个；前端 streamlit + requests + pandas |
