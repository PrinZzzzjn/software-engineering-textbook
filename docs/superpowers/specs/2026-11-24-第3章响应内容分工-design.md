# 设计：3.2.2 与 3.4.3 响应内容分工调整

## 意图

用户在修订第 3 章时发现两处问题：3.2.2 与 3.4.3 都讲响应内容，分工不清；3.4.3 开头直接说“422 由 Pydantic 自动处理”，缺少逻辑铺垫，显得突兀。用户已选择“方案 A：小节内重排”——保留两节各自的位置和现有内容体量，只调整边界与论述顺序。

## 目标

1. 3.2.2 明确为“响应的基本结构”：状态行、状态码分类、响应头、响应体；状态码表保留作为识读基础，末尾一句话把错误类型的详细讨论引向 3.4.3。
2. 3.4.3 重写为系统性的“输入、输出相关的响应错误类型与原因”：以一次请求被拒绝的关卡顺序（模型校验 → 身份认证 → 权限判断 → 资源存在性 → 业务规则）组织 422、401、403、404、400，解释各错误出现的位置、责任方和选择理由；`HTTPException` 作为表达规则性失败的机制在路由铺垫后出场。
3. 收敛 3.4.1 与 3.4.3 之间关于 422/400 分界的重复，保留 3.4.1 的例子性结论，把完整对照集中到 3.4.3。
4. 同步章内引用：3.3.4 对“401、403 与 422 在 3.4.3 展开”的指引继续有效；实训课后扩展中对 3.4.3 责任表的复习指引继续有效。

## 方案（用户已选 A）

### 3.2.2 的修改

- 保留现有全部小节与状态码表。
- 在状态码分类段之后、响应体部分之前或节末，增加一句边界声明：本节只说明“怎么读一条响应”（组成与状态码类别）；“为什么返回 422、401、403、404 或 400、各由谁判定”在 3.4.3 按请求处理顺序展开。措辞避免与后文重复讲责任方。
- 节末承接句保持不变或微调，仍指向 3.3 和 3.4。

### 3.4.3 的重写

按以下顺序组织：

1. **问题引入**：成功的响应由 `response_model` 约束结构（呼应 3.4.2）；失败的响应来自请求在到达业务逻辑前后被不同关卡拒绝。一次请求要依次通过输入校验、身份认证、权限判断、资源定位与业务规则检查，任一关卡失败即返回对应状态码。用这一条路径替代原来突兀的“422 由 Pydantic 自动处理”。
2. **逐关卡说明**（可用表格或分段）：
   - 输入模型校验失败 → 422 → Pydantic → 在函数外发生 → 类型、必填、长度；呼应 3.4.1 的 `Greeting` 例子。
   - 未认证 → 401；已登录无权限 → 403 → 认证/权限依赖（本章先知道责任方，第 8、9 章展开）；解释二者混淆的后果（前端无法决定跳登录还是提示无权限）。
   - 资源不存在 → 404 → 查不到目标资源。
   - 业务规则不满足 → 400 → 参数合法但与已有数据冲突（编码重复等）。
3. **机制说明**：这些失败需要在函数中主动结束请求，使用 `HTTPException(status_code=..., detail=...)`；保留 3-4-6 代码示例及其分析，但把分析改写为“参数类型符合约定、不触发 422，但资源不存在”的关卡语言。
4. **责任表**：保留现有五行表格，作为各错误“谁负责、何时出现”的总览。
5. **补充与易错点**：保留 422 来源（WebDAV，非 RFC 9110 核心状态码）的说明、“不得以 500 代替”的说明和手动抛 422 的易错点框。
6. 删除开头“422 由 Pydantic 自动处理”的孤立句，以及与 3.4.1 重复的“422 与 400 的分界，正是……”完整复述；用一句话承接即可。

### 3.4.1 的最小收敛

- 第 407 行“422 不是函数体抛出的异常……”的说明保留（它服务于最小示例）。
- 第 439 行“422 与 400 的分界，正是……”加粗总结句保留，但它已是本节的结论；3.4.3 只引用不重复。
- 不改动示例代码和编号。
