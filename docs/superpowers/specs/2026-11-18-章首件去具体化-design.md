# 章首件「本章要解决的问题」去具体化设计（方案 A：原位收紧）

日期：2026-11-18　状态：待批准

## 一、意图

学员反映：各章「本章要解决的问题」在加粗问题句之后的描述过于具体，容易把概念提前固定成某个实现、某份清单，限制自主思考，形成片面的先入为主印象。

本轮在不改变 C17 体例（位置、定名、三段结构）的前提下，收紧加粗问题句之后的两段文字：**问题句不动，现象段只写一类麻烦，路径段只给方向，不给答案清单。**

目标不是把话说得含糊，而是让本节结束时，学员带走的是一个想问下去的问题，而不是一张照着做的待办清单。

## 二、现状诊断

问题集中在加粗问题句之后的两段，分两类：

| 类型 | 表现 | 例 |
| --- | --- | --- |
| 路径段清单化，提前交出答案 | 数量、顺序公式、文件名、状态码、工具函数名、章末结论前置 | 03「四项工作」、08「六个文件…422/400/404/500」、09 判据前置、11「指标→口径→…」六步、12「四条覆盖三类路径」、18「三个坑」、22「六步」 |
| 现象段案例化，绑定本次实现 | 具体接口、JSON、页码、地址、命令、故障清单 | 06 接口代码块、14 JSON 片段、17 章号与个案、23 `127.0.0.1`、24 `docker-compose.yml` |

这两类都偏离了既有 C17-3 判据（现象描述只写通用的一类麻烦，不给原因、定义与解法，不出现代码与表格）。属于最近几章重写时放宽，不是新口味。

已基本合格的章：01、10（现象段尚需去案例）、13、15、16（路径段尚需去数量）、19（现象段合格、路径段公式化）、20、21、24（现象段合格）。逐章处理见第四节。

## 三、改写判据

### D1　三段职责不变

1. 加粗问题句：取自本章核心问题，保持现状，不写口语引导。
2. 现象段：说明没有这项能力时会出现的一类麻烦，2–4 句。
3. 路径段：说明本章从哪个角度处理、为什么值得这样处理，1–2 句。

### D2　路径段（第③段）

- 只给方向与判断，不给步骤清单。
- 禁用：数量（三件事、四条、六个文件）、顺序公式（A → B → C）、文件名／字段名／函数名／状态码／命令、章末结论。
- 不以「本章做三件事／分四步／按 X→Y→Z 的顺序」开头；改用「本章关心的是……」「本章不急着……而是……」「本章从一个问题出发：……」。
- 允许保留章节依赖与跨章边界（如认证与授权的分工、下一章才动手构建），压缩为半句。

### D3　现象段（第②段）

重申并恢复 C17-3：

- 只写一类麻烦，不绑定具体项目、页面、页码、地址、数值、人名。
- 可以指认症状，不给原因、不给定义、不给解法。
- 不出现代码块、JSON、表格、截图、命令。

### D4　术语

问题句与现象段不引入本章尚未教的新术语；绕不开时紧跟一句白话解释。工具类章（14、15、19、21–24）允许点名工具本身——那就是本章要学的对象——但不列其 API、函数名与参数。

### D5　风格

保持无人称陈述或具体对象作主语；不使用「你会」「到时候你」等授课口吻（C17-4）。

### D6　自检判据

读完本节，能否把它复述成一张待办清单？

- 能 → 不合格，继续收紧。
- 只能复述出一个问题或一个方向 → 合格。

## 八、追加：章引言的知识体系口径（2026-11-18）

用户追加要求：引言应从知识体系上讲，而不是从具体项目功能上讲。引言只做三件事——**接上**前章留下的状态、**起念**这个状态在真实使用中哪里不够、**定位**本章推进哪一步。

### I1–I6

1. **主语是知识问题**，不是页面、模块或文件。
2. **承接前章时，说前章解决了哪个知识问题、留下什么未解问题**，不说“上一章做完了哪个页面/接口”。
3. **项目元素只作一次性的例子**，不承担组织句子的作用；删了不影响理解就删。
4. **仍要具体可指认**，落到可感知的工程处境，不滑向“系统需要处理数据”这类空话。
5. **不预告路线**：不出现节号、步骤序列、组件清单、数量。
6. 事故型引言（01、02）保留；环境提示块（21、22）不动。

判断标准：引言回答“这个知识问题为什么现在必须处理”，不回答“这一章分几步讲”。
