# 案例数据统一管理与编辑页面 设计文档

> 日期：2026-11-24  
> 范围：执勤电子年鉴案例数据；教材、实训手册、教师工程参考、项目参考、共享文档中与该项目相关的案例数据。  
> 本设计对应第一阶段静态清单 [docs/案例数据清单_执勤电子年鉴.md](../案例数据清单_执勤电子年鉴.md) 的第二阶段。

## 1. 目标

1. 把散落在教材、手册、工程、验证脚本中的案例数据收进**一份可编辑的事实源**。
2. 提供两个修改入口：**命令行**与**本地 Streamlit 小页面**，用户改一个字段即可传播到所有引用它的地方。
3. 保留教学上故意存在的简化数据（如 3-1 的 D01），但把它们登记在事实源中，避免“不一致却没人知道”。
4. 修改后能自动检查教材与工程是否同步，防止漏改。

## 2. 非目标

- 不改教材的教学结构、例题逻辑或题意，只改其中的案例数据取值。
- 不把 D01/P01 等教学简化编号保留为“合法差异”；用户已明确：D01 与 D001 这类编号没有本质区别，应统一为同一值。
- 对早期教学章中“内存字典/路径参数”的写法，只统一数据取值，不改变该章教学结构或题意。
- 不引入网络服务、数据库或多人协作；页面是本地作者工具。
- 不改 `duty-historical` 的历史业务数据（器材、安全记录等），它不在当前教学主线。

## 3. 约束

- 教材/手册为 Markdown，工程为 Python，离线可运行；统一方案不引入运行依赖。
- 用户可编辑文件必须是纯文本（YAML），页面只是替代品，不能成为唯一入口。
- 所有工程仍可独立启动：运行副本随工程复制，不能要求各工程运行时访问仓库外的路径。
- 数据修改要可回滚：所有自动替换通过 git diff 审核，不做不可见修改。

## 4. 方案选择

### 方案 A：YAML 事实源 + CLI + Streamlit 页面（选用）

- `data/case_data.yaml`：唯一可编辑源，按四类数据组织，每项带 `id`、字段值、别名、用途和同步策略。
- `tools/case_data.py`：校验、生成运行副本、扫描引用、按规则应用到全仓。
- `tools/case_data_editor/app.py`：Streamlit 页面，做展示、编辑、保存、检查。
- 工程侧读取 `data/case_data.json` 运行副本；同步脚本把运行副本写入需要独立运行的工程。

优点：人能直接改 YAML；CLI 可进脚本；页面降低操作门槛；沿用现有 tools 风格。缺点：需要一次性把现有散落值接入规则。

### 方案 B：Python 模块事实源

把数据写成 dataclass/dict，由各工程 import。改动代码少，但非技术用户阅读不便，且各独立工程要处理导入路径。不选。

### 方案 C：只维护文档台账

零代码，但改一处不会传播，不能解决“教材和实训不同步”，不选。

## 5. 事实源结构

文件：`data/case_data.yaml`。顶层结构：

```yaml
version: 1
updated: 2026-11-24
description: 执勤电子年鉴案例数据事实源

datasets:
  baseline:
    description: 正式种子数据（D001/P001/W001 等）
    entities:
      departments:
        - id: D001
          fields: {dept_code: D001, full_name: 一中队, address: 一号营区}
          aliases: []
          used_in: [教材第15章, 实训6-1起, 项目参考]
      personnel: ...
      workstations: ...
      duty_records: ...
      users: ...
  teaching_simplified:
    description: 教学简化数据（D01/P01/W01 等）
    entities: ...
  verification:
    description: 测试与临时数据（alice、D013、随机日期等）
    entities: ...
  frontend_demo:
    description: 15-1 前端假数据（D001-D012）
    entities: ...
```

每条字段带同步策略：

- `sync: true`：改值时自动替换全仓所有登记引用。
- `sync: false`：保留原值，只在检查时报告差异与用途。
- `aliases`：旧值或短编号，用于扫描时识别“同一事实的不同写法”，是否替换由 `sync` 决定。

数据流：

```text
编辑 YAML → 校验（结构与引用） → 生成 case_data.json → 应用替换到全仓 → 自动检查 → git diff 审核
```

## 6. 修改入口

### 6.1 命令行 `tools/case_data.py`

命令规格：

| 命令 | 作用 |
| --- | --- |
| `python tools/case_data.py show` | 打印当前四类数据与字段摘要 |
| `python tools/case_data.py set <dataset> <entity> <id> <field> <value>` | 修改一个字段（写回 YAML） |
| `python tools/case_data.py build` | 从 YAML 生成 `data/case_data.json` |
| `python tools/case_data.py check` | 扫描教材、手册、工程、文档，报告未同步引用 |
| `python tools/case_data.py apply` | 按替换规则把当前值应用到全仓（先输出变更清单，需 `--yes` 才写入） |
| `python tools/case_data.py diff` | 显示最近一次 apply 会改哪些文件（dry-run 明细） |

`apply` 只替换字段级登记的值，不做自由文本智能改写；未登记位置由 `check` 报告，由人工决定是否加入规则。

### 6.2 Streamlit 页面

位置：`tools/case_data_editor/app.py`

启动：`streamlit run tools/case_data_editor/app.py`

页面结构（简单作者工具）：

```text
执勤电子年鉴 · 案例数据管理
─────────────────────────────────────────
左侧侧栏：数据集选择
  ○ 基准种子  ○ 教学简化  ○ 验证临时  ○ 前端演示

主区：
  表格：当前实体列表（ID / 名称 / 关键字段 / 用途）
  选择一行 → 展开 st.form：
    字段1 [当前值可编辑]
    字段2 [当前值可编辑]
    [保存修改]  [取消]
  底部操作区：
    [生成运行副本]  [检查引用]  [应用到全仓]  ⚠️ 二次确认
  操作结果区：
    成功/失败消息、受影响文件列表、旧值→新值对照
```

设计取舍：不做登录、不做数据库、不做多用户；编辑直接写 YAML，保存后立刻 `build`，由用户显式点 `apply`。页面沿用 `实训19-1/20-1` 的青绿主题配置（`#0F766E` 等），保持教材视觉体系一致。

## 7. 同步规则

### 7.1 替换原则

- **基线数据统一**：D01/D001、P01/P001、W01/W001 统一为 D001/P001/W001；一号楼/一号营区、张三/张伟、班长/一级值班员等同一事实的不同写法同步统一。教学简化不是可保留差异，而是旧值。
- 验证数据：`sync: false` 的部分（alice 的注册/登录、随机日期、冲突记录）不进正式种子；若某处借用正式 ID 做测试，则由 `check` 报告。
- 前端演示数据：15-1 的 D001–D002 与基准种子一致；D003–D012 只在 15-1 使用，16-1 起停用。
- 标题、章节编号、题意叙述不参与替换；字段值替换限制在登记上下文中。

### 7.2 文件范围与例外

| 目录 | 处理方式 |
| --- | --- |
| `软件工程实践-2.0/*.md` | 替换正文、代码、表格中的登记值；第 3–5 章的教学简化写法也统一为基线值 |
| `实训手册/` | 同步 starter、README、指南、记录表中的登记值 |
| `实训工程参考/` | 同步每个实训的 `项目/`、`starter/`、`snapshot-b/` 三套副本中的 seed、测试默认值、文档说明 |
| `项目参考/duty-simplified/` | 作为后端事实源同步；`duty_frontend*` 同步演示账号与说明文字 |
| `_shared/接口契约清单.md` | 同步种子数据汇总表 |
| `docs/` | 历史设计与复盘文档默认不回改；检查时作为“历史记录”单列 |
| `项目参考/duty-historical/` | 不同步；标记为主线外 |

例外登记：

- 第 11 章例 11-1 的 5 条记录：统计口径手算样本，与工程种子不同，独立命名 `hand_calc_sample_1`。
- 第 10 章 08:00–12:00 等规则判断题：规则样本，独立命名 `rule_sample_overlap`。
- 第 12 章随机日期测试：独立命名 `test_random_day`，保持随机生成策略。
- `D404`/`D99`：不存在反例，独立命名 `not_found_examples`。

### 7.3 工程接入方式

为使工程可独立运行，运行副本按以下方式分发：

1. `case_data.json` 放在仓库 `data/` 下作为生成产物。
2. 后端工程在 `main.py` 顶部通过一个很小的加载函数读取 `data/case_data.json`（按工程相对路径定位，找不到时回落到内置常量），把 `_seed_*()` 里的字面量换成读取结果。
3. 前端假数据工程（15-1 等）把 `SEED_DEPARTMENTS` 换成读取同一份 JSON 的部门演示数据 section。
4. 每个工程不新增第三方依赖，JSON 由标准库读取；页面用到的 PyYAML 只在作者工具环境安装。

> 教学取舍提示：教材正文的 seed 代码仍逐行展示字面量，便于学生理解；工程参考中的实际 main.py 用加载函数。这是“教材讲写法、工程按统一数据运行”的合理差异，需在检查清单中登记。

## 8. 验证方式

1. 对 CLI：构造临时 YAML，执行 `set/build/check/apply`，断言生成值与替换范围正确。
2. 对页面：用 Streamlit AppTest 验证“选择实体 → 改字段 → 保存 → 生成 JSON → 检查”闭环（至少 5 项断言）。
3. 对全仓：运行 `python tools/case_data.py check`，要求基准种子未同步引用为 0；教学简化、历史文档、手算样本按例外清单输出，不计失败。
4. 对工程：至少抽测 10-1、11-1、15-1 三个工程，运行 pytest / verify_app.py，确认仍可独立运行。
5. 对教材：抽查第 3、10、11、12、15 章，确认题意未被破坏，只有数据值变化。

## 9. 实施顺序

1. 建 `data/case_data.yaml`，把静态清单中的四类数据全部录入，标注 `sync` 与 `aliases`。
2. 实现 `tools/case_data.py` 的 show/set/build/check/diff/apply。
3. 实现 `tools/case_data_editor/app.py` 页面，复用 CLI 函数，不另写逻辑。
4. 小范围试运行：先用 dry-run 对 10-1、11-1、15-1 生成替换清单，人工确认规则。
5. 全仓应用替换，逐目录审查 diff；工程运行时接入 JSON 加载。
6. 运行验证项，补一份简短使用说明到 `docs/案例数据管理使用说明.md`。

## 10. 风险与规避

- **风险**：全仓替换误伤例题叙述或 Git 历史文档。  
  **规避**：`apply --dry-run` 输出逐处上下文；默认不写 `docs/` 历史文档；人工审核 git diff 后才提交。
- **风险**：工程各自独立运行，读不到统一 JSON。  
  **规避**：生成运行副本到工程目录或保留回落常量；抽测启动与测试。
- **风险**：教学简化值被统一后破坏教学链。  
  **规避**：`sync: false` 与例外清单；`check` 区分“未同步”与“允许差异”。
- **风险**：页面保存与 CLI 写入互相覆盖。  
  **规避**：页面只调用 CLI 的同一组函数；每次保存后展示当前值与更新时间；建议通过 git 管理版本。
