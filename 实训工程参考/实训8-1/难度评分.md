# 实训 8-1 难度评分

## 一、结论

| 项目 | 结论 |
| --- | --- |
| 规模 | **D3** |
| 认知 | **L4** |
| 课时 | 4 学时，180 分钟 |
| 综合判断 | **D3 / L4，合理偏紧** |
| 建议 | users 表、盐哈希、令牌、三个接口为必做；令牌过期与登出列课后扩展 |

「合理偏紧」的含义：按 180 分钟可以完成必做并留出排错时间，但没有富余做完整测试、权限与用户管理；课堂必须严格按边界收口，否则容易把 9-1 的内容提前，导致旧接口回归没时间做。

## 三、认知负荷

### 3.1 新概念计数

| 新概念 | 是否计入 | 说明 |
| --- | --- | --- |
| 盐哈希（`盐$迭代次数$摘要`、随机盐、重算比较） | 计入第 1 个 | 学生首次处理「不可逆存储 + 随机盐」 |
| 服务端令牌存储（随机令牌 + `TOKEN_STORE` + Bearer） | 计入第 2 个 | 首次处理「登录态、令牌生命周期、撤销」 |
| 依赖注入 `Depends` | 不计入 | 教材 4.5 已讲，7-1 已用 `Depends(get_db)`；8.4 只是把认证函数挂到接口入口 |
| Pydantic 请求/响应模型与 `response_model` | 不计入 | 4-1 六文件体例已讲；本实训只新增 `ConfigDict(from_attributes=True)` 与嵌套 `TokenOut`，是旧机制的扩展 |
| `HTTPBearer` | 不计入 | 属于令牌认证的实现细节，并入第 2 个概念 |
| `hashlib` / `secrets` | 不计入 | Python 标准库用法，不构成新的架构概念 |

新概念数 **2**，满足「新概念 ≤ 2」的约束。依赖注入已在 4.5 讲过，本实训不把它当新概念，也不在课堂上重新讲 `Depends` 的原理，只讲「把 `get_current_user` 挂到 `/me`」。

### 3.2 为什么是 L4 而不是 L3

L4 的依据不是代码行数，而是同时出现的四类负荷：

1. **安全语义**：认证失败 401 与权限不足 403 必须分清；后者本实训不做，但学生要知道为什么不做。
2. **静默失败**：忘记导入模型、哈希拼接顺序不一致、令牌未登记，启动都不报错，只在运行时表现为 500 或 401，排错依赖日志与手工验证。
3. **跨层装配**：模型导入、建表、seed、路由挂载、依赖注入、响应模型六处必须同时正确，缺一处接口就不通。
4. **回归约束**：新增认证不能改变 department/personnel 的路径、字段、状态码与排序；学生要主动跑旧接口，而不是只看新接口。

不是 L5 的原因：没有引入新框架、没有并发/性能设计、没有数据库迁移、没有多角色权限矩阵；新概念只有 2 个，且都有教材代码可对照。

## 四、180 分钟时间测算

| 环节 | 估算 | 说明 |
| --- | --- | --- |
| 读任务、确认边界 | 10 | 明确不做 403、列表、改密 |
| 复制起点、建环境、跑旧接口 | 15 | venv、依赖、health、两个列表 |
| users 表、CRUD、建表范围 | 30 | 六文件中的 3 个 + main 一行导入 |
| 盐哈希、令牌、REPL 验证 | 30 | 理解 `盐$迭代次数$摘要`、同密不同哈希、令牌登记 |
| schema、service、注册/登录路由 | 40 | 201/400/422/200/401 五条分支 |
| `/me`、`HTTPBearer`、依赖注入 | 30 | 401 的两种文案、令牌头格式 |
| 回归、重启、验收、提交 | 25 | 旧接口 + admin + 清理运行数据 |
| **合计** | **180** | 不含课后扩展 |

时间分配中，纯编码约 80 分钟，理解与排错约 65 分钟，验收与收尾约 25 分钟，缓冲约 10 分钟。紧在排错：如果学生把「哈希校验失败」误判为「数据库没存」，可能反复删库重建，半小时就过去了。教师在阶段 3、阶段 5 各设一个检查点，可以把这类问题截住在早期。

## 五、风险与降载方案

| 风险 | 概率 | 影响 | 降载 |
| --- | --- | --- | --- |
| 忘记导入 user 模型，注册 500 | 高 | 建表阶段卡住 | 阶段 2 用 `inspect` 查表，先确认 `users` 存在 |
| 哈希拼接顺序不一致，正确密码 401 | 中 | 误判为账号问题 | 阶段 3 用 REPL 先验证 `verify_password` |
| 用默认 `HTTPBearer()`，缺令牌 403 | 中 | 与验收口径不符 | 明确 `auto_error=False`，检查点验 401 |
| 登录直接返回 ORM，泄露 `password_hash` | 中 | 安全缺陷 | 路由必须挂 `UserOut`/`TokenOut` |
| 改旧接口导致回归失败 | 低 | 7-1 行为被破坏 | 每阶段结束跑两个列表与一次 CRUD |
| 时间不够 | 中 | 扩展做不完 | 令牌过期、登出直接移到课后，不占课堂 |

如果课堂只剩 120 分钟，建议砍掉：`create_admin` 之外的 seed 讨论、OpenAPI 细节、课后扩展；保留 users 表、哈希、令牌、三个接口与旧接口回归。如果课堂有 240 分钟，可加令牌过期与登出，但仍不建议提前做 403 与用户列表，避免与 9-1 重复。

## 六、与 7-1 的难度对比

| 维度 | 7-1 | 8-1 |
| --- | --- | --- |
| 规模 | D3（约 215 行、9 文件） | D3（净增 197 行、9 文件） |
| 认知 | L3/L4 | L4 |
| 主要负荷 | 六文件分层、分页过滤、固定排序 | 安全语义、令牌生命周期、静默失败、回归 |
| 排错难度 | 中（422/404 直接可见） | 高（401/500 需要推断哈希与令牌） |
| 结论 | 合理 | 合理偏紧 |

8-1 的代码量略低于 7-1，但认知负荷更高：7-1 的错误大多有明确状态码，8-1 的认证错误往往是「正确密码也 401」或「有令牌也 401」，需要学生理解哈希与令牌两条链路。因此同样 180 分钟，8-1 更紧。
