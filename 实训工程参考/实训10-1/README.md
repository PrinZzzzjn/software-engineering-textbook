# 实训 10-1 业务模块：规则描述

> **B 档口径（2026-11-23）**：课堂只做新增执勤记录 + 时间重叠 400；workstation/duty_record 模块由教师快照提供，批量处理为教师演示。
本实训从实训 9-1 的账号管理工程出发，新增哨位模块与执勤记录模块，把需求摘录中的三条业务约束落成 service 层的可测试代码。完成态见 `项目/`，学员起点见 `starter/`，实跑证据见 `验证记录.md`。认证与权限沿用 9-1：`PBKDF2` 盐哈希 + 进程内 `TOKEN_STORE`，写接口管理员、读接口公开。

## 二、教学目标与教材映射

完成本实训后，学生应能：

1. 区分数据合法与业务合法：字段格式由 schema 守，业务组合由 service 守。
2. 从需求文字中识别约束，并按单字段、跨字段、跨表、跨记录分类。
3. 为规则选择归属层，说明为什么时间顺序、关联存在与时段重叠不能交给 schema 或数据库。
4. 按「先便宜、后昂贵」固定校验顺序，并让每条失败返回可定位的 400 提示。
5. 用「已有开始 < 新结束 且 已有结束 > 新开始」判断重叠，正确处理首尾相接的边界。
6. 守住「先校验、后写入」：校验失败不提交，数据库没有半条记录。
7. 把规则清单转成正常、冲突、边界三类用例，并保留 9-1 与 8-1 的回归。

## 三、边界与不变量

### 3.1 规则清单（七列）

| 规则 | 来源（需求原句） | 范围类型 | 归属层 | 校验顺序 | 错误码与信息 | 用例 |
| --- | --- | --- | --- | ---: | --- | --- |
| 开始早于结束 | 摘录第 2 句 | 跨字段 | service | 1 | 400「开始时间必须早于结束时间」 | 正常／相等／倒置 |
| 人员存在 | 摘录第 1 句 | 跨表 | service | 2 | 400「人员不存在」 | 存在／不存在 |
| 哨位存在 | 摘录第 1 句 | 跨表 | service | 3 | 400「哨位不存在」 | 存在／不存在 |
| 同一哨位时间不重叠 | 摘录第 3 句 | 跨记录 | service | 4 | 400「该哨位在该时段已有执勤安排」 | 包含／部分重叠／相同／首尾相接／之后 |

重叠条件：`已有开始 < 新结束 且 已有结束 > 新开始`。首尾相接不满足第二个条件，属于连续值勤，不算冲突。

### 3.2 必须遵守

- 路径不加版本化前缀，统一 `include_router(..., prefix="")`；集合路径 `/workstations`、`/duty-records` 不带尾斜杠。
- 认证与授权沿用 9-1：`PBKDF2` 盐哈希 + `TOKEN_STORE`；写接口挂 `get_current_admin_user`，读接口公开。
- 全部业务规则只写在 `duty_record/service.py`；controller 只转发，crud 只读写，不在 schema 里写跨字段判断。
- 校验顺序固定：时间顺序 → 人员 → 哨位 → 重叠；顺序不能调换。
- 校验全部通过后才写入；失败路径不 `commit`。
- 执勤记录没有 PUT（更新）接口，与 `项目参考/duty-simplified/` 一致。
- 列表统一 `{items, total}`，固定 `order_by(id)`；分页参数 `page` / `page_size` 边界与第 7 章一致。
- 运行依赖、`.env.example`、`.gitignore` 与 9-1 相同，不新增依赖。

### 3.4 关于哨位模块的说明（教材一致性）

教材 10-1 步骤 3 要求「写 `DutyRecord` 模型与外键字段」，规则二要求「哨位必须是已登记哨位」，即隐含人员表与哨位表已存在；教材第 8 章排错清单也提到 `workstation` 路由。但 9-1 的实训链里只有 department、personnel、user。为了不改教材、又让三条规则可运行、可测试，本实训补建**最小的哨位模块**（六文件、与 personnel 同构、写接口管理员）。这属于对实训链的补全，不是对教材的改写。

## 六、操作步骤

1. **读需求、列约束（20 分钟）**：一句需求对一行，填「来源」列；从 10.2 摘录里找出人员存在、时间顺序、时段不重叠三条。
2. **分类与定层（20 分钟）**：填「范围类型」与「归属层」；跨字段、跨表、跨记录都放 service。
3. **建表并实现三条规则（50 分钟）**：先建 `Workstation` 与 `DutyRecord` 模型，再按清单写 `_validate_duty_record`。
4. **排序与错误信息（30 分钟）**：固定「时间 → 人员 → 哨位 → 重叠」；业务规则 400，格式 422，资源不存在 404。
5. **清单转用例（30 分钟）**：每条规则至少正常与冲突；重叠规则补首尾相接；冲突断言到具体提示。
6. **事务边界与回归（20 分钟）**：校验放写入前；失败后查列表确认无残留；重跑 9-1 与 8-1 用例。

详细的分阶段代码见 [分步实现指南.md](分步实现指南.md)。

## 十、常见问题与排错

| 现象 | 先查什么 |
| --- | --- |
| 规则通过但数据仍脏 | 校验是否写在 `crud.create` 之后；是否在循环里提前 `commit` |
| 首尾相接被判冲突 | 重叠条件是否误写成 `<=` / `>=`；应严格用 `<` 与 `>` |
| 人员不存在却提示时间冲突 | 校验顺序被调换；应先查时间顺序 |
| 422 与 400 混用 | 422 由 Pydantic 在进入函数前产生；业务规则才是 400 |
| 新建哨位返回 400「所属单位不存在」 | 先建 department，或使用 seed 的 D001/D002 |
| 写接口匿名就能成功 | 装饰器是否漏了 `dependencies=[Depends(get_current_admin_user)]` |
| 旧库启动后查不到新表 | 是否在 `main.py` 导入两个新模型后再 `create_all` |
