# 实训 5-1 分步实现指南

本指南严格对应教材实训 5-1 的六步：迁移 4-1 产物、补全配置与入口、虚拟环境与依赖、Git 两次初始提交、分支开发与冲突合并、启动验证与文档同步。示例为单位模块。

**代码一致性约定**：阶段 2 中标注为完整文件的代码块与 `项目/` 对应文件逐字一致。阶段 5 对健康响应的修改是临时 Git 演练，不回写教师完成态。所有命令以 Windows PowerShell 为准，文档服务端口统一为 8000。

## 阶段 0：准备起点与检查环境

在包含本实训材料的目录打开 PowerShell。把起点复制到临时工作目录，避免修改教师参考；若路径已存在，先另选目录名，不要覆盖已有练习。

```powershell
$work = Join-Path $env:TEMP "duty-train51-work"
if (Test-Path $work) { throw "请更换 `$work 的目录名，避免覆盖已有练习" }
Copy-Item -Recurse -LiteralPath .\starter -Destination $work
Set-Location $work
python --version
git --version
```

预期 Python 为 3.10 或更高，Git 能打印版本。`starter/app/` 就是 4-1 完成态，六个业务文件不是待补骨架。自己的 4-1 设计文档与接口验证记录另行保留，在阶段 6 更新。

常见错误：

- 直接在教师 `项目/` 上练习 Git，导致没有亲手补全入口与配置。
- 把 starter 当成 TODO 而重写六文件；本实训只迁移它们。
- 在实训参考根目录寻找 `main.py`；入口应在工作副本根目录，最终完成态位于 `项目/main.py`。

## 阶段 1：迁移 4-1 产物（15 分钟）

### 操作

1. 核对工作副本中的 `app/__init__.py`、`app/modules/__init__.py`、`app/modules/department/__init__.py`。
2. 核对 `controller.py`、`service.py`、`crud.py`、`model.py`、`schema.py`、`param.py` 六文件，保持名称与内容不变。
3. 本参考所用 4-1 已是包结构：controller 只有 `APIRouter`，没有 `app = FastAPI()`；模块内部使用相对导入。因此本步是**无改动，仅迁移**，不要再改导入或删除应用对象。
4. 确认 router 前缀仍为 `/departments`，根目录配置稍后在阶段 2 新建。

```powershell
Get-ChildItem .\app\modules\department -Name
python -c "from app.modules.department import controller; print(controller.router.prefix)"
```

### 预期

文件列表含三个下划线包文件和六个职责文件；第二条命令输出：

```text
/departments
```

若当前 Python 尚未安装 4-1 依赖，可先完成阶段 3，再回来执行导入检查。

### 常见错误

- 少了 `__init__.py` 或不在工作副本根目录执行，出现 `ModuleNotFoundError`。
- 把旧手册的 `/api/v1` 写进模块 router；模块只负责 `/departments`，根装配也使用空前缀。
- 为“工程化”新建第二套 service/crud；六文件已存在，不得重复创建。

## 阶段 2：补全配置与 main.py（25 分钟）

### 2.1 根 `main.py`

在工作副本根目录新建 `main.py`，完整内容如下，与 `项目/main.py` 逐字一致：

```python
from fastapi import FastAPI

from app.modules.department import controller as department_controller

app = FastAPI(title="Duty API", version="0.1.0")


@app.get("/health")
def health():
    return {"status": "healthy"}


app.include_router(department_controller.router, prefix="")
```

入口只创建应用、声明健康检查和挂路由。`prefix=""` 与模块 `/departments` 相加仍为 `/departments`；没有 `/api/v1`。本章模型是内存 dataclass，不写 `create_all`，也不导入 `app.core.database`。

### 2.2 `requirements.txt`

完整内容与 4-1 一致，只列两个直接运行依赖；Pydantic 由 FastAPI 带入，教师测试工具不写入运行清单：

```text
fastapi
uvicorn
```

### 2.3 `.env.example`

本章只列配置变量与示例值，不包含真实密钥，也不提前加入数据库或 JWT 配置：

```env
DEBUG=True
```

本机需要时复制为 `.env`，但 `.env` 不提交。当前应用尚未读取 `DEBUG`，本步学习的是配置边界，不引入额外配置库。

### 2.4 `.gitignore`

必须在第一次 `git add .` 前写好：

```gitignore
venv/
__pycache__/
*.pyc
.env
*.db
logs/
.pytest_cache/
```

### 2.5 项目 `README.md`

写明 Python 3.10+、虚拟环境、`python -m pip install -r requirements.txt`、`python -m uvicorn main:app --port 8000`，并画出实际目录。完整示例见 `项目/README.md`，不要把不存在的 `app/core/`、`tests/` 或数据库画进目录。

### 验证

完成阶段 3 的依赖安装后，在工作副本根目录执行：

```powershell
python -c "from main import app; print(sorted({r.path for r in app.routes if r.path in ['/health', '/departments', '/departments/{dept_code}']}))"
```

预期包含 `/health`、`/departments`、`/departments/{dept_code}`，不包含 `/api/v1/departments`。

### 常见错误

- `/docs` 404：启动对象或工作目录不对，应使用根 `main:app`。
- 业务接口全 404：根误加 `/api/v1`，或把集合路径写成 `/department`、多加末尾斜杠。
- 把旧手册的 `SECRET_KEY`、`ALGORITHM`、令牌时间抄入示例；本章标准库认证尚未开始，这些变量没有使用位置。

## 阶段 3：虚拟环境与依赖（20 分钟）

在工作副本根目录执行：

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -c "import sys; print(sys.prefix)"
python -m pip list
```

预期提示符出现 `(venv)`，`sys.prefix` 指向当前工作副本的 `venv`，`pip list` 可见 FastAPI、Uvicorn 和由 FastAPI 安装的 Pydantic。

若 PowerShell 阻止激活脚本，不更改系统执行策略，直接以完整路径执行：

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
.\venv\Scripts\python.exe -c "import sys; print(sys.prefix)"
```

Linux/macOS 的激活命令为 `source venv/bin/activate`。正式项目可进一步锁定版本；本教学快照为与 4-1 逐字一致，requirements 保持未锁定两项。

常见错误：

- 激活前执行 pip，把依赖装进系统 Python；用 `sys.prefix` 核实。
- 在非清单目录执行安装，出现 `No such file or directory: requirements.txt`；回到工作副本根目录。
- 把 `httpx`、`pytest` 写进运行依赖；它们只供教师运行根目录冒烟脚本，按需另装。

## 阶段 4：Git 初始化与两次提交（30 分钟）

### 4.1 初始化与作者身份

以下命令在工作副本根目录连续执行。作者信息只设置在本地仓库，请替换为自己的课程身份：

```powershell
git init -b main
git config user.name "Student Name"
git config user.email "student@example.com"
git check-ignore -v venv .env duty.db logs/dev.log __pycache__/sample.pyc
```

预期 `git check-ignore` 为每类路径打印一条匹配规则。该命令只检查路径，不需要真的创建 `.env` 或数据库。

### 4.2 第一次只提交忽略规则

```powershell
git add .gitignore
git commit -m "chore: add gitignore"
git status --short
```

预期提交只有一个 `.gitignore`；已存在的 venv 不出现在待提交列表中。

### 4.3 第二次提交完整工程

```powershell
git add .
git commit -m "chore: init fastapi project"
git status --short
git log --oneline
```

预期工作区无输出，历史有两条，顺序为工程初始化在上、忽略规则在下。检查跟踪清单：

```powershell
git ls-files
```

预期有 `main.py`、`requirements.txt`、`.env.example`、`.gitignore`、`README.md` 和 `app/` 内文件，没有 `venv/`、`.env`、`*.db`、日志或缓存。

常见错误：

- 第一次就 `git add .`，使本机文件误入暂存区；先交忽略规则是更稳妥的顺序。
- `.gitignore` 已写但文件早前被跟踪，规则不会自动移除旧索引；例如执行 `git rm -r --cached venv` 后单独提交移除。
- 提交信息写“更新”“最终版”；应说明本次唯一改动。

## 阶段 5：分支开发、合并与冲突解决（35 分钟）

### 5.1 `feature/health-version` 分支与快进合并

从 `main` 建功能分支，用 PowerShell 精确替换健康返回行，随后查看差异再提交：

```powershell
git switch -c feature/health-version
(Get-Content -Raw .\main.py).Replace('return {"status": "healthy"}', 'return {"status": "healthy", "version": "0.1.0"}') | Set-Content -Encoding ascii -NoNewline .\main.py
git diff -- main.py
git add main.py
git commit -m "feat: add service version to health"
git switch main
git merge feature/health-version
```

预期 `git diff` 只改变 return 行；因 main 没有分叉后的新提交，合并显示 `Fast-forward`。这是第三次提交。

### 5.2 制造一次确定的同处修改冲突

先从当前 main 建评审分支并提交一种改法：

```powershell
git switch -c feature/health-review
(Get-Content -Raw .\main.py).Replace('return {"status": "healthy", "version": "0.1.0"}', 'return {"status": "healthy", "version": "0.1.0", "review": "feature"}') | Set-Content -Encoding ascii -NoNewline .\main.py
git add main.py
git commit -m "feat: record feature health review"
```

再回 main 对同一行作不同修改并提交：

```powershell
git switch main
(Get-Content -Raw .\main.py).Replace('return {"status": "healthy", "version": "0.1.0"}', 'return {"status": "healthy", "version": "0.1.0", "review": "main"}') | Set-Content -Encoding ascii -NoNewline .\main.py
git add main.py
git commit -m "feat: record main health review"
git merge feature/health-review
```

最后一条预期返回非零状态并显示 `CONFLICT (content): Merge conflict in main.py`，这是本演练刻意制造的正常现象。打开文件：

```powershell
notepad .\main.py
```

找到 `<<<<<<< HEAD`、`=======`、`>>>>>>> feature/health-review` 三组标记。协商后的目标只保留一行返回：`return {"status": "healthy", "version": "0.1.0", "reviewed": True}`；删除两版旧 return 与全部冲突标记，其余文件内容不变。保存关闭后执行：

```powershell
git diff --check
python -m py_compile main.py
git add main.py
git commit -m "merge: resolve health response conflict"
git log --oneline --graph
git status --short
```

预期检查无冲突标记或语法错误，合并提交完成，历史图出现两条父提交汇合，工作区干净。冲突不是要不要保留某个标记的选择，而是由人决定最终契约。

### 常见错误

- 第一次合并期待 merge commit，却看到 Fast-forward；主分支未前进时这是正确结果，第二次双分支演练会显式形成汇合。
- 没有先提交功能分支就切回 main，导致改动被带过去；每次切换前看 `git status`。
- 机械保留两方全部 return，造成重复或逻辑不清；按最终响应契约人工取舍。
- 删除标记后忘记 add/commit，`git status` 仍显示 `both modified` 或 `unmerged paths`。

## 阶段 6：启动验证与文档同步（20 分钟）

### 6.1 真实启动

在已激活虚拟环境的工作副本根目录执行：

```powershell
python -m uvicorn main:app --port 8000
```

另开 PowerShell，请求三个地址：

```powershell
(Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8000/health).StatusCode
(Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8000/docs).StatusCode
(Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8000/departments).Content
```

预期前两次输出均为 200，列表响应含 `items`、`total`；健康响应是冲突解决后确定的 JSON。浏览器打开 <http://127.0.0.1:8000/docs>，应看到 `/health` 和“单位”五接口，路径没有 `/api/v1`。测试完回到服务终端按 `Ctrl+C`。

### 6.2 教师完成态冒烟

教师在实训根目录、已激活且另装验证依赖的环境中执行：

```powershell
python -m pip install httpx pytest
python verify_api.py
```

预期 `/health` 200、列表 200 且含 `items/total`、POST 201、DELETE 204 空响应体，最终输出 `PASS: 4/4 smoke checks`。该脚本只验证教师 `项目/main.py`，不用于替代学生请求自己的工作副本。

### 6.3 文档与交付同步

1. 将 4-1 设计文档的目录一节更新为实际根目录与 `app/modules/department/`；说明 `app/core/`、`tests/` 尚未到加入时机。
2. README 写入实际启动命令、依赖安装与目录，不写未经验证的地址。
3. 验证记录分别填写命令、预期、实际、结论；若服务经过了分支健康响应演练，记录最终实际 JSON。
4. 再查 `git status --short`、`git log --oneline --graph` 和 `git ls-files`，保存真实输出。
5. 若验证后又修改 README 或设计文档，按改动意图单独提交，不把无关变化塞入已有主题。

常见错误：

- 只在 TestClient 中成功就声称真实服务器已启动；两类证据分别记录。
- 验证 `/api/v1/departments` 并误把 404 当模块故障；正确路径是 `/departments`。
- 把预期状态码直接抄到“实际”列；必须来自真实响应。
- 文档仍画数据库或 tests，磁盘却没有；以本章职责与实际情况同步文档，不提前占目录。
