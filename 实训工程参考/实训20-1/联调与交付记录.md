## 二、一次完整排查记录

**现象**：新增单位时单位名称填了 101 个字，页面出现一长串英文列表 `[{'type': 'string_too_long', ...}]`，用户看不懂。

| 步骤 | 记录 |
| --- | --- |
| 现象 | 表单提示是不可读的英文列表，没有指出字段 |
| 状态码 | 422 |
| detail / 返回体 | `detail` 是数组，`msg` 为 `String should have at most 100 characters` |
| 后端日志 | 无异常堆栈，属于请求参数校验 |
| 定位 | 前端 `api_client._request` 把 `detail` 原样转成字符串，页面又直接 `st.error` |
| 修复 | `api_client` 把列表按 `msg` 压平成一句话；页面改调 `show_api_error`，加「提交内容有误」前缀 |
| 重跑 | 再提交 101 字名称，提示「提交内容有误：String should have at most 100 characters」；十步清单全部重跑通过 |

**结论**：422 是参数问题，不是服务器问题；先看 `detail` 结构，再决定在哪一层压平与展示。

## 三、错误处理记录

| 状态码 | 触发方式 | 页面提示 | 结果 |
| --- | --- | --- | --- |
| 401 | 用 `Bearer invalid-token` 写单位 / 页面令牌失效 | 清会话，回登录页「登录已过期，请重新登录」 | 通过（真实令牌失效场景 + 真 HTTP 401） |
| 403 | 无自然路径，注入 `ApiError(403, "Forbidden")` | 「当前账号没有权限执行该操作」 | 通过（注入验证） |
| 404 | `GET /departments/NOPE` 后打开删除/编辑 | 「数据不存在，可能已被删除」 | 通过（真 HTTP 404 + 注入） |
| 422 | 单位名称 101 字 | 「提交内容有误：String should have at most 100 characters」 | 通过（真 HTTP 422） |
| 500 | 无自然路径，注入 `ApiError(500, "Traceback ... SECRET-TOKEN")` | 「服务器开小差了，请稍后重试或联系管理员」，不含堆栈与令牌 | 通过（注入验证） |

补充：后端还有一个 400（重复单位编码），页面直接显示「单位编码已存在」，不属于五类固定映射，按 `else` 分支输出 `detail`。
