# 实训 9-1 分步实现指南

本指南按教材 9.1–9.4 与「◆ 实训 9-1」的顺序，把 8-1 的登录认证工程改造成带账号管理权限的工程。标注「完成态文件」的代码块与 `项目/` 中的同名文件逐字一致；标注「片段」的代码块只表示本阶段要追加的部分，阶段结束时以完成态文件为准。

约定：

- 命令默认在 `项目/` 目录执行，课堂端口用 8000；`验证记录.md` 的 8016 只用于教师隔离验证。
- 不引入版本化路径前缀，所有路由 `prefix=""`，集合路径不带尾斜杠。
- 认证与令牌实现保持 8-1 原样；只新增授权依赖与账号管理接口。
- 每个阶段结束都重启服务并做一次检查，不要等全部写完再排错。

## 阶段 0：读任务与确认边界（5 分钟）

先明确本实训只做四件事：

1. 在认证依赖之上新增管理员依赖，让未登录 401、普通用户 403。
2. 新增 `GET /users`，管理员分页查看账号，响应不含 `password_hash`。
3. 新增 `PUT /users/{user_id}`，管理员改角色与启用状态；禁用后不能登录。
4. 把 department、personnel 的写接口收回管理员。

以下内容**不做**：修改角色的完整业务校验（最后一个管理员、改自己角色）、完整禁用流程（清理旧令牌、前端提示）、用户删除、改密、按角色筛选、令牌过期、登出、数据库迁移。看到旧资料把这些塞进 90 分钟，一律跳过。

本阶段的检查点：能说清下面三条分别由哪一层产生：

| 情况 | 状态码 | 产生位置 |
| --- | --- | --- |
| 没带令牌或令牌无效 | 401 | `get_current_user` |
| 已登录但不是管理员 | 403 | `get_current_admin_user` |
| 请求体里的 `role` / `is_active` 非法 | 422 | Pydantic，进入函数前 |

## 阶段 2：管理员依赖与 401/403 分工（15 分钟）

### 2.1 为什么在 `get_current_user` 之上再包一层

`get_current_user` 只回答「你是谁」：从 Bearer 头取令牌，查 `TOKEN_STORE` 得到 `user_id`，再查 users 表得到 `role`，返回 `{id, role}`。它不判断角色，所以普通用户也能通过。

授权要回答「你能不能做」。这件事会出现在列表、修改、department/personnel 写接口等至少八个入口，写成独立依赖比在每个函数里复制 `if` 更可靠：接口声明处挂一次，业务函数不必重复检查，401 与 403 的归属也不会混。

### 2.2 追加依赖（完成态文件：`app/core/security.py`）

```python
import hashlib
import secrets

from fastapi import Depends, HTTPException
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from sqlalchemy.orm import Session

from app.core.database import get_db


ITERATIONS = 100_000


def get_password_hash(password: str) -> str:
    salt = secrets.token_hex(16)
    digest = hashlib.pbkdf2_hmac(
        "sha256", password.encode("utf-8"), bytes.fromhex(salt), ITERATIONS
    ).hex()
    return f"{salt}${ITERATIONS}${digest}"


def verify_password(plain_password: str, hashed_password: str) -> bool:
    salt, iterations, digest = hashed_password.split("$", 2)
    candidate = hashlib.pbkdf2_hmac(
        "sha256", plain_password.encode("utf-8"), bytes.fromhex(salt), int(iterations)
    ).hex()
    return secrets.compare_digest(candidate, digest)


# 令牌表：token -> user_id，内存字典，进程重启即清空
TOKEN_STORE: dict[str, int] = {}


def create_access_token(user_id: int) -> str:
    token = secrets.token_hex(16)
    TOKEN_STORE[token] = user_id
    return token


def resolve_token(token: str) -> int | None:
    return TOKEN_STORE.get(token)


bearer_scheme = HTTPBearer(auto_error=False)


def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(bearer_scheme),
    db: Session = Depends(get_db),
) -> dict:
    if credentials is None:
        raise HTTPException(status_code=401, detail="未提供令牌")
    user_id = resolve_token(credentials.credentials)
    if user_id is None:
        raise HTTPException(status_code=401, detail="令牌无效")
    from app.modules.user import crud

    user = crud.get_by_id(db, user_id)
    if user is None:
        raise HTTPException(status_code=401, detail="令牌无效")
    if not user.is_active:
        raise HTTPException(status_code=401, detail="账号已禁用")
    return {"id": user.id, "role": user.role}


def get_current_admin_user(current_user: dict = Depends(get_current_user)) -> dict:
    """在认证之上再做授权：不是管理员就返回 403。

    get_current_user 已处理未登录与令牌无效（401），本函数只处理
    “身份已确认但权限不足”（403）。角色每次从用户表读取，改角色即时生效。
    """
    if current_user["role"] != "admin":
        raise HTTPException(status_code=403, detail="权限不足")
    return current_user
```

要点：

- 依赖链是 `bearer_scheme → get_current_user → get_current_admin_user`，顺序由 FastAPI 保证：没登录时第一层先抛 401，根本走不到角色判断。
- 角色判断用 `!= "admin"` 而不是 `== "normal"`：以后即使增加第三种角色，默认也是拒绝，符合最小权限。
- 不在令牌里放角色。`get_current_user` 每次都按 `user_id` 查库，所以管理员把某人改成 `admin` 或禁用某人后，那人手里的旧令牌立刻按新角色或新状态生效；代价是每次请求多一次主键查询。

## 阶段 3：用户列表与分页（20 分钟）

先在 `app/modules/user/schema.py` 的 `UserOut` 之后追加 `UserPage`（完整 schema 见 4.1）：`items: list[UserOut]` 与 `total: int`。列表路由用它声明 `response_model`，字段过滤交给 `UserOut`。

### 3.1 分页参数（完成态文件：`app/modules/user/param.py`）

```python
from pydantic import BaseModel, Field


class UserQueryParams(BaseModel):
    """用户列表的分页参数，边界与第 7 章其它模块一致。"""

    page: int = Field(1, ge=1)
    page_size: int = Field(10, ge=1, le=100)
```

参数名、默认值与边界完全沿用第 7 章：`page` 最小 1，`page_size` 1–100。前端不需要为 users 另记一套分页规则。`page=0`、`page_size=101` 在进入函数前返回 422。

### 3.2 分页查询（完成态文件：`app/modules/user/crud.py`）

```python
from sqlalchemy.orm import Session

from app.core.pagination import paginate
from app.modules.user.model import User


def get_by_username(db: Session, username: str) -> User | None:
    return db.query(User).filter(User.username == username).first()


def get_by_id(db: Session, user_id: int) -> User | None:
    return db.query(User).filter(User.id == user_id).first()


def create(db: Session, username: str, password_hash: str) -> User:
    user = User(username=username, password_hash=password_hash)
    db.add(user)
    db.commit()
    db.refresh(user)
    return user


def update(db: Session, user: User, changes: dict) -> User:
    for field, value in changes.items():
        setattr(user, field, value)
    db.commit()
    db.refresh(user)
    return user


def list_page(db: Session, offset: int, limit: int):
    """复用第 7 章的分页公共件：只设置本模块的 query 与固定排序。"""
    query = db.query(User).order_by(User.id)
    return paginate(query, offset, limit)
```

`paginate` 内部先 `count()` 再取页，`total` 与 `items` 来自同一个 `query`；如果先 `count()` 再重新构造查询并加过滤，两者就可能不一致。用户列表暂时没有过滤条件，所以 `count()` 之前没有 `filter`；以后加按角色筛选，必须先过滤再计数。`order_by(User.id)` 给翻页一个稳定顺序，否则同一页可能重复或漏项。

### 3.3 列表 service（片段：追加到 `app/modules/user/service.py`）

```python
def list_users(db, params) -> dict:
    """用户列表：复用第 7 章定型的分页骨架，返回本页数据与总数。"""
    offset = (params.page - 1) * params.page_size
    items, total = crud.list_page(db, offset, params.page_size)
    return {"items": items, "total": total}
```

service 只做页号换算与结构组装；`UserPage` 的 `items` 复用 `UserOut`，只输出四个公开字段，`password_hash` 出不去。阶段 4 会在同一文件继续追加 `update_user`，最终全文见 4.2。

### 3.4 列表路由（片段：追加到 `app/modules/user/controller.py`）

先补导入：

```python
from app.core.database import get_db
from app.core.security import get_current_admin_user, get_current_user
from app.modules.user import service

from app.modules.user.schema import UserPage
```

再追加路由：

```python

def list_users(
    params: UserQueryParams = Depends(),
    db: Session = Depends(get_db),
):
    return service.list_users(db, params)
```

两个细节：

- `@router.get("")` 的空字符串让完整路径是 `/users`，不是 `/users/`。
- 列表函数不需要当前用户对象，所以权限依赖写在装饰器的 `dependencies=[...]` 里；`response_model=UserPage` 让返回前按 `UserOut` 过滤字段；`Depends()` 不带参数时把 `UserQueryParams` 当作查询参数模型。

## 阶段 4：修改角色与启用/禁用（20 分钟）

### 4.1 修改模型（完成态文件：`app/modules/user/schema.py`）

```python
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field


class UserCreate(BaseModel):
    username: str = Field(..., min_length=1, max_length=100)
    password: str = Field(..., min_length=6, max_length=128)


class UserOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    username: str
    role: str
    is_active: int


class UserPage(BaseModel):
    items: list[UserOut]
    total: int


class UserLogin(BaseModel):
    username: str = Field(..., min_length=1, max_length=100)
    password: str = Field(..., min_length=1, max_length=128)


class TokenOut(BaseModel):
    access_token: str
    token_type: str = "bearer"
    user: UserOut


class UserUpdate(BaseModel):
    """修改用户时只允许改角色与启用状态；Literal 把允许值写进类型。"""

    role: Literal["admin", "normal"] | None = None
    is_active: Literal[0, 1] | None = None
```

`| None` 表示「可以不传，不传时为 `None`」；`Literal[...]` 把允许值写死。两者配合的结果是：

- 只传 `role` 时，`is_active` 保持原值；只传 `is_active` 时，`role` 保持原值。
- 传 `role="superuser"` 或 `is_active=2` 时，Pydantic 在进入 service 之前拒绝，FastAPI 返回 422，错误 `type` 为 `literal_error`。
- 传 `{}` 是合法的，`model_dump(exclude_unset=True)` 得到空字典，`crud.update` 不修改任何字段，仍返回 200。若课堂需要「至少改一个字段」，那属于课后扩展，不加入本节。

### 4.2 修改 service 与禁用登录（完成态文件：`app/modules/user/service.py`）

```python
from fastapi import HTTPException

from app.core.security import create_access_token, get_password_hash, verify_password
from app.modules.user import crud
from app.modules.user.model import User


def create_user(db, data) -> User:
    if crud.get_by_username(db, data.username):
        raise HTTPException(status_code=400, detail="用户名已存在")
    return crud.create(db, data.username, get_password_hash(data.password))


def login(db, data) -> dict:
    user = crud.get_by_username(db, data.username)
    if not user or not verify_password(data.password, user.password_hash):
        raise HTTPException(status_code=401, detail="用户名或密码错误")
    if not user.is_active:
        raise HTTPException(status_code=401, detail="账号已禁用")
    token = create_access_token(user.id)
    return {"access_token": token, "token_type": "bearer", "user": user}


def list_users(db, params) -> dict:
    """用户列表：复用第 7 章定型的分页骨架，返回本页数据与总数。"""
    offset = (params.page - 1) * params.page_size
    items, total = crud.list_page(db, offset, params.page_size)
    return {"items": items, "total": total}


def update_user(db, user_id: int, data, current_user: dict) -> User:
    """修改角色与启用状态：先查存在性（404），再查业务规则（400），最后写入。"""
    user = crud.get_by_id(db, user_id)
    if not user:
        raise HTTPException(status_code=404, detail="用户不存在")
    if current_user["id"] == user_id and data.is_active == 0:
        raise HTTPException(status_code=400, detail="不能禁用自己")
    return crud.update(db, user, data.model_dump(exclude_unset=True))


def create_admin(db, username: str = "admin", password: str = "admin123") -> User:
    """幂等创建管理员账号，供启动 seed 与后续章节使用。"""
    user = crud.get_by_username(db, username)
    if user:
        return user
    user = crud.create(db, username, get_password_hash(password))
    return crud.update(db, user, {"role": "admin"})
```

三个要点：

- **判断顺序**是「存在性 404 → 业务规则 400 → 更新」。反过来先判断「不能禁用自己」，用户不存在时也可能命中错误分支，错误信息会误导调用方。
- `data.is_active == 0` 只有在客户端显式传 0 时才成立；`None` 不等于 0，所以只改 `role` 不会被误判为禁用自己。
- `model_dump(exclude_unset=True)` 只把客户端实际传过的字段交给 `crud.update`，没传的字段保持原值。若直接 `model_dump()`，未传字段会以 `None` 写入，`role` 和 `is_active` 会被清空。

`login` 中新增的 `is_active` 检查必须在签发令牌之前：被禁用账号即使密码正确，也不应拿到新令牌。响应取 401「账号已禁用」，与「用户名或密码错误」分开，便于前端提示。教材实训验收明确要求 401。

### 4.3 修改路由（完成态文件：`app/modules/user/controller.py`）

```python
from fastapi import APIRouter, Depends
from sqlalchemy.orm import Session

from app.core.database import get_db
from app.core.security import get_current_admin_user, get_current_user
from app.modules.user import service
from app.modules.user.param import UserQueryParams
from app.modules.user.schema import (
    TokenOut,
    UserCreate,
    UserLogin,
    UserOut,
    UserPage,
    UserUpdate,
)

router = APIRouter(prefix="/users", tags=["用户"])


@router.post("", response_model=UserOut, status_code=201)
def register(data: UserCreate, db: Session = Depends(get_db)):
    return service.create_user(db, data)


@router.post("/login", response_model=TokenOut)
def login_endpoint(data: UserLogin, db: Session = Depends(get_db)):
    return service.login(db, data)


@router.get("/me")
def me(current_user: dict = Depends(get_current_user)):
    return current_user


@router.get("", response_model=UserPage, dependencies=[Depends(get_current_admin_user)])
def list_users(
    params: UserQueryParams = Depends(),
    db: Session = Depends(get_db),
):
    return service.list_users(db, params)


@router.put("/{user_id}", response_model=UserOut)
def update_user(
    user_id: int,
    data: UserUpdate,
    current_user: dict = Depends(get_current_admin_user),
    db: Session = Depends(get_db),
):
    return service.update_user(db, user_id, data, current_user)
```

修改接口把权限依赖写在**参数**里，而不是装饰器里，因为 service 需要 `current_user["id"]` 来判断「不能禁用自己」。两种写法都执行同一个依赖，区别只在函数要不要用它的返回值。

路由顺序上，`/users/me` 在 `/users/{user_id}` 之前声明。`/me` 是 GET、`/{user_id}` 是 PUT，本不会冲突；保留这个顺序是为了以后给 `/{user_id}` 增加 GET 时不误吞 `/me`。

### 4.4 请求模型、业务规则与状态码的归属

| 请求 | 状态码 | 由谁产生 |
| --- | --- | --- |
| 管理员把普通用户 `role` 改为 `admin` | 200 | service → `crud.update` |
| 管理员把普通用户 `is_active` 改为 0 | 200 | service → `crud.update` |
| 管理员把自己的 `is_active` 改为 0 | 400 | service 的业务规则 |
| `user_id` 不存在 | 404 | service 的存在性检查 |
| `role="superuser"` | 422 | Pydantic，进入 service 前 |
| `is_active=2` | 422 | Pydantic，进入 service 前 |
| 匿名请求 | 401 | `get_current_user` |
| 普通用户请求 | 403 | `get_current_admin_user` |
| 被禁用账号登录 | 401 | service 的 `login` |

排查时先看请求有没有通过校验：422 说明还没进函数，401/403 说明停在依赖层，400/404 才轮到业务逻辑。

### 4.5 检查点

```powershell

try { Invoke-RestMethod -Method Put -Uri "$base/users/99999" -ContentType "application/json" -Body '{"role":"normal"}' -Headers @{ Authorization = "Bearer $admin" } } catch { $_.ErrorDetails.Message }
try { Invoke-RestMethod -Method Put -Uri "$base/users/2" -ContentType "application/json" -Body '{"role":"superuser"}' -Headers @{ Authorization = "Bearer $admin" } } catch { $_.ErrorDetails.Message }
```

预期依次为：改角色 200；禁用 200；alice 登录 401「账号已禁用」；管理员禁用自己 400「不能禁用自己」；不存在 404「用户不存在」；非法角色 422（`literal_error`）。最后记得把 alice 的 `is_active` 改回 1，或在下一阶段用新库重来。

## 阶段 5：把权限挂回已有数据接口（10 分钟）

这一步**不需要改 service、crud、schema，也不需要改任何业务逻辑**。每个写接口只在装饰器上多一个参数：

```python
dependencies=[Depends(get_current_admin_user)]
```

再加一行导入。这正是本章想让学生看到的：权限是接口入口的横切关注点，把它做成依赖之后，回收已有接口的成本是「一行导入 + 每个写接口一个参数」，而不是复制八段 `if`。

### 5.1 department（完成态文件：`app/modules/department/controller.py`）

```python
from fastapi import APIRouter, Depends, status
from sqlalchemy.orm import Session

from app.core.database import get_db
from app.core.security import get_current_admin_user
from app.modules.department import service
from app.modules.department.param import DepartmentQueryParams
from app.modules.department.schema import DepartmentCreate, DepartmentOut

router = APIRouter(prefix="/departments", tags=["单位"])


@router.get("")
def list_departments(
    params: DepartmentQueryParams = Depends(),
    db: Session = Depends(get_db),
):
    return service.list_departments(db, params)


@router.post(
    "",
    response_model=DepartmentOut,
    status_code=status.HTTP_201_CREATED,
    dependencies=[Depends(get_current_admin_user)],
)
def create_department(data: DepartmentCreate, db: Session = Depends(get_db)):
    return service.create_department(db, data)


@router.get("/{dept_code}", response_model=DepartmentOut)
def read_department(dept_code: str, db: Session = Depends(get_db)):
    return service.get_department(db, dept_code)


@router.put(
    "/{dept_code}",
    response_model=DepartmentOut,
    dependencies=[Depends(get_current_admin_user)],
)
def update_department(
    dept_code: str, data: DepartmentCreate, db: Session = Depends(get_db)
):
    return service.update_department(db, dept_code, data)


@router.delete(
    "/{dept_code}",
    status_code=status.HTTP_204_NO_CONTENT,
    dependencies=[Depends(get_current_admin_user)],
)
def delete_department(dept_code: str, db: Session = Depends(get_db)):
    service.delete_department(db, dept_code)
```

读接口（列表、详情）不挂依赖，普通用户与匿名访问仍是 200/404；写接口（POST/PUT/DELETE）挂管理员依赖。教材 9-4-5 点名新增与删除，本项目把 PUT 一并收回，理由见 `README.md` 第三节的取舍说明。

## 阶段 7：课后扩展（不计入 90 分钟）

### 7.1 修改角色的全部校验

教材只要求 `Literal` 取值校验与「不能禁用自己」。生产系统还需要：

- 禁止取消最后一个管理员：改角色前统计 `role="admin"` 且 `is_active=1` 的数量，若目标是最后一个则 400。
- 禁止修改自己的角色：与「不能禁用自己」同属防误操作规则，可在 service 统一判断。
- 角色变更审计：记录操作者、目标用户、旧值、新值与时间；审计表不参与登录链路。
- 把上述规则抽成 `validate_user_update(db, target, data, current_user)`，controller 不写业务判断。

### 7.2 禁用流程

本实训只做到「禁用后不能登录」。完整流程还应包括：

- 禁用时按 `user_id` 反向扫描 `TOKEN_STORE`，删除该用户的全部令牌，让已登录会话立即 401。
- 前端区分 401 的两种文案：「用户名或密码错误」与「账号已禁用」。
- 启用/禁用写审计；管理页展示最近操作。
- 若使用签名令牌，需要额外的撤销列表或短过期时间，说明取舍。

反向清理令牌的写法示意（不属于本实训完成态）：

```python
def revoke_user_tokens(user_id: int) -> None:
    for token, stored_user_id in list(TOKEN_STORE.items()):
        if stored_user_id == user_id:
            TOKEN_STORE.pop(token)
```

`list(...)` 是为了在遍历时安全删除；不要在 `for token, uid in TOKEN_STORE.items()` 中直接 `pop`。

### 7.3 列表增强

- 按角色筛选：`UserQueryParams` 增加 `role: Literal["admin", "normal"] | None = None`，`crud.list_page` 在 `count()` 之前 `filter`。
- 按用户名模糊搜索：同样先过滤再计数，并给 `total` 与 `items` 用同一个 query。
- 排序：本章固定 `id` 升序；若要按用户名排序，先明确分页稳定性与索引。

### 7.4 用户删除与改密

- 删除前检查是否存在业务引用（10-1 的执勤记录会引用人员，不一定引用用户）。
- 改密后清理该用户旧令牌；新密码仍走 `get_password_hash`。
- 删除用户后，其令牌在 `get_current_user` 中会因查不到用户而 401；这已经由 8-1 处理。

## 附：本实训容易踩的五个坑

1. 把管理员依赖写成 `Depends(get_current_user)`，普通用户仍能进管理接口。
2. 把 `dependencies` 写进函数体而不是路由装饰器，写接口仍对所有人开放。
3. 修改接口没把 `current_user` 传进 service，「不能禁用自己」永远不生效。
4. `login` 忘记检查 `is_active`，禁用只是数据库里的一个数字。
5. 为了让旧接口「兼容」而不加依赖，权限回收只做了一半；8-1 的注册/登录/`me` 契约并没有因此被保护。
