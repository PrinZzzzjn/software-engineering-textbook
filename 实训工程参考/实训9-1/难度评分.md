# 实训 9-1 难度评分

## 一、结论

| 项目 | 评定 |
| --- | --- |
| 规模 | **D3**（中等偏大：跨 3 个模块、8 个文件（7 个有代码变更）、净增约 111 行） |
| 认知 | **L4**（分析/评价：认证与授权分工、401/403 语义、校验层级与业务规则顺序） |
| 建议课时 | 2 学时 = **90 分钟** |
| 综合结论 | **偏紧** |
| 必做边界 | 管理员依赖 + 用户列表分页 + 用户修改/禁用 + 权限回收 + 两章回归 |
| 课后扩展 | 修改角色的全部校验、完整禁用流程、列表筛选、删除/改密 |

「偏紧」不是内容过多，而是**可见代码少、隐藏决策多**：学生写下的净增量只有约 111 行，但任何一个授权依赖挂错位置、任何一个 422/404/400 的归属判断错，测试都不会在启动时报错，只会在手工验证时暴露。90 分钟内要完成「写 + 验 + 回归」，余量主要留给排错。

## 三、认知负荷

### 3.1 新概念数：2 个主概念 + 4 个从属判断

| 概念 | 认知要求 | 学生常见误区 |
| --- | --- | --- |
| **管理员依赖**（`get_current_admin_user`） | 理解认证与授权的分层；理解依赖可以返回对象，也可以只做守卫 | 直接写 `HTTPBearer()` 导致匿名 403；把角色写死在令牌里；在函数体里复制 `if` |
| **权限回收** | 理解横切关注点；只加一个依赖参数就改变既有接口的权限 | 只改 department 不改 personnel；只改 POST 不改 PUT/DELETE；忘记导入；把依赖挂错位置 |

从属判断（不是新概念，但决定正确性）：

1. 401 与 403 的分工：未认证 vs 已认证但无权限。
2. 422 与 400/404 的分工：Pydantic 在函数前拦截 vs 业务层判断。
3. 修改顺序：存在性 404 → 业务规则 400 → 写入。
4. 角色即时生效：每次请求按 `user_id` 查库，而不是把角色缓存在令牌或闭包里。

### 3.2 为什么是 L4

L4 要求分析、比较、评价，而不是照着模板抄：

- **分析**：列表为什么要手工组装四个字段？直接返回 ORM 对象会泄露什么？
- **比较**：权限依赖写在装饰器 `dependencies=[...]` 与写在函数参数里，何时必须选后者？
- **评价**：教材只要求收回 department 的新增/删除，是否把 PUT 与 personnel 一并收回？本项目给出「是」的理由，并要求学生能复述取舍。
- **迁移**：把第 7 章的分页骨架迁移到 users 表，参数、排序、`total` 与 `items` 同源都要保持。
- **诊断**：普通用户仍 200、匿名得到 403、禁用仍能登录，分别说明哪一层漏了。

这些判断无法靠「运行不报错」自动确认，必须对照权限矩阵手工验证，因此认知负荷高于 D2 的「按步骤加接口」。

## 四、90 分钟时间预算

| 阶段 | 内容 | 预算 | 超时风险 |
| --- | --- | ---: | --- |
| 0 | 读任务、确认边界与矩阵 | 5 | 低 |
| 1 | 复制起点、建环境、跑通 8-1 | 10 | 中：环境与端口 |
| 2 | 管理员依赖与 401/403 | 15 | 中：依赖链理解 |
| 3 | 用户列表：参数、分页、字段过滤 | 20 | 中：`total` 与 `items` 同源 |
| 4 | 修改：`Literal`、404/400/422、禁用登录 | 20 | 高：判断顺序与 `exclude_unset` |
| 5 | 权限回收：6 个写接口 | 10 | 低：机械但易漏 |
| 6 | 回归、验收、提交 | 10 | 中：手工矩阵耗时 |
| 合计 | | **90** | |

最可能超时的两个点：

1. **阶段 4 的 `model_dump(exclude_unset=True)`**：写成 `model_dump()` 会把未传字段写成 `None`，表现为「只改角色却把启用状态清空」，而且不一定立刻报错。
2. **阶段 5 的遗漏**：department 与 personnel 各三个写接口，共 6 处依赖；学生容易只改教材点名的两个，或在某个装饰器上漏写。

## 五、取舍

### 5.1 保留在 90 分钟内的内容

- 管理员依赖与 401/403 分工：本章的核心，不能删。
- 用户列表分页与字段过滤：复用第 7 章骨架，是「旧知识迁移」的关键证据。
- 用户修改的基础校验：`Literal`、404、400、422；禁用后登录 401。
- department 与 personnel 写接口回收：权限矩阵的完整体验。
- 8-1 与 7-1 回归：防止「加权限把旧功能弄坏」。

### 5.2 移到课后的内容

| 内容 | 移出理由 |
| --- | --- |
| 修改角色的全部校验（最后一个管理员、改自己角色、审计） | 需要额外查询与规则设计，单靠 `Literal` 无法覆盖；放课后可讲「业务规则不是输入校验」 |
| 完整禁用流程（清理旧令牌、前端文案、审计） | 涉及 `TOKEN_STORE` 反向清理与会话失效，超出本章主线；教材只要求「不能登录」 |
| 列表按角色筛选 | 会引入「过滤必须在 `count()` 之前」的新坑，适合作为 7.3 的复习题 |
| 用户删除、改密、登出、令牌过期 | 与账号管理相关，但不是本章验收项；10-1 前后再补更自然 |

### 5.3 如果只有 60 分钟

保底路径：管理员依赖 + `GET /users` 分页 + department 写接口回收 + 8-1 回归；把 `PUT /users/{id}` 的禁用分支与 personnel 回收改成教师演示。这样仍能覆盖「认证/授权分工」与「权限回收」两个核心概念，但权限矩阵不完整，验收要相应缩减。

### 5.4 如果有 120 分钟

可加入：按角色筛选（先过滤再计数）、禁用时清理旧令牌、修改角色的两条防误操作规则。仍不建议加入用户删除与改密，避免把 9-1 变成账号系统大杂烩，挤压 10-1 的执勤记录。

## 六、评分说明

- **D3 而非 D2**：跨模块、8 个文件（7 个有代码变更）、三位数净增行，且包含既有接口的行为变更；不是单文件加一个函数。
- **D3 而非 D4**：没有新表、新依赖、新分层，也没有把整个项目重写；改动集中在 controller 与 service。
- **L4 而非 L3**：核心不是「照着写」，而是判断权限挂哪、错误码归谁、旧接口行为变了以后如何回归；学生必须能解释取舍。
- **偏紧而非适中**：90 分钟内代码量可控，但验证与排错占至少 20 分钟；一旦环境或依赖链出问题，容易挤掉回归时间。
