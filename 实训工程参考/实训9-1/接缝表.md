| 项目 | 内容 |
| --- | --- |
| 位置 | `app/core/security.py` |
| 名称 | `get_current_admin_user` |

## 四、不兼容点

### 4.1 已有接口出现 401/403

| 端点 | 8-1 行为 | 9-1 行为 | 兼容性 |
| --- | --- | --- | --- |
| `POST /departments` | 匿名 201 | 匿名 401、普通 403、管理员 201 | **不兼容**：匿名写入被拒 |
| `PUT /departments/{code}` | 匿名 200 | 匿名 401、普通 403、管理员 200 | **不兼容** |
| `DELETE /departments/{code}` | 匿名 204 | 匿名 401、普通 403、管理员 204 | **不兼容** |
| `POST /personnel` | 匿名 201 | 匿名 401、普通 403、管理员 201 | **不兼容** |
| `PUT /personnel/{number}` | 匿名 200 | 匿名 401、普通 403、管理员 200 | **不兼容** |
| `DELETE /personnel/{number}` | 匿名 204 | 匿名 401、普通 403、管理员 204 | **不兼容** |
| 两个模块的读接口 | 公开 | 公开 | 兼容 |
| 注册 / 登录 / `me` | 201 / 200 / 401·200 | 同左 | 兼容 |
| 登录被禁用账号 | 8-1 无禁用概念 | 401「账号已禁用」 | 新增分支 |

调用方需要做的迁移：

1. 所有写请求带 `Authorization: Bearer <token>`。
2. 使用管理员账号的令牌；普通用户令牌会得到 403。
3. 捕获 401（重新登录）与 403（提示无权限），不要把两者都当成「未登录」。
4. 读请求可以继续匿名，不强制改造。

### 4.2 前端从第 15 章起必须带令牌

| 场景 | 要求 |
| --- | --- |
| 管理页加载用户列表 | 登录后取 admin 令牌，`GET /users` 带 Bearer |
| 管理页修改角色/状态 | `PUT /users/{id}` 带 Bearer 与管理员的 JSON |
| 单位/人员的新增、编辑、删除 | 写请求必须带 Bearer；表单页隐藏或禁用只解决界面，不解决权限 |
| 单位/人员的列表与详情 | 可匿名；建议仍统一带令牌，减少两套请求封装 |
| 401 处理 | 清空本地令牌并跳登录；提示「登录已失效」 |
| 403 处理 | 保留登录态；提示「无权限执行该操作」，不跳登录 |
| 被禁用账号登录 | 401「账号已禁用」，前端不要显示成「密码错误」 |

### 4.3 令牌与账号的已知边界

| 边界 | 现状 | 影响 |
| --- | --- | --- |
| 禁用前已签发的令牌 | 下一次请求即 401 | `get_current_user` 检查 `is_active`，不需要反向清理 `TOKEN_STORE` |
| 改角色 | 旧令牌立即按新角色生效 | 升权/降权都即时；前端需刷新菜单 |
| 服务重启 | `TOKEN_STORE` 清空，users 表保留 | 所有旧令牌 401，需要重新登录 |
| 删除用户 | 本实训不提供 | `get_current_user` 对已删除用户已能返回 401 |

### 4.4 响应字段边界

| 端点 | 允许出现 | 禁止出现 |
| --- | --- | --- |
| `GET /users` | `id`、`username`、`role`、`is_active`、`total` | `password_hash`、盐、摘要 |
| `PUT /users/{id}` | 同上四项 | `password_hash` |
| 注册 / 登录 | 8-1 原字段 | `password_hash` |
| department / personnel | 8-1 原字段 | 无新增字段 |
