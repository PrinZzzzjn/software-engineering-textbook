# 第 20 章 前端开发综合实践

前面的各章分别让登录、数据与统计能够单独工作。但页面单独能用，不等于用户走完一条路径时系统仍然成立：登录态、数据刷新与错误提示，往往在页面之间断开。

## 本章要解决的问题

**给你一份接口文档和一个新页面需求，能否独立完成读取、编辑、联调与验收？**

每个页面单独验收都能通过，合起来却对不上：页面之间的登录态、数据刷新与错误提示各写一套，用户走一遍就露出断点。到了交付时，也说不清“做了什么、能跑什么、还有什么问题”。

本章关心的是：各自能用的页面合在一起，为什么会在登录态、数据刷新与错误提示上断开；以及交付时，怎样证明这套系统真的能按用户路径走完。

## 本章学习目标

读完第 20 章并完成实训后，你应该能：

1. 按用户真实路径完成前端联调，记录每一步的期望与实际。
2. 按“现象 → 状态码 → detail → 日志 → 定位”的顺序排查问题。
3. 识别非状态码问题（空白页、状态错乱、重复提交）并给出排查方向。
4. 统一错误处理，让用户看到可读提示而不是堆栈。
5. 整理交付清单，并用三分钟说清做了什么、能跑什么、还有什么问题。

## 20.1 页面的接口映射

综合实践的第一步不是写代码，而是读接口文档。按 OpenAPI 规范，一份接口文档至少要给出：URL、方法、查询参数、请求体字段、返回结构、错误状态码。页面结构就是由这些信息推出来的：

**四条映射规则**

- 返回 `items` 与 `total` → 需要列表与分页；
- 有写接口 → 需要新增/编辑表单与删除确认；
- 有 401/403/404/422 → 需要对应的错误提示；
- 有筛选参数 → 需要筛选区，并把条件放进请求。

读文档时把“页面要有的东西”列成一张表，再动手；比先写界面、再回头找接口要快。

页面结构定下来后，最快的做法是照一个结构相近的旧页面改。人员管理页可以照单位页改，主要改三处：接口路径 `/departments` → `/personnel`；展示字段改成人员字段；过滤条件改用人员的 `name`。人员的字段是 `certificate_number`、`name`、`dept_code`、`rank`，与单位字段几乎不重合，照抄字段名会直接报错或出现空列。

照抄时先分清哪些能复用、哪些不能：

| 可复用 | 不可照抄 |
| --- | --- |
| 页面区域（标题、筛选、内容、操作） | 接口路径 |
| 表格、表单、错误处理的写法 | 字段名 |
| 分页与筛选的交互方式 | 查询参数与字段名（按 `/docs` 核对） |
| 守卫与三态的处理位置 | 状态码的具体含义（按 `/docs` 核对） |

扩展步骤：复制页面文件；改标题与图标；改接口路径与字段；改表单字段；运行并按联调清单走一遍。每改一处运行一次，不要一次改十处。

复制之后，还要判断什么时候该抽象。页面只有两三个、差异又大时，复制并逐处修改更快；页面多、结构稳定时，再把公共部分抽成组件或函数。判断标准与第 15 章一致：同样的代码出现第二次，再抽；不要为了“看起来专业”提前造一套页面框架。

> 💡 **易错点**：照抄旧页面只改标题，不改接口路径与字段。页面能打开，但表格空列、排序失效、提交 422；这些是“静默失败”，不会报错，只能靠对照 `/docs` 发现。

## 20.2 用户路径与联调清单

联调不是“把页面点一遍”，而是按用户真实路径验证：未登录访问 → 登录 → 列表 → 搜索 → 新增 → 编辑 → 删除 → 统计 → 切换条件 → 退出。这种按真实用户路径串起多个页面的验证通常称为联调（集成调试）。每一步都要有明确期望，否则失败了也看不出来。

| 步骤 | 操作 | 期望 |
| --- | --- | --- |
| 1 | 未登录直接访问单位页 | 被守卫拦住，提示登录 |
| 2 | 用管理员账号登录 | 进入首页，侧边栏显示当前用户 |
| 3 | 打开单位管理 | 列表显示，分页正常 |
| 4 | 搜索“保障” | 只显示匹配的单位 |
| 5 | 新增一个单位 | 列表出现新记录 |
| 6 | 编辑该单位名称 | 列表显示新名称 |
| 7 | 删除该单位 | 二次确认后列表少一条 |
| 8 | 打开数据统计 | 指标卡与图表有数据 |
| 9 | 切换人员或年份 | 指标与图表跟着变 |
| 10 | 退出登录 | 回到登录页，子页面再次被拦截 |

**先主流程，后边角**

先保证主流程，再管边角。失败先记录，不要立刻改代码；全部走完后按影响排序，先修影响主流程的。

> 💡 **易错点**：只测“正常路径”，不测失败与边界。接口通的页面不代表权限、空数据、重复提交都没问题；联调清单里至少要有一条未登录、一条无权限、一条空结果。

## 20.3 统一错误处理

每个页面各写一套 `try/except` 会重复，提示也不一致。把“错误 → 提示”的映射收拢到一个函数：

**代码 20-1-1** · 示例代码（Python）

```python
def show_api_error(exc) -> None:
    if exc.status_code == 401:
        st.session_state.clear()
        st.warning("登录已过期，请重新登录")
        st.rerun()
    elif exc.status_code == 403:
        st.error("当前账号没有权限执行该操作")
    elif exc.status_code == 404:
        st.error("数据不存在，可能已被删除")
    elif exc.status_code == 422:
        st.error(f"提交内容有误：{exc.detail}")
    elif exc.status_code == 500:
        st.error("服务器开小差了，请稍后重试或联系管理员")
    elif exc.status_code == 0:
        st.error(f"无法连接后端服务：{exc.detail}")
    else:
        st.error(exc.detail)
```

页面里统一调用：

**代码 20-1-2** · 示例代码（Python）

```python
try:
    data = api.get("/departments", params=params)
except api.ApiError as exc:
    show_api_error(exc)
    st.stop()
```

各状态码的处理策略：401 清登录态并回登录；403 提示没权限、不重试；404 提示数据不存在、刷新列表；422 显示具体字段问题；500 提示稍后重试并记录时间与操作；空数据不是错误，用 `st.info` 提示。

错误提示要“说人话”，不要把堆栈直接给用户；401 必须在统一入口处理；提示里不要泄露令牌、密码与服务器路径。

错误提示统一之后，排查按一条固定顺序进行：

```mermaid
flowchart LR
    A[现象] --> B[状态码]
    B --> C[detail / 返回体]
    C --> D[后端日志]
    D --> E[定位页面/接口/字段]
    E --> F[修复并重跑清单]
```

*图 20-1：前端联调的排查顺序*

状态码是第一线索：

| 状态码 | 含义 | 先查什么 | 页面提示 |
| --- | --- | --- | --- |
| 401 | 没登录/登录过期 | 令牌是否存在、请求头 | 清登录态，回登录 |
| 403 | 登录了但没权限 | 当前角色、接口权限 | “当前账号没有权限” |
| 404 | 资源不存在 | 路径、编码是否已删除 | “数据不存在，可能已被删除” |
| 422 | 参数校验失败 | 字段名、类型、必填 | 显示具体字段问题 |
| 500 | 后端异常 | 后端日志/堆栈 | “服务器开小差了，请稍后重试” |

401 与 403 要分清：一个是“没证件”，一个是“证件不够级别”。500 先看后端日志，不要在前端反复改。

有些问题没有状态码可查，常见如下：

| 现象 | 先查什么 |
| --- | --- |
| 页面不渲染 | 是否有未捕获异常；`st.stop()` 位置 |
| 数据不更新 | 是否 `st.rerun()`；取数是否在操作之前 |
| 样式异常 | `config.toml` 是否重启；是否重复注入 CSS |
| 图表空白 | 数据结构/字段名是否与接口一致 |
| 页面卡顿 | 是否在循环里发请求；是否一次取太多 |

> 💡 **易错点**：把 500 当成前端问题反复改页面。500 的根因在后端，前端只能提示“稍后重试”并保留日志；先看后端日志，再决定改哪一层。

## 20.4 交付清单与验收

一份可交接的前端成果至少包括：

| 类别 | 内容 |
| --- | --- |
| 代码 | 前端项目，可运行 |
| 截图 | 登录、列表、新增/编辑/删除、统计 |
| 联调记录 | 10 步清单的通过情况 |
| 错误处理 | 401/403/404/422/500 各一条记录 |
| 已知问题 | 还没解决的问题 + 原因 |
| 说明 | 如何启动、依赖、测试账号 |

已知问题也要写。交付不是“没有问题”，而是“问题说清楚”：什么情况下会出问题、目前怎么规避。藏起来的问题会在验收时集中爆发。

**成果展示的四段**

交付之外，还要做一次成果展示。四段结构：一句话说明做了什么；演示主流程；说一个排查过的故障（现象 → 原因 → 改法）；说一个已知问题或下一步。展示的重点不是“功能多”，而是“能说清边界”。

**验收清单的粒度**

验收清单的粒度要合适。清单太粗（“页面能用”）无法判断通过与否；太细（每个按钮一行）会拖慢验收。一个够用的粒度是：**每个用户可见的主流程一行，每个错误状态一行，每个已知问题一行**。主流程证明“能用”，错误状态证明“坏了知道为什么”，已知问题证明“边界说清楚了”。

> 💡 **易错点**：把“演示成功”当成“验收通过”。演示只走一条顺利路径；验收要看联调记录、错误处理记录与已知问题，三者齐全才算可交付。

## 示范例题

#### 例 20-1：照单位页扩展人员页

**题目**：把单位管理页复制成人员管理页，要求改标题、接口路径与展示字段；说明哪些地方不能照抄。

**解**：

**代码 20-2-1** · 示例代码（Python）

```python
import streamlit as st

st.set_page_config(page_title="人员管理", page_icon="👥", layout="wide")
st.title("👥 人员管理")

with st.container(border=True):
    keyword = st.text_input("姓名", placeholder="输入关键字")

# 取数：路径改为 /personnel；参数以 /docs 为准
data = api.get("/personnel", params={"name": keyword, "page": 1, "page_size": 10})
items = data.get("items", [])

st.dataframe(
    [{"certificate_number": p["certificate_number"], "name": p["name"], "rank": p.get("rank")} for p in items],
    width="stretch",
    hide_index=True,
)
```

不能照抄的地方：接口路径（`/departments` vs `/personnel`）；字段名（`dept_code`/`full_name` vs `certificate_number`/`name`）；过滤条件（单位按名称，人员按姓名）。以 `/docs` 为准。

#### 例 20-2：读接口文档找差异

**题目**：单位列表与人员列表的返回字段不同：单位是 `dept_code`、`full_name`、`address`，人员是 `certificate_number`、`name`、`dept_code`、`rank`。请说明照抄单位页会出什么问题，以及如何避免。

**解**：

1. 照抄 `dept_code` 当人员编号：人员的主键是 `certificate_number`，字段不存在，表格出现空列或 `KeyError`。
2. 照抄 `address`，人员没有该字段，整列为空，容易被误读为数据缺失。
3. 避免方法：扩页面前先打开 `/docs`，逐项核对路径、查询参数、返回字段；把差异列成对照表；改完用一条真实请求验证字段与排序。

## ◆ 实训 20-1：前端开发综合实践

> **2026-11-23 课时调整**：本实训由 4 学时减为 2 学时（90 分钟）。课堂只做 6 步主路径、一个代表性故障、一个页面接入统一错误、一页交付清单；10 步全路径、五页全量替换与三分钟展示转为课后。

### 一、任务目标与验收

| 目标 | 验收标志 |
| --- | --- |
| 用户路径跑通 | 登录→查询→新增→编辑→删除主流程可用 |
| 排查有记录 | 至少一次按顺序定位的过程 |
| 错误可读 | 用户看到提示而非堆栈 |
| 交付清单齐全 | 页面、接口、测试、说明、已知问题 |
| 展示清楚 | 三分钟讲清边界 |

本轮 2 学时只要求：6 步主路径跑通、一条完整排查记录、一个页面接入统一错误、一页交付清单、19-1 主流程回归；三分钟展示与五页全量替换为课后目标。

### 二、课前准备

- 前后端均可启动
- 一份用户路径清单
- 交付清单模板

### 三、操作步骤（90 分钟最低必做）

1. **起点检查（10 分钟）**
   - 做什么：确认 19-1 页面能打开、后端 `/health` 正常、管理员账号能登录。
   - 操作：启动前后端，打开首页与一个业务页。
   - 预期输出：→ 页面可用，接口能返回数据
   - 做错会看到什么：页面空白先查接口与控制台；后端未启动先起 8000。
2. **6 步用户路径联调（30 分钟）**
   - 做什么：未登录访问 → 登录 → 列表 → 搜索 → 新增 → 退出；每步先写期望，再记录实际。
   - 操作：按清单逐项走，失败只记录不立刻改。
   - 预期输出：→ 主流程通过；失败步骤能指出页面、接口或字段
   - 做错会看到什么：只测单个页面；按真实路径串联。
3. **一个代表性故障排查（20 分钟）**
   - 做什么：挑一个失败步骤，按“现象 → 状态码 → detail/返回体 → 后端日志 → 定位页面/接口/字段”顺序记录。
   - 操作：先看响应码与 `detail`，再看后端日志，最后才改前端。
   - 预期输出：→ 能指出前后端哪一层出问题，并给出修复动作
   - 做错会看到什么：一上来改代码；先确认失败层。
4. **一个页面接入统一错误（15 分钟）**
   - 做什么：新建 `components/errors.py`，按 401/403/404/422/500/0 写映射（至少覆盖 4 类）；选一个页面把 `try/except` 改为 `show_api_error(exc)`。
   - 操作：先写映射，再改一个页面的异常处理；取数失败后 `st.stop()`。
   - 预期输出：→ 该页面错误提示可读，不裸露堆栈
   - 做错会看到什么：只弹“出错了”；补具体原因与下一步。
5. **交付清单（10 分钟）**
   - 做什么：补一页清单（代码、截图、联调记录、错误记录、已知问题、启动说明）。
   - 操作：照教师给的一页模板填。
   - 预期输出：→ 清单能让别人按说明启动与复现
   - 做错会看到什么：清单只有文件列表；补“怎么启动、怎么验证”。
6. **提交（5 分钟）**
   - 做什么：确认页面可启动，回归 19-1 主流程未被改坏。
   - 操作：重走一遍 6 步主路径。
   - 预期输出：→ 主流程仍通过
   - 做错会看到什么：改提示时动坏了业务逻辑；回归比较改动前后的行为。

> 10 步全路径、五页全量替换、三分钟展示与已知问题分级为课后扩展；课堂不要求全部完成。

### 四、排错清单

| 现象 | 先查什么 |
| --- | --- |
| 页面空白 | 接口是否返回、控制台是否有异常 |
| 状态错乱 | session_state 键冲突或未清理 |
| 重复提交 | 按钮未禁用 |
| 跨域失败 | 后端 CORS 与前端基地址 |

## 本章小结

**核心结论**：

1. **联调**按用户路径验证，不按页面逐个点；每步有明确期望，失败先记录后排序修复。
2. 排查按“现象 → 状态码 → detail → 日志 → 定位”的顺序；401/403/404/422/500 分别对应身份、权限、资源、参数、服务器。
3. 统一错误处理收拢到一个函数：401 清登录态，403 提示权限，404 提示不存在，422 显示字段问题，500 提示稍后重试；空数据不是错误。
4. 复用页面照抄结构、不照抄字段；接口路径、字段名、排序参数以 `/docs` 为准。
5. **验收清单**包括代码、截图、联调记录、错误记录、已知问题与说明；已知问题要说清，不藏。

把这章压缩成一句话：**综合实践不是再写一个页面，而是用真实用户路径证明这些页面能一起交付。**

**自检**：回到章首的学习目标，逐条问自己做到了没有——

- [ ] 按用户真实路径完成前端联调，记录每一步的期望与实际。

- [ ] 识别非状态码问题（空白页、状态错乱、重复提交）并给出排查方向。
