## 第 1 章 软件工程基本概念

#### 习题 1-1【Bloom：记忆】

**参考答案**：需求（需求规格说明书、用户故事、原型）；设计（架构图、ER 图、接口文档）；编码（源代码、提交记录）；测试（测试用例、测试报告、缺陷记录）；部署（部署文档、镜像、运行日志）；运维（运维记录、版本更新）。

#### 习题 1-2【Bloom：理解】

**参考答案**：

1. 错误。软件 = 程序 + 数据 + 文档；只交源代码不交文档，不构成完整交付软件。
2. 错误。敏捷强调小步设计、持续验证，不是不设计；文档可以按需要精简，但设计活动不能省。
3. 错误。测试的任务是发现缺陷、提供质量证据、降低风险，不能证明程序“没有错误”。
4. 正确。变更成本随阶段后移而上升，越晚发现修复代价越高。

#### 习题 1-3【Bloom：分析】

**参考答案**：

可指出的缺陷（至少三处）：

1. 跳过需求与设计，直接按页面写代码——需求/设计阶段；应先明确角色、功能、统计口径与验收标准，再划分模块与接口。
2. 数据库表边写边改、接口字段在群里口头约定——设计阶段；应先确定表结构与接口契约，并形成可查的文档。
3. 本机跑通后直接拷到服务器——测试/部署阶段；应先有测试用例与可重复的部署流程，再上线。
4. “本月值班次数”口径不一致——需求阶段；应把“本月”定义为可验收的统计口径，并在需求评审中确认。

（答出其中任意三处即可；若只答“没写文档”而未指出阶段与措施，不构成完整诊断。）

#### 习题 1-4【Bloom：评价】（开放题）

**参考要点**：

- 选择“迭代”较为稳妥：8 周短、需求可调整、需要尽早得到可运行版本；每轮交付可运行增量，便于在答辩前收敛。
- 若选敏捷，需要说明团队能维持短周期评审与验收；若选瀑布，需要说明需求已稳定且变更有审批。
- 应坚持的两项实践（示例）：每轮开始前明确验收标准（需求/接口契约）；每轮结束前跑通测试与可重复部署。
- 可裁剪的一项（示例）：完整的正式设计文档，保留最小需求说明与接口文档，用代码注释补充。
- 裁剪的风险：交接与维护信息丢失，答辩时难以说明设计依据；应说明补偿措施。
- 评分看“选择依据—坚持项—裁剪项—风险”是否自洽，不要求唯一答案。

#### 习题 1-5【Bloom：理解】（概念辨析）

**参考答案**：这句话把“过程模型”与“工程纪律”混为一谈。生命周期阶段可以重叠，但需求、设计、测试等活动不能省略；敏捷通过短迭代加快反馈，而不是取消设计与文档。四个根本挑战中的“变化”要求缩短反馈周期，“协作”要求共同约定，“质量”要求持续验证——这些都需要设计与测试活动。敏捷不排斥的两项实践：① 迭代前明确验收标准并按迭代评审；② 持续集成与自动化测试。这句话还漏掉了「人与组织」维度：没有共同约定与评审，短迭代只会把分歧放大。

## 第 2 章 需求分析方法

#### 习题 2-1【Bloom：理解】

**参考答案**：

1. 坏故事。角色写成泛化的“用户”，功能“好用的系统”与价值“用得舒服”都无法验证，无法写验收标准。
2. 好故事。角色（学生）、功能（通过学号借书）、价值（不用带借书证）清楚，可进一步写验收标准。
3. 坏故事。“支持所有功能”没有边界，无法判断做到什么程度算完成；应拆成具体功能，并说明角色与价值。

#### 习题 2-2【Bloom：应用】

**参考答案**：

故事示例：作为图书馆员，我想要在学生还书时自动计算并显示逾期罚款，以便按规则处理归还。

验收标准：

1. 逾期 1 天及以上时，系统按既定规则计算罚款金额并显示，归还完成后生成罚款记录。
2. 未逾期时，罚款显示为 0，且不生成罚款记录。

（若角色选“学生”，则价值改为“知道要缴多少罚款、为什么缴”，验收标准相应改成学生可见的金额与明细；角色与价值需一致。）

#### 习题 2-3【Bloom：应用】

**参考答案**：

改写：在馆藏 1000 条、20 人并发的条件下，输入完整书名后 1 秒内显示匹配结果。

异常场景补充：无匹配结果时，系统显示“未找到相关图书”，并提供按分类浏览的入口，不显示空白页。

#### 习题 2-4【Bloom：分析】

**参考答案**：

可指出的缺失（至少三处）：

1. **单位未写明**：接口规格应明确输入输出的单位，以及“磅力·秒”与“牛顿·秒”的换算关系。
2. **数据格式与字段含义未对齐**：应明确字段名称、类型、量纲，避免两边对同一字段作不同假设。
3. **跨团队验证缺失**：应增加联调测试或独立核验，检查双方对接口的理解是否一致。
4. **假设未显式化**：应把“对方使用什么单位、什么坐标系”写成显式假设，并在评审中确认。

（答出其中任意三处即可。）

#### 习题 2-5【Bloom：理解】（概念辨析）

**参考答案**：用户表达的是“想要的”解决方案，需求要回答“真正的业务问题”；直接照做容易做出没人用的功能。不同利益相关者的诉求可能冲突，必须识别并取舍。需求还必须写成可验收的条件，否则无法判断是否完成。因此要把用户表述转成目标、角色、用户故事与验收标准，再回到业务方确认。

#### 习题 2-6【Bloom：分析】（概念辨析）

**参考答案**：

| 缺口 | 方法 | 理由 |
| --- | --- | --- |
| ① 纠纷处理规则 | 用户访谈 | 业务规则与例外要靠追问“为什么”“特殊情况怎么办”才能问出来 |
| ② 发布时是否漏填 | 现场观察 | 真实操作习惯与隐性流程，看比问准；观察法正是补「隐性流程」的方法 |
| ③ 全校接受程度 | 问卷调查 | 需要大范围意见与比例，问题要具体、避免引导性提问 |
| ④ 求购页面长什么样 | 原型法 | 界面与交互需求靠草图确认，原型是沟通工具不是最终界面 |

文档分析用于补字段、约束与接口（如现有交易规则、平台字段表）。五种方法常组合使用，没有一种能单独拿到完整需求。

## 第 4 章 HTTP 与接口设计

#### 习题 4-1【Bloom：记忆】

**参考答案**：

- 200：成功
- 201：已创建（新增成功）
- 204：成功但无返回体（常用于删除）
- 400：请求格式错误
- 401：未认证（没登录或令牌无效）
- 403：无权限（已登录但无权访问）
- 404：未找到
- 422：参数校验失败
- 500：服务器内部错误

#### 习题 4-2【Bloom：理解】

**参考答案**：

1. 不符合。URL 里出现动词 `get`，查询集合应写成 `GET /api/v1/departments/`。
2. 符合。POST 到资源集合表示新增，成功应返回 201。
3. 符合。GET 到单个资源路径表示查询该部门。
4. 不符合。修改应使用 PUT（或 PATCH）定位到单个资源，写成 `PUT /api/v1/departments/1`；用 POST 加动作路径模拟修改，失去了方法语义。

#### 习题 4-3【Bloom：应用】

**参考答案**：

| 操作 | 方法 | URL | 成功状态码 |
| --- | --- | --- | --- |
| 查询列表 | GET | `/api/v1/equipments/` | 200 |
| 查询单个 | GET | `/api/v1/equipments/1` | 200 |
| 新增 | POST | `/api/v1/equipments/` | 201 |
| 修改 | PUT | `/api/v1/equipments/1` | 200 |
| 删除 | DELETE | `/api/v1/equipments/1` | 204 |

可选补充：列表查询可用查询参数 `page`、`page_size`、`category` 等；新增成功返回 201，并可在响应体中返回新资源或 `Location` 头。

#### 习题 4-4【Bloom：分析】

**参考答案**：

1. **删除用 GET**：`GET /api/v1/departments/delete?id=1` 把删除放在安全方法上，浏览器预取、缓存或爬虫可能重复触发删除。修正：改为 `DELETE /api/v1/departments/1`。
2. **查询用 POST**：`POST /api/v1/departments/query` 把查询写成会改变状态的方法，破坏缓存与幂等语义。修正：改为 `GET /api/v1/departments/1` 或带查询参数的 GET。
3. **成功与失败都返回 200**：调用方无法从状态码判断结果，前端只能靠解析响应体猜。修正：成功用 200/201，参数错误用 422，未找到用 404，服务器错误用 500。
4. **URL 单复数不一致**：`/departments/1` 与 `/department/1` 指向同一资源却有两种写法，前端容易写错，文档与代码难以对账。修正：统一为复数资源名。

（答出其中任意三处即可。）

#### 习题 4-5【Bloom：理解】（概念辨析）

**参考答案**：① 缓存：GET 名词资源可被浏览器、代理按 URL 缓存与复用，把动作写进 URL 会破坏缓存语义；② 可读性：`DELETE /departments/1` 一眼看出“对 1 号部门做删除”，`POST /departments/delete/1` 需要读实现才知道行为；③ 契约：同一资源的不同动作共享 URL，前端与文档可按“资源 + 方法”稳定组织，减少字段与路径的分叉。动作写进 URL 还会让幂等性、状态码语义变得含糊。

## 第 5 章 FastAPI 核心机制

#### 习题 5-1【Bloom：记忆】

**参考答案**：

| 机制 | 对应符号或写法 | 解决的问题 |
| --- | --- | --- |
| 路由 | `@app.get(...)`；`APIRouter` + `include_router` | 把“URL + 方法”与函数绑定，并按模块拆分 |
| 数据 | `BaseModel`、`Field` | 定义请求与响应的结构，在进入函数前完成校验 |
| 错误 | `HTTPException` | 规则性失败提前返回状态码与人话说明 |
| 复用 | `Depends`、`get_db` | 公共逻辑只写一次，接口只声明、不重复 |

#### 习题 5-2【Bloom：分析】

**参考答案**：

1. 版本 A 返回 422，`detail` 中的 `type` 为 `int_parsing`：`n` 声明为 `int`，`abc` 无法解析为整数，FastAPI 在进入函数前就拦下，函数体不执行。
2. 版本 B 返回 500：`n` 声明为 `str`，`abc` 是合法字符串，请求进入函数体；执行 `n * n` 时字符串乘法要求另一个操作数是整数，抛出 `TypeError`，未捕获的异常变成 500。
3. 类型注解是 FastAPI 的校验依据：它把“类型不对”的请求挡在函数之外（422），而不是让错误数据进入业务代码、最后以 500 收场。版本 B 若确实接受字符串，函数体也必须按字符串处理，不能直接做数值运算。

#### 习题 5-3【Bloom：应用】

**参考答案**：

```python
# app/routers/borrows.py
from fastapi import APIRouter

router = APIRouter(prefix="/borrows", tags=["借还"])

@router.get("")
def list_borrows():
    return {"items": [], "total": 0}
```

```python
# main.py
from fastapi import FastAPI
from app.routers import borrows

app = FastAPI()
app.include_router(borrows.router, prefix="/api/v1")
```

最终访问路径为 `/api/v1/borrows`：模块的 `prefix="/borrows"` 与 `include_router` 的 `prefix="/api/v1"` 相加；`tags` 只影响 `/docs` 的分组。

#### 习题 5-4【Bloom：应用】

**参考答案**：

```python
from datetime import datetime
from pydantic import BaseModel, Field

class DutyCreate(BaseModel):
    personnel_certificate_number: str = Field(..., min_length=6, max_length=18)
    start_time: datetime

@router.post("", status_code=201)
def create_duty(data: DutyCreate):
    return data
```

1. 提交空请求体 `{}`：两个必填字段都缺失，返回 422；`detail` 中 `loc` 分别指向 `["body", "personnel_certificate_number"]` 与 `["body", "start_time"]`，`type` 为 `missing`。
2. 证件号只有 3 个字符：返回 422，`loc` 指向 `["body", "personnel_certificate_number"]`，`type` 为 `string_too_short`。
3. 两种情况都在进入函数前被 Pydantic 拦下，函数体不执行；合法请求返回 201。

#### 习题 5-5【Bloom：分析】（综合：接口语义与机制）

**参考答案**：

1. **所有路由写在 `main.py`**：项目变大后文件无法维护，模块边界消失。违背本章 5.1.3 的拆分规则。改造：每个业务模块一个 `APIRouter` 文件，`main.py` 只调用 `include_router`。
2. **用 POST 加动词路径做删除**：违背第 4 章的 RESTful 规则——URL 表示资源、方法表示动作；`POST` 不保证幂等，删除语义也容易让缓存或重试误触发。改造：`DELETE /api/v1/departments/{dept_id}`，成功返回 204。
3. **每个函数自己 `db = SessionLocal()`**：会话创建与关闭逻辑重复，出错时容易漏关，测试时也无法替换成假数据库。违背本章 5.1.6 的复用规则。改造：用 `get_db` 依赖，接口声明 `db: Session = Depends(get_db)`。

```python
# app/routers/departments.py
from fastapi import APIRouter, Depends
from sqlalchemy.orm import Session

from app.core.database import get_db

router = APIRouter(prefix="/departments", tags=["部门"])

@router.delete("/{dept_id}", status_code=204)
def delete_department(dept_id: int, db: Session = Depends(get_db)):
    ...
```

```python
# main.py
from app.routers import departments
```

## 第 8 章 用户模块：登录认证

#### 习题 8-1【Bloom：理解】

**参考答案**：

1. 用户提交用户名与密码到登录接口。
2. 后端按用户名查用户，用 `verify_password` 校验密码；通过后签发 JWT 令牌，令牌载荷包含用户标识 `sub`、角色 `role` 与过期时间 `exp`。
3. 客户端保存令牌，之后每次请求把它放进请求头：`Authorization: Bearer <token>`。
4. 受保护接口通过 `OAuth2PasswordBearer` 取出令牌，用签发时的密钥和算法解析；签名正确、未过期且载荷含用户标识，才确认当前用户。
5. 解析失败或没带令牌返回 401。
6. 401 表示身份未确认（没登录、令牌无效或过期）；403 表示身份已确认但权限不足（例如普通用户访问管理员接口）。

#### 习题 8-2【Bloom：应用】

**参考答案**：

```python
def create_user(db, data: UserCreate):
    if db.query(User).filter(User.username == data.username).first():
        raise HTTPException(status_code=400, detail="用户名已存在")
    user = User(
        username=data.username,
        password_hash=get_password_hash(data.password),
        role=data.role,
    )
    db.add(user)
    db.commit()
    db.refresh(user)
    return user
```

重复用户名返回 400。响应中不能包含 `password_hash`，因为哈希值虽然不是明文，但仍可用于离线暴力破解；输出模型应只返回 `id`、`username`、`role`、`is_active` 等可公开字段。

#### 习题 8-3【Bloom：应用】

**参考答案**：


#### 习题 8-4【Bloom：分析】

**参考答案**：

1. **密码正确但登录 401**：先查用户名是否真的存在；再查密码校验是否用了 `verify_password`，而不是直接比较明文；最后查账号是否被停用（`is_active` 为 0 也会返回 401）。排查步骤：查数据库用户记录、打印校验结果（不要打印密码）、检查停用状态。
2. **登录成功但访问 `/me` 仍 401**：先看请求头是否写成 `Authorization: Bearer <token>`（缺 Bearer、拼写错误、多了空格都会失败）；再检查令牌是否过期；最后检查服务端密钥或算法是否与签发时一致。排查步骤：用 `jwt.decode` 单独解析令牌，观察异常类型。
3. **普通用户访问管理员接口 403**：这是授权问题，不是认证问题。检查用户 `role` 是否为 `admin`，以及权限依赖的判断条件是否写反。排查步骤：查看令牌载荷中的 `role`，再对照 `get_current_admin_user` 的判断。

**参考答案**：

| 现象 | 补什么 | 属于哪一层 | 为什么 |
| --- | --- | --- | --- |
| ① 两个同名账号 | `username = Column(String(100), unique=True, nullable=False)` | 数据库约束 | 唯一约束是最后一道防线：即便注册接口漏了查重，数据库也会拒绝第二条；否则第 8 章 8.1.5 按用户名 `.first()` 会取到不确定的一条 |
| ② `role` / `is_active` 为空 | `role = Column(String(20), default="normal")`、`is_active = Column(Integer, default=1)` | 数据库约束 | 默认值让「不传」也有确定取值；少了它，新建用户的角色是 `NULL`，权限依赖判断不等于 `admin` 就落到 403，登录检查启用状态也可能出错 |

## 第 10 章 数据模块：增删查改

#### 习题 10-1【Bloom：理解】

**参考答案**：

- `page`：第几页，从 1 开始。
- `page_size`：每页多少条。
- `offset`：查询时跳过前面的记录数，等于 `(page - 1) * page_size`。
- `limit`：本次最多返回多少条，通常等于 `page_size`。
- `total`：满足过滤条件的总记录数，与当前页无关。

关系：`offset` 与 `limit` 由 `page`、`page_size` 换算得出；`total` 在分页前用 `count()` 得到。响应必须返回 `total`，否则前端无法判断还有没有下一页、总页数是多少。

```python
class CRUDBase:
    def __init__(self, model, pk: str = "id"):
        self.model = model
        self.pk = pk

    def get(self, db, obj_id):
        return db.query(self.model).filter(getattr(self.model, self.pk) == obj_id).first()

    def get_multi(self, db, page: int = 1, page_size: int = 10):
        page = max(page, 1)
        page_size = min(max(page_size, 1), 100)
        query = db.query(self.model)
        total = query.count()
        items = query.offset((page - 1) * page_size).limit(page_size).all()
        pages = (total + page_size - 1) // page_size
        return {"items": items, "total": total, "page": page, "page_size": page_size, "pages": pages}

    def create(self, db, data):
        obj = self.model(**data.model_dump())
        db.add(obj); db.commit(); db.refresh(obj)
        return obj
```

## 第 12 章 业务模块：规则描述

#### 习题 12-1【Bloom：理解】

**参考答案**：

业务规则写在 service，因为 service 承载“业务上允许什么、拒绝什么”，可以单独测试，也能被多个入口（接口、批量导入、定时任务）复用。

- 放在 controller：每个入口都要重复写一遍规则；换一个入口（如批量导入）就可能漏掉校验；controller 会变得又长又难测。
- 放在 schema：schema 只适合校验单字段的格式与范围；“开始时间早于结束时间”依赖两个字段的关系，“同一人员时间不重叠”还要查数据库，schema 做不到，也不应该做。

**参考答案**：

1. 先校验时间顺序（不查库，最便宜）。
2. 再校验人员、工位存在（各一次主键查询）。
3. 最后校验时间重叠（一次范围查询，代价最高）。
4. 全部通过后再写入。

#### 习题 13-3【Bloom：分析】

**参考答案**：

可能原因：

1. **月度天数没有去重**：同一天多条记录被逐条累加，月度之和大于实际天数。
2. **跨月记录被重复计入两个月**：按开始和结束分别归月，导致一条记录贡献两个月。
3. **总天数与月度天数口径不同**：总天数用 `set` 去重，月度用记录计数。
4. **数据重复导入**：同一批记录被导入两次，总天数因日期相同仍去重，月度计数却翻倍。

修正方案：统一“天数 = 不同日期数”的口径；每个月维护日期集合，取集合长度；跨月记录只按约定归属一次；导入前做唯一性校验或幂等处理。修正后用 3–5 条记录手算核对总天数与月度之和。

**参考要点**：

#### 习题 15-2【Bloom：分析】

**参考答案**：

问题：

1. **部分写入**：循环里每写一条就 `commit`，第 N 条失败时前 N−1 条已经落库，留下半批数据。
2. **会话脏状态**：异常后没有 `rollback`，会话可能停留在失败事务中，后续请求继续报错。
3. **性能差**：每条记录一次提交，事务开销大，批量导入会非常慢。
4. **难以重试**：失败后不知道哪些已写入，重试可能产生重复数据。

修正：

```python
try:
    for row in rows:
        db.add(DutyRecord(**row))
    db.commit()
except Exception:
    db.rollback()
    raise
```

先完成所有校验与 `add`，最后一次性 `commit`；异常时 `rollback` 并继续抛出，让统一异常处理器返回 500 或业务错误。

3. **第 2 周：重复代码与性能**。抽取完全重复的分页/CRUD；列表加分页；消除明显的 N+1；补测试覆盖正常、边界、异常。

#### 习题 16-1【Bloom：记忆】

**参考答案**：

- `st.title`：显示页面标题。
- `st.write`：显示文本、数据或其他对象。
- `st.text_input`：显示单行文本输入框。
- `st.button`：显示按钮，点击时返回 True。

- `st.container`：把一组内容装进一个容器，可加边框形成卡片。

- `st.session_state`：跨脚本重跑保存用户状态。

#### 习题 16-2【Bloom：理解】

**参考答案**：

Streamlit 在每次交互后会把脚本从头到尾重新执行一遍，重新生成页面树；然后比较新旧页面树，只把变化的部分发给浏览器。所以页面不是被局部修改，而是被重新计算后对比出来的。

普通变量在每次重跑时都会重新初始化，所以点击按钮后 `count` 又从 0 开始；`st.session_state` 存在 Session 中，跨重跑保留，因此计数能累加。

#### 习题 16-3【Bloom：应用】

**参考答案**：

```python
import streamlit as st

st.title("我的第一个页面")

left, right = st.columns([2, 1])

with left:
    st.write("这是左侧的说明文字。")

with right:
    if st.button("点我"):
        st.write("你点击了按钮")
```

#### 习题 16-4【Bloom：分析】

**参考答案**：

原因：每次点击按钮都会触发脚本重跑；`count = 0` 在重跑时重新执行，把计数重置为 0，然后 `count += 1` 变成 1。所以页面上永远是 1。

修正一：把计数放进 `session_state`：

```python
if "count" not in st.session_state:
    st.session_state.count = 0
if st.button("点我 +1"):
    st.session_state.count += 1
st.write("当前计数：", st.session_state.count)
```

修正二：普通变量做不到跨重跑保留；除非把值写到文件、数据库或 URL 参数等外部存储，再在每次重跑时读回来。这正说明 `session_state` 是为“跨重跑状态”设计的。

#### 习题 16-5【Bloom：理解】（原理解释）

**参考答案**：事件模型：每次交互触发脚本从头执行，页面是“重新算出来”的结果，而不是被局部修改。保留输入靠两层：① 组件自身的值由前端组件状态与参数维持；② 需要跨重跑共享的业务状态（登录信息、页码、提示）放进 `st.session_state`。普通局部变量会随重跑重建，因此不能用来保存跨次状态。

#### 习题 19-1【Bloom：理解】

## 第 20 章 数据编辑与页面状态

#### 习题 20-1【Bloom：理解】

**参考答案**：

`st.session_state` 用于跨脚本重跑保存状态：页码、每页条数、筛选条件、登录态、当前用户等。普通变量在每次重跑时重新初始化，只有放进 `session_state` 才能保留。

生命周期：

- 初始化：`if "key" not in st.session_state: st.session_state.key = ...`
- 读取：请求参数、当前用户从 `session_state` 取。
- 修改：翻页、筛选、登录时写入。
- 清理：退出登录时 `st.session_state.clear()`。

临时输入通常不放进 `session_state`，因为它们只在当前操作中有意义，放进去会让状态越来越多、难以清理；真正需要跨页面或跨重跑保留的才放。

## 第 23 章 Docker 基础

#### 习题 23-1【Bloom：记忆】

**参考答案**：

| 操作 | 命令 |
| --- | --- |
| 查看本地镜像 | `docker images` |
| 查看运行中的容器 | `docker ps` |
| 查看所有容器 | `docker ps -a` |
| 构建镜像 | `docker build -t duty-backend:1.0 .` |
| 运行容器并映射端口 | `docker run -p 8000:8000 duty-backend:1.0` |
| 查看容器日志 | `docker logs <容器ID或名称>` |

#### 习题 23-2【Bloom：理解】

**参考答案**：

镜像分层：每条 `RUN`、`COPY`、`ADD` 生成一层，层是只读的；某一层变化时，它和它上面的层都要重建，下面的层命中缓存。`requirements.txt` 变化频率低，放在前面复制并安装依赖，依赖层就能长期命中缓存；业务代码变化频繁，放在最后复制，改代码时只重建代码层。

`.dockerignore` 让构建上下文不包含虚拟环境、`.git`、日志、数据库与密钥；上下文更小，构建更快，镜像也不会把无关或敏感文件带进去，所以体积更小、更安全。

#### 习题 23-3【Bloom：应用】

**参考答案**：

```bash
docker build -t duty-backend:1.0 .
docker run -d --name duty-api -p 8000:8000 duty-backend:1.0
docker logs -f duty-api
```

`-d` 让容器在后台运行，`--name` 指定容器名，`-p 8000:8000` 映射宿主机与容器端口，`docker logs -f` 持续查看日志。

#### 习题 23-4【Bloom：分析】

**参考答案**：

可能原因：

1. **启动命令立即结束**：`CMD` 执行的是短命令（如 `echo`），进程结束容器就退出。排查：`docker logs <容器>` 看输出；检查 `CMD` 是否是常驻服务命令。
2. **应用启动报错**：依赖缺失、配置错误、数据库连不上。排查：看容器日志的异常堆栈；检查环境变量与数据库地址。
3. **端口被占用**：宿主机端口已被其他进程占用，容器启动失败。排查：`docker ps -a` 看退出码；检查宿主机端口。
4. **镜像架构不匹配**：在 ARM 机器上运行 amd64 镜像。排查：看 `docker logs` 或平台警告；使用匹配架构的镜像。
5. **前台进程被守护化**：应用把自己放到后台，容器没有前台进程，立即退出。排查：让启动命令保持前台运行。

#### 习题 23-5【Bloom：理解】（概念辨析）

**参考答案**：虚拟机通过 Hypervisor 虚拟出完整硬件并运行独立操作系统内核；容器共享宿主机内核，用命名空间做隔离、用 cgroups 限制资源，只打包应用与依赖。因此容器启动快、体积小，但隔离强度低于虚拟机，也不能运行与宿主机内核不兼容的系统。说“轻量级虚拟机”容易让人误以为容器有独立内核与同等级隔离。

#### 习题 24-2【Bloom：应用】

#### 习题 24-3【Bloom：分析】

**参考答案**：

可能原因：

1. **`COPY . .` 放在依赖安装之前**：代码变化会让依赖层之前的层失效，依赖被重新安装。修正：先 `COPY requirements.txt` 并安装依赖，最后 `COPY . .`。

3. **`.dockerignore` 没生效或上下文变化**：无关文件变化导致上下文哈希变化。修正：检查 `.dockerignore` 是否覆盖虚拟环境、日志、数据库。
4. **使用 `--no-cache` 构建**：显式禁用缓存。修正：去掉该参数，或只在需要时使用。

#### 习题 24-4【Bloom：评价】（开放题）

**参考要点**：

“镜像越小越好”有前提：不能删除运行必需的文件、不能牺牲可诊断性。删掉调试工具与系统库，可能让容器无法启动或在故障时无法排查；如果因此导致线上问题，节省的体积远远不值。

“能跑优先”也有前提：不能把虚拟环境、日志、数据库、密钥打进镜像；否则镜像臃肿且不安全。

建议原则：

1. 先保证可运行、可验证、可排查。
2. 用 slim 基础镜像、先依赖后代码、`--no-cache-dir`、`.dockerignore` 做低风险优化。
3. 多阶段构建用于分离构建工具与运行产物，保留必要的诊断能力。
4. 每次优化后跑 `/health` 与核心接口，确认功能未受影响。
5. 用“体积 + 启动时间 + 可排查性”综合评价，而不是只看 MB。

## 第 25 章 前后端服务部署

#### 习题 25-1【Bloom：理解】

**参考答案**：

`depends_on` 只控制启动顺序：它让 Compose 先启动被依赖的服务，但不保证该服务“已经可用”。`healthcheck` 定义如何判断服务健康，例如访问 `/health`；配合 `condition: service_healthy`，前端会等后端健康后再启动。

只写 `depends_on` 不够，因为容器“启动”不等于“服务就绪”：后端可能还在初始化数据库，前端已经发请求，就会连接失败。

#### 习题 25-2【Bloom：应用】

**参考答案**：

```yaml
name: duty-system
services:
  backend:
    build: ./duty
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: sqlite:///./duty.db
      SECRET_KEY: change-me-in-production
      ALGORITHM: HS256
      DEBUG: "False"
    volumes:
      - ./duty/logs:/app/logs
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 20s
  frontend:
    build: ./duty_frontend
    ports:
      - "8501:8501"
    environment:
      DUTY_API_BASE_URL: http://backend:8000
    depends_on:
      backend:
        condition: service_healthy
```

#### 习题 25-3【Bloom：应用】

**参考答案**：

1. `http://127.0.0.1:8000`：不可用。前端容器里的 `127.0.0.1` 指前端自己，不是宿主机或后端容器。
2. `http://duty-backend:8000`：可用（前提是两个容器在同一自定义网络，且容器名可解析）。
3. `http://backend:8000`：可用（前提是后端容器设置了 `--network-alias backend`，或 Compose 服务名为 `backend`）。

结论：容器间访问要用容器名或网络别名，不用宿主机的回环地址。

#### 习题 25-4【Bloom：分析】

**参考答案**：

1. **前端提示无法连接**：`DUTY_API_BASE_URL` 仍指向 `127.0.0.1`，或两个容器不在同一网络。排查：`docker exec duty-frontend env | grep DUTY_API_BASE_URL`；进容器访问 `http://backend:8000/health`。
2. **后端容器启动即退出**：启动命令报错、依赖缺失、数据库路径不可写。排查：`docker logs duty-backend` 看堆栈；检查 `DATABASE_URL` 与挂载路径。
3. **登录 401**：用户不存在、密码错误、`SECRET_KEY` 与签发时不一致。排查：确认数据库中有测试账号；检查环境变量中的 `SECRET_KEY` 是否前后一致。
4. **重建容器后数据丢失**：数据库文件在容器层，没有挂载到宿主机。排查：`docker inspect` 看 `Mounts`；确认 `-v` 或 Compose 的 `volumes` 指向宿主机数据目录。
