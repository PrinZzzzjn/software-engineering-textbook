# 第 7 章 数据模块：查询复用

第 6 章已经能让列表按页返回 `items` 与 `total`。当系统里出现第二个也要分页、也要按条件筛选的列表接口时，两段查询会长得几乎一样，却又各自带着不同的过滤条件。本章回答两个问题——这些查询怎样写才不会互相矛盾，哪些部分真的可以收拢到一处。

## 本章要解决的问题

**多个模块的列表查询结构相近，怎样保证它们行为一致、又不互相绑架？**

一处查询写得对，不等于别的模块也对。搜索后总数对不上、翻页出现重复记录、A 模块修好的边界在 B 模块仍然出错——这些问题都不是"代码不能运行"，而是同一类逻辑在每个模块里各写一遍之后产生的偏差。

本章关心的是：这些查询里哪些部分真正相同、可以只写一次；哪些差异属于各模块自身，必须留在模块里；以及怎样在收拢之后确认行为没有改变。

## 本章学习目标

读完第 7 章并完成实训后，应能：

1. 指出多个模块列表查询中真正重复的部分，并说明重复带来的维护成本。
2. 用参数模型集中约束分页参数边界，避免在每个模块重复判断。
3. 保证过滤先于计数，使 `total` 与 `items` 描述同一批数据。
4. 用固定排序键保证翻页稳定，并说明为何不让前端传排序字段。
5. 判断哪些查询代码可以收拢、哪些必须留在各模块，并用回归验证改造前后的行为一致。

## 7.1 从两个列表接口识别重复

先看重复在哪里，再谈要不要收拢。

先比较第 6 章的单位列表与本章给出的人员列表查询，会看到相同的骨架：接收 `page` 与 `page_size`，换算出 `offset` 与 `limit`，查询总数，取出当前页，最后返回 `items` 与 `total`。人员模块的读写是第 6 章 6.4 的课后拓展，本章直接给出它的列表查询代码，用来与单位模块并排比较；两段 `crud.py` 的共同部分如下：

**代码 7-1-1** · 两个模块 `list_page` 的共同骨架（示意，Python）

```python
def list_page(db, offset: int, limit: int):
    items = (
        db.query(模型)
        .order_by(固定排序列)
        .offset(offset)
        .limit(limit)
        .all()
    )
    total = db.query(模型).count()
    return items, total
```

真正不同的只有三处：查询哪张表、按哪一列排序、是否带过滤条件。单位的查询不带过滤，人员的查询可以按 `dept_code` 筛选。这三处差异决定了"按模型取一条、分页取多条、创建一条"这类操作虽然结构相同，却不能整个照搬——过滤条件与排序列是各模块自己的语义。

复制粘贴在编写阶段没有错，错在复制之后缺少唯一性约束。分页公式、边界判断、计数次序一旦需要调整，每个文件都要改一遍；漏掉一处，同一系统里就出现两种行为。这就是**维护成本**：它不表现为程序无法运行，而表现为每次修改都要额外确认"其他模块是否已经同步"。

由此得到第一步结论：先把"结构相同"和"语义相同"分开。骨架结构相同，是收拢的候选；过滤条件、排序列、主键名是各模块的语义，收拢时要作为参数留出来，不能写死。

## 7.2 用参数模型集中约束分页边界

分页参数 `page` 与 `page_size` 在每个模块都要用，边界判断如果散落在各个 service 里，就可能出现"单位页最少 1 条、用户页最少 0 条"这类不一致。收拢的第一处，是把参数的来历与边界写在一个地方。

做法是把查询参数收进 `param.py`，用 Pydantic 的 `Field` 把边界写在类型声明里：

**代码 7-1-2** · `app/modules/department/param.py`（分页参数，Python）

```python
from pydantic import BaseModel, Field


class DepartmentQueryParams(BaseModel):
    page: int = Field(default=1, ge=1)
    page_size: int = Field(default=10, ge=1, le=100)
```

`ge=1` 表示页码从 1 开始，`le=100` 给每页条数设上限。不给上限时，调用方传 `page_size=100000`，一次查询就可能把整张表取走。过滤参数也放进同一个模型，例如人员模块增加 `dept_code`：

**代码 7-1-3** · `app/modules/personnel/param.py`（带过滤参数，Python）

```python
class PersonnelQueryParams(BaseModel):
    page: int = Field(default=1, ge=1)
    page_size: int = Field(default=10, ge=1, le=100)
    dept_code: str | None = None
```

参数模型由 FastAPI 通过 `Depends()` 注入并校验，越界的请求在进入函数之前就得到 422，service 不必再写边界判断。service 只负责把页码换算成偏移量：

**代码 7-1-4** · `app/modules/department/service.py`（列表，Python）

```python
def list_departments(db, params):
    offset = (params.page - 1) * params.page_size
    items, total = crud.list_page(db, offset, params.page_size)
    return {"items": items, "total": total}
```

同一含义的参数在全项目使用同一个名字，是这里的一条隐性约定：都叫 `page` 与 `page_size`，过滤字段用各自表的列名。名字统一之后，前端不必为每个模块记忆一套参数，后续若要收拢公共逻辑，也不需要为兼容不同的参数名写分支。

## 7.3 过滤先于计数

分页数字对不上，是最常见的一类查询缺陷。先看一个具体现象：单位表有 120 条记录，搜索框输入"张"，表格显示 3 行，页脚却写着"共 120 条"。点第 2 页，内容为空。

两种常见的错误应对都只改显示、不改原因：一是在结果不足一页时隐藏分页，但用户清空搜索后分页还得恢复；二是把总数改成 `len(items)`，这样第一页永远显示 10 条，翻页随之失效。

真正的原因在执行次序。`total` 与 `items` 必须出自同一个已经过滤的查询；如果先调用 `count()` 再追加过滤，`total` 统计的是过滤前的 120 条，`items` 取到的却是过滤后的 3 条。两个数字各自都算对了，组合在一起却互相矛盾。

**代码 7-1-5** · `app/modules/personnel/crud.py`（过滤后计数，Python）

```python
def list_page(db, offset, limit, dept_code: str | None = None):
    query = db.query(Personnel)
    if dept_code:
        query = query.filter(Personnel.dept_code == dept_code)
    total = query.count()
    items = (
        query.order_by(Personnel.certificate_number)
        .offset(offset)
        .limit(limit)
        .all()
    )
    return items, total
```

`if dept_code` 放在 `count()` 之前，`total` 与 `items` 就描述同一批数据。用户没有填写过滤条件时，`dept_code` 为 `None` 或空串，此时跳过 `filter`；以空串调用过滤会混淆"未筛选"与"筛选空值"两种状态，也会产生一次没有意义的条件拼接。

这不是需要死记的约定，而是"总数与列表必须描述同一批数据"的直接推论。分页数字不一致时，先检查 `count()` 所在行上方是否已经加入全部过滤条件。

## 7.4 用固定排序键保证翻页稳定

列表查询还需要一个稳定的顺序。缺少顺序时，数据库不承诺两次查询返回相同的行序；用户翻到第 2 页，可能看到第 1 页已经出现过的记录，也可能漏掉某条。所以分页查询必须显式带 `order_by`。

一种做法是让前端传排序字段。但用户可控的字符串不能直接拼进 SQL：传入一个不存在的字段会返回 500，传入一个本不该参与排序的字段则会暴露不该暴露的顺序。要支持前端选择排序列，就必须在后端建立白名单，把允许的字符串映射到模型列，无法映射时回落到默认列：

**代码 7-1-6** · 排序列白名单（需要多字段排序时，Python）

```python
sort_fields = {
    "dept_code": Department.dept_code,
    "full_name": Department.full_name,
}
column = sort_fields.get(sort_by, Department.dept_code)
query = query.order_by(column.asc())
```

白名单把"允许哪些列"和"非法输入落到哪里"都固定在后端，同时挡住注入与不存在的字段。但本项目四个业务模块的列表都只有一个默认顺序，不需要在前端切换排序列。这种情况下更简单也够用的做法，是在后端固定排序列：

**代码 7-1-7** · `app/modules/department/crud.py`（固定排序键，Python）

```python
items = (
    db.query(Department)
    .order_by(Department.dept_code)
    .offset(offset)
    .limit(limit)
    .all()
)
```

固定键与白名单解决的是同一个问题的两种规模：只有一个默认顺序时用固定键，代码更少、接口也不必多一个参数；确实需要用户切换多列排序时，再引入白名单。无论哪种，默认顺序都必须固定——否则两次请求可能返回同一批数据但顺序不同，翻页重复就由此产生。

## 7.5 复用边界与回归验证

分清了重复与差异，就可以回答"哪些代码该收拢"。判据只有一条：**换一个模型仍然不需要任何改动的代码，才可以收拢；需要知道当前处理的是单位还是人员的，留在各自模块。**

按这条判据逐个看：分页骨架里的 `offset`、`limit`、`count` 运算对所有模型都相同，属于可收拢的结构；而过滤字段（`dept_code`）、排序列（`dept_code` 或 `certificate_number`）、主键名都是各模块的语义，应作为参数传进来或留在模块内。新增单位前检查编码是否重复、新增人员前检查所属单位是否存在，这类规则只有各自的模块知道；若塞进公共代码，公共代码就得先判断"当前是不是单位"，从此开始认识具体业务，每新增一个模块都要回来改它。软件设计文献把这类"什么都管、谁都要改"的类称为**上帝类**（Brown et al., 1998），维护难度反而高于复制粘贴。

即便决定收拢，也要选择合适的方式。优先使用组合而非深继承（Gamma et al., 1994）：让模块持有一个公共查询函数的调用，而不是派生多层子类。继承层次一深，读代码就要跨越多个文件才能确定某个方法最终执行的是哪一版；层次越浅，改动越容易定位。

收拢之后必须做回归验证（Regression Test）：代码更整洁不等于行为未变。回归测试指修改后重新运行既有测试，确认原有行为未被破坏（ISO/IEC/IEEE 24765:2017）。本课程的回归做法是改造前后用同一组请求逐字段比对 `items` 与 `total`，不要求先学 pytest；第 12 章的自动化测试只是把这一动作固定下来。至少验证三件事：列表仍能正常分页，详情仍能按各自的主键查到，新增仍能写入并返回。

本章并排比较的两份代码，一份来自第 6 章的 department，一份是本节给出的 personnel；回归时用同一组请求逐字段比对这两份代码的 `items` 与 `total`，「换一个模型仍一字不改」的判据才有可核对的对象。

改造顺序也影响排查：先改一个模块并验证，再改第二个并验证，最后删除旧代码。同时改两个模块，一旦出问题就很难判断是哪一步引入的。

## 示范例题

三道例题分别对应本章的三个动作：写出正确的过滤分页、判断复用边界、把列表接口接到统一的二字段返回。

#### 例 7-1：写出过滤后计数的分页查询

**题目**：人员列表支持按 `dept_code` 筛选。写出 `list_page`，要求 `total` 与 `items` 描述同一批数据，并说明把 `count()` 写在过滤之前会得到什么结果。

**解**：

**代码 7-1-8** · `app/modules/personnel/crud.py`（节选，Python）

```python
def list_page(db, offset, limit, dept_code: str | None = None):
    query = db.query(Personnel)
    if dept_code:
        query = query.filter(Personnel.dept_code == dept_code)
    total = query.count()
    items = (
        query.order_by(Personnel.certificate_number)
        .offset(offset)
        .limit(limit)
        .all()
    )
    return items, total
```

若把 `total = query.count()` 移到 `if dept_code` 之前，`total` 统计的是全部人员，而 `items` 只含筛选结果。假设总表 120 人、某单位 3 人，筛选该单位时列表显示 3 行、总数却是 120；前端按 120 计算页数，翻到第 2 页便为空。次序错误不会抛异常，因此只能靠"总数与列表是否同源"这一判据发现。

#### 例 7-2：判断哪些代码可复用

**题目**：下面四段代码，哪些可以收拢到公共查询代码，哪些应留在各自的 service？说明理由。

1. 按主键查一条记录。
2. 分页查询多条记录，带 `offset`、`limit` 和计数。
3. 新增单位前检查 `dept_code` 是否重复。
4. 新增人员前检查 `dept_code` 是否存在。

**解**：

1. 可以收拢。所有模型都按主键查一条，只是主键名不同，可把模型与主键名作为参数传入。
2. 可以收拢。`count`、`offset`、`limit` 的运算对每个模型都相同；过滤字段与排序列作为参数留出。
3. 不可以。它依赖"单位编码唯一"这条业务规则，只有单位模块知道；放进公共代码就会让公共代码认识单位。
4. 不可以。它依赖"人员必须属于某单位"这条业务规则，只有人员模块知道；应留在人员 service。

判据仍是那一条：换一个模型仍然一字不改的，才可收拢；需要知道具体业务含义的，留在模块内。

#### 例 7-3：把列表接口接到二字段返回

**题目**：第 6 章的 department 列表已经能分页返回 `items` 与 `total`。在补上过滤与固定排序之后，service 与 controller 应怎样写，才能保持薄层透传？

**解**：

机制变化落在 `crud.py` 与 `param.py`，入口代码不必改。crud 返回 `(items, total)` 二元组，service 组装成二字段字典，controller 声明响应模型后透传：

**代码 7-1-9** · `app/modules/department/service.py`（列表，Python）

```python
def list_departments(db, params):
    offset = (params.page - 1) * params.page_size
    items, total = crud.list_page(db, offset, params.page_size)
    return {"items": items, "total": total}
```

**代码 7-1-10** · `app/modules/department/controller.py`（列表接口，Python）

```python
@router.get("")
def list_departments(
    params: DepartmentQueryParams = Depends(),
    db: Session = Depends(get_db),
):
    return service.list_departments(db, params)
```

过滤次序与固定排序都已经落在 `crud.py` 里，参数边界落在 `param.py` 里，service 只做换算与组装，controller 只声明契约并透传。本章的目标不是让入口代码变复杂，而是把变化收敛到该收敛的层。

## ◆ 实训 7-1：数据模块：查询复用

### 一、任务目标与验收

| 目标 | 验收标志 |
| --- | --- |
| 识别重复 | 列出至少三处结构相同的查询代码，并标出其中的模块差异 |
| 参数边界集中 | 分页参数收进 `param.py`，越界请求返回 422 |
| 过滤计数次序正确 | 带过滤条件时 `total` 与 `items` 描述同一批数据 |
| 翻页稳定 | 列表带固定 `order_by`，反复翻页无重复记录 |
| 回归通过 | 改造前后同一组请求的 `items` 与 `total` 逐字段一致（手工清单即可） |

### 二、课前准备

- 第 6 章的 department 落库版代码（列表已能分页返回 `items`/`total`）
- 人员模块的 `crud.py`、`param.py`（含 `dept_code` 过滤）
- 一份"改造前"的响应样例与现有接口验证清单

### 三、操作步骤

1. **找重复与差异**
   - 做什么：把两个模块的 `list_page` 并排比较
   - 操作：标出结构相同的部分，再逐项列出模型、排序列、过滤条件的不同
   - 预期输出：→ 至少三处结构相同，且差异都被明确列为参数或模块语义
   - 做错会看到什么：把带过滤条件的查询当成"完全一样"；应先把差异参数化
2. **集中参数边界**
   - 做什么：把分页参数收进 `param.py` 并加 `Field` 约束
   - 操作：设置 `ge=1`、`le=100`，从 service 中删除重复的边界判断
   - 预期输出：→ 越界请求返回 422，各模块边界一致
   - 做错会看到什么：只在 service 里判断边界；应在参数模型里集中声明
3. **修正计数次序**
   - 做什么：确认过滤条件都在 `count()` 之前
   - 操作：用带 `dept_code` 的查询验证 `total` 是否随筛选变化
   - 预期输出：→ 筛选后的 `total` 等于实际返回的行数总和
   - 做错会看到什么：筛选后 `total` 不变；应检查条件加在了 `count()` 之后
4. **固定排序并回归**
   - 做什么：给列表加固定 `order_by`，然后验证改造前后响应一致
   - 操作：反复翻页比对记录，再用同一组请求比对改造前后的 `items` 与 `total`
   - 预期输出：→ 翻页无重复，两次响应逐字段一致
   - 做错会看到什么：翻页出现重复；应检查是否漏掉 `order_by`

### 四、排错清单

| 现象 | 先查什么 |
| --- | --- |
| 筛选后总数不变 | 过滤条件是否加在 `count()` 之后 |
| 翻页出现重复记录 | 查询是否缺少固定的 `order_by` |
| 越界参数未报错 | 边界是否只写在 service、未写进参数模型 |
| 改造后行为变化 | 是否把带业务含义的代码也收拢了，退回各自模块 |

### 五、提交与验收

## 本章小结

**核心结论**：

1. **重复与差异要分开**：多个模块的列表查询骨架相同，但过滤字段、排序列、主键名是各自的语义；收拢结构，把差异作为参数留出。
2. **边界集中**：分页参数用 `param.py` 的 `Field` 统一约束，越界在进入函数前返回 422，避免各模块重复判断。
3. **查询正确性**：`filter` 必须在 `count()` 之前，使 `total` 与 `items` 出自同一个查询；空串跳过过滤，列表带固定 `order_by` 以保证翻页稳定。
4. **复用边界与回归**：换一个模型仍一字不改的才可收拢，业务规则留在模块内；优先组合而非深继承；改造后用同一组请求逐字段比对响应。

本章讨论的复用，其目标不是提高抽象程度，而是把真正相同的部分收拢到一处，同时让属于各模块的差异留在原处。
