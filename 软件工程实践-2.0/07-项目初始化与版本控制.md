## 7.1 概念讲解

### 7.1.1 覆盖与丢失

没有版本控制时，项目会遇到三类问题，而且往往同时出现。

**覆盖**：两个人改同一个文件，后发回的那份把先改的内容盖掉。文件名里的“最终版”“真的最终版”“最终版-小张”就是覆盖留下的痕迹。

**丢失**：代码只存在某一台电脑上。硬盘坏了、系统重装了、文件夹误删了，项目就没了。即使有备份，也常常不知道备份的是哪一天的版本。

**无法回退**：改出一个 bug 后，想回到“昨天能跑”的状态，却找不到那一版；只能凭记忆一行行改回去，改着改着又引入新问题。

这三类问题指向同一个缺失：**项目没有记录“每次修改是什么、为什么改、改完是什么状态”。** 补上这份记录，就是**版本控制**：用一个仓库保存项目的历史，每次修改成为一条可查看、可比较、可回退的记录。

判断版本控制是否真的起作用，看一个可观察的现象：**能否在五分钟内回答“上周三那一版改了什么、为什么改、谁改的”。** 能，历史就是可用的；不能，仓库只是一个文件柜。

> 💡 **易错点**：把“文件复制一份”当成版本控制。`项目-备份-最终版-2` 这类文件夹没有记录改了什么，也无法比较两版的差异；版本一多，连作者自己都分不清。

### 7.1.2 三个区域与一次提交

Git 把一次修改从“正在编辑的文件”送到“历史记录”，中间经过暂存区。

```mermaid
flowchart LR
    W[工作区<br/>修改文件] -->|git add| S[暂存区]
    S -->|git commit| R[本地仓库]
    R -->|git push| Remote[远程仓库]
    Remote -->|git pull| W
```

*图 7-1：Git 的工作区、暂存区、本地仓库与远程仓库*

三个区域各管一件事：**工作区**是当前正在编辑的目录；**暂存区**存放“这次准备提交哪些改动”；**本地仓库**保存已经提交的历史。`git add` 把改动放进暂存区，`git commit` 把暂存区记录成一次**提交**，`git push` 把本地提交共享到远程仓库。`git status` 看当前有哪些改动，`git log` 看历史。

暂存区的意义在于“选择”：一次改动了五个文件，可以只把其中相关的三个放进这次提交，另外两个留到下一次。这样每条提交只讲一件事，回退时才能精确地撤掉一件事，而不是连带撤掉无关改动。

**代码 7-1-1** · 命令（Bash）

```bash
git init -b main
git add .
git commit -m "chore: init fastapi project"
```

**提交信息与提交粒度**

提交信息是给未来的自己和同伴看的。常用类型前缀有：`feat:` 新功能、`fix:` 修复、`docs:` 文档、`test:` 测试、`chore:` 构建或杂务。一个提交只做一件事，提交信息就能说清这件事。

“update”“修改一下”“最终版”这类提交信息，过两周连作者自己都看不懂改了什么。反过来，“feat: add hello endpoint”“fix: correct database path”能让历史自己讲故事。

**提交什么，不提交什么**

虚拟环境、数据库文件、日志和密钥都不应该提交。它们要么体积大，要么因机器而异，要么含敏感信息。`.gitignore` 把这些路径排除掉：

**代码 7-1-2** · `.gitignore` 片段

```gitignore
venv/
__pycache__/
*.pyc
.env
*.db
logs/
.pytest_cache/
```

`.gitignore` 必须在第一次提交前写好。如果已经误提交了 `venv/`，先把它加进 `.gitignore`，再用 `git rm -r --cached venv` 从索引中移除，然后提交这次移除。注意：`.gitignore` 只影响“以后是否跟踪”，已经进入历史的大文件仍留在历史里，所以第一次提交前就要设好。

> 💡 **易错点**：提交了整个虚拟环境或 `.env`。仓库会迅速变大，密钥也会随历史永久留存；即使后来删除文件，历史里仍然能翻到。发现时先停手，按上面的步骤从索引移除，并更换已泄露的密钥。

### 7.1.3 分支与合并

分支让改动可以并行。主分支保持可用，新功能在独立分支上开发，完成后再合并回来。

**为什么要分支**：两个人同时改 `main`，谁的提交在后面，谁就要先处理对方的改动；如果改的是同一处，冲突会在最不适合的时候出现。分支把“各自的实验”隔开，合并时再集中处理差异。

**代码 7-1-3** · 命令（Bash）

```bash
git switch -c feature/hello
# 修改代码
git add main.py
git commit -m "feat: add hello endpoint"
git switch main
git merge feature/hello
```

如果主分支在分叉后没有新提交，合并通常是“快进”，历史是一条直线。如果两边都改了同一处，Git 无法自动决定保留哪一版，就会产生冲突。冲突文件里会出现三组标记：

**代码 7-1-4** · 示例（文本）

```text
<<<<<<< HEAD
当前分支的内容
=======
要合并进来的内容
>>>>>>> feature/hello
```

处理方法是：打开文件，保留需要的内容，删掉三组标记，然后 `git add` 标记为已解决，再 `git commit` 完成合并。冲突不是错误，它只是提示“这里需要人做决定”。

**分支策略的取舍**

小团队不必一上来就套用完整的分支模型。一个够用的起点是：`main` 始终保持可运行；每个功能或修复开一个短分支；合并前至少一人看过改动；合并后删除分支。分支开得越久，合并冲突越多；分支切得越细，集成越频繁，但每次集成的成本也越低。选择取决于团队规模与发布节奏，而不是“越专业越好”。

> 💡 **易错点**：所有工作都直接提交在 `main` 上，或者一个分支开两周不合并。前者让任何人随时可能破坏主分支，后者让冲突在最后集中爆发。分支的生命周期应与一次可验收的改动相当。

### 7.1.4 可复现的项目结构

版本控制解决“改了什么”，项目结构解决“代码该放哪”。把所有代码写在一个文件里，短期能跑，长期会出三个问题：找不到代码、改一处牵动全身、别人无法接手。标准目录结构按职责分区，让每个文件有固定的位置，也让第 6 章的分层与模块化落到磁盘上。

**本书从本章起统一使用下面这套教学工程结构**：第 8 章及以后所有代码里出现的 `app/core`、`app/routers`、`app/schemas`、`app/models` 都指这里，后续章节不再另起一套目录。

**代码 7-1-5** · 示例（文本）

```text
duty/
├── main.py                  # 应用入口：创建 app、挂路由、建表
├── requirements.txt         # 依赖清单
├── .env.example             # 环境变量示例
├── .gitignore               # 不提交的内容
├── app/
│   ├── core/                # 跨模块基础设施：database.py、security.py、dependencies.py
│   ├── routers/             # 接口：每个业务模块一个 router，如 departments.py
│   ├── schemas/             # Pydantic 输入／输出模型，如 user.py
│   └── models/              # ORM 表模型（第 8 章 8.1.2 起），如 user.py
├── tests/                   # 测试
├── alembic/                 # 数据库迁移（教学工程暂不使用）
└── logs/                    # 运行日志（不提交）
```

`main.py` 负责创建应用、注册路由、启动服务；`app/core/` 放数据库连接、密码哈希、令牌与认证依赖等跨模块基础设施；`app/routers/` 每个业务模块一个 `router`；`app/schemas/` 放输入／输出模型；`app/models/` 放 ORM 表模型；`tests/` 与代码同仓；`logs/` 存运行日志。每个 Python 包目录都要有 `__init__.py`，否则导入时可能找不到模块。

> **和第 6 章的四层怎么对上**：6.1.5 讲的 controller / service / crud / model 是完整项目的分层方式，通常还按业务模块再分一层目录——duty 参考工程就是 `app/api/v1/module_system/`、`app/api/v1/module_duty/` 这种写法，每个模块里再分 controller、service、crud、model。本书为降低起步难度，把接口合到 `app/routers/`、把基础设施合到 `app/core/`、把模型分成 `app/schemas/`（对外）与 `app/models/`（建表）。职责划分的道理相同，只是目录少一层；等工作量上来，再按模块拆开不迟。

**虚拟环境与依赖清单**

虚拟环境的作用是隔离依赖。系统 Python 里可能装着各种版本的库，两个项目需要同一个库的不同主版本时，装在一起就会冲突。虚拟环境给每个项目一套独立的库。

**代码 7-1-6** · 命令（Bash）

```bash
python -m venv venv
```

Windows 下激活：

**代码 7-1-7** · 命令（Bash）

```bash
venv\Scripts\activate
```

Linux 或 macOS 下激活：

**代码 7-1-8** · 命令（Bash）

```bash
source venv/bin/activate
```

激活后，命令提示符前通常会出现 `(venv)`。此时安装的依赖只进入这个环境。依赖清单 `requirements.txt` 记录项目需要哪些库，别人拿到清单就能复现环境。本章骨架用到的最小清单如下：

**代码 7-1-9** · `requirements.txt` 示例（文本）

```text
fastapi
uvicorn[standard]
sqlalchemy
pydantic
```

其中 `fastapi` 是 Web 框架、`uvicorn[standard]` 是开发服务器、`sqlalchemy` 负责 ORM 与数据库连接、`pydantic` 负责输入校验（第 5 章 5.1.3）。第 8 章做登录时再往清单里加 `python-jose[cryptography]` 与 `passlib`。教学环境先用机房统一安装的版本；**正式项目应当把版本锁定**（例如 `fastapi==0.110.0`），否则半年后换机器装到的可能是另一个版本，就失去了「可复现」的意义。

装齐依赖的命令：

**代码 7-1-10** · 命令（Bash）

```bash
pip install -r requirements.txt
```

> 💡 **易错点**：在系统 Python 里直接 `pip install`。项目换机器时依赖版本对不上，或者不同项目互相覆盖。看到命令提示符前没有 `(venv)`，先激活再装。

### 7.1.5 配置管理与可复现启动

目录、虚拟环境与依赖清单解决“代码和库能不能装齐”；还有一类东西同样影响复现：配置。数据库地址、密钥、调试开关随环境变化，不能写死在代码里。

**环境变量：把配置从代码里拿出来**

项目通常提供两个文件：`.env.example` 记录需要哪些变量、示例值是什么；`.env` 保存本机实际值。

**代码 7-1-11** · `.env` 示例

```env
DATABASE_URL="sqlite:///./duty.db"
SECRET_KEY="change-me-in-env"
ALGORITHM="HS256"
ACCESS_TOKEN_EXPIRE_MINUTES=30
DEBUG=True
```

`.env.example` 进 Git，`.env` 不进 Git。原因是 `.env` 往往含真实密钥，提交上去等于泄露；而 `.env.example` 让新同事知道要配哪些项。生产环境必须替换默认 `SECRET_KEY`。

**配置管理：把代码、依赖、配置与忽略规则放在一起**

到这里可以给本章的核心概念一个正式名称。**配置管理**指把代码、依赖清单、环境配置、忽略规则与变更记录放在同一个可复现的仓库里，使任何一台机器按同一份说明都能得到相同的运行结果。它包含四件事：

| 组成 | 解决什么 | 本章对应 |
| --- | --- | --- |
| 版本控制 | 改了什么、能否回退 | 7.1.1–7.1.3 |
| 依赖清单 | 装哪些库、哪个版本 | 7.1.4 |
| 环境配置 | 地址、密钥等随环境变化的值 | 本节 `.env` |
| 忽略规则 | 哪些东西不该进仓库 | 7.1.2 `.gitignore` |

四件事缺一件，“换台机器能跑”就不成立：没有依赖清单，装不齐库；没有环境配置，数据库地址写死；没有忽略规则，密钥进仓库；没有版本控制，改坏了回不去。

**把应用跑起来**

入口文件把应用创建起来，并注册一个最小的健康检查（Health Check）接口：

**代码 7-1-12** · `main.py`（健康检查，Python）

```python
from fastapi import FastAPI

app = FastAPI(title="Duty API", version="0.1.0")

@app.get("/health")
def health():
    return {"status": "healthy"}
```

运行 `uvicorn main:app --reload --port 8000` 后，访问 `/health` 应返回 `{"status":"healthy"}`，访问 `/docs` 应能打开接口文档。健康检查的意义不只是“证明服务活着”，它还是部署后判断服务是否可用的第一项证据。

**从 `@app.get` 到 `@router.get`**

第 4 章用 `app = FastAPI()` 和 `@app.get` 写了最小接口，第 5 章 5.1.2 讲了 `APIRouter` 的机制。本章的项目骨架把这两件事落地：每个业务模块一个 `router`，`main.py` 只负责把它们挂进应用，数据库连接则单独放在一个文件里。

**代码 7-1-13** · `app/routers/departments.py`（模块路由，Python）

```python
from fastapi import APIRouter

router = APIRouter(prefix="/departments", tags=["部门"])

@router.get("")
def list_departments():
    return {"items": [], "total": 0}
```

`router` 不是凭空出现的变量：它由本文件顶部的 `APIRouter(...)` 创建，`prefix` 统一加上 URL 前缀，`tags` 只影响 `/docs` 里的分组显示。模块内所有接口都用 `@router.get`、`@router.post` 注册（机制见第 5 章 5.1.2 与补课卡 K-03）。

**代码 7-1-14** · `main.py`（组装，Python）

```python
from fastapi import FastAPI

from app.core.database import Base, engine
from app.routers import departments

app = FastAPI(title="Duty API", version="0.1.0")

app.include_router(departments.router, prefix="/api/v1")

Base.metadata.create_all(bind=engine)

@app.get("/health")
def health():
    return {"status": "healthy"}
```

`include_router` 把模块的 `router` 挂到应用上，`prefix="/api/v1"` 是所有业务接口的统一前缀。第 8 章做出用户模块后，照同样方式再加一行 `app.include_router(users.router, prefix="/api/v1")`。到那时 `@router.get("/me")` 的完整路径是 `/api/v1/users/me`——`/api/v1` 来自 `include_router`，`/users` 来自模块自己的 `APIRouter(prefix="/users")`，两者拼起来才是完整 URL。

**代码 7-1-15** · `app/core/database.py`（数据库连接，Python）

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, Session, sessionmaker

import os

DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./duty.db")

engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)

class Base(DeclarativeBase):
    """所有表模型的共同父类；继承它，表才会被 create_all 建出来。"""

def get_db():
    """依赖：每个请求开一个会话，用完在 finally 里关闭。"""
    db: Session = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

三句话认识它们：

- `Base` 是所有表类的父类。第 8 章 8.1.2 会定义 `class User(Base)`、第 10 章定义 `class Department(Base)`，表结构就是这些类的字段；定义好之后还要在 `main.py` 里导入这些模型类，`Base.metadata.create_all(bind=engine)` 才会在启动时把表建出来。本章还没有表模型，所以此刻 `create_all` 不会建表，`/health` 也不依赖数据库，服务照样能启动。
- `Session` 是一次数据库会话，查询、新增、提交都通过它。
- `get_db` 把“开会话、用完关掉”包成依赖，所以接口里写 `db: Session = Depends(get_db)` 即可，不需要自己开关连接。

这三件套的最小讲解在第 5 章 5.1.4（补课卡 K-07），本节把它们落成了项目里的真实文件。第 10 章起用它们做增删查改；第 8 章的用户模块直接复用这里的 `Base` 与 `get_db`，不再重复定义。

**本章的边界**

配置管理不是“把所有东西都塞进仓库”。运行日志、数据库文件、虚拟环境与密钥应当排除；只读的构建产物、临时文件也不必提交。判断标准是：**别人 clone 仓库并按说明安装后，能否得到与你相同的可运行状态。** 能，配置就完整；不能，缺的那一项就是该补的配置。

本章只讲 Git 的最小模型与项目初始化，不展开 rebase 的高级用法、完整 Git Flow 与 CI 配置。这些内容在真实团队中很重要，但不是本章的理解门槛。

#### 例 7-2：完成第一次 Git 提交【Bloom：应用】

**题目**：写出把一个已搭好骨架的 FastAPI 项目纳入 Git 的命令，要求：初始化主分支为 `main`、提交前排除虚拟环境与密钥、完成第一次提交。

**解**：

**代码 7-2-1** · 命令（Bash）

```bash
git init -b main
git add .gitignore
git commit -m "chore: add gitignore"
git add .
git commit -m "chore: init fastapi project"
```

其中 `.gitignore` 至少包含：

**代码 7-2-2** · `.gitignore` 片段

```gitignore
venv/
__pycache__/
.env
*.db
logs/
```

先单独提交 `.gitignore` 的好处是：后续 `git add .` 时，虚拟环境、`.env` 与数据库文件已经被排除，不会误入仓库。

## ◆ 实训 7-1：项目初始化与版本控制（对应课次 6 · 4 学时）

### 一、任务目标与验收

| 目标 | 验收标志 |
| --- | --- |
| 项目能启动 | `uvicorn main:app` 后可访问 `/health` 与 `/docs` |
| 目录符合约定 | app/core、app/routers、app/schemas 等各就各位 |
| 依赖可复现 | `pip install -r requirements.txt` 能装齐 |
| Git 历史可读 | 至少 3 次提交，信息说明做了什么 |
| 分支合并完成 | 有一次分支开发与合并记录 |

### 二、课前准备

- Python 3.10+ 与 Git 已安装
- 第 6 章的表结构与接口清单
- 一个空目录作为项目根目录

### 三、操作步骤

1. **建目录与虚拟环境**
   - 做什么：按 7.1.4 建出 `app/core`、`app/routers`、`app/schemas`、`app/models` 四个包目录，并建虚拟环境
   - 操作：`mkdir duty && cd duty && python -m venv venv`；激活后 `pip install -r requirements.txt`；四个包目录各放一个 `__init__.py`
   - 预期输出：→ 提示符前出现 `(venv)`，依赖装齐
   - 做错会看到什么：没有 `(venv)` 就装依赖；`ModuleNotFoundError: No module named 'app'` 多为包目录缺 `__init__.py`
2. **写入口与数据库**
   - 做什么：写 `main.py`、`app/core/database.py` 与一个最小的 `app/routers/departments.py`，把路由挂进应用
   - 操作：按 7.1.5 落盘，`include_router` 记得带 `prefix="/api/v1"`，然后启动服务
   - 预期输出：→ `/health` 返回 200，`/docs` 可打开
   - 做错会看到什么：`/docs` 404：检查 `include_router` 前缀与启动文件；`ImportError`：检查导入路径与 `__init__.py`
3. **初始化 Git 并首次提交**
   - 做什么：先写 `.gitignore` 并单独提交，再把整个骨架纳入版本控制
   - 操作：`git init -b main`、`git add .gitignore`、`git commit`、`git add .`、`git commit`
   - 预期输出：→ `git log` 有 2 条提交，`venv/`、`.env`、`*.db` 均未被跟踪
   - 做错会看到什么：`git status` 出现 `venv/`：`.gitignore` 没生效或写错路径
4. **分支开发与合并**
   - 做什么：在独立分支上改一处并合并回 `main`，练习一次完整提交闭环
   - 操作：`git switch -c feature/health`，改一处、提交、切回 `main` 合并
   - 预期输出：→ 历史可读，无冲突或冲突已解决
   - 做错会看到什么：冲突标记未删干净；保留需要的内容后删除三组标记再提交

### 四、排错清单

| 现象 | 先查什么 |
| --- | --- |
| 服务起不来 | 端口占用、依赖缺失、语法错误 |
| `/docs` 打不开 | 服务是否启动、路由前缀是否正确 |
| 依赖装到系统环境 | 虚拟环境是否激活 |
| 提交为空 | `git status`、`.gitignore` 是否误伤 |
| 合并冲突 | 保留目标内容，删除 `<<<<<<<` 三组标记后再 `git add` |

提交项目仓库与 `git log` 截图；验收按“能启动”“目录与配置”“Git 历史”三项判定。

## 本章小结

**核心结论**：

1. 没有版本控制会同时出现覆盖、丢失与无法回退；**版本控制**用仓库记录每次修改，使历史可查看、可比较、可回退。
2. Git 用工作区、暂存区、本地仓库组织一次**提交**；暂存区让每条提交只包含相关的改动，提交信息说明改了什么、为什么改。
3. 分支用于并行开发；合并时同一处出现不同改动会产生冲突，冲突需要人工决定保留哪一版。
4. 标准目录结构把分层与模块化落到磁盘；虚拟环境隔离依赖，依赖清单让换机器能复现。
5. **配置管理**把代码、依赖、环境配置、忽略规则与变更记录放在一起；`.env.example` 进 Git、`.env` 不进，密钥与数据库地址不写死在代码里。

把这章压缩成一句话：**可回溯靠提交，可协作靠分支，可复现靠配置管理。**

**本章不引入**：rebase 的高级用法、完整 Git Flow、CI 配置。这些在真实团队中按需了解。

**学完本章，你可以体会到**：项目初始化不是“建个文件夹”，而是把后面所有章节要复用的启动、配置与版本管理一次做对。
