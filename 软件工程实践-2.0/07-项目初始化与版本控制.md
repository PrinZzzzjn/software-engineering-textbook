## 7.1 概念讲解

### 7.1.1 标准目录结构解决什么问题

把所有代码写在一个文件里，短期能跑，长期会出三个问题：找不到代码、改一处牵动全身、别人无法接手。标准目录结构按职责分区，让每个文件有固定的位置，也让分层与模块化落到磁盘上。

**本书从本章起统一使用下面这套教学工程结构**：第 8 章及以后所有代码里出现的 `app/core`、`app/routers`、`app/schemas`、`app/models` 都指这里，后续章节不再另起一套目录。

**代码 7-1-1** · 示例（文本）

```text
duty/
├── main.py                  # 应用入口：创建 app、挂路由、建表
├── requirements.txt         # 依赖清单
├── .env.example             # 环境变量示例
├── .gitignore               # 不提交的内容
├── app/
│   ├── core/                # 跨模块基础设施：database.py、security.py、dependencies.py
│   ├── routers/             # 接口：每个业务模块一个 router，如 departments.py
│   ├── schemas/             # Pydantic 输入／输出模型，如 user.py
│   └── models/              # ORM 表模型（第 8 章 8.1.2 起），如 user.py
├── tests/                   # 测试
├── alembic/                 # 数据库迁移（教学工程暂不使用）
└── logs/                    # 运行日志（不提交）
```

`main.py` 负责创建应用、注册路由、启动服务；`app/core/` 放数据库连接、密码哈希、令牌与认证依赖等跨模块基础设施；`app/routers/` 每个业务模块一个 `router`；`app/schemas/` 放输入／输出模型；`app/models/` 放 ORM 表模型；`tests/` 与代码同仓；`logs/` 存运行日志。每个 Python 包目录都要有 `__init__.py`，否则导入时可能找不到模块。

> **和第 6 章的四层怎么对上**：6.1.5 讲的 controller / service / crud / model 是完整项目的分层方式，通常还按业务模块再分一层目录——duty 参考工程就是 `app/api/v1/module_system/`、`app/api/v1/module_duty/` 这种写法，每个模块里再分 controller、service、crud、model。本书为降低起步难度，把接口合到 `app/routers/`、把基础设施合到 `app/core/`、把模型分成 `app/schemas/`（对外）与 `app/models/`（建表）。职责划分的道理相同，只是目录少一层；等工作量上来，再按模块拆开不迟。

### 7.1.2 虚拟环境与依赖清单

虚拟环境的作用是隔离依赖。系统 Python 里可能装着各种版本的库，两个项目需要同一个库的不同主版本时，装在一起就会冲突。虚拟环境给每个项目一套独立的库。

**代码 7-1-3** · 命令（Bash）

```bash
python -m venv venv
```

Windows 下激活：

**代码 7-1-5** · 命令（Bash）

```bash
venv\Scripts\activate
```

Linux 或 macOS 下激活：

**代码 7-1-7** · 命令（Bash）

```bash
source venv/bin/activate
```

激活后，命令提示符前通常会出现 `(venv)`。此时安装的依赖只进入这个环境。依赖清单 `requirements.txt` 记录项目需要哪些库，别人拿到清单就能复现环境。本章骨架用到的最小清单如下：

**代码 7-1-9** · requirements.txt 示例（文本）

```text
fastapi
uvicorn[standard]
sqlalchemy
pydantic
```

其中 `fastapi` 是 Web 框架、`uvicorn[standard]` 是开发服务器、`sqlalchemy` 负责 ORM 与数据库连接、`pydantic` 负责输入校验（第 5 章 5.4）。第 8 章做登录时再往清单里加 `python-jose[cryptography]` 与 `passlib`。教学环境先用机房统一安装的版本；**正式项目应当把版本锁定**（例如 `fastapi==0.110.0`），否则半年后换机器装到的可能是另一个版本，就失去了「可复现」的意义。

装齐依赖的命令：

**代码 7-1-10** · 命令（Bash）

```bash
pip install -r requirements.txt
```

> 💡 **常见坑**：在系统 Python 里直接 `pip install`。项目换机器时依赖版本对不上，或者不同项目互相覆盖。看到命令提示符前没有 `(venv)`，先激活再装。

### 7.1.3 配置与环境变量

代码里不该写死数据库地址、密钥和调试开关。这些值随环境变化，应该放进环境变量。项目通常提供两个文件：`.env.example` 记录需要哪些变量、示例值是什么；`.env` 保存本机实际值。

**代码 7-1-11** · .env 示例

```env
DATABASE_URL="sqlite:///./duty.db"
SECRET_KEY="change-me-in-env"
ALGORITHM="HS256"
ACCESS_TOKEN_EXPIRE_MINUTES=30
DEBUG=True
```

`.env.example` 进 Git，`.env` 不进 Git。原因是 `.env` 往往含真实密钥，提交上去等于泄露；而 `.env.example` 让新同事知道要配哪些项。生产环境必须替换默认 `SECRET_KEY`。

### 7.1.4 应用入口与健康检查

入口文件把应用创建起来，并注册一个最小的健康检查（Health Check）接口：

**代码 7-1-13** · 示例代码（Python）

```python
from fastapi import FastAPI

app = FastAPI(title="Duty API", version="0.1.0")

@app.get("/health")
def health():
    return {"status": "healthy"}
```

运行 `uvicorn main:app --reload --port 8000` 后，访问 `/health` 应返回 `{"status":"healthy"}`，访问 `/docs` 应能打开接口文档。健康检查的意义不只是“证明服务活着”，它还是部署后判断服务是否可用的第一项证据。

### 7.1.5 从 `@app.get` 到 `@router.get`：路由挂载与数据库接入

第 4 章用 `app = FastAPI()` 和 `@app.get` 写了最小接口，第 5 章 5.3 讲了 `APIRouter` 的机制。本章的项目骨架把这两件事落地：每个业务模块一个 `router`，`main.py` 只负责把它们挂进应用，数据库连接则单独放在一个文件里。

**第一步：模块创建自己的 router。** 以部门模块为例，文件是 `app/routers/departments.py`：

**代码 7-1-15** · 示例代码（Python）

```python
from fastapi import APIRouter

router = APIRouter(prefix="/departments", tags=["部门"])

@router.get("")
def list_departments():
    return {"items": [], "total": 0}
```

`router` 不是凭空出现的变量：它由本文件顶部的 `APIRouter(...)` 创建，`prefix` 统一加上 URL 前缀，`tags` 只影响 `/docs` 里的分组显示。模块内所有接口都用 `@router.get`、`@router.post` 注册（机制见第 5 章 5.3 与补课卡 K-03）。

**第二步：`main.py` 把各模块挂进应用。** 主文件不再逐个写接口，只做三件事——创建应用、挂路由、建表：

**代码 7-1-17** · 示例代码（Python）

```python
from fastapi import FastAPI

from app.core.database import Base, engine
from app.routers import departments

app = FastAPI(title="Duty API", version="0.1.0")

app.include_router(departments.router, prefix="/api/v1")

Base.metadata.create_all(bind=engine)

@app.get("/health")
def health():
    return {"status": "healthy"}
```

`include_router` 把模块的 `router` 挂到应用上，`prefix="/api/v1"` 是所有业务接口的统一前缀。这里先挂本章建好的部门模块；第 8 章做出用户模块后，照同样方式再加一行 `app.include_router(users.router, prefix="/api/v1")`。到那时 `@router.get("/me")` 的完整路径是 `/api/v1/users/me`——`/api/v1` 来自 `include_router`，`/users` 来自模块自己的 `APIRouter(prefix="/users")`，两者拼起来才是完整 URL。

**第三步：数据库连接放在 `app/core/database.py`。** 完整内容如下：

**代码 7-1-19** · 示例代码（Python）

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, Session, sessionmaker

import os

DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./duty.db")

engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)

class Base(DeclarativeBase):
    """所有表模型的共同父类；继承它，表才会被 create_all 建出来。"""

def get_db():
    """依赖：每个请求开一个会话，用完在 finally 里关闭。"""
    db: Session = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

三句话认识它们：

- `Base` 是所有表类的父类。第 8 章 8.1.2 会定义 `class User(Base)`、第 10 章定义 `class Department(Base)`，表结构就是这些类的字段；定义好之后还要在 `main.py` 里导入这些模型类，`Base.metadata.create_all(bind=engine)` 才会在启动时把表建出来。本章还没有表模型，所以此刻 `create_all` 不会建表，`/health` 也不依赖数据库，服务照样能启动。
- `Session` 是一次数据库会话，查询、新增、提交都通过它。
- `get_db` 把“开会话、用完关掉”包成依赖，所以接口里写 `db: Session = Depends(get_db)` 即可，不需要自己开关连接。

这三件套的最小讲解在第 5 章 5.7（补课卡 K-07），本节把它们落成了项目里的真实文件。第 10 章起用它们做增删查改；第 8 章的用户模块直接复用这里的 `Base` 与 `get_db`，不再重复定义。

### 7.1.6 Git 记录了什么

Git 把一次修改从“工作区（Working Tree）”送到“本地仓库”，中间经过“暂存区（Staging Area）”。

```mermaid
flowchart LR
    W[工作区<br/>修改文件] -->|git add| S[暂存区]
    S -->|git commit| R[本地仓库]
    R -->|git push| Remote[远程仓库]
    Remote -->|git pull| W
```

*图 7-1：Git 的工作区、暂存区、本地仓库与远程仓库*

图中自左向右是改动从本机流向远程仓库的路径，`git pull` 那条回边表示别人推上去的改动会再回到你的工作区。三个动作要分清：`git add` 把改动放进暂存区，`git commit` 把暂存区的内容记录成一次提交，`git push` 把本地提交共享到远程仓库。`git status` 看当前有哪些改动，`git log` 看历史。

初始化仓库并完成第一次提交：

**代码 7-1-22** · 命令（Bash）

```bash
git init -b main
git add .
git commit -m "chore: init fastapi project"
```

如果 `git init` 的默认分支不是 `main`，可以用 `git branch -M main` 改名，或在初始化时加 `-b main`。

### 7.1.7 .gitignore：哪些东西不该进仓库

虚拟环境、数据库文件、日志和密钥都不应该提交。它们要么体积大，要么因机器而异，要么含敏感信息。`.gitignore` 把这些路径排除掉：

**代码 7-1-24** · .gitignore 片段

```gitignore
venv/
__pycache__/
*.pyc
.env
*.db
logs/
.pytest_cache/
```

`.gitignore` 必须在第一次提交前写好。如果已经误提交了 `venv/`，先把它加进 `.gitignore`，再用 `git rm -r --cached venv` 从索引中移除，然后提交这次移除。

### 7.1.8 分支与合并

分支让改动可以并行。主分支保持可用，新功能在独立分支上开发，完成后再合并回来。

**代码 7-1-26** · 命令（Bash）

```bash
git switch -c feature/hello
# 修改代码
git add main.py
git commit -m "feat: add hello endpoint"
git switch main
git merge feature/hello
```

如果主分支在分叉后没有新提交，合并通常是“快进”，历史是一条直线。如果两边都改了同一处，Git 无法自动决定保留哪一版，就会产生冲突。冲突文件里会出现三组标记：

**代码 7-1-28** · 示例（文本）

```text
<<<<<<< HEAD
当前分支的内容
=======
要合并进来的内容
>>>>>>> feature/hello
```

处理方法是：打开文件，保留需要的内容，删掉三组标记，然后 `git add` 标记为已解决，再 `git commit` 完成合并。冲突不是错误，它只是提示“这里需要人做决定”。

### 7.1.9 提交信息与提交粒度

提交信息是给未来的自己和同伴看的。常用类型前缀有：`feat:` 新功能、`fix:` 修复、`docs:` 文档、`test:` 测试、`chore:` 构建或杂务。一个提交只做一件事，提交信息就能说清这件事。

“update”“修改一下”“最终版”这类提交信息，过两周连作者自己都看不懂改了什么。反过来，“feat: add hello endpoint”“fix: correct database path”能让历史自己讲故事。

### 7.1.10 常见故障排查

| 现象 | 先查什么 |
| --- | --- |
| 服务起不来 | 端口占用、依赖缺失、语法错误 |
| `/docs` 打不开 | 服务是否启动、路径是否正确 |
| 422 | 请求体字段、类型、必填 |
| 404 | 路径前缀、尾斜杠、方法 |
| 数据库为空 | `.env` 的 `DATABASE_URL`、启动目录 |
| 导入失败 | 虚拟环境是否激活、`__init__.py` 是否存在、包路径 |
| Git 提交为空 | `git status`、`.gitignore` 是否误伤 |

排查的顺序通常是：先看现象，再看日志或错误信息，最后才改代码。不要一上来就重装环境，那会把真正的原因一起覆盖掉。

### 三、操作步骤

1. **建目录与虚拟环境**
   - 做什么：按 7.1.1 建出 `app/core`、`app/routers`、`app/schemas`、`app/models` 四个包目录，并建虚拟环境

2. **写入口与数据库**

3. **初始化 Git 并首次提交**
   - 做什么：先写 `.gitignore` 并单独提交，再把整个骨架纳入版本控制
   - 操作：`git init -b main`、`git add .gitignore`、`git commit`、`git add .`、`git commit`
   - 预期输出：→ `git log` 有 2 条提交，`venv/`、`.env`、`*.db` 均未被跟踪

4. **分支开发与合并**
   - 做什么：在独立分支上改一处并合并回 `main`，练习一次完整提交闭环

## 本章小结

**核心结论**：

1. 项目初始化要建立三件事：结构清楚、环境可复现、提交有记录。
2. 标准目录结构把分层与模块化落到磁盘；每个 Python 包目录要有 `__init__.py`。
3. 虚拟环境隔离依赖，`requirements.txt` 记录依赖，换机器时据此复现。
4. 配置放环境变量：`.env.example` 进 Git，`.env` 不进；密钥与数据库地址不写死在代码里。
5. Git 用暂存区组织提交；`.gitignore` 排除虚拟环境、数据库、日志与密钥；分支用于并行开发，冲突需要人工决定保留哪一版。

**学完本章，你可以体会到**：项目初始化不是“建个文件夹”，而是把后面所有章节要复用的启动、配置与版本管理一次做对。

## 本章提示页

> 先自己做，卡住了再看。提示按“方向 → 关键步骤 → 完整解答”排列。

**例 7-3（引导练习）：完成第二次提交并查看历史【Bloom：应用】**

**提示 1（方向）**

先看 `git status` 确认改动，再暂存具体文件，最后提交。

**提示 2（关键步骤）**

`git add main.py` 只暂存入口文件；`git log --oneline --graph` 能同时看到提交号、信息和分支走向。

**完整解答**

**代码 7-4-1** · 命令（Bash）

```bash
git status
git add main.py
git commit -m "feat: add hello endpoint"
git log --oneline --graph
```

`git status` 用于确认只有预期文件被修改；`git add main.py` 精确暂存，避免把不相关改动一起提交；`git commit` 记录这次功能；`git log` 查看历史。

**例 7-4（引导练习）：建分支并合并【Bloom：应用】**

**提示 1（方向）**

创建并切换分支用 `git switch -c`；合并前先切回目标分支。

**提示 2（关键步骤）**

如果 `main` 在分叉后没有新提交，合并会“快进”，历史上看不到分叉。

**完整解答**

**代码 7-4-3** · 命令（Bash）

```bash
git switch -c feature/hello
git add main.py
git commit -m "feat: add hello endpoint"
git switch main
git merge feature/hello
git log --oneline --graph
```

若 `main` 在分叉后没有新提交，合并为快进合并，历史是一条直线；若两边都有新提交，Git 会生成一次合并提交，历史出现分叉。
