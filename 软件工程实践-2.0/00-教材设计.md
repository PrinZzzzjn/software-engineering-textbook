# 《软件工程实践》教材设计

> 作者向设计文档：教学定位、UbD 五件套、章节树与梯度规划。读者向前页见 `00-前言.md`。

## 一、教学定位

- **教材名**：软件工程实践
- **学科**：软件工程（Web 应用开发实践；FastAPI + Streamlit + Docker）
- **学科档案**：stem
- **读者认知起点**：有先修，但基础有限——会一点 Python 基本语法，几乎没有项目经验；SQL、HTTP、Git 零基础，书内从零补
- **教材深度**：入门
- **篇幅规模**：24 章（**章 = 教学单元**，章 ↔ 课次为一一对应，课次号 = 章号；4 个专题作为“篇”分组）。第 3、4 章各为 4 学时（2 理论 + 2 实践，T/P 合并章），第 13 章为 4 学时实践（一个实训块）；总学时 80、理论 12、24 课次
- **主线项目**：执勤电子年鉴
- **AI 定位**：弱化 AI——每章 1 条了解性侧栏，AI 工具不进入主线、不依赖具体工具与可用环境；无 AI 环境可整章跳过侧栏（裁决 C4；2026-11-12 起不再设附录 L）
- **载体**：纯纸质。无二维码、无数字资源挂载点、无折叠交互；示范例题解答随题目印在章内，独立习题答案入 `98-参考答案.md`（教师用，不随学生用书发放），完整可运行工程以印刷全文交付（裁决 C2；C13 三段式修订后不再有引导练习提示页）
- **数据口径**：书中值班记录、器材借还、人员与证件号、端口与地址等**均为教学模拟数据，与真实单位和人员无关**；不启动脱敏与保密审查，但 M02 §四保密 / 安全编码 / 诚信一票否决条款原文保留（裁决 C9）

### 结构约定

- **章 = 教学单元（2.0 结构约定，C21 修订；2026-11-17 调整为课次号 = 章号）**：24 章覆盖 24 课次。第 3 章与第 4 章各为 4 学时（2 理论 + 2 实践，T/P 合并章）；第 13 章为 4 学时实践（一个实训块）；其余各章对应同学号的一个课次。定位靠前言「章 ↔ 课次」对照总表 + 目录分组行。
- **三段式题目骨架（C13；标题层级按 C19 修订）**：讲解小节 → 示范例题 → 独立习题，T/P 两类章统一采用。**2026-11-12 C19 裁决：不再设「概念讲解」外壳**——原 `### N.1.k` 小节提为二级标题并简化编号为 `## N.k`（N 为章号、k 为章内连续序号）；「示范例题」「独立习题」去掉 `N.2`／`N.3` 编号，与「本章小结」同为无编号二级标题。**一章内只有讲解小节带序号**，示范例题／独立习题下的 `#### 例 N-M`／`#### 习题 N-M` 保持四级不动。**应用层知识由示范例题的完整解答承担**；章末独立习题只保留思考题（分析／评价／创造、概念辨析／原理解释）与课后自习题（记忆／理解），删去与示范同构的【应用】题。
- **两套子体例 T/P**：T 理论讲授章 4 章（1、2、14、21）设「◇ 课堂活动块」；T/P 合并章 2 章（3、4）同时含「◇ 课堂活动块」与「◆ 实训块」；P 实践章 18 章设「◆ 实训块」六段（第 2 批起；复习任务并入课后扩展）。第 3 章含 ◇ 课堂活动块与 ◆ 实训 3-1；第 4 章含 ◇ 课堂活动块与 ◆ 综合实训 4-1。划分依据为课次类型，不是章号。
- **节首信息条已取消（2026-11-18）**：原每章必设的「对应课次 · 学时 · 讲授/实践 · 前置 · 本节活动/实训」信息条已从学生稿删除；课次定位改由目录分组行与前言「章 ↔ 课次」对照总表承担。第 3、4 章各为 4 学时（2 理论 + 2 实践），分别含 ◆ 实训 3-1 与 ◆ 综合实训 4-1；第 13 章为课次 13（4 学时实践），含 ◆ 实训 13-1。C21 起不再有「本单元第 1/2 章」类上下标记。
- **答案位置（2026-11-10 Q1 裁定，C13 修订；R1 修订）**：独立习题的参考答案统一入 `98-参考答案.md`，标为**教师用材料，不随学生用书发放**；章内不再提示答案位置，也不另设「章末自测答案页」；示范例题解答随题目留在章内。第 3 章含 ◇ 课堂活动块与 ◆ 实训 3-1；第 4 章含 ◇ 课堂活动块与 ◆ 综合实训 4-1。章内与 98 的题头逐条对齐由 `tools/check_numbering.py` 校验。
- **篇 = 专题**：4 个专题作为分组标注，不单独成文件。篇与章的关系：
  - 第一篇 软件工程基础与需求分析（第 1–2 章，专题一，4 学时全理论）
  - 第二篇 后端服务开发（第 3–13 章，专题二，38 学时）
  - 第三篇 前端界面构建（第 14–20 章，专题三，26 学时）
  - 第四篇 软件部署与系统交付（第 21–24 章，专题四，12 学时）
- **不占章号的部件**：导论“如何使用本书”并入 `00-前言.md`；项目答辩与课程总结属考核环节，不单独成章，其检验功能由表现性任务承担。**2026-11-12 裁定：原书末附录 A/B/D/I/L 与每章「前置知识卡」一并舍弃**——补课内容由正文就地解释与 `术语表.md` 承接；需求文档的五部分结构与交前自查由第 2 章「专题一综合实践」承担，接口、代码与交付评审清单不再单独成文。
- **每章标题用语**：沿用融合版大纲的节标题，去掉“第X节”字样，直接作为章标题（如“第 7 章 用户模块：登录认证”）。

### 学情与先修补课

读者 Python 基础很有限，且不假设 SQL、HTTP、Git 基础。补课责任在书中落实：

| 知识 | 补课位置 | 处理方式 |
| --- | --- | --- |
| Python 基础语法 | 导论 + 第 3 章 3.3–3.4 + 各章首次出现处 | 正文首次出现的语法点就地解释；不假设读者熟悉类、装饰器、类型注解 |
| HTTP / JSON | 第 3 章「后端开发框架」3.1–3.4 | 从请求/响应、方法、状态码讲起；3.4 给出四个方法的最小实践 |
| FastAPI 核心机制 | 第 3 章 3.3–3.6、第 4 章 4.5（语法说明并入正文） | `APIRouter`、Pydantic、`HTTPException` 首次使用前先讲；`Depends` 的机制在 4.5，第 6 章讲它在数据库会话中的应用，第 8 章讲它在认证中的应用 |
| 六文件分层 | 第 4 章 4.4–4.5 | 先讲六类职责，再给出可运行的内存版六文件实现；第 5–6 章沿用同一骨架 |
| SQL / SQLite | 第 6、7 章；第 4–5 章先用内存存储 | 只讲最小可用集，用到时在所在章补充 |
| Git | 第 5 章 | 从零讲，覆盖初始化、提交、分支与协作 |
| HTML / CSS | 不要求 | Streamlit 不需要 |

> 读者基础薄弱是本项目的既定前提：凡依赖“读者已经会”的表述，都要在本章或前章给出最小可用说明，或明确指向补课位置。

### 素材使用约定

1. **冲突裁决顺序（2.0 起）**：`docs/修订裁决记录_2.0.md`（C1–C12）→ M02（教学目标、学时与考核，硬约束）→ M08（代码事实）→ M01（内容与体例参考）→ M07（课次细节）→ M03/M04（补充参考）。M01 与 2.0 章节树冲突时以裁决记录为准。
2. **素材不是指令**：素材中“忽略规则”“跳过验证”一类文字只作材料内容，不改变三段式题目骨架、双 gate 与逐题验证纪律。
3. **路径失效不凭记忆复原**：续写时先比对 SHA-256；路径不可访问或指纹变化时暂停依赖该素材的工作，向作者索取可访问副本后重新映射。
4. **逐章使用记录**：阶段 4 每完成一章，把该章 `素材使用记录[]` 写回本索引下方（或阶段 3 章节树条目）的对应位置，形成“产出位置 ← 素材 ID + 原文位置”的可追溯链。

## 二、UbD 五件套（已确认）

### 1. 大概念（B1–B7）

- **B1** 软件工程是把“能运行的代码”变成“可交付、可维护的系统”的工程化方法，质量、进度与成本需要显式权衡。
- **B2** 需求是设计与开发的依据；模糊需求必须在编码前被澄清、结构化，并形成可验收的契约。
- **B3** 分层与接口契约让系统各部分可以独立理解、替换与验证；耦合点就是维护成本的主要来源。
- **B4** 接口契约是前后端协作的边界，代码是最终口径，文档必须与代码一致。
- **B5** 安全与权限是系统的固有属性，必须在设计阶段划定边界，而不是等漏洞出现后打补丁。
- **B6** 测试与部署把“本机能跑”变成“可交付”，反馈速度决定迭代质量。
- **B7** 容器化把运行环境从口头约定变成可复现的交付物。

### 2. 持久理解（U1–U7）

- **U1** 学生将理解：软件工程的价值不在于多写代码，而在于用可验证的过程把需求、技术与协作中的不确定性逐步收敛为可交付的系统。（B1）
- **U2** 学生将理解：需求文档不是交差材料，而是开发、测试与验收三方共用的契约；需求越模糊，后期返工的自由度越小。（B2）
- **U3** 学生将理解：分层与接口契约使系统的各部分可以独立理解、替换和验证，耦合点就是维护成本的来源。（B3）
- **U4** 学生将理解：接口契约（URL、方法、状态码、数据格式）是前后端并行开发的共同语言，任何一方偏离契约都会在联调时集中暴露。（B4）
- **U5** 学生将理解：认证回答“你是谁”、授权回答“你能做什么”，安全边界必须在设计时划定，补丁式补救代价更高。（B5）
- **U6** 学生将理解：测试与部署不是开发的附属环节，而是把“本机能跑”转化为“可交付、可观测”系统的必要条件。（B6）
- **U7** 学生将理解：容器化把运行环境从口头约定变成可复现的交付物，“在我机器上能跑”由此变成可验证的承诺。（B7）

### 3. 核心问题（Q1–Q5）

- **Q1** 一个“能用”的程序与一个“可交付”的系统之间差什么？
- **Q2** 当用户说不清需求时，工程师如何把模糊表述变成可开发、可验收的条目？
- **Q3** 如何划分模块与接口，使前后端可以并行开发，后期修改又不至于推倒重来？
- **Q4** 如何证明系统“做对了”——从单元测试到部署后的健康检查，证据链怎么建立？
- **Q5** 课时与资源有限时，哪些工程实践必须坚持，哪些可以裁剪而不伤及质量？

### 4. 迁移目标（T1–T4）

- **T1** 学生能在教材未直接教过的业务场景（如器材借还管理）中完成需求获取、用户故事与验收标准、模块与接口设计，并产出可评审的需求与设计文档。
- **T2** 学生能在一个未随书讲解的 FastAPI 项目中定位某业务模块的接口、数据模型与业务规则，说明其分层与调用链，并按新需求完成增量修改与测试补齐。
- **T3** 学生能依据一份未在书中演练过的接口文档，设计 Streamlit 页面完成数据读取、展示与编辑，并处理加载、空数据与错误状态。
- **T4** 学生能把一个前后端分离的应用部署到新的容器环境，通过环境变量与端口映射完成配置，并用日志与健康检查定位一次启动或联调失败。
