**已会**：第 2 章的用户故事、验收标准三个检查与 MoSCoW 优先级。
**本章只加**：需求文档——把散落的需求组织成开发、测试、验收三方共用的契约。
**关系**：第 2 章解决“一条需求怎么写”；本章解决“几十条需求怎样放在一起，还能互相对得上”。

上一章解决的是“一条需求怎么写”。一个系统有几十条需求，分散在访谈记录、聊天消息和几个人的脑子里；开发、测试和验收三方各拿一份不同的理解，问题就会在联调时集中爆发。

## 本章要解决的问题

**怎样让需求文档成为开发、测试、验收三方共用的契约，而不是交差材料？**

同一批需求，开发读作任务清单，测试读作检查依据，验收读作付款条件。缺少一份共同的文件，三方各自保留一份理解，看起来都完成了，合起来却对不上。

本章把上一章的方法用一遍：整理功能清单、排优先级、补验收标准与非功能需求，最后通过评审落稿，重点是把文档真正写出来。

## 本章学习目标

读完第 3 章并完成实训后，你应该能：

1. 说明开发、测试、验收三方分别从需求文档里取什么，并按“背景与角色、功能清单、用户故事与验收标准、非功能需求、约束与假设”五个部分组织正文（另附文档信息）。
2. 把一条业务描述写成“动词 + 对象”的功能条目，标注 Must / Should / Could / Won’t 并给出理由。
3. 为关键功能写出“给定—当—则（Given-When-Then）”形式的验收标准。
4. 检查需求文档内部的角色、术语、字段与优先级是否一致，并组织一次可执行的评审。
5. 按教学模拟数据口径编写需求文档中的人员、部门与联系方式示例。

## 3.1 需求文档的读者

聊天记录回答“谁在什么时候说了什么”，需求文档回答“系统要做什么、做到什么程度算完成、依据是什么”。前者是过程材料，后者是契约。需求文档（Requirements Document）的正式名称是**需求规格说明书**（Software Requirements Specification，SRS），它把分散的条目组织成一份可评审、可交接、可追溯的材料。

契约的价值在于**同一份材料能被不同角色各取所需**：

| 读者 | 从文档里取什么 | 取不到会怎样 |
| --- | --- | --- |
| 开发 | 功能边界、角色权限、字段与约束 | 边写边猜，接口与表结构反复改 |
| 测试 | 验收标准、异常情况、非功能指标 | 只能测“点得通”，边界与异常靠运气 |
| 验收 | 本期范围、Must 条目、完成定义 | 争论“这算不算做完”，无法签字 |

因此，需求文档至少要做到三件事：说清边界，说清条目，说清验收。边界回答“做什么、不做什么”；条目回答“每一项功能是什么、优先级如何”；验收回答“怎样算完成”。缺了任何一件，文档就会退化成一份愿望清单。

> 💡 **易错点**：把需求文档写成“项目介绍”。读者读完知道了系统很重要、背景很宏大，却仍然不知道第一期要交哪几个功能、每个功能做到什么程度算完成。

## 3.2 需求文档的结构

一份可评审的需求文档，正文通常包含五个部分。结构不必死板，但这五块对应的信息不能缺；文档开头另附一段**文档信息**（版本、日期、编写人、修订说明），用来追溯每一版改了什么。

| 部分 | 写什么 | 合格标准 |
| --- | --- | --- |
| 背景与角色 | 系统解决什么问题、给谁用、不做什么；谁使用、谁被管理、各自能做什么、能看哪些数据 | 能说清系统边界（System Boundary）与角色权限 |
| 功能清单 | 按业务域组织的“动词 + 对象”条目，每条标注优先级 | 覆盖主要业务流程，条目可验证 |
| 用户故事与验收标准 | 关键功能的角色、功能、价值，以及“给定—当—则” | 每条 Must 功能都有可执行的验收标准 |
| 非功能需求 | 性能、安全与保密、可用性、兼容性、可靠性 | 每条可度量 |
| 约束与假设 | 技术栈、部署环境、时间人员限制、前提条件 | 能判断方案是否可行 |

```mermaid

    A[问清<br/>访谈与观察] --> B[写清<br/>清单与故事]
    B --> C[评清<br/>评审与修订]
    C --> D[落稿<br/>版本与记录]
    C -. 发现问题 .-> B
```

*图 3-1：需求文档的编写闭环*

图中四步是一个循环而不是一条直线：先问清业务，再写成清单与故事，评审后落稿定版；评审发现的问题会退回「写清」重做。下面按五部分依次说明，实训 3-1 再完整走一遍。

**背景与角色**

背景与角色不是“项目简介”，而是边界的声明。它要回答三个问题：这个系统解决什么业务问题；给哪些角色使用；本期明确不做什么。

“不做什么”尤其重要。没有它，评审时每个人都按自己的想象补充范围，开发到后期才发现做多了或做偏了。把 Won’t 写进文档，等于提前把范围争议摆到桌面上。

角色表要区分两类人：一类是系统的使用者，例如值班员、管理员；另一类是业务中被管理或记录的对象，例如被排班的人员。两者可能重叠，但职责不同。每个角色至少写清三件事：主要操作、数据权限、不能做什么。数据权限是需求文档里最容易被漏掉的一栏，却直接决定后面的认证与授权设计。例如“普通用户只能查看本部门数据”就是一条必须写进需求、并在测试中验证的约束。

**功能清单：动词加对象**

**功能清单**的写法是“动词 + 对象”，例如“新增值班记录”“查询部门列表”“校验时间冲突”。这样写有两个好处：一是能直接对应到接口或操作，二是能暴露“页面清单”式的伪需求。

按业务域（Business Domain）分组，可以让读者看出主流程是否完整。一个值班系统的业务域通常包括登录与账号、部门、人员、工位、值班、查班、统计。分组之后逐域检查：每个域的主要操作是否都有对应条目？有没有把“页面”当成“功能”？

> 💡 **易错点**：功能清单写成“部门管理、人员管理、值班管理”。这不是功能，是模块名。读的人不知道“管理”具体包含哪些操作，也无法判断做到什么程度算完成。

**功能优先级**

文档里的每条功能都要标 Must / Should / Could / Won't，并写一句理由。判定标准与第 2 章 2.6 相同：如果本期不做这一条，哪条业务流程会断？会断的才是 Must；能用人工或现有工具替代的，通常是 Should 或 Could。文档层面只多要求一件事：理由要写在条目旁边，评审时才有讨论依据。

**用户故事与验收标准**

用户故事的写法沿用第 2 章 2.4，验收标准的三个检查沿用 2.5；文档里统一把关键功能的验收标准写成“给定—当—则”，便于测试直接执行：

- **给定**某个前置条件；
- **当**执行某个操作；
- **则**系统产生某个可观察的结果。

例如：“给定部门与起止日期，当值班管理员查询值班记录，则列表返回该范围内的记录，并显示日期、时段、值班人员与工位。”这条标准可以被测试直接执行，也可以被验收人员直接判断。

**约束与假设**

约束与假设记录外部条件：必须使用的技术栈、部署环境、时间与人员限制、必须遵守的规范；以及“部门与人员的基础数据由管理员提前维护”这类前提。假设一旦不成立，方案就要重评，所以它必须写出来。

## 3.3 非功能需求的量化

**非功能需求**覆盖性能、安全与保密、可用性、兼容性和可靠性。它们的共同要求是“可度量”。

| 类别 | 要写什么 | 示例 |
| --- | --- | --- |
| 性能 | 响应时间、数据量、并发 | 1000 条值班记录下列表查询 2 秒内返回 |
| 安全与保密 | 认证、授权、审计、模拟数据占位显示 | 未登录不能访问；普通用户只能看本部门数据；联系方式以 138****0000 形式占位显示 |
| 可用性 | 操作步骤、错误提示、学习成本 | 常用操作不超过 3 步；错误提示说明原因和处理办法 |
| 兼容性 | 浏览器、分辨率、网络环境 | 支持 Chrome/Edge 最新版；内网环境可离线部署 |
| 可靠性 | 数据备份、故障恢复 | 每日自动备份；异常退出后数据不丢失 |

量化不是给每条需求硬凑一个数字，而是回答“用什么条件、看什么结果，能判断它达标”。如果一个指标无法在测试中构造出对应条件，通常说明它还太模糊。

**指标的选择范围**

一份文档里的非功能需求越多，后续测试与验收的成本越高。可以按三个条件筛选：**影响主流程**（如登录失败不能泄露密码是否存在）、**影响安全边界**（如越权访问）、**影响交付环境**（如内网离线部署）。三条都不满足的指标，放到后续迭代，不占用本期的验收精力。

> 💡 **易错点**：把“系统要稳定、安全”写进非功能需求就以为完成了。没有条件、没有指标，测试无法设计用例，验收也无法判断通过与否。

## 3.4 需求评审清单

需求文档最常见的质量问题不是“写少了”，而是“前后对不上”：角色表里有“查班人员”，用户故事里却把查班操作写给了管理员；功能清单里有“导入导出”，却找不到对应的用户故事；正文叫“值班记录”，图表里叫“值班单”。

因此，落稿前要做四项一致性检查：角色名全文一致；功能清单与用户故事能一一对应；术语与字段名一致；交叉引用（编号、章节）指向真实存在的条目。**评审**清单就是把这四项检查固定下来，让不同的人按同一套标准看文档。

| 检查项 | 要问的问题 | 常见缺陷 |
| --- | --- | --- |
| 角色一致 | 角色表里的每个角色，是否在功能与故事里出现，权限是否写清 | 列了角色却没有权限说明 |
| 功能可验收 | 每条功能是否写成“动词 + 对象”，是否有优先级与理由 | 名词清单、全部 Must |
| 故事能对应 | 每条关键功能是否有用户故事与验收标准 | 功能清单与故事对不上 |
| 指标可度量 | 非功能需求是否给出条件与指标 | “稳定、安全、好用” |
| 术语与引用一致 | 同一对象是否只有一个叫法，编号是否指向真实条目 | “值班记录”与“值班单”混用 |

评审意见要具体、可执行。“写得不错”“再完善一下”不是评审意见；“功能清单未使用动词加对象，建议把‘部门管理’拆成查询、新增、修改、删除四条”才是。每条意见都要有处理结果：采纳、不采纳及理由，形成闭环。

**一个反例**

某份文档的角色表写着“值班员、管理员、查班人员”，功能清单有“新增查班记录”，用户故事却写成“作为管理员，我想要新增查班记录”。读者无法判断查班记录到底该由谁创建：如果由查班人员创建，故事的角色错了；如果由管理员创建，角色表里的“查班人员”就多余。这个问题不靠通读发现，靠的是逐项对照角色表、功能清单与故事。

> 💡 **易错点**：把评审做成“集体通读一遍”。通读只能发现语句问题；一致性缺陷要靠清单逐项对照，尤其是角色、字段与编号。

## 示范例题

#### 例 3-1：把访谈记录整理成功能清单与优先级【Bloom：应用】

**题目**：下面是某值班系统的访谈记录片段。请据此写出“功能清单与优先级”一节，列出 5 条功能，标注 MoSCoW 并各写一句理由。

> 值班管理员每天要排班，最怕两个人排到同一时段；值班记录现在记在纸上，月底统计要靠人翻；查班记录也分散；人员调动后，联系方式经常对不上。

**解**：

| 编号 | 业务域 | 功能 | 优先级 | 理由 |
| --- | --- | --- | --- | --- |
| F-01 | 值班 | 新增值班记录 | Must | 没有它无法记录值班，主流程走不通 |
| F-02 | 值班 | 查询值班记录 | Must | 排班核对与月底统计都依赖查询 |
| F-03 | 值班 | 校验同一人员同一时段重复值班 | Should | 很重要，但首期可先人工核对 |
| F-04 | 统计 | 按月份统计值班次数 | Should | 替代手工翻纸，首期可先导出后人工汇总 |
| F-05 | 查班 | 新增查班记录 | Could | 有更好；首期可沿用纸质记录，上线后再迁移 |

理由说明：每条功能都写成“动词 + 对象”；Must 只保留不写就无法走通主流程的两条；Should 与 Could 都给出了首期的替代办法，符合 MoSCoW 的判定标准。访谈记录中的“联系方式对不上”暂不进入本期功能，可在背景与目标中记为已知问题，避免范围膨胀。

#### 例 3-2：评审一份需求文档片段【Bloom：分析】

**题目**：下面是某需求文档片段。请按评审清单指出至少三处问题，并说明每条对应评审清单的哪一项。

> **3 功能需求**
>
> 系统要有部门管理、人员管理、工位管理、值班管理、查班管理、统计、登录、权限、导入导出、消息提醒。
>
> **用户故事**
>
> 作为管理员，我想要管理所有数据，以便系统正常运行。
>
> 验收标准：系统要好用、响应快。

**解**：

1. **功能清单写成名词清单**：没有使用“动词 + 对象”，也没有按业务域分组和标注优先级。对应清单项“功能清单按动词加对象编写，覆盖主要业务流程”。
2. **用户故事缺角色、功能与价值**：“管理员”过于宽泛，“管理所有数据”没有边界，“系统正常运行”不是价值。对应清单项“用户故事有明确的角色、功能与价值”。
3. **验收标准不可验证**：“好用、响应快”没有条件、没有指标，无法判断通过与否。对应清单项“验收标准可验证，覆盖正常、边界、异常”。
4. **缺少优先级**：十项功能没有 MoSCoW，无法判断本期范围。对应清单项“MoSCoW 划分合理，Must 有理由”。
5. **范围可能膨胀**：“消息提醒”未说明是否属于本期，背景与目标也未写“不做什么”。对应清单项“背景与目标说清了系统边界”。

答出其中任意三处即可；每处都要指出问题与对应清单项，不能只写“写得不清楚”。

## 教学模拟数据的写法

本书出现的值班记录、器材借还、人员与证件号等**全部是教学模拟数据，与真实单位和人员无关**（见前言「关于书中的数据」）。练习里不需要、也不应该把真实业务数据带进需求文档：既养成职业习惯，也避免把与课程无关的信息写进作业和提交记录。

落到文档上有三条可检查的写法：

| 场景 | 教学模拟数据写法 | 不要这样写 |
| --- | --- | --- |
| 人员姓名 | 张同学、李同学、编号 U-001 | 真实姓名 |
| 联系方式 | `138****0000` 等占位格式 | 完整手机号 |
| 部门与编号 | 第一值班组、D-01 | 真实机构名称与编号 |

## ◆ 实训 3-1：需求文档编写（对应课次 3 · 2 学时）

### 一、任务目标与验收

| 目标 | 验收标志 |
| --- | --- |
| 正文五部分齐全 | 背景与角色、功能清单、用户故事与验收标准、非功能需求、约束与假设齐备，另有文档信息 |
| 功能清单可执行 | 每条为“动词+对象”，带优先级与理由 |
| 关键功能有验收标准 | 至少 5 条“给定—当—则” |
| 文档内部一致 | 角色、字段、优先级无冲突 |
| 评审记录完整 | 列出问题、责任人与修改结论 |

### 二、课前准备

- 第 2 章产出的用户故事与利益相关者清单
- duty 系统的业务背景材料（教学模拟数据）
- 一份空白评审记录表

### 三、操作步骤

1. **搭文档骨架**
   - 做什么：新建需求文档文件并立起五部分正文与文档信息
   - 操作：新建 `需求文档.md`，先写文档信息表，再写入「背景与角色、功能清单、用户故事与验收标准、非功能需求、约束与假设」五个二级标题
   - 预期输出：→ 文档信息表 + 五个二级标题齐备，顺序与 3.2 结构表一致
   - 做错会看到什么：只有功能清单，缺背景与约束；回到本节结构表补齐
2. **写功能与优先级**
   - 做什么：把业务描述拆成功能条目并排序
   - 操作：逐条写成「动词＋对象」，每条标 Must / Should / Could / Won’t 并附一句理由
   - 预期输出：→ 每条一行，优先级可解释
   - 做错会看到什么：把“要好看”写成功能；改为可验收的非功能需求
3. **写验收标准**
   - 做什么：为 5 条关键功能写可判定的验收标准
   - 操作：每条按「给定—当—则」写清前置条件、动作与可观察结果
   - 预期输出：→ 验收人能据此判断通过／不通过
   - 做错会看到什么：只写“正常显示”；补输入、动作与可观察结果
4. **评审与修订**
   - 做什么：交换文档做一次评审并记录处理结论
   - 操作：两人交换，按 3.4 的评审清单逐项打勾，记录问题、责任人与结论
   - 预期输出：→ 评审记录含问题、责任人、结论
   - 做错会看到什么：评审变成互相夸奖；按“缺失、冲突、不可验证”三类找问题

### 四、排错清单

| 现象 | 先查什么 |
| --- | --- |
| 功能条目无法验收 | 缺少对象、条件或结果，改成“动词+对象+可观察结果” |
| 优先级全是 Must | 回到 MoSCoW 定义，Must 只留“不做就不能上线”的 |
| 验收标准写成实现步骤 | 写外部可观察行为，不写内部函数调用 |
| 文档前后字段名不一致 | 用全文搜索统一术语，必要时建术语表 |

### 五、提交与验收

提交 `需求文档.md` 与评审记录；验收按“结构完整”“可验收性”“一致性”三项检查。

### 六、课后扩展

- 把评审记录里的问题按“阻断开发/影响验收/可延后”分级
- 为文档补一张角色—功能权限表
- 用 3.4 的评审清单再自查一遍
- **复习任务**：回看第 2 章 2.4（用户故事）与 2.5（验收标准），对照本章 3.2（五部分结构）与 3.4（一致性检查），把本章文档中对应的条目各找出一处并核对

## 本章小结

**核心结论**：

1. 需求文档是开发、测试与验收三方共用的契约，必须说清边界、条目和验收。
2. 正文按五个部分组织：背景与角色、功能清单、用户故事与验收标准、非功能需求、约束与假设；开头另附文档信息。
3. 功能清单用“动词 + 对象”写，按业务域分组；Must 的判定标准是“不做则主流程走不通”。
4. 用户故事要写清角色、功能、价值；验收标准用“给定—当—则”，覆盖正常、边界与异常。
5. 非功能需求必须可度量；落稿前要做角色、功能、术语与交叉引用的一致性检查，并按教学模拟数据口径处理人员、部门与联系方式示例。

把这章压缩成一句话：**需求文档不是把需求抄一遍，而是让三方拿同一份材料，各自找得到自己要的判断依据。**

**本章不引入**：IEEE 830 全文、需求管理工具、需求追踪矩阵。这些在后续课程或工程环境中按需了解。

**学完本章，你可以体会到**：需求文档不是写给老师看的作业，而是让开发、测试、业务三方少吵几次架的共用底稿。
