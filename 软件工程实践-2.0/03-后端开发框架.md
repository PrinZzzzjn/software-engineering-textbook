# 第 3 章 后端开发框架

第 2 章把模糊的愿望整理成可验收的条目，条目描述的是系统对外承诺的行为。承诺要变成运行中的行为，还需要一层结构接住每一次请求，让约定在代码里只写一次。

本章以 FastAPI 为例，观察这层结构站在请求与业务代码之间的什么位置。

## 本章要解决的问题

**一个后端开发框架替开发者完成了哪些工作？如何用它把接口约定转化为可运行、可校验、可核对的接口？**

接口契约写在文档里，只是一组约定。约定不会自己执行：若每个接口都各自接收请求、各自判断失败，同样的工作就会一遍遍重复，错误也散落在各处，阅读者看不出哪些是约定、哪些是例外。

本章观察一个请求从进入框架到抵达业务代码之间经历了什么：哪些约定被强制执行，哪些失败在何处被拦下。

## 本章学习目标

读完本章，应能：

1. 说明后端开发框架处理的重复工作，以及接口契约在其中的位置。
2. 拆解一次请求与响应，按 2xx / 4xx / 5xx 判断责任方，并区分 401、403、422 的排查方向。
3. 说明 FastAPI 的定位与路由机制：装饰器、`APIRouter` 与两段前缀。
4. 写出一个资源的 GET / POST / PUT / DELETE 四种方法对应的五个端点，并说明各自的成功与失败状态码。
5. 用 Pydantic 定义输入与输出模型，解释 422 与 `response_model` 的作用。
6. 用 `HTTPException` 表达规则性失败，区分 400、404 与 422 的分工。

## 3.1 接口与契约

Web 应用按部署位置分为三层：前端负责显示与交互，后端负责接收请求、处理业务并返回数据，数据库负责持久化存储。前端与后端通常由不同人员开发，二者协作的共同依据是接口。

后端处理一次请求分为五个步骤：接收请求、读取并校验参数、执行规则、读写数据、按契约返回。后续各节分别展开其中的约定、校验与错误返回。

**接口**是前端调用后端能力的方式。接口不是单个函数，而是一组双方共同遵守的规则，规定请求地址、请求方法、数据格式、成功响应与失败响应。

**接口契约**是接口提供方与调用方达成的可验证约定，内容包括调用方式、数据格式、错误行为与兼容演进。完整契约包含五项：

1. 请求地址与请求方法；
2. 请求数据的字段、位置与类型；
3. 成功响应的结构；
4. 失败响应的状态码与说明；
5. 接口升级时保持兼容的方式。

契约的用途是核对、测试与追责，不是供人阅读的说明文字。契约可以写在 Markdown 文档、代码注释或 **OpenAPI** 等机器可读规范中；FastAPI 根据路由与模型自动生成 OpenAPI 文档，`/docs` 是其可视化版本。

框架将契约转化为程序：**路由**将地址与方法映射到函数，**输入模型**校验数据，**异常处理**返回约定的错误，**依赖注入**复用公共逻辑。

契约是约定的应然状态，代码是当前的实然状态。二者不一致时，应先记录差异，包括差异项、期望值与实际值，再判断修改哪一方；不应默认以代码为准。

一个模块通常包含多个接口，其命名与返回格式应保持一致。该问题属于模块级设计，见第 4 章 4.3。

> 💡 **易错点**：将接口约定保存在聊天记录中。聊天记录没有版本、没有固定位置，也不能被测试或文档引用。契约应写入接口文档或 `/docs`，且只保留一份。

## 3.2 请求与响应

浏览器与服务器之间使用 HTTP（HyperText Transfer Protocol）通信。一次 HTTP 交互由**请求**与**响应**组成：前端发送请求，后端返回响应。按 RFC 9110 的消息结构，请求由方法、请求目标、头部与可选正文组成；响应由状态码、响应头与响应体组成。以下按这七个部分说明。

**请求行：方法与目标**

常用的 HTTP 方法有四个。方法不仅是书写习惯，还包含语义约定：

| 方法 | 语义 | 是否幂等 | 成功状态码 | 典型操作 |
| --- | --- | --- | --- | --- |
| GET | 查询 | 是，且安全 | 200 | 查询列表或单个资源 |
| POST | 新增 | 否 | 201 | 在集合中新增一个资源 |
| PUT | 修改 | 是 | 200 | 修改或整体替换单个资源 |
| DELETE | 删除 | 是 | 204 | 删除单个资源 |

按 RFC 9110，**安全**指不改变服务器状态；**幂等**指同一请求重复执行多次，服务器最终状态与执行一次相同。GET 安全且幂等；PUT 与 DELETE 幂等，但不安全；POST 既不保证安全，也不保证幂等。

因此，用 GET 执行删除属于危险设计：浏览器、缓存与爬虫均可能重复发起 GET。删除必须使用 DELETE，使方法语义与实际影响一致。

同一资源由方法与 URL 共同定位。以下五组写法构成一个资源的完整操作：

| 操作 | 方法与 URL | 成功状态码 |
| --- | --- | --- |
| 查询列表 | `GET /departments` | 200 |
| 查询单个 | `GET /departments/D001` | 200 |
| 新增 | `POST /departments` | 201 |
| 修改 | `PUT /departments/D001` | 200 |
| 删除 | `DELETE /departments/D001` | 204 |

请求目标是请求行中的路径部分，通常以 URL（统一资源定位符）表示。`/departments` 指向单位集合。完整形式还包含协议、主机与端口（如 `http://127.0.0.1:8000/...`），但主机与端口由部署环境决定，本章只写路径。

同一地址既可以指向集合，也可以指向集合中的成员：

| 写法 | 指向 | 典型用途 |
| --- | --- | --- |
| `/departments` | 单位集合 | 查询列表、新增 |
| `/departments/D001` | 集合里的一个成员 | 查询、修改、删除编码为 D001 的单位 |

`/D001` 是路径中的取值，其含义与写法见第 4 章 4.3。

**请求头与请求正文**

头部字段存放请求的附加信息，不直接参与业务数据。初学阶段需认识以下两个字段：

| 头部 | 作用 | 例子 |
| --- | --- | --- |
| `Authorization` | 证明“我是谁” | `Authorization: Bearer <令牌>` |
| `Content-Type` | 说明正文是什么格式 | `Content-Type: application/json` |

无正文的 GET 请求通常不需要 `Content-Type`；带 JSON 正文的 POST / PUT 请求应写 `application/json`。认证头部的完整用法见第 8 章，本章只需了解其存在。

正文是请求的可选部分，用于提交新增或修改所需的数据。带正文的请求通常使用 **JSON**（JavaScript Object Notation），格式见 RFC 8259。JSON 的结构与 Python 的字典、列表接近：

```json
{"dept_code": "D001", "full_name": "一中队", "address": "一号营区"}
```

正文的字段名属于接口契约，前后端必须使用同一套命名。正文校验在 3.5 由 Pydantic 模型完成。

一次请求中的数据可能位于四个位置，初学时容易混淆：

| 数据位置 | 典型用途 | 首次出现 |
| --- | --- | --- |
| 路径参数 `/departments/D001` | 定位某一个资源 | 3.4 |
| 查询参数 `?page=1&page_size=10` | 筛选、分页、排序 | 例 3-1 |
| 请求头 `Authorization` | 认证信息 | 3.2 |
| 请求体 JSON | 新增或修改的字段 | 3.4 |

四类数据在 FastAPI 中均由函数参数接收，写法见 3.3、3.5；接口组如何分配参数见第 4 章 4.3。

**响应状态码**

**状态码**使调用方在读取响应体之前判断结果类别。初学阶段应掌握以下状态码：

| 状态码 | 含义 | 谁的问题 | 典型场景 |
| --- | --- | --- | --- |
| 200 | 成功 | — | 查询、修改成功 |
| 201 | 已创建 | — | 新增成功 |
| 204 | 成功但无返回体 | — | 删除成功 |
| 400 | 请求格式错误 | 调用方 | JSON 语法错误、业务规则不满足 |
| 401 | 未认证 | 调用方 | 没登录或令牌无效 |
| 403 | 无权限 | 调用方 | 已登录但无权访问该资源 |
| 404 | 未找到 | 调用方 | URL 或资源不存在 |
| 422 | 内容校验失败 | 调用方 | 类型不对、必填项缺失 |
| 500 | 服务器内部错误 | 服务方 | 未捕获的异常 |

状态码按首位数字分为五类：1xx 信息、2xx 成功、3xx 重定向、4xx 调用方问题、5xx 服务方问题（RFC 9110）；本章只涉及 2xx、4xx、5xx。分类的作用是划分责任：4xx 应先检查前端提交内容，5xx 应先检查服务端日志。若所有错误均返回 500，双方都将失去排查线索。

401 表示身份未确认，403 表示身份已确认但权限不足。二者混用会导致前端无法判断应转向登录页还是提示无权限。422 表示请求内容不符合约定，在进入业务代码前由校验拦截，不属于服务器故障。422 不在 RFC 9110 的核心状态码表中，来自 WebDAV（RFC 4918）；FastAPI 借用其表示请求体校验失败。

失败由哪一层抛出，可参照下表。该表区分输入校验与业务规则，是后续模块判断错误码的依据：

| 失败类型 | 状态码 | 谁负责 | 例子 |
| --- | --- | --- | --- |
| 输入不符合约定 | 422 | Pydantic | 缺字段、类型不对 |
| 未登录或令牌失效 | 401 | 认证依赖 | 请求头没有令牌 |
| 已登录但无权限 | 403 | 权限依赖 | 普通用户调用管理接口 |
| 资源不存在 | 404 | service 或 crud | 单位编码查不到 |
| 业务规则不满足 | 400 | service | 编码重复、时间冲突 |

**响应头与响应体**

响应头存放响应的附加信息。例如 `Content-Type: application/json` 说明响应体为 JSON。多数业务代码无需主动设置，FastAPI 会按返回内容自动补充；缓存、跨域等头部将在后续章节按需出现。

响应体是服务器返回的数据，通常为 JSON。单位列表的响应示例如下：

```json
{
  "items": [
    {"dept_code": "D001", "full_name": "一中队", "address": "一号营区"},
    {"dept_code": "D002", "full_name": "二中队", "address": "二号营区"}
  ],
  "total": 2
}
```

`items` 为本页数据，`total` 为总条数。分页接口通常同时返回这两个字段，前端据此计算总页数。响应体字段名属于接口契约，前后端必须使用同一套命名，例如统一使用 `full_name`，不混用 `departmentName`。

部分响应没有响应体：204 表示成功但无返回内容，删除接口常用该状态码。此时调用方只读取状态码。

> 💡 **易错点**：新增成功与失败均返回 200，仅在响应体中写 `{"success": false}`。调用方必须解析响应体才能判断结果，缓存、重试与错误监控均会失效。状态码的用途正是向这些环节传递结果。

## 3.3 FastAPI 与路由

FastAPI 是基于 Python 的 Web 接口框架。为说明其作用，可先分析不使用框架时需完成的工作：监听端口；解析 HTTP 请求行与头部；将 URL 与方法匹配到函数；从查询串与请求体取值；检查类型；将返回值转换为 JSON；捕获异常并确定状态码；编写接口文档。上述工作在每个接口中重复出现，且容易遗漏。框架统一完成这些公共工作，开发者只需声明 URL 对应的函数、输入类型与输出结构。

FastAPI 的定位是接口优先：参数校验写在函数签名中，接口文档自动生成。与 Django、Flask 等 Python Web 框架相比，FastAPI 更强调以类型注解描述输入输出，并据此生成 OpenAPI 文档。

本章按框架承担的职责分析 FastAPI，三项机制如下：

- **路由**：将 URL 与 HTTP 方法映射到函数；
- **数据**：用 Pydantic 模型校验输入并控制输出；
- **错误**：用 `HTTPException` 表达规则性失败。

复用公共逻辑的 `Depends` 在第 4 章 4.5 随查询参数一并讲。

**应用的启动**

**代码 3-3-1** · 命令（Bash）

```bash
uvicorn main:app --reload --port 8000
```

命令中，`main` 为文件名（`main.py`），`app` 为文件中创建的应用变量。uvicorn 是 ASGI 服务器，负责监听端口、接收 HTTP 请求并交给 FastAPI 应用处理。`--reload` 仅用于开发环境，文件修改后自动重启；部署时不应使用。启动后访问 `http://127.0.0.1:8000/docs`，即可查看 3.1 所述 OpenAPI 文档的可视化版本；本章示例均可在此验证。

**从装饰器到 APIRouter**

**代码 3-3-2** · `main.py`（最小应用，Python）

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/hello/{name}")
def hello(name: str):
    return {"message": f"你好，{name}"}
```

上述代码包含三个新要素。`app = FastAPI()` 创建应用对象，它是所有路由的挂载点。`@app.get("/hello/{name}")` 是**装饰器**：它将下方函数登记到 `app`，规则为收到对 `/hello/xxx` 的 GET 请求时调用该函数，并将 `xxx` 传给 `name`。装饰器是 Python 的语法：在函数定义前加一行 `@xxx`，表示将该函数交给 `xxx` 登记或包装。用于路由时，URL 与函数写在同一位置。

`name: str` 中的冒号后为**类型注解**，标明变量或返回值的预期类型。注解不改变运行结果，但 FastAPI 会读取注解，先完成类型转换与校验，再进入函数体；校验失败时返回 422，机制见 3.5。FastAPI 接口的函数签名通常均需类型注解。

方法写在装饰器上：`@app.get` 登记 GET，`@app.post` 登记 POST，`@app.put` 登记 PUT，`@app.delete` 登记 DELETE。同一个 URL 配上不同方法，就是不同接口；方法与 URL 的组合才构成完整地址。

项目规模扩大后，数十个接口全部挂在 `app` 上，会使 `main.py` 成为过长文件。**APIRouter** 是模块级的挂载点：各业务模块分别创建 `router` 并登记本模块接口，主文件再通过 `include_router` 将其组装到 `app`。

**代码 3-3-3** · `routers.py`（路由文件，Python）

```python
from fastapi import APIRouter

router = APIRouter(prefix="/departments", tags=["单位"])

@router.get("")
def list_departments():
    return {"items": [], "total": 0}
```

**代码 3-3-4** · `main.py`（组装，Python）

```python
from fastapi import FastAPI

from routers import router as departments_router

app = FastAPI()

app.include_router(departments_router, prefix="")
```

后续章节中的 `@router.get(...)` 所使用的 `router` 并非独立定义：它由模块顶部的 `APIRouter(...)` 创建，最终由 `main.py` 的 `include_router` 挂入应用。两段前缀相加，该列表接口的完整路径为 `/departments`；`tags` 不影响 URL，只决定 `/docs` 中的分组名。该创建—挂载链路是第 4 章模块模板的核心动作：每个模块对应一个 controller 文件，`main.py` 只负责组装。

将路由拆分到模块的目的不是增加文件数量，而是缩小变更影响范围。新增业务模块时，只需新增一个 router 文件并在 `main.py` 登记一行；修改某模块的 URL 前缀时，只需修改该模块顶部的 `prefix`。若全部路由写在 `main.py`，每次修改均需打开同一文件，冲突与遗漏的概率随之上升。

> 💡 **易错点**：在 `/docs` 中遇到 404 时，首先怀疑接口实现有误。多数情况是前缀未完整拼接：模块 `prefix` 与 `include_router` 的 `prefix` 均需计入，缺少任一段都会少一级路径。

**同步端点与异步端点**

FastAPI 支持普通函数与 `async def` 两种端点，二者执行位置不同：`def` 端点由框架放入线程池执行；`async def` 端点在事件循环上执行。若在 `async def` 端点中调用阻塞函数（例如 `time.sleep` 或同步数据库驱动），事件循环将被占用，全部请求均被延迟，而不只是当前请求。

本章示例统一使用 `def`。示例服务的并发量低，同步端点已经够用；仅当需要处理大量并发 I/O，且所用库提供异步版本时，才应使用 `async def`；此时函数体内不得包含阻塞调用。

## 3.4 一个资源的四个方法

3.2 说明了四种方法的语义与状态码，3.3 说明了如何登记路由。本节把两者合起来：用一个内存字典充当数据存储，为“单位”资源写出五个端点，覆盖查询列表、查询单个、新增、修改与删除。

数据先放在一个内存字典里：进程重启后内容清空，每个请求看到的都是同一份数据。

**代码 3-4-1** · `main.py`（一个资源的五个接口，Python）

```python
from fastapi import FastAPI, HTTPException, status

app = FastAPI()

DEPARTMENTS = {
    "D001": {"dept_code": "D001", "full_name": "一中队", "address": "一号营区"},
}


@app.get("/departments")
def list_departments():
    return {"items": list(DEPARTMENTS.values()), "total": len(DEPARTMENTS)}


@app.get("/departments/{dept_code}")
def get_department(dept_code: str):
    if dept_code not in DEPARTMENTS:
        raise HTTPException(status_code=404, detail="单位不存在")
    return DEPARTMENTS[dept_code]


@app.post("/departments", status_code=status.HTTP_201_CREATED)
def create_department(data: dict):
    dept_code = data.get("dept_code")
    full_name = data.get("full_name")
    if not dept_code or not full_name:
        raise HTTPException(status_code=400, detail="缺少必填字段")
    if dept_code in DEPARTMENTS:
        raise HTTPException(status_code=400, detail="单位编码已存在")
    DEPARTMENTS[dept_code] = {
        "dept_code": dept_code,
        "full_name": full_name,
        "address": data.get("address"),
    }
    return DEPARTMENTS[dept_code]


@app.put("/departments/{dept_code}")
def update_department(dept_code: str, data: dict):
    if dept_code not in DEPARTMENTS:
        raise HTTPException(status_code=404, detail="单位不存在")
    item = DEPARTMENTS[dept_code]
    if "full_name" in data:
        item["full_name"] = data["full_name"]
    if "address" in data:
        item["address"] = data["address"]
    return item


@app.delete("/departments/{dept_code}", status_code=status.HTTP_204_NO_CONTENT)
def delete_department(dept_code: str):
    if dept_code not in DEPARTMENTS:
        raise HTTPException(status_code=404, detail="单位不存在")
    del DEPARTMENTS[dept_code]
```

**五个端点与参数位置**

五个端点共用同一个资源地址，靠方法与路径区分：

| 操作 | 方法与 URL | 参数位置 | 成功 | 失败 |
| --- | --- | --- | --- | --- |
| 查询列表 | `GET /departments` | 无（本章不分页） | 200 | — |
| 查询单个 | `GET /departments/{dept_code}` | 路径参数 | 200 | 404 |
| 新增 | `POST /departments` | 请求体 | 201 | 400 |
| 修改 | `PUT /departments/{dept_code}` | 路径参数 + 请求体 | 200 | 404 |
| 删除 | `DELETE /departments/{dept_code}` | 路径参数 | 204 | 404 |

这里由函数手写字段检查，失败返回 400；使用输入模型后，同类失败改由框架返回 422。**400 不是输入校验的正式口径**，它只保留给“格式正确但业务不允许”的情况。

**请求与结果的对照**

启动应用后，可在 `/docs` 中逐条验证。下表给出一组可复现的请求与结果：

| 请求 | 结果 |
| --- | --- |
| `GET /departments` | 200，返回 `items` 与 `total` |
| `GET /departments/D001` | 200，返回 D001 的记录 |
| `GET /departments/D404` | 404，`detail` 为“单位不存在” |
| `POST /departments`，正文 `{"dept_code": "D002", "full_name": "二中队"}` | 201，返回新建记录 |
| 重复提交同一 `dept_code` | 400，`detail` 为“单位编码已存在” |
| `PUT /departments/D001`，正文 `{"full_name": "一中队（改）"}` | 200，`full_name` 已更新 |
| `DELETE /departments/D002` | 204，无响应体 |
| 再次 `DELETE /departments/D002` | 404，资源已不存在 |

**幂等性与 DELETE 的语义**

GET、PUT、DELETE 是幂等的，POST 不是：

- 重复 `GET /departments/D001`，结果与服务器状态均不变。
- 重复 `PUT /departments/D001` 提交同一正文，最终记录相同。
- 第一次 `DELETE /departments/D002` 返回 204，第二次返回 404；两次执行后服务器状态相同，都是“该单位不存在”。**幂等看的是服务器状态，不是响应码**。
- 重复 `POST` 会再次创建，或因编码重复返回 400；服务器状态可能改变，因此 POST 不幂等。

若把删除写成 `GET /departments/delete?dept_code=D001`，浏览器预取、缓存刷新或爬虫都可能重复触发删除。GET 的语义是“读取”，一旦它改变状态，调用方与中间环节都无法按语义判断后果。DELETE 的语义明确，重复调用也只会得到“不存在”，风险可控。

> 💡 **易错点**：认为“删除返回 404 就说明 DELETE 不幂等”。幂等性判断的是执行后的服务器状态，不是每次响应的状态码。第一次删除后资源已不存在，第二次返回 404 正是幂等的表现。

## 3.5 输入与输出模型

**用 Pydantic 声明输入**

3.4 的新增接口在函数体内逐项检查字段。若再增加人员、器材两个资源，同样的检查要再写两遍；字段增多时，遗漏一项即可能让非法数据进入业务逻辑。此外，检查只存在于函数体内，接口文档与调用方均不可见。

FastAPI 使用 **Pydantic** 接收请求体：以类声明字段名称、类型与约束，Pydantic 将 JSON 转换为类实例；类型不符、字段缺失或超出范围时，返回结构化错误信息。

- **BaseModel** 是 Pydantic 的基类。模型继承 BaseModel 后，获得校验、类型转换、序列化（`model_dump()`）与生成文档的能力。
- **Field** 为单个字段添加约束与说明。`min_length`、`max_length` 限制长度；`examples` 会出现在自动生成的接口文档中；第一个参数为 `...`（Ellipsis）时表示该字段必填，无默认值。
- **类型注解**（如 `full_name: str`）是模型的核心。Pydantic 根据注解决定转换与校验方式；FastAPI 将注解写入 OpenAPI 文档。

先看一个最小示例：

**代码 3-5-1** · `main.py`（最小输入模型，Python）

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()


class Greeting(BaseModel):
    name: str = Field(..., min_length=1, max_length=20)


@app.post("/hello")
def hello(data: Greeting):
    return {"message": f"你好，{data.name}"}
```

`data: Greeting` 表示从请求体读取 JSON，按 `Greeting` 解析后传入函数。提交 `{"name": ""}` 时，`name` 违反 `min_length=1`，请求在进入函数前返回 422；`detail.loc` 指向 `["body", "name"]`，可直接定位字段。

422 不是函数体抛出的异常，而是进入函数前的前置校验结果：请求体按模型解析，字段缺失或类型不符时由框架直接返回 422，函数体不执行。函数体只需判断模型无法表达的规则，即业务规则。

3.4 的单位新增接口改用模型后，函数体中的手写检查随之删除：

**代码 3-5-2** · `schema.py`（输入模型，Python）

```python
from pydantic import BaseModel, Field


class DepartmentCreate(BaseModel):
    dept_code: str = Field(..., min_length=2, max_length=20)
    full_name: str = Field(..., min_length=2, max_length=100)
    address: str | None = Field(default=None, max_length=500)
```

**代码 3-5-3** · 用模型重写新增接口（Python）

```python
from fastapi import HTTPException, status

from schema import DepartmentCreate


@app.post("/departments", status_code=status.HTTP_201_CREATED)
def create_department(data: DepartmentCreate):
    if data.dept_code in DEPARTMENTS:
        raise HTTPException(status_code=400, detail="单位编码已存在")
    DEPARTMENTS[data.dept_code] = data.model_dump()
    return DEPARTMENTS[data.dept_code]
```

提交 `{"dept_code": "D"}` 时，请求在进入函数前返回 422，响应 `detail` 指明字段及违反的约束。编码重复属于“参数符合约定但业务不允许”，仍在函数内由 `HTTPException` 返回 400。**422 与 400 的分界，正是“输入不符合约定”与“业务规则不满足”的分界。**

**输入与输出要分开**

输入模型负责接收数据，输出模型负责返回数据，二者可以不同。输入可能包含密码与确认密码，输出只需用户名与 id；输入可接受内部字段，输出不得包含内部字段。最小对照如下：

```python
class GreetingOut(BaseModel):
    message: str
```

在接口上声明 `response_model=GreetingOut` 后，FastAPI 在返回前按模型过滤字段。用户表的 `password_hash` 不得出现在响应中；若直接返回数据库对象，新增字段可能导致敏感信息泄露。

单位接口的输出模型只保留公开字段：

**代码 3-5-4** · `schema.py`（输出模型，Python）

```python
from pydantic import BaseModel, ConfigDict


class DepartmentOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    dept_code: str
    full_name: str
    address: str | None = None


class DepartmentPage(BaseModel):
    items: list[DepartmentOut]
    total: int
```

**代码 3-5-5** · 用输出模型声明返回结构（Python）

```python
from schema import DepartmentPage


@app.get("/departments", response_model=DepartmentPage)
def list_departments():
    items = list(DEPARTMENTS.values())
    return {"items": items, "total": len(items)}
```

`response_model` 的过滤属于 OWASP API Security 所列的过度数据暴露防护，第 8 章起反复使用。

## 3.6 规则性失败

422 由 Pydantic 自动处理。资源不存在、编码重复等规则性失败，则需在函数中主动结束请求，并给出状态码与说明：

**代码 3-6-1** · 主动返回规则性失败（Python）

```python
from fastapi import HTTPException


@app.get("/departments/{dept_code}")
def get_department(dept_code: str):
    if dept_code not in DEPARTMENTS:
        raise HTTPException(status_code=404, detail="单位不存在")
    return DEPARTMENTS[dept_code]
```

该例中 `dept_code` 类型符合约定，不触发 422；但编码不存在，属于参数符合约定而资源不存在的情况，使用 `HTTPException` 返回 404。二者分工对应 3.2 的责任表：**422 表示参数不符合约定，`HTTPException` 表示参数符合约定但业务不允许或资源不存在**。前者在进入函数前发生，后者在函数内发生，二者均不得以 500 代替。404、401、403、400 均使用 `HTTPException`；422 交由 Pydantic 处理，不手动抛出。

失败应在进入业务逻辑前或规则判断处结束，不得落入 500。例如单位编码重复时，由 service 抛出 `HTTPException(400, ...)`；普通用户删除他人单位时，由权限依赖抛出 403。上述情况均不属于参数校验。

> 💡 **易错点**：使用 `HTTPException(422)` 手动抛出参数错误。422 应由模型校验自然产生；手动抛出会使“谁在何种条件下拒绝请求”失去统一位置，排查时无法区分模型约束与业务规则。

#### 例 3-3：判断操作对应的方法、参数位置与状态码

**题目**：图书管理需要四个操作：查询图书列表、新增一本图书、修改某本图书的信息、删除某本图书。请分别为它们写出方法、URL 框架、参数位置与成功状态码，并指出哪几个操作是幂等的。

**解**：

| 操作 | 方法 | URL 框架 | 参数位置 | 成功状态码 | 幂等 |
| --- | --- | --- | --- | --- | --- |
| 查询列表 | GET | `/books` | 查询参数（分页、筛选） | 200 | 是 |
| 新增图书 | POST | `/books` | 请求体 | 201 | 否 |

3. 查询、修改、删除重复执行后服务器状态不变，是幂等的；新增重复执行会创建多条记录，不是幂等的。

#### 例 3-4：补一条业务规则并判断状态码

**题目**：在 3.4 的单位应用中，新增单位时除了检查编码重复，还要检查“单位全称不得重复”。请写出检查代码，并说明为什么该失败返回 400，而不是 422 或 404。

**解**：

**代码 3-4-2** · 新增接口中的两条规则（Python）

```python
@app.post("/departments", status_code=status.HTTP_201_CREATED)
def create_department(data: dict):
    dept_code = data.get("dept_code")
    full_name = data.get("full_name")
    if not dept_code or not full_name:
        raise HTTPException(status_code=400, detail="缺少必填字段")
    if dept_code in DEPARTMENTS:
        raise HTTPException(status_code=400, detail="单位编码已存在")
    if any(item["full_name"] == full_name for item in DEPARTMENTS.values()):
        raise HTTPException(status_code=400, detail="单位全称已存在")
    DEPARTMENTS[dept_code] = {
        "dept_code": dept_code,
        "full_name": full_name,
        "address": data.get("address"),
    }
    return DEPARTMENTS[dept_code]
```

1. 编码与全称的重复检查都在函数体内，属于业务规则，不是字段格式问题。
2. 返回 400 的理由：请求的格式与字段都符合约定，只是业务上不允许重复；400 表示“请求本身有问题，但问题不在字段格式”。
3. 不返回 422：422 由 Pydantic 在进入函数前产生，只处理类型、必填与长度一类字段约束；重复需要查询已有数据，模型看不到这些数据。
4. 不返回 404：404 表示“要操作的资源不存在”，而新增的目标资源尚不存在，语义不符。
5. 使用模型后，字段缺失改由 422 返回，函数体只保留这两条重复检查；3.5 的写法即为最终形态。

   - 做错会看到什么：204 仍带 JSON 正文；检查函数是否返回了内容。
4. **用 `/docs` 制造失败（15 分钟）**
   - 做什么：提交缺字段或类型不符的正文，观察当前写法返回 400；再与 3.5 的模型写法对照，说明改为模型后会变成 422。
   - 预期输出：能说清 400 与 422 的分工。
   - 做错会看到什么：把所有失败都归为 400；回到 3.2 的责任表。
5. **填写记录表（10 分钟）**
   - 做什么：把五个端点的正常与失败请求逐行填入记录表。
   - 预期输出：四种成功与失败状态码各至少一行。
   - 做错会看到什么：只记录了成功路径；补齐 404 与字段错误两行。
6. **提交（5 分钟）**
   - 做什么：整理代码与记录表，按教师要求提交。
   - 预期输出：代码可重新启动，记录表与 `/docs` 行为一致。

### 四、排错清单

| 现象 | 先查什么 |
| --- | --- |
| 所有接口 404 | 装饰器路径是否与访问路径一致；是否漏写方法 |
| 新增返回 307 | URL 末尾斜杠不一致；统一集合地址的写法 |
| 删除返回 200 且带正文 | 装饰器是否声明 `status_code=204`；函数是否返回了内容 |

| 字段错误返回 500 | 是否直接索引不存在的键；改用 `data.get(...)` 或模型 |

## 本章小结

**核心结论**：

1. **后端开发框架**将路由、校验、错误返回与公共逻辑复用收为统一约定；**接口契约**是前后端共同约定的 URL、方法、输入、输出与错误码。
2. 请求由方法、请求目标（URL）、头部与可选正文组成；响应由状态码、响应头与响应体组成。HTTP 方法具有语义：GET 安全且幂等，PUT 与 DELETE 幂等，POST 不幂等。
3. 状态码按 2xx / 4xx / 5xx 划分：2xx 成功，4xx 调用方问题，5xx 服务方问题。401 表示身份未确认，403 表示权限不足，422 表示参数校验失败。
4. 路由由装饰器登记方法与 URL，`APIRouter` 将路由拆到模块；模块前缀与挂载前缀相加构成完整路径。
5. 一个资源的五个端点由方法与 URL 共同区分：查询 200、新增 201、修改 200、删除 204；资源不存在返回 404。DELETE 重复执行后服务器状态不变，因此是幂等的。
6. 422 由 Pydantic 在进入函数前产生；400、404 等规则性失败由 `HTTPException` 在函数内产生。依赖注入在第 4 章 4.5 随查询参数与六文件实现一并讲。

本章可概括为：**契约将前端需求与后端响应写成双方可核对的约定，框架将该约定转化为可运行、可校验、可替换的服务。**

**先导概念与后续展开**：下表列出本章先使用、后续展开的概念，便于查阅。本章的五个端点按模块分层组织见第 4 章 4.5；工程目录与文件内容见第 5 章 5.1。

| --- | --- | --- | --- |
| 令牌 | 登录后签发的凭证，服务端用字典记录“令牌属于谁” | 第 8 章 8.2 | 第 8、12、13 章 |
