# 第 3 章 后端开发框架

> **节首信息条**｜**专题二第 1 章**｜对应课次 3 · 2 学时 · 理论讲授｜前置：第 1–2 章

本章进入专题二：后端服务开发。

Web 后端需要重复完成四类工作：将不同请求地址映射到处理函数；校验请求数据是否符合约定；按约定返回成功或失败结果；复用数据库连接、登录校验等公共逻辑。若每个接口均独立实现这四类工作，代码会重复，错误也会分散。**后端开发框架**将上述工作收为统一约定：开发者只编写业务函数，框架负责接收请求、校验数据、序列化 JSON、处理错误，并生成接口文档。

本章以 FastAPI 为例。3.1–3.2 说明接口契约与 HTTP 的基本约定；3.3–3.6 分析框架的四项机制；最后以路由、输入模型与依赖注入各一个最小示例，说明机制之间的配合。

## 本章要解决的问题

**一个后端开发框架替开发者完成了哪些工作？如何用它把接口约定转化为可运行、可校验、可核对的接口？**

接口契约在文档中只是一组约定。程序要按契约运行，还需完成四项工作：将请求地址映射到函数；拦截不符合约定的输入；按语义返回错误；复用公共逻辑。缺任一项，服务只能启动，不能按契约工作。

## 本章学习目标

读完本章，应能：

1. 说明后端开发框架处理的重复工作，以及接口契约在其中的位置。
2. 拆解一次请求与响应，按 2xx / 4xx / 5xx 判断责任方，并区分 401、403、422 的排查方向。
3. 说明 FastAPI 的定位，以及四项机制各自解决的问题：装饰器路由与 `APIRouter`、Pydantic 输入模型、`Depends`、`HTTPException`。
4. 用路由与输入模型示例说明机制的配合方式，并解释 422 与 `HTTPException` 的分工。
5. 启动 FastAPI 应用并打开 `/docs`，说明 `def` 与 `async def` 的执行位置差异及适用场景。
6. 用 `Depends` 抽取重复的请求前置逻辑，说明其执行时机与职责边界。

## 3.1 接口与契约

Web 应用按部署位置分为三层：前端负责显示与交互，后端负责接收请求、处理业务并返回数据，数据库负责持久化存储。前端与后端通常由不同人员开发，二者协作的共同依据是接口。

后端处理一次请求分为五个步骤：接收请求、读取并校验参数、执行规则、读写数据、按契约返回。本章按这五个步骤展开框架的能力。

**接口**是前端调用后端能力的方式。接口不是单个函数，而是一组双方共同遵守的规则，规定请求地址、请求方法、数据格式、成功响应与失败响应。

**接口契约**是接口提供方与调用方达成的可验证约定，内容包括调用方式、数据格式、错误行为与兼容演进。完整契约包含五项：

1. 请求地址与请求方法；
2. 请求数据的字段、位置与类型；
3. 成功响应的结构；
4. 失败响应的状态码与说明；
5. 接口升级时保持兼容的方式。

契约的用途是核对、测试与追责，不是供人阅读的说明文字。

契约可采用三种载体：Markdown 文档、代码注释，或 **OpenAPI** 等机器可读规范。OpenAPI 描述每条接口的路径、方法、参数、请求体与响应；FastAPI 根据路由与模型自动生成该文档，`/docs` 是其可视化版本。

框架将契约转化为程序：**路由**将地址映射到函数，**输入模型**校验数据，**异常处理**返回约定的错误，**依赖注入**复用公共逻辑（3.6）。3.4–3.6 依次说明这四项机制。

契约是约定的应然状态，代码是当前的实然状态。二者不一致时，应先记录差异，包括差异项、期望值与实际值，再判断修改哪一方；不应默认以代码为准。

一个模块通常包含多个接口，其命名与返回格式应保持一致。该问题属于模块级设计，见第 4 章 4.4。

> 💡 **易错点**：将接口约定保存在聊天记录中。聊天记录没有版本、没有固定位置，也不能被测试或文档引用。契约应写入接口文档或 `/docs`，且只保留一份。

## 3.2 请求与响应

浏览器与服务器之间使用 HTTP（HyperText Transfer Protocol）通信。一次 HTTP 交互由**请求**与**响应**组成：前端发送请求，后端返回响应。按 RFC 9110 的消息结构，请求由方法、请求目标、头部与可选正文组成；响应由状态码、响应头与响应体组成。以下按这七个部分说明。

**请求：方法**

常用的 HTTP 方法有四个：

| 方法 | 语义 | 例子 |
| --- | --- | --- |
| GET | 查询 | 查询部门列表 |
| POST | 新增 | 新增一个部门 |
| PUT | 修改 | 修改部门名称 |
| DELETE | 删除 | 删除一个部门 |

HTTP 方法不仅表示书写习惯，还包含语义约定。按 RFC 9110，GET 应是安全的（不改变服务器状态）且幂等的（重复调用结果一致）；PUT 与 DELETE 通常也应幂等；POST 通常不保证幂等。因此，用 GET 执行删除属于危险设计：浏览器、缓存与爬虫均可能重复发起 GET。

**请求：请求目标**

请求目标是请求行中的路径部分，通常以 URL（统一资源定位符）表示。`/api/v1/departments/` 指向部门集合。完整形式还包含协议、主机与端口（如 `http://127.0.0.1:8000/...`），但主机与端口由部署环境决定，本章只写路径。

同一地址既可以指向集合，也可以指向集合中的成员：

| 写法 | 指向 | 典型用途 |
| --- | --- | --- |
| `/api/v1/departments/` | 部门集合 | 查询列表、新增 |
| `/api/v1/departments/1` | 集合里的一个成员 | 查询、修改、删除 id 为 1 的部门 |

`/1` 是路径中的取值，其含义与写法见第 4 章 4.4。

**请求：头部**

头部字段存放请求的附加信息，不直接参与业务数据。初学阶段需认识以下两个字段：

| 头部 | 作用 | 例子 |
| --- | --- | --- |
| `Authorization` | 证明“我是谁” | `Authorization: Bearer <令牌>` |
| `Content-Type` | 说明正文是什么格式 | `Content-Type: application/json` |

无正文的 GET 请求通常不需要 `Content-Type`；带 JSON 正文的 POST/PUT 请求应写 `application/json`。认证头部的完整用法见第 6 章，本章只需了解其存在。

**请求：正文**

正文是请求的可选部分，用于提交新增或修改所需的数据。带正文的请求通常使用 **JSON**（JavaScript Object Notation），格式见 RFC 8259。JSON 的结构与 Python 的字典、列表接近：

```json
{"dept_code": "D01", "dept_name": "一中队"}
```

正文的字段名属于接口契约，前后端必须使用同一套命名。正文校验在 3.5 由 Pydantic 模型完成。

一次请求中的数据可能位于四个位置，初学时容易混淆：

| 数据位置 | 典型用途 | 首次出现 |
| --- | --- | --- |
| 路径参数 `/departments/1` | 定位某一个资源 | 3.4 |
| 查询参数 `?page=1&page_size=10` | 筛选、分页、排序 | 例 3-1 |
| 请求头 `Authorization` | 认证信息 | 3.2 |
| 请求体 JSON | 新增或修改的字段 | 3.5 |

四类数据在 FastAPI 中均由函数参数接收，写法见 3.4、3.5；接口组如何分配参数见第 4 章 4.4。

**响应：状态码**

**状态码**使调用方在读取响应体之前判断结果类别。初学阶段应掌握以下状态码：

| 状态码 | 含义 | 谁的问题 | 典型场景 |
| --- | --- | --- | --- |
| 200 | 成功 | — | 查询、修改成功 |
| 201 | 已创建 | — | 新增成功 |
| 204 | 成功但无返回体 | — | 删除成功 |
| 400 | 请求格式错误 | 调用方 | JSON 语法错误、缺少必要字段 |
| 401 | 未认证 | 调用方 | 没登录或令牌无效 |
| 403 | 无权限 | 调用方 | 已登录但无权访问该资源 |
| 404 | 未找到 | 调用方 | URL 或资源不存在 |
| 422 | 内容校验失败 | 调用方 | 类型不对、必填项缺失 |
| 500 | 服务器内部错误 | 服务方 | 未捕获的异常 |

状态码按首位数字分为五类：1xx 信息、2xx 成功、3xx 重定向、4xx 调用方问题、5xx 服务方问题（RFC 9110）；本章只涉及 2xx、4xx、5xx。分类的作用是划分责任：4xx 应先检查前端提交内容，5xx 应先检查服务端日志。若所有错误均返回 500，双方都将失去排查线索。

401 表示身份未确认，403 表示身份已确认但权限不足。二者混用会导致前端无法判断应转向登录页还是提示无权限。422 表示请求内容不符合约定，在进入业务代码前由校验拦截，不属于服务器故障。422 不在 RFC 9110 的核心状态码表中，来自 WebDAV（RFC 4918）；FastAPI 借用其表示请求体校验失败。

失败由哪一层抛出，可参照下表。该表区分输入校验与业务规则，是后续模块判断错误码的依据：

| 失败类型 | 状态码 | 谁负责 | 例子 |
| --- | --- | --- | --- |
| 输入不符合约定 | 422 | Pydantic | 缺字段、类型不对 |
| 未登录或令牌失效 | 401 | 认证依赖 | 请求头没有令牌 |
| 已登录但无权限 | 403 | 权限依赖 | 普通用户调用管理接口 |
| 资源不存在 | 404 | service 或 crud | 部门编码查不到 |
| 业务规则不满足 | 400 | service | 编码重复、时间冲突 |

**响应：响应头**

响应头存放响应的附加信息。例如 `Content-Type: application/json` 说明响应体为 JSON。多数业务代码无需主动设置，FastAPI 会按返回内容自动补充；缓存、跨域等头部将在后续章节按需出现。

**响应：响应体**

响应体是服务器返回的数据，通常为 JSON。部门列表的响应示例如下：

```json
{
  "items": [
    {"id": 1, "dept_code": "D01", "dept_name": "一中队"},
    {"id": 2, "dept_code": "D02", "dept_name": "二中队"}
  ],
  "total": 2
}
```

`items` 为本页数据，`total` 为总条数。分页接口通常同时返回这两个字段，前端据此计算总页数。响应体字段名属于接口契约，前后端必须使用同一套命名，例如统一使用 `dept_name`，不混用 `departmentName`。

部分响应没有响应体：204 表示成功但无返回内容，删除接口常用该状态码。此时调用方只读取状态码。

> 💡 **易错点**：新增成功与失败均返回 200，仅在响应体中写 `{"success": false}`。调用方必须解析响应体才能判断结果，缓存、重试与错误监控均会失效。状态码的用途正是向这些环节传递结果。

## 3.3 FastAPI 是什么

FastAPI 是基于 Python 的 Web 接口框架。为说明其作用，可先分析不使用框架时需完成的工作：监听端口；解析 HTTP 请求行与头部；将 URL 匹配到函数；从查询串与请求体取值；检查类型；将返回值转换为 JSON；捕获异常并确定状态码；编写接口文档。上述工作在每个接口中重复出现，且容易遗漏。框架统一完成这些公共工作，开发者只需声明 URL 对应的函数、输入类型与输出结构。

FastAPI 的定位是接口优先：参数校验写在函数签名中，接口文档自动生成。与 Django、Flask 等 Python Web 框架相比，FastAPI 更强调以类型注解描述输入输出，并据此生成 OpenAPI 文档。

本章按框架承担的职责分析 FastAPI，四项机制如下：

- **路由**：将 URL 与 HTTP 方法映射到函数；
- **数据**：用 Pydantic 模型校验输入并控制输出；
- **错误**：用 `HTTPException` 表达规则性失败；
- **复用**：用 `Depends` 抽取公共逻辑。

3.4 说明路由，3.5 说明数据与错误，3.6 说明复用。

**应用的启动**

**代码 3-3-1** · 命令（Bash）

```bash
uvicorn main:app --reload --port 8000
```

命令中，`main` 为文件名（`main.py`），`app` 为文件中创建的应用变量。uvicorn 是 ASGI 服务器，负责监听端口、接收 HTTP 请求并交给 FastAPI 应用处理。`--reload` 仅用于开发环境，文件修改后自动重启；部署时不应使用。启动后访问 `http://127.0.0.1:8000/docs`，即可查看 3.1 所述 OpenAPI 文档的可视化版本；3.4 起的示例均可在此验证。

**同步端点与异步端点**

FastAPI 支持普通函数与 `async def` 两种端点，二者执行位置不同：`def` 端点由框架放入线程池执行；`async def` 端点在事件循环上执行。由此产生一项约束：若在 `async def` 端点中调用阻塞函数（例如 `time.sleep` 或同步数据库驱动），事件循环将被占用，全部请求均被延迟，而不只是当前请求。

本章示例统一使用 `def`。教学环境并发压力较小，且可减少概念层次。仅当需要处理大量并发 I/O，且所用库提供异步版本时，才应使用 `async def`；此时函数体内不得包含阻塞调用。

第 5 章将该应用放入完整工程目录，第 21 章以后将其打包进容器。

## 3.4 装饰器路由与 APIRouter

**代码 3-4-1** · `main.py`（最小应用，Python）

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/hello/{name}")
def hello(name: str):
    return {"message": f"你好，{name}"}
```

上述代码包含三个新要素。`app = FastAPI()` 创建应用对象，它是所有路由的挂载点。`@app.get("/hello/{name}")` 是**装饰器**：它将下方函数登记到 `app`，规则为收到对 `/hello/xxx` 的 GET 请求时调用该函数，并将 `xxx` 传给 `name`。装饰器是 Python 的语法：在函数定义前加一行 `@xxx`，表示将该函数交给 `xxx` 登记或包装。用于路由时，URL 与函数写在同一位置。本章不要求自行编写装饰器，只需理解 `@xxx` 表示函数被登记。

`name: str` 中的冒号后为**类型注解**，标明变量或返回值的预期类型。注解不改变运行结果，但 FastAPI 会读取注解，先完成类型转换与校验，再进入函数体；校验失败时返回 422，机制见 3.5。FastAPI 接口的函数签名通常均需类型注解。

**APIRouter：将路由拆分到模块**

项目规模扩大后，数十个接口全部挂在 `app` 上，会使 `main.py` 成为过长文件。**APIRouter** 是模块级的挂载点：各业务模块分别创建 `router` 并登记本模块接口，主文件再通过 `include_router` 将其组装到 `app`。

**代码 3-4-2** · `routers.py`（路由文件，Python）

```python
from fastapi import APIRouter

router = APIRouter(prefix="/departments", tags=["部门"])

@router.get("")
def list_departments():
    return {"items": [], "total": 0}
```

**代码 3-4-3** · `main.py`（组装，Python）

```python
from fastapi import FastAPI

from routers import router as departments_router

app = FastAPI()

app.include_router(departments_router, prefix="/api/v1")
```

后续章节中的 `@router.get(...)` 所使用的 `router` 并非独立定义：它由模块顶部的 `APIRouter(...)` 创建，最终由 `main.py` 的 `include_router` 挂入应用。两段前缀相加，该列表接口的完整路径为 `/api/v1/departments`；`tags` 不影响 URL，只决定 `/docs` 中的分组名。该创建—挂载链路是第 4 章模块模板的核心动作：每个模块对应一个 controller 文件，`main.py` 只负责组装。

将路由拆分到模块的目的不是增加文件数量，而是缩小变更影响范围。新增业务模块时，只需新增一个 router 文件并在 `main.py` 登记一行；修改某模块的 URL 前缀时，只需修改该模块顶部的 `prefix`。若全部路由写在 `main.py`，每次修改均需打开同一文件，冲突与遗漏的概率随之上升。

> 💡 **易错点**：在 `/docs` 中遇到 404 时，首先怀疑接口实现有误。多数情况是前缀未完整拼接：模块 `prefix` 与 `include_router` 的 `prefix` 均需计入，缺少任一段都会少一级路径。

## 3.5 输入模型与规则性失败

**输入模型的必要性**

请求体并非零散的键值，而是具有名称与约束的结构。新增部门需提交 `dept_code` 与 `dept_name`，二者均为字符串，具有长度范围，且均不可缺失。若不使用模型，则需在函数中手写检查：

```python
if "dept_code" not in data: ...
if not isinstance(data["dept_code"], str): ...
if len(data["dept_code"]) < 2: ...
```

上述检查在每个接口中重复出现，遗漏一项即可能使非法数据进入业务逻辑。此外，检查仅存在于函数体内，接口文档与调用方均不可见。模型将请求体的结构声明在一处，由框架统一解析、校验并生成文档。

**Pydantic、BaseModel 与 Field**

FastAPI 使用 **Pydantic** 接收请求体：以类声明字段名称、类型与约束，Pydantic 将 JSON 转换为类实例；类型不符、字段缺失或超出范围时，返回结构化错误信息。

- **BaseModel** 是 Pydantic 的基类。模型继承 BaseModel 后，获得校验、类型转换、序列化（`model_dump()`）与生成文档的能力。
- **Field** 为单个字段添加约束与说明。`min_length`、`max_length` 限制长度；`examples` 会出现在自动生成的接口文档中；第一个参数为 `...`（Ellipsis）时表示该字段必填，无默认值。
- **类型注解**（如 `name: str`）是模型的核心。Pydantic 根据注解决定转换与校验方式；FastAPI 将注解写入 OpenAPI 文档。

**最小示例**

以下示例不含业务含义，用于说明机制：

**代码 3-5-1** · `main.py`（最小输入模型，Python）

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()


class Greeting(BaseModel):
    name: str = Field(..., min_length=1, max_length=20)


@app.post("/hello")
def hello(data: Greeting):
    return {"message": f"你好，{data.name}"}
```

`data: Greeting` 表示从请求体读取 JSON，按 `Greeting` 解析后传入函数。提交 `{"name": ""}` 时，`name` 违反 `min_length=1`，请求在进入函数前返回 422；`detail.loc` 指向 `["body", "name"]`，可直接定位字段。

422 不是函数体抛出的异常，而是进入函数前的前置校验结果：请求体按模型解析，字段缺失或类型不符时由框架直接返回 422，函数体不执行。函数体只需判断模型无法表达的规则，即业务规则。

**项目中的输入模型**

项目中的模型仅将字段替换为业务字段，写法相同：

**代码 3-5-2** · `schemas.py`（输入模型，Python）

```python
from pydantic import BaseModel, Field


class DepartmentCreate(BaseModel):
    dept_code: str = Field(..., min_length=2, max_length=10)
    dept_name: str = Field(..., min_length=2, max_length=50)
```

`...` 表示必填；`min_length`、`max_length` 为约束。将模型写入函数签名后，框架按模型读取并校验请求体：

```python
@router.post("")
def create_department(data: DepartmentCreate):
    return data
```

提交 `{"dept_code": "D"}` 时，请求在进入函数前返回 422，响应 `detail` 指明字段及违反的约束。

**输入模型与输出模型的分离**

输入模型负责接收数据，输出模型负责返回数据，二者可以不同。输入可能包含密码与确认密码，输出只需用户名与 id；输入可接受内部字段，输出不得包含内部字段。最小对照如下：

```python
class GreetingOut(BaseModel):
    message: str
```

在接口上声明 `response_model=GreetingOut` 后，FastAPI 在返回前按模型过滤字段。用户表的 `password_hash` 不得出现在响应中；若直接返回数据库对象，新增字段可能导致敏感信息泄露。

部门接口的输出模型仅保留公开字段：

**代码 3-5-3** · 输出模型与 `response_model`（节选，Python）

```python
class DepartmentOut(BaseModel):
    id: int
    dept_code: str
    dept_name: str

@router.get("/{dept_id}", response_model=DepartmentOut)
def read_department(dept_id: int):
    ...
```

`response_model` 的过滤属于 OWASP API Security 所列的过度数据暴露防护，第 6 章起反复使用。

**Optional 与 Literal 的用法**

`Optional[int] = None` 表示该参数不填时不过滤；`Literal["admin", "normal"]` 将取值限定在固定集合内。两种写法将在第 7、11 章出现，此处只需了解形式。

**HTTPException 与规则性失败**

422 由 Pydantic 自动处理。资源不存在、无权限等规则性失败，则需在函数中主动结束请求，并给出状态码与说明：

**代码 3-5-4** · 主动返回规则性失败（Python）

```python
from fastapi import HTTPException

ITEMS = {1: {"id": 1, "name": "扳手"}}


@app.get("/items/{item_id}")
def read_item(item_id: int):
    if item_id not in ITEMS:
        raise HTTPException(status_code=404, detail="器材不存在")
    return ITEMS[item_id]
```

该例中 `item_id` 类型符合约定，不触发 422；但 id 不存在，属于参数符合约定而业务不允许的情况，使用 `HTTPException` 返回 404。二者分工对应 3.2 责任表：**422 表示参数不符合约定，`HTTPException` 表示参数符合约定但业务不允许**。前者在进入函数前发生，后者在函数内发生，二者均不得以 500 代替。404、401、403、400 均使用 `HTTPException`；422 交由 Pydantic 处理，不手动抛出。

失败应在进入业务逻辑前或规则判断处结束，不得落入 500。例如部门编码重复时，由 service 抛出 `HTTPException(400, ...)`；普通用户删除他人部门时，由权限依赖抛出 403。上述情况均不属于参数校验。

> 💡 **易错点**：使用 `HTTPException(422)` 手动抛出参数错误。422 应由模型校验自然产生；手动抛出会使“谁在何种条件下拒绝请求”失去统一位置，排查时无法区分模型约束与业务规则。

## 3.6 依赖注入：Depends

**重复的前置逻辑**

列表接口需读取分页参数，数据库接口需获取会话，受保护接口需确认当前用户。上述工作每次请求均须完成，且涉及多个接口。各接口分别实现时，修改一处即需修改多处，遗漏一处即减少一道检查。

**机制**

FastAPI 使用**依赖注入**消除此类重复：将请求进入函数前必须完成的工作写成普通函数，再通过 `Depends` 声明在参数默认值上。框架在处理请求前调用该函数，并将返回值传入接口函数。

依赖可以嵌套，即一个依赖自身也可以声明依赖；测试时还可通过 `app.dependency_overrides` 替换，本章不展开。

**最小示例**

**代码 3-6-1** · 依赖注入最小示例（Python）

```python
from fastapi import Depends, FastAPI

app = FastAPI()


def page_params(page: int = 1, page_size: int = 10):
    return {"page": page, "page_size": page_size}


@app.get("/items")
def list_items(params: dict = Depends(page_params)):
    return {"page": params["page"], "page_size": params["page_size"], "items": []}
```

`page` 与 `page_size` 仍来自查询串，其名称与类型写在依赖签名中。访问 `/items` 返回第 1 页、每页 10 条；访问 `/items?page=abc` 时，`abc` 无法转换为 `int`，请求在进入 `list_items` 前返回 422。函数体内不含取值与检查代码。

**依赖的职责边界**

依赖只承担准备与拦截：读取参数、获取会话、确认当前用户、拒绝无权限请求。业务规则仍属于 service（第 4 章 4.5）。若将编码是否重复等判断放入依赖，422 与 400 的分工将重新模糊。

项目中依赖注入有三处应用：数据库会话 `get_db`（第 6 章 6.1）、认证依赖（第 6 章 6.5）与权限依赖（第 7 章 7.2）。

> 💡 **易错点**：依赖的返回值缺少类型注解，或将业务判断放入依赖。前者使接口获得的类型与文档不一致；后者使进入函数前的检查与函数内的业务判断混合，排查时无法区分 422 与 400。

## 示范例题

#### 例 3-1：读一条请求与响应【Bloom：理解】

**题目**：下面是一条 HTTP 请求和对应的响应。请指出方法、URL、查询参数、状态码和响应体，并说明该操作的内容。

```text
GET /api/v1/departments/?page=1&page_size=10 HTTP/1.1

200 OK
{"items": [...], "total": 5}
```

**解**：

1. 方法为 `GET`，表示查询，不改变服务器状态。
2. URL 为 `/api/v1/departments/`，指向部门资源集合。
3. `page=1` 与 `page_size=10` 是**查询参数**（Query Parameter），位于 URL 问号之后，用于筛选、分页或排序；此处表示第 1 页、每页 10 条。
4. 状态码为 `200 OK`，表示请求成功。
5. 响应体为 JSON，包含 `items`（本页记录）与 `total`（总条数）。
6. 该操作查询部门列表第 1 页，每页 10 条，并返回总条数供前端计算页数。

#### 例 3-2：用 Pydantic 模型接收请求体【Bloom：应用】

**题目**：为“新增器材”接口定义输入模型：`device_code` 必填，2–20 个字符；`device_name` 必填，2–50 个字符。写出模型与接口，并说明提交 `{"device_code": "E", "device_name": "投影仪"}` 时的结果。

**解**：

**代码 3-2-1** · `schemas.py`（输入模型，Python）

```python
from pydantic import BaseModel, Field


class DeviceCreate(BaseModel):
    device_code: str = Field(..., min_length=2, max_length=20)
    device_name: str = Field(..., min_length=2, max_length=50)
```

**代码 3-2-2** · `devices.py`（新增接口，Python）

```python
@router.post("", status_code=201)
def create_device(data: DeviceCreate):
    return data
```

1. `DeviceCreate` 继承 `BaseModel`；两个字段的 `...` 表示必填，`min_length`、`max_length` 给出长度约束。
2. 接口参数声明为 `data: DeviceCreate`，FastAPI 据此从请求体读取 JSON 并按模型校验。
3. 提交 `{"device_code": "E", "device_name": "投影仪"}` 时，`device_code` 仅 1 个字符，违反 `min_length=2`，返回 422。
4. `detail` 中 `loc` 指向 `["body", "device_code"]`，`type` 为 `string_too_short`，可定位具体字段；校验在进入函数前完成，函数体不执行。
5. 合法请求返回 201；若声明 `response_model`，返回时按输出模型过滤字段。输入与输出必须分别定义。

#### 例 3-3：将重复的取参逻辑抽取为依赖【Bloom：应用】

**题目**：下面的三个列表接口分别读取 `page`、`page_size`，并在函数体中检查范围。请改用 `Depends`：写出依赖函数与其中一个接口，说明参数来源、越界时返回的状态码，以及该改造相对原写法的改进。

```python
@app.get("/departments")
def list_departments(page: int = 1, page_size: int = 10):
    if page < 1 or page_size < 1 or page_size > 100:
        raise HTTPException(400, "分页参数越界")
    return {"page": page, "page_size": page_size, "items": []}

# /personnel、/records 两个接口与此完全同构，略
```

**解**：

**代码 3-3-2** · 抽出的分页依赖（Python）

```python
from fastapi import Depends, Query


def page_params(
    page: int = Query(1, ge=1),
    page_size: int = Query(10, ge=1, le=100),
):
    return {"page": page, "page_size": page_size}
```

**代码 3-3-3** · 用依赖改写后的接口（Python）

```python
@app.get("/departments")
def list_departments(params: dict = Depends(page_params)):
    return {"page": params["page"], "page_size": params["page_size"], "items": []}
```

1. 参数仍来自 URL 查询串，但声明由接口签名移至依赖签名；`Query(ge=1)`、`Query(le=100)` 将范围写为约束，不再依赖函数体内的 `if`。
2. 三个接口均改为 `params: dict = Depends(page_params)`，取值逻辑只写一次；修改上限（例如每页最多 50 条）时只改依赖。
3. 越界请求在进入接口前被拦截，状态码为 **422**，不再手动抛出 400。越界属于参数不符合约定，由 Pydantic 处理；400 保留给参数符合约定但业务不允许的情况。
4. 依赖只承担准备与约束；三个接口的函数体仅保留按参数返回数据的逻辑。

## 本章小结

**核心结论**：

1. **后端开发框架**将路由、校验、错误返回与公共逻辑复用收为统一约定；**接口契约**是前后端共同约定的 URL、方法、输入、输出与错误码。
2. 请求由方法、请求目标（URL）、头部与可选正文组成；参数分布于请求目标与正文。响应由状态码、响应头与响应体组成。HTTP 方法具有语义，GET 应安全且幂等。
3. 状态码按 2xx / 4xx / 5xx 划分：2xx 成功，4xx 调用方问题，5xx 服务方问题。401 表示身份未确认，403 表示权限不足，422 表示参数校验失败。
4. FastAPI 的四项机制为路由（装饰器与 `APIRouter`）、数据（Pydantic 模型）、错误（`HTTPException`）与复用（`Depends`）。422 由 Pydantic 在进入函数前产生；规则性失败由 `HTTPException` 在函数内产生。
5. 路由、输入模型与 `Depends` 的示例将四项机制串为可运行的最小链路。`Depends` 的机制见 3.6；第 4 章将模块纳入模块模板并展开接口组（4.4）；工程目录与文件内容见第 5 章 5.1。

本章可概括为：**契约将前端需求与后端响应写成双方可核对的约定，框架将该约定转化为可运行、可校验、可替换的服务。**
