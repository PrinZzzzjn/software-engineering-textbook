## 3.1 接口契约与联调三处失败

一个 Web 应用通常分成三层：浏览器里的前端负责显示与交互；服务器上的后端负责接收请求、处理业务、返回数据；数据库负责持久化存储。前端与后端由不同的人、甚至不同的团队开发，两边唯一的共同依据就是接口。

**接口契约**指前后端共同约定的调用方式，至少包含五项：URL（找谁）、方法（做什么）、输入（带什么参数或数据）、输出（返回什么字段）、错误（失败时返回什么状态码与说明）。它和需求文档一样，是一份“写下来才算数”的约定。

没有契约时，联调失败通常来自三个地方：

| 失败来源 | 典型现象 | 根因 |
| --- | --- | --- |
| 地址对不上 | 404，页面空白 | 前端写 `/department`，后端注册 `/departments`；单复数、前缀不一致 |
| 字段对不上 | 页面有行无值，或整列空白 | 前端读 `deptName`，后端返回 `dept_name`；命名风格不一致 |
| 错误语义对不上 | 操作失败却提示成功，或报错无法定位 | 成功与失败都返回 200；401 与 403 混用 |

三类问题的共同点是：**两边各自都“按自己的理解做对了”，合起来却失败。** 这和第 2 章火星气候探测者号的单位事故是同一种失败——不是谁写错了代码，而是约定没有被写下来、没有被共同检查。

有了契约，联调就从“互相猜”变成“对照检查”：地址、字段、状态码逐项对，对不上就是契约没对齐，而不是“你的代码有 bug”。

接口一旦被前端调用，URL、方法、参数名、返回字段就成了双方的契约。需求条目里写的字段名、状态码含义，必须与代码实际返回一致；不一致时，以代码为准去修正需求条目，而不是让前端去猜。联调时的大多数“数据不对”，追到最后都是契约不一致：字段名不同、分页参数不同、错误码含义不同。一个模块通常有多个接口，它们之间的命名与返回格式也要一致；这属于模块级设计，第 4 章 4.3 展开。

> 💡 **易错点**：把接口约定放在聊天记录里。聊天记录不是契约：它没有版本、没有固定位置，也无法被测试和文档引用。契约要写在接口文档或代码的 `/docs` 里，并且只有一份。

## 3.2 请求响应与状态码

浏览器与服务器之间用 HTTP（HyperText Transfer Protocol）通信。一次**请求**包含四个位置的信息：

| 要素 | 回答的问题 | 例子 |
| --- | --- | --- |
| URL | 找谁 | `/api/v1/departments/` |
| 方法 | 做什么 | `GET` |
| 参数 | 带什么条件 | `page=1&page_size=10` |
| 请求体 | 提交什么数据 | `{"dept_code": "D01", "dept_name": "一中队"}` |

一次**响应**包含三部分：状态码（结果如何）、响应头（附加信息）和响应体（返回的数据）。

**方法：动作的语义**

常用的 HTTP 方法有四个：

| 方法 | 语义 | 例子 |
| --- | --- | --- |
| GET | 查询 | 查询部门列表 |
| POST | 新增 | 新增一个部门 |
| PUT | 修改 | 修改部门名称 |
| DELETE | 删除 | 删除一个部门 |

方法不只是“习惯”，它带有语义约定。GET 应当是安全的（不改变服务器状态）且幂等的（重复调用结果一致）；PUT 和 DELETE 通常也应当是幂等的；POST 通常不保证幂等。理解这一点，才能解释为什么“用 GET 删除数据”是危险设计：浏览器、缓存和爬虫都可能重复发起 GET。

**参数：三个位置**

接口的参数只有三个位置，放哪里取决于它的作用：

| 类型 | 位置 | 例子 | 适合 |
| --- | --- | --- | --- |
| 路径参数 | URL 路径里 | `/departments/1` | 定位单个资源 |
| 查询参数 | `?` 后面 | `/departments?page=1&page_size=10` | 筛选、分页、排序 |
| 请求体 | 请求正文 | `{"dept_code": "D01"}` | 新增或修改要提交的字段 |

把“要定位的对象”放进路径，把“可选的筛选条件”放进查询，把“要提交的数据”放进请求体，接口的含义最清楚。反过来，`/departments?id=1` 也能工作，但它把“定位”降级成了“筛选”，语义就弱了一层。请求体的校验在 3.5 展开。

**JSON：前后端交换数据的共同格式**

后端返回的数据通常用 **JSON**（JavaScript Object Notation）表示。JSON 支持对象、数组、字符串、数字、布尔值和空值，结构与 Python 的字典、列表很接近。一个部门列表的响应可能长这样：

```json
{
  "items": [
    {"id": 1, "dept_code": "D01", "dept_name": "一中队"},
    {"id": 2, "dept_code": "D02", "dept_name": "二中队"}
  ],
  "total": 2
}
```

`items` 是本页数据，`total` 是总条数。分页接口通常同时返回这两个字段，前端才能算出总页数。JSON 的字段名就是接口契约的一部分，前后端必须使用同一套命名，不能一边叫 `dept_name`、一边叫 `departmentName`。

**状态码：结果类别的三段语义**

**状态码**让调用方在读取响应体之前就知道结果类别。初学阶段先掌握下面几个：

| 状态码 | 含义 | 谁的问题 | 典型场景 |
| --- | --- | --- | --- |
| 200 | 成功 | — | 查询、修改成功 |
| 201 | 已创建 | — | 新增成功 |
| 204 | 成功但无返回体 | — | 删除成功 |
| 400 | 请求格式错误 | 调用方 | JSON 语法错误、缺少必要字段 |
| 401 | 未认证 | 调用方 | 没登录或令牌无效 |
| 403 | 无权限 | 调用方 | 已登录但无权访问该资源 |
| 404 | 未找到 | 调用方 | URL 或资源不存在 |
| 422 | 参数校验失败 | 调用方 | 类型不对、必填项缺失 |
| 500 | 服务器内部错误 | 服务方 | 未捕获的异常 |

按第一位数字，状态码可以分成三段：**2xx 表示成功，4xx 表示调用方的问题，5xx 表示服务方的问题。** 这条分段的实际价值是分工：看到 4xx，前端先查自己传了什么；看到 5xx，后端先查服务端日志。如果所有错误都返回 500，前端会一直以为“服务器坏了”，后端也拿不到“参数不对”的线索。

401 与 403 的区别值得单独记住：401 回答“你是谁”，403 回答“你能做什么”。把两者混用，前端就不知道该跳登录页还是提示无权限。422 则回答“你传的参数不符合约定”，它不是服务器故障，而是请求在进入业务代码之前就被校验拦下了。

失败由谁抛出，可以对照下面这张责任表。它把“参数校验”与“业务规则”分开，是后面每个模块判断错误码的依据：

| 失败类型 | 状态码 | 谁负责 | 例子 |
| --- | --- | --- | --- |
| 参数不符合约定 | 422 | Pydantic | 缺字段、类型不对 |
| 未登录或令牌失效 | 401 | 认证依赖 | 请求头没有令牌 |
| 已登录但无权限 | 403 | 权限依赖 | 普通用户调用管理接口 |
| 资源不存在 | 404 | service 或 crud | 部门编码查不到 |
| 业务规则不满足 | 400 | service | 编码重复、时间冲突 |

> 💡 **易错点**：新增成功与失败都返回 200，只在响应体里写 `{"success": false}`。调用方必须先解析响应体才知道结果，缓存、重试和错误监控都会失效；状态码本来就是给这些环节看的。

## 3.3 接口组的资源与动作

**RESTful** 是一种常见的接口设计风格，核心做法是：URL 表示资源，HTTP 方法表示动作，状态码表示结果。

| 操作 | 方法与 URL | 成功状态码 |
| --- | --- | --- |
| 查询集合 | `GET /api/v1/departments/` | 200 |
| 查询单个 | `GET /api/v1/departments/1` | 200 |
| 新增 | `POST /api/v1/departments/` | 201 |
| 修改 | `PUT /api/v1/departments/1` | 200 |
| 删除 | `DELETE /api/v1/departments/1` | 204 |

这张表同时是一个资源的**接口组**：查询列表、查询单个、新增、修改、删除五个动作。一个业务模块（按业务对象划分的一组接口与代码）通常围绕一个业务对象提供这样一组接口，所以它也是模块对外的承诺。第 4 章 4.3 会把接口组与模块职责对齐；本章先把单个资源的五个动作定清楚。

资源名用名词复数，动作交给方法。`GET /getDepartments` 把动作写进了 URL，`POST /departments/delete/1` 用 POST 模拟删除，都不符合这种风格。反过来，只要 URL 是资源、方法是标准动作、状态码能表达结果，接口就具备了可预测性：前端不需要为每个接口记一套特殊规则，实训 3-1 的核对也可以照着这张表逐行打勾。

**RESTful 之外的设计方式**

RESTful 适合“资源清楚、增删改查为主”的系统，本课程的 duty 项目正属于这一类。但它不是唯一选择：需要一次取回多张关联表的数据时，RESTful 可能要多次请求；对外提供固定业务动作时，把动作写进 URL 反而更直白。选择 RESTful 的理由，是它用同一套规则覆盖大多数接口，降低前后端记忆成本；代价是遇到复杂查询时，需要在“资源化”和“可读性”之间做折中。

> 💡 **易错点**：只看 URL 是否用了名词，不看方法与状态码。`GET /departments/1` 与 `DELETE /departments/1` 用的是同一个资源地址，区别在方法；如果删除也写成 `GET`，风格问题就变成了数据安全问题。

## 3.4 装饰器路由与 APIRouter

FastAPI 是一个用 Python 写 Web 接口的框架：你定义函数，它负责把 HTTP 请求接进来、把返回值变成 JSON。与 Django、Flask 相比，它的定位是“接口优先”——参数校验写在函数签名里，接口文档自动生成，正好覆盖前后端联调最需要的两件事。本书选它，就是因为这两点让契约有一个双方都能打开的共同参照。

**代码 3-4-1** · `main.py`（最小应用，Python）

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/hello/{name}")
def hello(name: str):
    return {"message": f"你好，{name}"}
```

四行代码里有三个新东西。`app = FastAPI()` 造出一个应用对象，它是所有路由的挂载点。`@app.get("/hello/{name}")` 是一个**装饰器**：它把下面的函数登记到 `app` 上，规则是“有人用 GET 访问 `/hello/xxx` 时，调用这个函数，并把 `xxx` 传给 `name`”。函数返回字典，框架负责转成 JSON。本书里你不需要自己写装饰器，只要看懂 `@xxx` 意味着“这个函数被登记或包装了”。

第三个是 `name: str` 这个写法：冒号后面是**类型注解**，标明变量或返回值的预期类型。注解本身不改变运行结果，但 FastAPI 会读它，先做转换与校验，再进入函数体；校验失败时返回的状态码是 422，完整机制见 3.5。写 FastAPI 接口时几乎每个函数签名都要用类型注解；暂时不会写复杂的类，不影响学本书。

**APIRouter：把路由拆到模块**

项目变大后，几十个接口都挂在 `app` 上，`main.py` 会乱成一团长文件。**APIRouter** 是“小一号的挂载点”：各业务模块各自建一个 `router`，写好自己的接口；主文件再用 `include_router` 把它们组装回 `app`。

**代码 3-4-2** · `routers.py`（路由文件，Python）

```python
from fastapi import APIRouter

router = APIRouter(prefix="/departments", tags=["部门"])

@router.get("")
def list_departments():
    return {"items": [], "total": 0}
```

**代码 3-4-3** · `main.py`（组装，Python）

```python
from fastapi import FastAPI

from routers import router as departments_router

app = FastAPI()

app.include_router(departments_router, prefix="/api/v1")
```

所以后面章节看到 `@router.get(...)` 时，`router` 不是凭空出现的——它由本模块顶部的 `APIRouter(...)` 创建，最终被 `main.py` 的 `include_router` 挂进应用。两段前缀相加，这个列表接口的完整路径是 `/api/v1/departments`；`tags` 不影响 URL，只决定 `/docs` 里的分组名。这条“创建—挂载”链路，是第 4 章项目目录的核心动作：每个模块一个 controller 文件，`main.py` 只负责组装。

把路由拆到模块，不是为了“文件更多”，而是为了让变化只影响一处：新增一个业务模块，只加一个 router 文件并在 `main.py` 登记一行；改某个模块的 URL 前缀，只改该模块顶部的 `prefix`。若所有路由都写在 `main.py`，每次改动都要打开同一个大文件，冲突和遗漏的概率都会上升。

> 💡 **易错点**：在 `/docs` 里看到 404，先怀疑“接口没写对”。多数情况是前缀没拼上：模块 `prefix` 与 `include_router` 的 `prefix` 两段都要算，缺一段就会少一级路径。

## 3.5 输入模型与规则性失败

3.2 说请求体是提交数据的位置。请求体不是零散参数，而是一个有名字、有约束的结构，FastAPI 用一个 Pydantic 模型来接住它。**BaseModel** 是模型要继承的基类，`Field` 用来给字段加约束。

**代码 3-5-1** · `schemas.py`（输入模型，Python）

```python
from pydantic import BaseModel, Field


class DepartmentCreate(BaseModel):
    dept_code: str = Field(..., min_length=2, max_length=10)
    dept_name: str = Field(..., min_length=2, max_length=50)
```

`...` 表示必填；`min_length`、`max_length` 是约束。把模型写进函数签名，框架就知道“从请求体读 JSON，并按模型校验”：

```python
@router.post("")
def create_department(data: DepartmentCreate):
    return data
```

提交 `{"dept_code": "D"}` 会在进入函数前得到 422，响应 `detail` 里指明是哪个字段、违反了什么。

**422 发生在哪一层**

这是本章唯一一次完整说明 422，后面遇到时只回链到这里。422 不是函数体抛出的异常，而是请求进入函数之前的“门卫”返回的结果。因果链是：请求体先按模型解析 → 字段缺失或类型不符 → 校验失败 → 框架直接返回 422，函数体一行都不执行。因此，函数里不需要再写 `if not data.dept_code`；真正需要在函数里判断的，是模型无法表达的规则，例如“部门编码不能重复”——那属于业务规则，机制见第 10 章。

路径参数与查询参数同样受类型注解保护。访问 `/departments/abc` 而函数签名写的是 `dept_id: int`，同样在进入函数前返回 422。判断口径只有一条：**参数本身不符合约定，交 422；参数符合约定但业务上不允许，交 `HTTPException`。**

**输入与输出分开定义**

用户表里有 `password_hash`，但它绝不能出现在返回里。如果直接把数据库表模型当输出，新增一个字段就可能把敏感信息漏出去。正确做法是另建一个只含公开字段的输出模型：

**代码 3-5-2** · 输出模型与 `response_model`（节选，Python）

```python
class DepartmentOut(BaseModel):
    id: int
    dept_code: str
    dept_name: str

@router.get("/{dept_id}", response_model=DepartmentOut)
def read_department(dept_id: int):
    ...
```

`response_model` 会在返回前按模型过滤字段。输入模型负责“收”，输出模型负责“发”，两者的字段集合可以不同；这是一条从第 6 章起反复使用的规则。

查询参数常有“不填就不过滤”的场景，用 `Optional[int] = None` 表示；角色的合法取值是有限集合，用 `Literal["admin", "normal"]` 限定，写错在定义时就暴露。这两个写法在第 6、7、11 章会出现。

**HTTPException：规则性失败**

校验失败（422）由 Pydantic 自动处理，不需要手写。但“部门不存在”“无权限”这类规则性失败，需要在函数里主动结束请求，并给出状态码与说明：

**代码 3-5-3** · 主动返回规则性失败（Python）

```python
from fastapi import HTTPException

raise HTTPException(status_code=404, detail="部门不存在")
```

它与 422 的分工，就是 3.2 责任表里的两行：**422 是“参数不符合约定”，`HTTPException` 是“参数符合约定、但业务上不允许”。** 前者在进入函数前发生，后者在函数体内发生；两者都不能用 500 代替。所有规则性失败——404、401、403、400——都用它；校验类失败（422）交给 Pydantic，不用手抛。

同一个函数里可以按规则选择不同状态码；关键是让失败在进入业务之前或规则判断处结束，不要落到 500。例如创建部门时编码重复，service 应抛 `HTTPException(400, "部门编码已存在")`；普通用户删除别人的部门，权限依赖应抛 403。这些都不是参数校验，不能交给 Pydantic，也不应该用 500 掩盖。

> 💡 **易错点**：用 `HTTPException(422)` 手抛参数错误。422 应当由模型校验自然产生；手抛会让“谁在什么条件下拒绝”失去统一位置，排错时也分不清是模型约束还是业务规则。

## 3.6 三文件最小工程与 Depends

把 3.4–3.5 的机制拼成一个能跑的完整工程：只有三个文件、约 70 行。纸上读代码建议按 `schemas.py` → `deps.py` → `main.py` 的顺序，与下面三个文件的排印顺序一致。跟着敲一遍，第 4 章把文件放进目录、第 6 章起读模块代码会更容易。

**代码 3-6-1** · `schemas.py`（全文，Python）

```python
from pydantic import BaseModel, Field


class DepartmentCreate(BaseModel):
    """新增部门的输入模型（第 6 章起会反复出现这种写法）。"""
    dept_code: str = Field(..., min_length=2, max_length=10, examples=["D01"])
    dept_name: str = Field(..., min_length=2, max_length=50, examples=["一中队"])


class DepartmentOut(BaseModel):
    """返回给前端的输出模型：只有这三个字段，多一点都不给。"""
    id: int
    dept_code: str
    dept_name: str
```

**Depends：把公共逻辑抽成参数**

先忘记框架，看一个普通的 Python 问题：很多函数都需要先拿到“数据库”，于是每个函数的第一行都在重复 `db = 拿数据库()`。更好的做法是把“拿数据库”抽成一个函数，需要的人声明一下就行。FastAPI 把这个想法做成了语法。

**代码 3-6-2** · `deps.py`（全文，Python）

```python
from fastapi import Depends, HTTPException

# 用一个字典模拟数据库；第 8 章会把它换成真正的 SQLAlchemy 查询
FAKE_DB: dict[int, dict] = {
    1: {"id": 1, "dept_code": "D01", "dept_name": "一中队"},
    2: {"id": 2, "dept_code": "D02", "dept_name": "二中队"},
}


def get_db() -> dict:
    """公共依赖：所有需要访问“数据库”的路由都声明它。"""
    return FAKE_DB


def get_department_or_404(dept_id: int, db: dict = Depends(get_db)) -> dict:
    """公共依赖：按 id 取部门，取不到直接抛 404。"""
    if dept_id not in db:
        raise HTTPException(status_code=404, detail="部门不存在")
    return db[dept_id]
```

**Depends** 读作“给我 `get_db()` 的返回值”。框架在调用接口函数前先执行依赖，把结果塞进参数；看到 `xxx = Depends(yyy)`，就读作“xxx 由 yyy 提供”。三个推论：

1. 公共逻辑只写一次，改一处全体生效（比如给所有数据库会话加日志）。
2. 依赖可以叠依赖：`get_department_or_404` 内部又依赖 `get_db`，第 6 章会看到认证部分的两层嵌套。
3. 测试时可以把依赖换成假的（不连真数据库）——这是第 12 章模块测试的钥匙。

**代码 3-6-3** · `main.py`（全文，Python）

```python
from fastapi import APIRouter, Depends, FastAPI, status

from deps import get_db, get_department_or_404
from schemas import DepartmentCreate, DepartmentOut

router = APIRouter(prefix="/departments", tags=["部门"])


@router.get("", response_model=list[DepartmentOut])
def list_departments(db: dict = Depends(get_db)):
    """查询部门列表：GET + 集合资源。"""
    return sorted(db.values(), key=lambda d: d["id"])


@router.get("/{dept_id}", response_model=DepartmentOut)
def read_department(dept: dict = Depends(get_department_or_404)):
    """查询单个部门：路径参数定位资源，公共依赖处理 404。"""
    return dept


@router.post("", response_model=DepartmentOut, status_code=status.HTTP_201_CREATED)
def create_department(data: DepartmentCreate, db: dict = Depends(get_db)):
    """新增部门：请求体由 Pydantic 校验，失败返回 422。"""
    new_id = max(db) + 1
    record = {"id": new_id, **data.model_dump()}
    db[new_id] = record
    return record


@router.delete("/{dept_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_department(
    dept: dict = Depends(get_department_or_404),
    db: dict = Depends(get_db),
):
    """删除部门：成功返回 204，没有响应体。"""
    db.pop(dept["id"])


app = FastAPI(title="Duty API", version="0.1.0")
app.include_router(router, prefix="/api/v1")


@app.get("/health")
def health():
    return {"status": "ok"}
```

三个文件的分工可以对照一个请求来读：`router` 从 `main.py` 顶部来；数据结构在 `schemas.py` 里约束；公共逻辑在 `deps.py` 里复用。`schemas.py` 约 16 行，只做输入输出模型；`deps.py` 约 22 行，放 `HTTPException` 与 `Depends`；`main.py` 约 42 行，写路由并组装应用。

**启动与自查**（在自己机器上）：

```text
$ pip install "fastapi[standard]"
$ uvicorn main:app --port 8000
→ 打开 http://127.0.0.1:8000/docs，能看到 5 个接口（4 个部门 + 1 个 health）
→ GET  /api/v1/departments 返回 200 与两条部门
→ POST /api/v1/departments 提交 {"dept_code":"D03","dept_name":"三中队"} 返回 201
→ POST /api/v1/departments 提交 {"dept_code":"D"} 返回 422（违反 min_length=2）
→ DELETE /api/v1/departments/999 返回 404
```

> 说明：`data.model_dump()` 是 Pydantic v2 的写法（把模型转成字典）；网上旧资料里的 `data.dict()` 是 v1 写法，两者不通用。装好 `fastapi[standard]` 后默认就是 v2。

**与数据库的关系**：真实项目里 `get_db` 会开一个数据库会话，`yield` 之后在 `finally` 里关闭；表则用 Python 类映射，叫 **ORM**（对象关系映射）。这两件属于设计阶段的事，完整写法与分层理由见第 4 章 4.4；本章只需要认出 `db: Session = Depends(get_db)` 这个签名，知道“依赖负责开关会话，接口只管用”。不启动服务、用代码自动验证接口，属于测试章的内容，见第 12 章。

**交给第 4 章**：这三个文件不是另一套目录，而是项目目录的种子。`schemas.py` 会归入模块的 `schema.py`；`deps.py` 里的 `get_db` 会归入 `app/core/database.py`；路由函数会归入 `app/modules/dept/controller.py`；第 4 章 4.5 会给出逐项归位表，并画出一条请求经过这些文件的路径。

## 示范例题

#### 例 3-1：读一条请求与响应【Bloom：理解】

**题目**：下面是一条 HTTP 请求和对应的响应。请指出方法、URL、查询参数、状态码和响应体，并说明这次操作在做什么。

```text
GET /api/v1/departments/?page=1&page_size=10 HTTP/1.1

200 OK
{"items": [...], "total": 5}
```

**解**：

1. 方法是 `GET`，表示查询，不改变服务器状态。
2. URL 是 `/api/v1/departments/`，指向部门资源集合。
3. 查询参数是 `page=1` 与 `page_size=10`，表示取第 1 页、每页 10 条。
4. 状态码是 `200 OK`，表示请求成功。
5. 响应体是 JSON，包含 `items`（本页记录）与 `total`（总条数）。
6. 这次操作在做：查询部门列表的第 1 页，每页 10 条，并返回总条数供前端计算页数。

#### 例 3-2：判断接口设计是否 RESTful【Bloom：理解】

**题目**：下面是四个接口设计，请判断哪些符合 RESTful 资源设计，并说明理由。

- A. `GET /getDepartments`
- B. `GET /api/v1/departments/`
- C. `POST /api/v1/departments/`
- D. `POST /api/v1/departments/delete/1`

**解**：

1. **A 不符合**：URL 里出现动词 `get`，资源应当用名词；查询集合应写成 `GET /api/v1/departments/`。
2. **B 符合**：URL 是资源集合，方法是 GET，表示查询部门列表。
3. **C 符合**：URL 是资源集合，方法是 POST，表示在集合中新增一个部门，成功时返回 201。
4. **D 不符合**：删除应当用 DELETE 方法定位到单个资源，写成 `DELETE /api/v1/departments/1`；用 POST 加动作路径模拟删除，失去了方法的语义。

#### 例 3-3：用 Pydantic 模型接住请求体【Bloom：应用】

**题目**：为“新增器材”接口定义输入模型：`device_code` 必填、2–20 个字符；`device_name` 必填、2–50 个字符。写出模型与接口，并说明提交 `{"device_code": "E", "device_name": "投影仪"}` 时会发生什么。

**解**：

**代码 3-3-1** · `schemas.py`（输入模型，Python）

```python
from pydantic import BaseModel, Field


class DeviceCreate(BaseModel):
    device_code: str = Field(..., min_length=2, max_length=20)
    device_name: str = Field(..., min_length=2, max_length=50)
```

**代码 3-3-2** · `devices.py`（新增接口，Python）

```python
@router.post("", status_code=201)
def create_device(data: DeviceCreate):
    return data
```

1. `DeviceCreate` 继承 `BaseModel`，两个字段的 `...` 表示必填，`min_length`、`max_length` 给出长度约束。
2. 接口参数写成 `data: DeviceCreate`，FastAPI 就知道“从请求体读 JSON，并按模型校验”。
3. 提交 `{"device_code": "E", "device_name": "投影仪"}` 时，`device_code` 只有 1 个字符，违反 `min_length=2`，返回 422。
4. `detail` 中 `loc` 指向 `["body", "device_code"]`，`type` 为 `string_too_short`，能定位到具体字段；校验在进入函数前完成，函数体不执行。
5. 合法请求返回 201；若用 `response_model` 声明输出模型，返回时还会按输出模型过滤字段——输入与输出必须分开定义。

### 四、排错清单

| 现象 | 先查什么 |
| --- | --- |
| `/docs` 打不开 | 服务是否启动、端口是否被占用、`uvicorn` 的模块名是否写对 |
| 所有接口 404 | `include_router` 的 `prefix` 与模块 `prefix` 是否都写、单复数是否一致 |
| 非法请求仍成功 | 接口参数是否声明为模型类型、字段约束是否写在模型里 |
| 422 与 400 混用 | 参数不合约定交 422（Pydantic），业务规则不满足交 `HTTPException(400)` |
| 删除成功却报错 | 204 表示无响应体；不要把返回体写进 204 接口 |
| 输出带出内部字段 | 是否直接把输入或数据库对象当返回值；改用 `response_model` |

## 本章小结

**核心结论**：

1. **接口契约**是前后端共同约定的 URL、方法、输入、输出与错误码；联调失败通常来自地址、字段或错误语义没对齐。
2. 请求由 URL、方法、参数、请求体四要素构成；响应由状态码、响应头、响应体构成；方法带有语义，GET 应当安全且幂等。
3. 状态码按 2xx / 4xx / 5xx 分段：2xx 成功，4xx 调用方的问题，5xx 服务方的问题；401 回答“你是谁”，403 回答“你能做什么”，422 表示参数校验失败。
4. RESTful 用 URL 表示资源、方法表示动作、状态码表示结果；一个资源的五个动作构成接口组，也是实训核对的清单。
5. FastAPI 的四件机制是路由（装饰器 + `APIRouter`）、数据（Pydantic 模型）、错误（`HTTPException`）与复用（`Depends`）；422 由 Pydantic 在进入函数前产生，规则性失败由 `HTTPException` 在函数内产生。
6. 三文件最小工程把四件机制串成一条可运行的链路；第 4 章会把它放进项目目录，第 6 章起在业务模块中逐个落地。

把这章压缩成一句话：**契约把“前端要什么”与“后端给什么”写成双方都能核对的约定，框架把这纸约定变成能跑、能校验、能替换的服务。**

**本章不引入**：GraphQL、gRPC、OpenAPI 规范全文、中间件、生命周期钩子、异步细节、OAuth2 流程。这些在后续课程或工程环境中按需了解。
