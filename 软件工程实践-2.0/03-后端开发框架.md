# 第 3 章 后端开发框架

> **节首信息条**｜**专题二第 1 章**｜对应课次 3 · 2 学时 · 理论讲授｜前置：第 1–2 章

从本章起进入专题二：后端服务开发。

一个 Web 后端反复处理几件同类事：把不同的请求地址交给不同的函数；检查请求里的数据是否符合约定；按约定返回成功或失败；把数据库连接、登录校验这类公共逻辑复用起来。如果每个接口都从头写一遍，代码会重复，错误也会分散。**后端开发框架**就是把这些重复工作收进一套约定：开发者只写业务函数，框架负责接请求、校验数据、序列化成 JSON、处理错误，并生成接口文档。

本章以 FastAPI 为例，先看接口契约与 HTTP 的基本约定，再拆开框架的四件机制，最后用路由、输入模型与依赖注入各一个最小例子，把机制串成能跑的链路。

## 本章要解决的问题

**一个后端开发框架替开发者做了什么？怎样用它把一个接口约定变成可运行、可校验、可核对的接口？**

接口契约写在纸上只是一组约定。要让程序真的按它运行，还要完成四件事：把请求地址映射到函数、把输入拦住、把错误按语义返回、把公共逻辑抽出来复用。少一件，服务就只是能启动，而不是能按契约工作。

## 本章学习目标

读完本章后，你应该能：

1. 说明后端开发框架替开发者处理了哪些重复工作，以及接口契约在其中的位置。
2. 拆解一次请求与响应，按 2xx / 4xx / 5xx 的分段判断“这是谁的问题”，区分 401、403、422 的排查方向。
3. 说明 FastAPI 是什么、为什么选它，以及它的四件机制各自解决什么问题：装饰器路由与 `APIRouter`、Pydantic 输入模型、`Depends`、`HTTPException`。
4. 用路由与输入模型的小例子，说明这些机制怎样配合，并解释 422 与 `HTTPException` 的分工。
5. 启动一个 FastAPI 应用、打开 `/docs`，并说明 `def` 与 `async def` 的执行位置差别及各自适用场景。
6. 用 `Depends` 把重复的请求前置逻辑抽成依赖，说明它何时执行、该放什么、不该放什么。

## 3.1 接口与契约

一个 Web 应用通常分成三层：浏览器里的前端负责显示与交互；服务器上的后端负责接收请求、处理业务、返回数据；数据库负责持久化存储。按部署位置，这通常称为前端、后端与数据库三层。前端与后端由不同的人、甚至不同的团队开发，两边唯一的共同依据就是接口。

后端在一次请求里依次做五件事：接请求、读并校验参数、执行规则、读写数据、按契约返回。本章按这五件事拆开框架。

**接口**是前端调用后端能力的方式：它不是某一个函数，而是一组双方都认的规则。

**接口契约**是接口提供方与调用方对调用方式、数据格式、错误行为、兼容演进等达成的可验证约定。把它拆开，至少包含五件事：请求发到哪个地址、用什么方法；带什么数据、放在哪里、叫什么名字、是什么类型；成功时返回什么结构；失败时返回什么状态码和错误说明；接口以后怎么升级而不破坏旧调用方。契约不是“写给人看的说明”，而是双方都能拿来核对、测试和追责的依据。

契约可以写在 Markdown 文档、代码注释里，或者用 **OpenAPI** 这类机器可读的规范描述。OpenAPI 写清每条接口的路径、方法、参数、请求体与响应；FastAPI 会根据路由与模型自动生成它，`/docs` 就是这份文档的可视化版本。

框架把这纸契约变成程序：**路由**负责把地址映射到函数，**输入模型**负责校验数据，**异常处理**负责返回约定的错误；**依赖注入**负责复用公共逻辑（3.6）。本章后面几节依次拆开这四件。

契约是约定的“应然”，代码是当前的“实然”。不一致时先记录差异——哪一项、期望什么、实际是什么——再判断改哪边；不要默认“以代码为准”。

一个模块通常有多个接口，它们之间的命名与返回格式也要一致；这属于模块级设计，第 4 章 4.4 展开。

> 💡 **易错点**：把接口约定放在聊天记录里。聊天记录没有版本、没有固定位置，也无法被测试和文档引用；契约要写在接口文档或 `/docs` 里，并且只有一份。

## 3.2 请求与响应

浏览器与服务器之间用 HTTP（HyperText Transfer Protocol）通信。一次 HTTP 交互由**请求**和**响应**组成：前端发请求，后端回响应。按 RFC 9110 的消息结构：

- **请求**由方法、请求目标、头部和可选的正文组成；
- **响应**由状态码、响应头和响应体组成。

下面按这七个部分依次展开。

**请求：方法**

常用的 HTTP 方法有四个：

| 方法 | 语义 | 例子 |
| --- | --- | --- |
| GET | 查询 | 查询部门列表 |
| POST | 新增 | 新增一个部门 |
| PUT | 修改 | 修改部门名称 |
| DELETE | 删除 | 删除一个部门 |

方法不只是“习惯”，它带有语义约定。按 HTTP 语义标准（RFC 9110），GET 应当是安全的（不改变服务器状态）且幂等的（重复调用结果一致）；PUT 和 DELETE 通常也应当是幂等的；POST 通常不保证幂等。理解这一点，才能解释为什么“用 GET 删除数据”是危险设计：浏览器、缓存和爬虫都可能重复发起 GET。

**请求：请求目标**

请求目标是请求行里的路径部分，通常写作 URL（统一资源定位符）。`/api/v1/departments/` 指向部门集合；完整形式还含协议、主机和端口（如 `http://127.0.0.1:8000/...`），但主机与端口由部署环境决定，本章只写路径。

同一个地址既可以指向集合，也可以指向集合里的一个成员：

| 写法 | 指向 | 典型用途 |
| --- | --- | --- |
| `/api/v1/departments/` | 部门集合 | 查询列表、新增 |
| `/api/v1/departments/1` | 集合里的一个成员 | 查询、修改、删除 id 为 1 的部门 |

`/1` 是路径里的一个值，含义与写法在第 4 章 4.4 讲接口组时展开。

**请求：头部**

头部字段放请求的附加信息，不直接参与业务数据。初学阶段先认识两个：

| 头部 | 作用 | 例子 |
| --- | --- | --- |
| `Authorization` | 证明“我是谁” | `Authorization: Bearer <令牌>` |
| `Content-Type` | 说明正文是什么格式 | `Content-Type: application/json` |

没有正文的 GET 请求通常不需要 `Content-Type`；带 JSON 正文的 POST/PUT 请求要写 `application/json`。认证头部的完整用法在第 6 章登录认证展开，本章只需要知道它存在。

**请求：正文**

正文是请求中可选的部分，用来提交新增或修改所需的数据。带正文的请求通常用 **JSON**（JavaScript Object Notation）表示，格式见 RFC 8259；它的结构与 Python 的字典、列表很接近：

```json
{"dept_code": "D01", "dept_name": "一中队"}
```

正文里的字段名就是接口契约的一部分，前后端必须使用同一套命名。正文的校验在 3.5 用 Pydantic 模型完成。

一次请求里的数据可能出现在四个位置，初学时容易混：

| 数据位置 | 典型用途 | 首次出现 |
| --- | --- | --- |
| 路径参数 `/departments/1` | 定位某一个资源 | 3.4 |
| 查询参数 `?page=1&page_size=10` | 筛选、分页、排序 | 例 3-1 |
| 请求头 `Authorization` | 认证信息 | 3.2 |
| 请求体 JSON | 新增或修改的字段 | 3.5 |

这四类数据在 FastAPI 里都由函数参数接住，写法见 3.4、3.5；模块的接口组如何分配参数，见第 4 章 4.4。

**响应：状态码**

**状态码**让调用方在读取响应体之前就知道结果类别。初学阶段先掌握下面几个：

| 状态码 | 含义 | 谁的问题 | 典型场景 |
| --- | --- | --- | --- |
| 200 | 成功 | — | 查询、修改成功 |
| 201 | 已创建 | — | 新增成功 |
| 204 | 成功但无返回体 | — | 删除成功 |
| 400 | 请求格式错误 | 调用方 | JSON 语法错误、缺少必要字段 |
| 401 | 未认证 | 调用方 | 没登录或令牌无效 |
| 403 | 无权限 | 调用方 | 已登录但无权访问该资源 |
| 404 | 未找到 | 调用方 | URL 或资源不存在 |
| 422 | 内容校验失败 | 调用方 | 类型不对、必填项缺失 |
| 500 | 服务器内部错误 | 服务方 | 未捕获的异常 |

状态码按第一位数字分五类：1xx 信息、2xx 成功、3xx 重定向、4xx 调用方的问题、5xx 服务方的问题（RFC 9110）；本章只用 2xx、4xx、5xx。分段的实际价值是分工：4xx 先查前端传了什么，5xx 先查服务端日志；全返回 500 会让双方都失去线索。

401 回答“你是谁”，403 回答“你能做什么”；混用会让前端不知道该跳登录页还是提示无权限。422 回答“你传的内容不符合约定”，是进入业务代码前就被校验拦下，不是服务器故障。422 不在 RFC 9110 的核心表中，它来自 WebDAV（RFC 4918），FastAPI 借用它表示请求体校验失败。

失败由谁抛出，可以对照下面这张责任表。它把“输入校验”与“业务规则”分开，是后面每个模块判断错误码的依据：

| 失败类型 | 状态码 | 谁负责 | 例子 |
| --- | --- | --- | --- |
| 输入不符合约定 | 422 | Pydantic | 缺字段、类型不对 |
| 未登录或令牌失效 | 401 | 认证依赖 | 请求头没有令牌 |
| 已登录但无权限 | 403 | 权限依赖 | 普通用户调用管理接口 |
| 资源不存在 | 404 | service 或 crud | 部门编码查不到 |
| 业务规则不满足 | 400 | service | 编码重复、时间冲突 |

**响应：响应头**

响应头放附加信息，例如 `Content-Type: application/json` 说明响应体是 JSON。多数业务代码不用主动设置，FastAPI 会按返回内容自动补上；缓存、跨域等头部在后续章节按需出现。

**响应：响应体**

响应体是服务器返回的数据，通常是 JSON。一个部门列表的响应可能长这样：

```json
{
  "items": [
    {"id": 1, "dept_code": "D01", "dept_name": "一中队"},
    {"id": 2, "dept_code": "D02", "dept_name": "二中队"}
  ],
  "total": 2
}
```

`items` 是本页数据，`total` 是总条数。分页接口通常同时返回这两个字段，前端才能算出总页数。响应体里的字段名就是接口契约的一部分，前后端必须使用同一套命名，不能一边叫 `dept_name`、一边叫 `departmentName`。

有些响应没有响应体：204 表示成功但没有内容，删除接口常用它。这时调用方只看状态码，不读响应体。

> 💡 **易错点**：新增成功与失败都返回 200，只在响应体里写 `{"success": false}`。调用方必须先解析响应体才知道结果，缓存、重试和错误监控都会失效；状态码本来就是给这些环节看的。

## 3.3 FastAPI 是什么

FastAPI 是一个用 Python 写 Web 接口的框架（FastAPI 官方文档）。要理解它为什么存在，可以先看不用框架时要做什么：自己监听端口、解析 HTTP 请求行和头部、把 URL 匹配到函数、从查询串和请求体里取值、检查类型、把返回值转成 JSON、捕获异常并决定状态码、再写一份接口文档。这些事每个接口都要重复，而且很容易漏。框架把这些公共工作做一次，开发者只需要声明“这个 URL 用这个函数处理，输入是什么类型，输出是什么结构”。

FastAPI 的定位是“接口优先”：参数校验写在函数签名里，接口文档自动生成。与 Django、Flask 相比，它更强调用类型注解描述输入输出并据此生成 OpenAPI 文档。本课程选它，是因为 `/docs` 给了双方一个能打开的共同参照。

本章按“框架替我们做什么”来读 FastAPI：

- **路由**：把 URL 与 HTTP 方法映射到函数；
- **数据**：用 Pydantic 模型校验输入、控制输出；
- **错误**：用 `HTTPException` 表达规则性失败；
- **复用**：用 `Depends` 把公共逻辑抽出来（3.6 展开）。

3.4 讲路由，3.5 讲数据与错误，3.6 讲复用。

**应用怎么跑起来**

**代码 3-3-1** · 命令（Bash）

```bash
uvicorn main:app --reload --port 8000
```

这行命令里，`main` 是文件名（`main.py`），`app` 是文件里创建的应用变量。uvicorn 是 ASGI 服务器：监听端口、接收 HTTP 请求，交给 FastAPI 应用处理。`--reload` 只在开发时用，改动文件后自动重启；部署时不加。启动后打开 `http://127.0.0.1:8000/docs`，看到的就是 3.1 说的 OpenAPI 文档；3.4 起的例子都可以在这里验证。

**同步 def 与异步 async def**

FastAPI 同时支持普通函数和 `async def` 定义的端点，两者的执行位置不同：`def` 端点由框架放到线程池里执行，`async def` 端点直接在事件循环上执行。这个区别的后果是：在 `async def` 里调用会阻塞的函数（例如 `time.sleep`、同步数据库驱动），卡住的是整个服务，而不只是这一个请求。

本书的示例统一用 `def`：教学环境的并发压力小，代码读起来也少一层概念。只有确实要处理大量并发 I/O，且所用库提供异步版本时，才需要写 `async def`；写的时候要保证函数体内没有阻塞调用。

## 3.4 装饰器路由与 APIRouter

**代码 3-4-1** · `main.py`（最小应用，Python）

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/hello/{name}")
def hello(name: str):
    return {"message": f"你好，{name}"}
```

四行代码里有三个新东西。`app = FastAPI()` 造出一个应用对象，它是所有路由的挂载点。`@app.get("/hello/{name}")` 是一个**装饰器**：它把下面的函数登记到 `app` 上，规则是“有人用 GET 访问 `/hello/xxx` 时，调用这个函数，并把 `xxx` 传给 `name`”。装饰器是 Python 的写法：函数定义前加一行 `@xxx`，表示把它交给 `xxx` 登记或包装；用在路由上，URL 与函数写在同一处。本书不需要你自己写装饰器，看懂 `@xxx` 意味着“这个函数被登记了”即可。

第三个是 `name: str` 这个写法：冒号后面是**类型注解**，标明变量或返回值的预期类型。注解本身不改变运行结果，但 FastAPI 会读它，先做转换与校验，再进入函数体；校验失败时返回的状态码是 422，完整机制见 3.5。写 FastAPI 接口时几乎每个函数签名都要用类型注解；暂时不会写复杂的类，不影响学本书。

**APIRouter：把路由拆到模块**

项目变大后，几十个接口都挂在 `app` 上，`main.py` 会乱成一团长文件。**APIRouter** 是“小一号的挂载点”：各业务模块各自建一个 `router`，写好自己的接口；主文件再用 `include_router` 把它们组装回 `app`。

**代码 3-4-2** · `routers.py`（路由文件，Python）

```python
from fastapi import APIRouter

router = APIRouter(prefix="/departments", tags=["部门"])

@router.get("")
def list_departments():
    return {"items": [], "total": 0}
```

**代码 3-4-3** · `main.py`（组装，Python）

```python
from fastapi import FastAPI

from routers import router as departments_router

app = FastAPI()

app.include_router(departments_router, prefix="/api/v1")
```

所以后面章节看到 `@router.get(...)` 时，`router` 不是凭空出现的——它由本模块顶部的 `APIRouter(...)` 创建，最终被 `main.py` 的 `include_router` 挂进应用。两段前缀相加，这个列表接口的完整路径是 `/api/v1/departments`；`tags` 不影响 URL，只决定 `/docs` 里的分组名。这条“创建—挂载”链路，是第 4 章项目目录的核心动作：每个模块一个 controller 文件，`main.py` 只负责组装。

把路由拆到模块，不是为了“文件更多”，而是为了让变化只影响一处：新增一个业务模块，只加一个 router 文件并在 `main.py` 登记一行；改某个模块的 URL 前缀，只改该模块顶部的 `prefix`。若所有路由都写在 `main.py`，每次改动都要打开同一个大文件，冲突和遗漏的概率都会上升。

> 💡 **易错点**：在 `/docs` 里看到 404，先怀疑“接口没写对”。多数情况是前缀没拼上：模块 `prefix` 与 `include_router` 的 `prefix` 两段都要算，缺一段就会少一级路径。

## 3.5 输入模型与规则性失败

**为什么需要输入模型**

请求体不是零散的键值，而是有名字、有约束的结构：新增部门要提交 `dept_code` 与 `dept_name`，都是字符串、有长度范围、缺一不可。不用模型就要手写一连串检查：

```python
if "dept_code" not in data: ...
if not isinstance(data["dept_code"], str): ...
if len(data["dept_code"]) < 2: ...
```

每个接口重复一遍，漏一条就会把脏数据放进业务逻辑；而且检查只在函数体里，文档与调用方都看不到。模型把“请求体长什么样”声明在一处，交给框架解析、校验与生成文档。

**Pydantic、BaseModel 与 Field**

FastAPI 用 **Pydantic** 接住请求体：用一个类声明字段的名字、类型与约束，Pydantic 把 JSON 转成实例，类型不对、字段缺失或超范围时给出结构化错误。

- **BaseModel** 是 Pydantic 的基类；继承它就获得校验、类型转换、序列化（`model_dump()`）与生成文档的能力。
- **Field** 给单个字段加约束与说明：`min_length`、`max_length` 限制长度，`examples` 出现在文档里；第一个参数写 `...`（Ellipsis）表示必填。
- **类型注解**（如 `name: str`）是模型的核心：Pydantic 读注解决定怎么转换、怎么校验；FastAPI 又把注解读进 OpenAPI 文档。

**一个最小例子**

先不看项目，用一个没有业务含义的例子看清机制：

**代码 3-5-1** · `main.py`（最小输入模型，Python）

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()


class Greeting(BaseModel):
    name: str = Field(..., min_length=1, max_length=20)


@app.post("/hello")
def hello(data: Greeting):
    return {"message": f"你好，{data.name}"}
```

`data: Greeting` 告诉 FastAPI：“从请求体读 JSON，按 `Greeting` 解析，再传进来。”提交 `{"name": ""}` 时违反 `min_length=1`，请求在进入函数前就返回 422，`detail.loc` 指向 `["body", "name"]`，能直接定位字段。

422 不是函数体抛出的，而是进入函数前的“门卫”：请求体按模型解析，字段缺失或类型不符时直接返回 422，函数体不执行。函数里真正要判断的，是模型无法表达的规则——那属于业务规则。

**回到项目：DepartmentCreate**

真实项目里的模型只是把字段换成业务字段，写法相同：

**代码 3-5-2** · `schemas.py`（输入模型，Python）

```python
from pydantic import BaseModel, Field


class DepartmentCreate(BaseModel):
    dept_code: str = Field(..., min_length=2, max_length=10)
    dept_name: str = Field(..., min_length=2, max_length=50)
```

`...` 表示必填；`min_length`、`max_length` 是约束。把模型写进函数签名，框架就知道“从请求体读 JSON，并按模型校验”：

```python
@router.post("")
def create_department(data: DepartmentCreate):
    return data
```

提交 `{"dept_code": "D"}` 会在进入函数前得到 422，响应 `detail` 里指明是哪个字段、违反了什么。

**输入与输出分开定义**

输入模型负责“收”，输出模型负责“发”。两者可以不同：输入需要密码、确认密码，输出只需要用户名和 id；输入可以接受内部字段，输出绝不能带出去。先看一个最小对照：

```python
class GreetingOut(BaseModel):
    message: str
```

在接口上声明 `response_model=GreetingOut`，FastAPI 会在返回前按模型过滤字段。用户表的 `password_hash` 绝不能出现在返回里；直接把数据库对象当输出，新增一个字段就可能漏出敏感信息。

回到部门接口，输出模型只保留公开字段：

**代码 3-5-3** · 输出模型与 `response_model`（节选，Python）

```python
class DepartmentOut(BaseModel):
    id: int
    dept_code: str
    dept_name: str

@router.get("/{dept_id}", response_model=DepartmentOut)
def read_department(dept_id: int):
    ...
```

`response_model` 的过滤是 OWASP API Security 所说的“过度数据暴露”防护，从第 6 章起反复使用。

**Optional 与 Literal：两个常用写法**

`Optional[int] = None` 表示“不填就不过滤”；`Literal["admin", "normal"]` 把取值限定在固定集合。这两个写法在第 6、7、11 章出现，这里先认识形式即可。

**HTTPException：规则性失败**

422 由 Pydantic 自动处理。“资源不存在”“无权限”这类规则性失败，则要在函数里主动结束请求，给出状态码与说明：

**代码 3-5-4** · 主动返回规则性失败（Python）

```python
from fastapi import HTTPException

ITEMS = {1: {"id": 1, "name": "扳手"}}


@app.get("/items/{item_id}")
def read_item(item_id: int):
    if item_id not in ITEMS:
        raise HTTPException(status_code=404, detail="器材不存在")
    return ITEMS[item_id]
```

这里 `item_id` 类型符合约定，不会触发 422；但 id 不存在，属于“参数符合约定、业务上不允许”，用 `HTTPException` 返回 404。分工就是 3.2 责任表的两行：**422 是“参数不符合约定”，`HTTPException` 是“参数符合约定、但业务上不允许”**；前者在进入函数前，后者在函数内，都不能用 500 代替。404、401、403、400 都用它；422 交给 Pydantic，不手抛。

关键是让失败在进入业务之前或规则判断处结束，不要落到 500。例如部门编码重复由 service 抛 `HTTPException(400, ...)`，普通用户删除别人的部门由权限依赖抛 403；这些都不是参数校验。

> 💡 **易错点**：用 `HTTPException(422)` 手抛参数错误。422 应当由模型校验自然产生；手抛会让“谁在什么条件下拒绝”失去统一位置，排错时也分不清是模型约束还是业务规则。

## 3.6 依赖注入：Depends

**重复的前置逻辑**

列表接口要取分页参数，数据库接口要拿会话，受保护接口要确认“当前用户是谁”。这些事每次请求都要先做，且不止一个接口要做；各写一遍就会改一处、漏一处。

**机制**

FastAPI 用**依赖注入**解决这类重复：把“请求进来之前必须先完成的事”写成一个普通函数，再用 `Depends` 把它声明在参数默认值上。框架在处理请求前先调用这个函数，把返回值传给接口函数。

依赖可以嵌套——一个依赖自己也可以声明依赖；测试时还可以用 `app.dependency_overrides` 替换掉，这一点本章不展开。

**最小例子**

**代码 3-6-1** · 依赖注入最小例子（Python）

```python
from fastapi import Depends, FastAPI

app = FastAPI()


def page_params(page: int = 1, page_size: int = 10):
    return {"page": page, "page_size": page_size}


@app.get("/items")
def list_items(params: dict = Depends(page_params)):
    return {"page": params["page"], "page_size": params["page_size"], "items": []}
```

`page`、`page_size` 仍来自查询串，名字与类型写在依赖签名里。访问 `/items` 得到第 1 页、每页 10 条；`/items?page=abc` 无法转成 `int`，在进入 `list_items` 前返回 422。函数体里没有一行取值与检查。

**依赖只做准备，不做业务**

依赖只做“准备与拦截”：取参数、拿会话、查当前用户、拒绝无权限的请求。业务规则仍属于 service（第 4 章 4.5）；把“编码是否重复”塞进依赖，会让 422 与 400 的分工重新变模糊。

项目里有三处会用到它：数据库会话 `get_db`（第 5 章 5.1）、认证依赖与权限依赖（第 6 章 6.5）。

> 💡 **易错点**：依赖的返回值不写类型注解，或把业务也塞进依赖。前者让接口拿到的类型与文档对不上，后者让“进入函数前的检查”与“函数里的业务判断”混在一起，排错时又分不清 422 与 400。

## 示范例题

#### 例 3-1：读一条请求与响应【Bloom：理解】

**题目**：下面是一条 HTTP 请求和对应的响应。请指出方法、URL、查询参数、状态码和响应体，并说明这次操作在做什么。

```text
GET /api/v1/departments/?page=1&page_size=10 HTTP/1.1

200 OK
{"items": [...], "total": 5}
```

**解**：

1. 方法是 `GET`，表示查询，不改变服务器状态。
2. URL 是 `/api/v1/departments/`，指向部门资源集合。
3. `page=1` 与 `page_size=10` 是**查询参数**（Query Parameter），写在 URL 的问号后面，用来筛选、分页或排序；这里表示取第 1 页、每页 10 条。
4. 状态码是 `200 OK`，表示请求成功。
5. 响应体是 JSON，包含 `items`（本页记录）与 `total`（总条数）。
6. 这次操作在做：查询部门列表的第 1 页，每页 10 条，并返回总条数供前端计算页数。

#### 例 3-2：用 Pydantic 模型接住请求体【Bloom：应用】

**题目**：为“新增器材”接口定义输入模型：`device_code` 必填、2–20 个字符；`device_name` 必填、2–50 个字符。写出模型与接口，并说明提交 `{"device_code": "E", "device_name": "投影仪"}` 时会发生什么。

**解**：

**代码 3-2-1** · `schemas.py`（输入模型，Python）

```python
from pydantic import BaseModel, Field


class DeviceCreate(BaseModel):
    device_code: str = Field(..., min_length=2, max_length=20)
    device_name: str = Field(..., min_length=2, max_length=50)
```

**代码 3-2-2** · `devices.py`（新增接口，Python）

```python
@router.post("", status_code=201)
def create_device(data: DeviceCreate):
    return data
```

1. `DeviceCreate` 继承 `BaseModel`，两个字段的 `...` 表示必填，`min_length`、`max_length` 给出长度约束。
2. 接口参数写成 `data: DeviceCreate`，FastAPI 就知道“从请求体读 JSON，并按模型校验”。
3. 提交 `{"device_code": "E", "device_name": "投影仪"}` 时，`device_code` 只有 1 个字符，违反 `min_length=2`，返回 422。
4. `detail` 中 `loc` 指向 `["body", "device_code"]`，`type` 为 `string_too_short`，能定位到具体字段；校验在进入函数前完成，函数体不执行。
5. 合法请求返回 201；若用 `response_model` 声明输出模型，返回时还会按输出模型过滤字段——输入与输出必须分开定义。

#### 例 3-3：把重复的取参逻辑抽成依赖【Bloom：应用】

**题目**：下面的三个列表接口各自取 `page`、`page_size`，并在函数体里检查范围。请改成用 `Depends`：写出依赖函数与其中一个接口，说明参数从哪里来、越界时谁返回什么状态码，以及这次改造相对原来的写法好在哪。

```python
@app.get("/departments")
def list_departments(page: int = 1, page_size: int = 10):
    if page < 1 or page_size < 1 or page_size > 100:
        raise HTTPException(400, "分页参数越界")
    return {"page": page, "page_size": page_size, "items": []}

# /personnel、/records 两个接口与此完全同构，略
```

**解**：

**代码 3-3-2** · 抽出的分页依赖（Python）

```python
from fastapi import Depends, Query


def page_params(
    page: int = Query(1, ge=1),
    page_size: int = Query(10, ge=1, le=100),
):
    return {"page": page, "page_size": page_size}
```

**代码 3-3-3** · 用依赖改写后的接口（Python）

```python
@app.get("/departments")
def list_departments(params: dict = Depends(page_params)):
    return {"page": params["page"], "page_size": params["page_size"], "items": []}
```

1. 参数仍来自 URL 查询串，但声明从接口签名挪到了依赖签名；`Query(ge=1)`、`Query(le=100)` 把范围写成约束，不再靠函数体里的 `if`。
2. 三个接口都改成 `params: dict = Depends(page_params)`，取值逻辑只写一次；上限要改（例如每页最多 50 条）时只改依赖。
3. 越界在进入接口前被拦住，状态码是 **422**，不再是手抛的 400：越界属于「参数不符合约定」，归 Pydantic；400 留给「参数符合约定、业务上不允许」。
4. 依赖只做准备与约束；三个接口的函数体只剩「按参数返回数据」。

## ◇ 课堂活动块（课次 3 · 理论讲授）

**听讲要点**（课上跟着讲师过一遍，课后自查能否复述）：

1. 后端开发框架替开发者处理路由、校验、错误返回与复用；接口契约是前后端共同的依据。
2. HTTP 方法的语义与幂等性，以及为什么“用 GET 删除数据”是危险设计。
3. 状态码按 2xx / 4xx / 5xx 分段看“谁的问题”；401、403、422 的分工与排查方向。
4. FastAPI 的定位：接口优先、类型注解校验、自动生成 `/docs`；它替开发者处理路由、校验、错误与复用。
5. FastAPI 四件机制：路由（装饰器 + `APIRouter`）、数据（Pydantic 模型）、错误（`HTTPException`）、复用（`Depends`，3.6）。
6. 契约是约定的“应然”，代码是当前的“实然”；两者不一致时先记录差异，再判断改哪边。路由与输入模型的小例子把这几件机制串起来。
7. 应用靠 uvicorn 启动：`main` 是文件、`app` 是应用变量；`--reload` 只用于开发，部署不加。
8. `def` 端点在线程池执行、`async def` 端点在事件循环执行；`async def` 里调用阻塞函数会卡住整个服务。`Depends` 在请求进入函数前执行，只做准备与拦截，不做业务。

## 本章小结

**核心结论**：

1. **后端开发框架**把路由、校验、错误返回与公共逻辑复用收进一套约定；**接口契约**是前后端共同约定的 URL、方法、输入、输出与错误码。
2. 请求由方法、请求目标（URL）、头部与可选正文组成；参数分布在请求目标和正文里；响应由状态码、响应头、响应体组成。方法带有语义，GET 应当安全且幂等。
3. 状态码按 2xx / 4xx / 5xx 分段：2xx 成功，4xx 调用方的问题，5xx 服务方的问题；401 回答“你是谁”，403 回答“你能做什么”，422 表示参数校验失败。
4. FastAPI 的四件机制是路由（装饰器 + `APIRouter`）、数据（Pydantic 模型）、错误（`HTTPException`）与复用（`Depends`）；422 由 Pydantic 在进入函数前产生，规则性失败由 `HTTPException` 在函数内产生。
5. 路由、输入模型与 `Depends` 的小例子把这四件机制串成一条可运行的最小链路；`Depends` 的机制在 3.6，第 4 章把模块放进模块模板并展开接口组（4.4），工程目录与文件内容在第 5 章 5.1。

把这章压缩成一句话：**契约把“前端要什么”与“后端给什么”写成双方都能核对的约定，框架把这纸约定变成能跑、能校验、能替换的服务。**
