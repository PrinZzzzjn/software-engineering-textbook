### 1.6 教学目标

**知识与技能**

- 能说出前端、后端、数据库各自负责"显示、处理、存储"，并能独立分析"新增一条值班记录"这类功能中每一层做什么。
- 能说出接口四要素——URL、方法、参数、返回，并能按"请求进来 → 匹配 URL → 确认方法 → 解析参数 → 执行 → 返回"的顺序复述一次完整流程。
- 能说出 URL 的常见组成与"路由"的作用，能区分 GET、POST、PUT、DELETE 的操作语义。
- 能区分路径参数与查询参数，能针对"查某一个"和"查一批"选择正确的参数形式并说明理由。
- 能说出 200、201、404、422 四个状态码的含义，能读懂响应由"状态码 + 返回体"组成。
- 能说出 FastAPI 框架的作用，能读懂最小接口代码，能把四要素映射到代码，能解释 `/docs` 与 422 的来源。

**过程与方法**

- 经历"点按钮—看请求—看响应"的观察过程，用"数据从哪来、到哪去"的追问建立请求—响应直觉。
- 通过"读代码—对四要素—看文档"三步法，学会用 duty 的 `/docs` 验证对接口的理解，而不是靠猜。
- 通过"没有框架"与"用 FastAPI"的对比，学会从"工具实现"中分离出"接口约定"，理解框架封装了什么、没封装什么。

**情感态度与价值观**

- 建立"接口是前后端约定"的工程意识，体会约定清晰、协作顺畅。
- 面对英文报错先看状态码和提示，养成不怕报错、按图索骥的排障习惯。
- 理解"框架替我们做脏活，但 HTTP 约定还要自己懂"，避免只会调库、不懂原理。
- 通过 duty 系统服务值班业务，体会技术服务实战、信息强军的价值追求。

### 2.1 本堂课的授课思路

本课以 duty 值班数据统计系统的"查询部门"为贯穿案例，按"项目牵引—三个教学循环—回归项目—揭幕框架"展开。开课先让学员看一次真实的"点按钮—出数据"，用"数据从哪来"的追问建立请求—响应直觉，并提出本课三个问题：后端在做什么、一个接口怎么描述、接口给什么、谁来落实。第一个循环讲三层分工、请求—响应与接口四要素，让学员能在 duty 的 `/docs` 上把一个真实接口"对号入座"，并独立分析一个未见过的接口；第二个循环把四要素拆开，讲 URL 与路由、HTTP 方法与操作语义、路径参数与查询参数；第三个循环讲返回与状态码，最后揭幕 FastAPI，把前面出现的 `/docs`、422、装饰器、函数签名全部收拢到"框架替我们做了什么"。三个循环均按"要领讲解—案例解析—课堂研讨—小结讲评"四环节推进：本课次为理论课，不设示范引领、组织练习、纠偏校正，改以真实案例解析替代跟做、以课堂研讨替代改错。

全课采用"先行为、后实现"的顺序：前面只讲接口的行为约定，把"框架"留到最后揭幕。导入时只点一句"duty 是用 FastAPI 写的，最后一节拆开看它替我们做了什么"；前面用 `/docs` 时只当"项目自带的说明书"，不讲它怎么来的；讲 422 时只留扣"为什么自动返回 422"，最后一节回收。这样最后一节不是孤立的新知识点，而是把前面所有线索收拢的总收。

### 2.2 板书设计

板书分三区：左区固定呈现**三层分工与请求—响应**，中区固定呈现**接口四要素与处理流程、HTTP 方法**，右区随课堂进度逐步添加**参数对比、状态码、FastAPI 揭幕**。左、中两区全程在板，案例解析与课堂研讨不断回到板书对照。

**左区固定区**（知识点一、二 · 三层分工与请求—响应）：

```text
前端（显示） → 后端（处理） → 数据库（存储）
       请求 →        响应 ←

前端：收集操作、画页面
后端：接请求、处理业务、返回 JSON
数据库：存数据、查数据
```

**中区固定区**（知识点三、四、五 · 四要素、流程与方法）：

```text
接口四要素：
  URL    找谁      /api/v1/departments/
  方法   做什么    GET / POST / PUT / DELETE
  参数   带什么    page=1&page_size=10
  返回   给什么    200 + {"items": [...], "total": 5}

处理流程：
请求进来 → 匹配 URL → 确认方法 → 解析参数 → 执行 → 返回

方法语义：GET 查 / POST 增 / PUT 改 / DELETE 删
```

**右区动态区**（随课堂进度逐步添加）：

```text
循环二：
路径参数：/hello/{name}    → 定位"某一个"
查询参数：/hello?name=...  → 筛选"一批"

循环三：
状态码：200 成功 / 201 新增 / 404 没找到 / 422 参数不对

FastAPI 揭幕：
@app.get("/hello")
def hello():
    return {"message": "你好，后端"}
URL 和方法在装饰器上，参数在函数签名上，返回自动变 JSON
```

#### 一、后端在做什么——分工、请求响应与接口四要素

##### 【要领讲解】（约 21 分钟）

##### 前端、后端、数据库的分工

（← 对应知识点「前端、后端、数据库的分工」①②）

教员在黑板左侧画三个框：

```text
浏览器（前端）  →  服务器（后端）  →  数据库
   显示              处理              存储
```

用"查部门"走一遍五步：

| 步骤 | 谁在做 | 做什么 |
|---|---|---|
| 1 | 前端 | 用户在页面上点"查询部门" |
| 2 | 后端 | 收到请求，去数据库查部门 |
| 3 | 数据库 | 把部门数据返回给后端 |
| 4 | 后端 | 把数据整理成 JSON，返回给前端 |
| 5 | 前端 | 把 JSON 显示成表格 |

打一个比方：前端像值班室门口的**接待员**，负责把用户的操作变成请求、把结果显示出来；后端像**业务科室**，负责按规矩办事；数据库像**档案室**，负责把数据存好、查出来。

强调一句话：**后端不负责"画页面"，它负责"按要求取数据、处理数据、返回数据"。**

##### 请求—响应模型与 JSON

（← 对应知识点「请求—响应模型与 JSON」①②）

- **请求**：前端发给后端的话。
- **响应**：后端回给前端的话。

一次请求在"话"的层面大概长这样：

```text
GET /api/v1/departments/?page=1&page_size=10
Host: 127.0.0.1:8000
```

第一行告诉我们三件事：用什么方法（`GET`）、找哪个路径（`/api/v1/departments/`）、带什么条件（`page=1&page_size=10`）。第二行告诉我们找哪台服务器。

后端返回的数据通常长这样：

```json
{
  "items": [
    {"id": 1, "name": "作训科"},
    {"id": 2, "name": "通信科"}
  ],
  "total": 2
}
```

认识 JSON 只需三件事：大括号 `{}` 是一个对象，中括号 `[]` 是一串数据，`"键": 值` 是一对说明。前端拿到 JSON 后，自己决定画成表格还是卡片——**后端不管长相，只管内容**。

一句话：**请求是前端说的话，响应是后端回的话，JSON 是双方约定的"普通话"。**

##### 接口四要素：一次后端请求的完整流程

（← 对应知识点「接口四要素：一次后端请求的完整流程」①②）

用 duty 的部门列表接口举例，把四要素与后端的四个动作对上：

| 要素 | 回答的问题 | 后端动作 | duty 部门列表 |
|---|---|---|---|
| URL | 找谁 | 匹配路由 | `/api/v1/departments/` |
| 方法 | 做什么 | 确定操作语义 | `GET`（查） |
| 参数 | 带什么 | 解析输入 | `page=1&page_size=10` |
| 返回 | 给什么 | 构造响应 | `200 + {"items": [...], "total": 5}` |

一次请求的完整流程：

```text
请求进来 → 匹配 URL（找谁）→ 确认方法（做什么）→ 解析参数（带什么）→ 执行 → 返回（给什么）
```

口诀：**一个接口 = 找谁（URL）+ 做什么（方法）+ 带什么（参数）+ 给什么（返回）。**

强调"四格缺一不可"：没有 URL 不知道找谁；没有方法不知道干什么；没有参数可能找错范围；没有返回前端拿不到东西。

##### 【案例解析】（约 8 分钟）

（← 对应知识点「前端、后端、数据库的分工」④；知识点「接口四要素」③④）

**第一步，带看部门列表接口。** 教员打开 duty 的 `/docs`，找到部门列表接口，带学员逐格填四要素：

| 四要素 | 在这个接口里是什么 |
|---|---|
| URL | `/api/v1/departments/` |
| 方法 | `GET` |
| 参数 | `page`、`page_size`，都可选，默认第 1 页、每页 10 条 |
| 返回 | 一个 JSON：`items` 是部门列表，`total` 是总数 |

**第二步，独立分析"新增一条值班记录"。** 教员只给需求，不给答案，请学员说出每一步由哪一层完成：

| 步骤 | 哪一层 | 做什么 |
|---|---|---|
| 1 | 前端 | 收集表单，发出"新增"请求 |
| 2 | 后端 | 检查数据是否完整、合法 |
| 3 | 数据库 | 把记录写进表里 |
| 4 | 后端 | 把结果整理成 JSON，告诉前端"新增成功" |

**第三步，独立分析一个未见过的接口。** 教员给出 `/health` 的接口说明：URL 是 `/health`，方法 `GET`，没有参数，返回 `{"status": "ok"}`。请学员说出四要素，并画出"请求—执行—返回"三步流程。

#### 二、接口怎么描述——URL、方法与参数

##### 【要领讲解】（约 13 分钟）

##### URL 与路由：找谁

（← 对应知识点「URL 与路由：找谁」①②）

把一条完整 URL 拆开看：

| 部分 | 例子 | 说明 |
|---|---|---|
| 协议 | `http://` | 用什么方式说话 |
| 主机 | `127.0.0.1` | 找哪台服务器 |
| 端口 | `8000` | 找服务器上的哪个服务 |
| 路径 | `/api/v1/departments/` | 找哪个资源 |
| 查询串 | `?page=1&page_size=10` | 带什么条件 |

**路由**就是一张"URL 路径 → 处理函数"的对应表，像总机的转接表：拨 ` departments/` 转到"查部门列表"的分机，拨 `departments/3` 转到"查 3 号部门"的分机。

所以 `/departments/` 与 `/departments/3` 看起来只差一个 `3`，却会进入不同的处理逻辑；如果路径在表里找不到，就只能回 **404 没找到**。

一句话：**URL 是门牌号，路由是总机的转接表。**

##### HTTP 方法与操作语义：做什么

（← 对应知识点「HTTP 方法与操作语义：做什么」①②）

| 方法 | 意思 | duty 中的例子 |
|---|---|---|
| GET | 查 | 查部门列表、查 3 号部门 |
| POST | 新增 | 新增一个部门 |
| PUT | 修改 | 修改部门名称 |
| DELETE | 删除 | 删除一个部门 |

方法的语义是**约定**，不是建议：GET 只读，POST 新增，PUT 修改，DELETE 删除。

为什么"新增"不能用 GET？三个理由：

1. GET 的语义是"只读"，用它改数据，前后端都会误解；
2. GET 可能被浏览器缓存、预取或重复执行，新增操作会被重复触发；
3. GET 的参数放在 URL 里，不适合传大量数据。

一句话：**URL 是对象，方法是动作。** `GET /departments/` 是"查部门集合"，`POST /departments/` 是"新增一个部门"。

##### 路径参数与查询参数：带什么

（← 对应知识点「路径参数与查询参数：带什么」①②）

先看两种写法。这里先只看"参数写在哪"，`@app.get` 是什么，最后一节讲：

```python
@app.get("/hello/{name}")
def hello(name: str):
    return {"message": f"你好，{name}"}
```

访问 `/hello/张三` → `{"message": "你好，张三"}`。

```python
@app.get("/hello")
def hello(name: str = "同学"):
    return {"message": f"你好，{name}"}
```

访问 `/hello?name=张三` → `{"message": "你好，张三"}`；不传 `name` 时用默认值"同学"。

对比：

| 类型 | 位置 | 例子 | 适合 |
|---|---|---|---|
| 路径参数 | URL 路径里 | `/hello/张三` | 定位"某一个" |
| 查询参数 | `?` 后面 | `/hello?name=张三` | 筛选、带条件 |

口诀：**定位一个走路径，筛选一批问号后。**

duty 中两种参数并存：部门详情用路径参数 `/api/v1/departments/{dept_id}`，部门列表用查询参数 `?page=1&page_size=10`。

##### 【案例解析】（约 4 分钟）

（← 对应知识点「URL 与路由」「HTTP 方法与操作语义」「路径参数与查询参数」③）

教员打开 duty 的 `/docs`，并排看两个接口：

| 需求 | 接口 | 参数类型 |
|---|---|---|
| 查第 3 页的部门 | `/api/v1/departments/?page=3&page_size=10` | 查询参数 |
| 查 3 号部门 | `/api/v1/departments/3` | 路径参数 |

带学员指认：第一个接口的 URL 以 `/departments/` 结尾，`page` 在 `?` 后面；第二个接口的 URL 把 `3` 直接写进了路径。

再演示一次"路径写错"：访问一个不存在的路径，返回 404——**路由表里没有这一行，所以找不到。**

教员再次说明：`/docs` 是"说明书"，先会查、会用，它是怎么来的，最后一节讲。

##### 【课堂研讨】（约 3 分钟）

（← 对应知识点「URL 与路由」「HTTP 方法与操作语义」「路径参数与查询参数」⑤）

快速问答：

1. "查第 3 页的部门"用哪种参数？
2. "查 3 号部门"用哪种参数？
3. "新增部门"能不能用 GET？
4. URL 写错会返回什么？

归纳：第 1 题查询参数，第 2 题路径参数，第 3 题不能、要用 POST，第 4 题返回 404。

##### 【小结讲评】（约 2 分钟）

一句口诀收束本循环：

> URL 门牌号，方法是动作；定位一个走路径，筛选一批问号后。

过渡：接口办完事，给前端回什么？——进入循环三。

#### 三、接口给什么、谁来落实——状态码与 FastAPI 框架

##### 【要领讲解】（约 13 分钟）

##### 返回与状态码：给什么

（← 对应知识点「返回与状态码：给什么」①②）

一次响应由两部分组成：**状态码 + 返回体**。返回体通常就是前面看到的 JSON。

先记四个状态码：

| 状态码 | 意思 | 生活类比 | duty 中的例子 |
|---|---|---|---|
| 200 | 成功 | 办妥了 | 查到部门列表 |
| 201 | 新增成功 | 新登记上了 | 新增一个部门 |
| 404 | 没找到 | 查无此地址 | 查一个不存在的部门、路径写错 |
| 422 | 参数不对 | 材料不合格 | 页码传了字母 |

强调：**先看状态码，再看内容。** 200 不代表数据一定对，但 404、422 一定说明这次请求有问题。

讲到 422 时留扣：**"参数不对，为什么会自动返回 422？这个'自动'是谁做的？——最后一节揭幕。"**

##### FastAPI 框架：原理、作用与开发方式的变化

（← 对应知识点「FastAPI 框架」①②）

先问一个问题：**如果没有框架，写一个 `/hello` 接口要做什么？**

要做的事包括：监听端口、接收网络连接、解析 HTTP 请求行和请求头、判断路径是不是 `/hello`、判断方法是不是 GET、把返回的字典转成 JSON、设置状态码 200、把响应发回去……这些"脏活"每写一个接口都要重复一遍。

没有框架时，代码大致是这个样子（示意，不要求掌握）：

```python
# 示意：没有框架时，这些事都要自己做
server = socket(...)                 # 监听端口
request = parse_http(server.recv())  # 解析 HTTP 请求
if request.path == "/hello" and request.method == "GET":
    body = json.dumps({"message": "你好，后端"})  # 手动转 JSON
    send_response(200, body)                     # 手动设状态码
```

**用了 FastAPI，同样的接口只剩五行：**

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/hello")
def hello():
    return {"message": "你好，后端"}
```

只讲三件事：

1. `@app.get("/hello")`：告诉框架"有人用 GET 访问 `/hello` 时，执行下面的函数"；
2. `return {"message": ...}`：返回一个字典，框架自动把它变成 JSON；
3. `/docs`：框架根据代码自动生成的接口说明书，不用自己写。

启动服务：

```bash
uvicorn main:app --reload --port 8000
```

`main` 是文件名，`app` 是 `FastAPI()` 实例，`--reload` 是改了代码自动重启，`--port 8000` 是端口。

**FastAPI 和前面的接口四要素怎么结合？**看这张表：

| 四要素 | 在 FastAPI 代码里的位置 |
|---|---|
| URL | `@app.get("/hello")` 里的 `"/hello"` |
| 方法 | `@app.get` 里的 `get` |
| 参数 | 函数签名 `def hello(name: str)` |
| 返回 | `return {...}`，框架自动转成 JSON、自动设状态码 |

**回收前面的伏笔：**

- 前面用的 `/docs`，就是 FastAPI 根据这些代码自动生成的；
- 前面看到的 422，就是 FastAPI 根据函数签名里的类型（如 `name: str`）自动校验，不合格时返回的，提示里的 `loc` 和 `msg` 告诉你是哪个参数、错在哪；
- 前面看到的 404，是路由表里没有匹配的 URL 时框架返回的。

**开发方式的变化**：从"自己处理协议细节"变成"声明接口契约"——你只写"URL + 方法 + 函数 + 参数类型 + 返回值"，框架负责剩下的。

一句话：**FastAPI 不是 Python 本身，是 Python 的一个 Web 框架；它替我们做脏活，但 HTTP 的四要素、方法、状态码这些约定，还要我们自己懂。**

##### 【案例解析】（约 4 分钟）

（← 对应知识点「返回与状态码」③；知识点「FastAPI 框架」③）

读 duty 的 `/health`：

```python
@app.get("/health")
def health():
    return {"status": "ok"}
```

对照四要素：URL `/health`，方法 `GET`，无参数，返回 `{"status": "ok"}`。

现场演示四件事：

1. 在 `/docs` 里找到 `/health`，点 "Try it out"，再点 "Execute"，看到状态码 200 和响应体；
2. 访问一个不存在的路径（如 `/healthh`），看到 404；
3. 在部门列表接口把 `page` 传成 `abc`，看到 422，指出响应里的 `detail`、`loc` 和 `msg`；
4. 回到代码：这三件事——200 的默认值、404 的路由匹配、422 的类型校验——都不是手写的，是 FastAPI 做的。

点题：**现在回头看，前面看到的 `/docs` 和 422 都不是天上掉下来的，是这个框架在背后替我们做。**

##### 【课堂研讨】（约 3 分钟）

（← 对应知识点「FastAPI 框架」⑤；知识点「返回与状态码」⑤）

快速问答：

1. FastAPI 就是 Python 吗？
2. 用了 FastAPI，还要不要懂 HTTP？
3. `/docs` 是手写的吗？
4. 422 是谁返回的？
5. 没有框架会怎样？

归纳：FastAPI 是 Python 的 Web 框架，不是 Python 本身；用了框架更要懂 HTTP，否则不知道四要素怎么落到代码；`/docs` 是框架自动生成的；422 是框架根据类型声明自动校验返回的；没有框架，就要自己处理协议细节，开发慢、易出错。

##### 【小结讲评】（约 3 分钟）

四句话收束全课：

> 后端 = 接收请求，返回数据。
> 一个接口 = URL + 方法 + 参数 + 返回。
> 先看状态码，再看内容；路径定位一个，查询筛选一批。
> FastAPI = 把四要素和协议细节封装起来的框架：你声明契约，它做脏活。

回归 duty：打开 `/docs`，任选一个接口，能不能说出它的四要素，并指出它在代码里对应哪一行？——这就是本课要带走的能力。

布置作业，预告课次5：表怎么建、接口怎么定。

### 3.2 教学设计

【循环一：后端在做什么——分工、请求响应与接口四要素】

【要领讲解】设计意图：本循环覆盖知识点 1—3，落在 ①② 理解层。顺序按"具体分工 → 运行机制 → 接口形式"递进：先用 duty 的"查部门"让学员看清三层各干什么（① 认知），再解释请求—响应为什么必须经过后端、数据为什么用 JSON 装（② 解释），最后把接口抽象成四要素和一条处理流程（①② 合并）。本课次是理论课，不急于写代码；"后端"先作为黑盒讲，框架的名字只在导入时点一句，为最后的揭幕留扣。

【案例解析】设计意图：对应知识点 1 的 ④ 独立 与知识点 3 的 ③④。先由教员带看部门列表接口，把四要素与处理环节对上（③ 模仿）；再给"新增一条值班记录"和"一个未见过的 `/health` 接口"两个小任务，让学员独立说出"哪一层做什么""四要素是什么"（④ 独立）。理论课的"独立"以口头分析和画流程替代写代码，重点是让学员把刚学的骨架用起来，而不是照抄结论。

【课堂研讨】设计意图：对应 ⑤ 辨析。三个问题分别针对"表格是后端画的""返回一定是 JSON""只写 URL 不写方法"三个高频误解。先让学员说，再由教员用 duty 页面和真实返回对照纠正；理论课的辨析靠说理，不靠改错题。答完这三个问题，学员对"三层分工"和"四要素缺一不可"的理解就从"听过"变成"说得清"。

【小结讲评】设计意图：用三句话和一句口诀把三个知识点压成可复述的结构，降低零基础学员的记忆负担；并用"四要素的每一格拆开是什么"过渡到循环二。此处刻意保持"框架"不出场，让 `/docs` 只作为"项目自带的说明书"出现，为循环三的揭幕保留认知落差。

【教学方法】案例贯穿法（一个"查部门"讲到底）+ 流程图归纳 + 追问式讲授 + 独立分析小任务。

【课程思政】以"前端显示、后端处理、数据库存储"的分工，类比部队岗位分工——每个岗位守好自己的职责，系统才能顺畅运转；以"接口是前后端约定"引出"约定就是纪律"，为后续模块协作打基础。

【课堂互动】"表格是谁画的"用举手投票，先让学员选边，再请两名不同选择的学员说理由；"新增值班记录"请一名学员口头说流程，其他学员补充。

【循环二：接口怎么描述——URL、方法与参数】

【要领讲解】设计意图：本循环覆盖知识点 4—6，落在 ①②。把四要素的后三格拆开：URL 对应"找谁"、方法对应"做什么"、参数对应"带什么"。URL 先讲组成再讲路由表，让学员理解"路径不是随便写的，它决定请求进哪个处理函数"；方法用"查/增/改/删"的语义约定讲，重点解释"新增为什么不能用 GET"；参数用路径/查询并排对比，直接落到 duty 的部门列表与部门详情。三块都只讲"接口的行为约定"，不讲"框架怎么实现"，把实现留给循环三。

【案例解析】设计意图：对应 ③ 模仿。用 duty 部门列表（查询参数）与部门详情（路径参数）两个真实接口并排，让学员在 `/docs` 上把 URL、方法、参数逐项指认出来；`/docs` 在这里只当"说明书"用，明确告诉学员"先会用，最后讲它怎么来的"，既满足当前指认的需要，又不提前泄露框架。

【课堂研讨】设计意图：对应 ⑤ 辨析。两个"查第 3 页 / 查 3 号"的对照问题，直接把"路径定位一个、查询筛选一批"的口诀用起来；"新增能不能用 GET""URL 写错会怎样"分别巩固方法语义和 404 的因果。问题短、答案唯一，适合在 45 分钟后快速推进，也为循环三的状态码做铺垫。

【小结讲评】设计意图：用"URL 门牌号、方法是动作、参数分两路"的口诀收束本循环，把三个知识点压成一句可复述的话；同时以"接口给什么、谁来落实"过渡到循环三，形成"是什么—怎么描述—给什么/谁实现"的完整链条。

【教学方法】对比法（列表/详情、路径/查询并排）+ 口诀归纳 + `/docs` 指认。

【课程思政】以"URL 是门牌号、方法是动作"强调按规矩办事、按约定协作；以"路径定位一个、查询筛选一批"类比工作中"定位到人、筛选到事"的精准作风。

【课堂互动】"查第 3 页还是查 3 号"用快速抢答；"新增能不能用 GET"先举手投票，再请学员说理由，最后由教员用方法语义收口。

【循环三：接口给什么、谁来落实——状态码与 FastAPI 框架】

【要领讲解】设计意图：本循环覆盖知识点 7—8，是本课的收束与揭幕。先讲"返回 = 状态码 + 返回体"，把 200/201/404/422 四个码讲清（①②）；讲到 422 时故意留扣——"参数不对为什么会自动返回 422？这个'自动'是谁做的？"——把学员的注意力引向框架。接着揭幕 FastAPI：先描述"没有框架时要自己处理什么"，再展示五行最小接口，最后把四要素逐格映射到代码，回收前面所有伏笔（`/docs` 是它生成的、422 是它自动校验的、路由和方法写在装饰器上）。这一步把"框架"从名词变成"替我们做脏活的工具"，完成全课的总收。

【案例解析】设计意图：对应 ③ 模仿。以 duty 的 `/health` 为真实样本，先读代码、再对四要素、最后到 `/docs` 点一次 "Try it out"，把"代码—文档—响应"三者对应起来；穿插 404（路径不对）与 422（参数类型不对）的现场演示，让学员亲眼看到"框架在哪里接手"。最后用一段"没有框架"的示意代码做对比，让"开发方式的变化"看得见，而不是停留在口号上。

【课堂研讨】设计意图：对应 ⑤ 辨析。五个问题分别针对"FastAPI 就是 Python""用了框架就不用懂 HTTP""`/docs` 是手写的""422 是手写的""没有框架也一样"五个误解。答完这五个问题，学员就能把"框架"和"HTTP 约定"分开：约定是根本，框架是实现。这是本课从"会看接口"走向"理解工具"的关键一步。

【小结讲评】设计意图：用四句话收束全课——后端做什么、接口四要素、状态码怎么读、框架干什么；再回归 duty，让学员任选一个接口说四要素并指出它在代码里的位置，完成从"听懂"到"说清"的闭环；最后布置作业、预告课次5 的接口设计，使本课成为专题二的认知起点。

【教学方法】揭幕式总结（先留扣、后回收）+ 对比法（有框架/无框架）+ 代码—文档—响应三方对照 + 回归项目检查。

【课程思政】以状态码的"标准回执"类比部队文书流转——事事有回音、件件有交代；以"框架替我们做脏活，但 HTTP 约定还要自己懂"说明工具与基本功的关系，防止"只会调库、不懂原理"；以 duty 服务值班业务，体会技术服务实战、信息强军的价值。

【课堂互动】讲 422 时先让学员猜"这个 422 是谁返回的"，再揭幕；讲"没有框架"时请学员列举"框架可能替我们做了哪些事"，最后由教员用五行代码逐条对照。

### 4.2 教后反思
