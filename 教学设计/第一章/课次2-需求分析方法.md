# 课次2：需求分析方法——把"想要"变成"可验证"

## 一、课次基本信息

| 项目 | 内容 |
|---|---|
| 所属专题 | 专题一：软件工程基础 |
| 学时 | 2 学时（理论，约 90 分钟） |
| 教材对应 | 第2章 需求工程 |
| 开场案例 | 火星气候探测者号事故（1999） |
| 与 duty 的关系 | 本课次以概念与方法为主；duty 仅在课末作为实践课的预告出现 |

## 二、教学目标

**知识与技能**

- 能说清需求的三个组成部分：功能需求、非功能需求、约束条件。
- 能区分"用户想要的"与"用户需要的"。
- 能说出需求获取的常用方法及其适用场景：访谈、观察、问卷、原型、文档分析。
- 了解 SRS 结构（课前阅读），能按讲义中的结构自查需求文档。
- 能按"作为[角色]，我想要[功能]，以便[价值]"编写用户故事、写验收标准；能用 INVEST 清单自查（讲义）。
- 能用 MoSCoW 划分优先级，并对非功能需求做初步量化。
- 能说出需求评审的检查要点和变更管理的基本做法。

**过程与方法**

- 经历"真实失败案例 → 追问需求根因 → 建立需求方法 → 形成检查清单"的学习过程。
- 学会用"角色—场景—规则—验收"的框架分析需求。

**情感态度与价值观**

- 建立"需求是契约、需求错误代价最高"的意识。
- 养成追问、确认、记录、评审的习惯。

## 教学内容

> 对应教学计划：专题一基本内容第 2 条"需求分析方法"，以及第 3 条中的"功能优先级划分"。

1. **需求的定义与分类**：功能需求、非功能需求、约束条件。
2. **利益相关者**：用户、管理员、运维等；"想要的"与"需要的"。
3. **需求获取方法**：访谈、观察、问卷、原型、文档分析及适用场景。
4. **需求表达**：用户故事格式；验收标准。SRS 结构、INVEST 清单放到课前讲义，课堂只用于自查，不展开讲。
5. **功能优先级**：MoSCoW（Must / Should / Could / Won't）。
6. **非功能需求**：性能、安全、可用性、可维护性；量化描述。
7. **需求评审与变更**：评审清单、变更影响、追踪。
8. **需求与后续环节的关系**：需求如何影响设计、编码、测试。

## 三、重点与难点

**重点**

- 需求的分类与边界。
- 需求获取方法的综合运用。
- 用户故事的规范编写与验收标准。
- 功能优先级的划分。

**难点**

- 区分"用户想要的"与"用户需要的"。
- 非功能需求的量化描述。
- 需求文档的完整性与一致性。
- 跨团队接口与假设的显式化。

## 四、学情分析与教学策略

学生已经知道生命周期中有"需求"阶段，但缺少真实的需求分析体验：容易把"界面"当成"需求"，也容易漏掉权限、异常、性能、接口约定等"用户看不见但系统必须有"的内容。

本课次**以理论和知识体系为主**，用真实失败案例开场，让学生先感到"需求问题真实、代价高"，再建立方法框架。duty 只在课末作为实践课的预告，不展开。

教学策略：

- **案例先行**：火星气候探测者号的单位不一致，说明需求/接口约定不清的代价；
- **概念分层**：需求 = 功能 + 非功能 + 约束；想要的 ≠ 需要的；
- **方法闭环**：获取 → 表达 → 优先级 → 评审 → 变更；
- **出口题**：用 3 个问题检验是否真正理解。

## 六、教学过程

### 环节1：开场案例——火星气候探测者号（15 分钟）

**教师讲述（事实，不渲染）**

> 1999 年 9 月 23 日，美国宇航局的火星气候探测者号在进入火星轨道时失联。事后调查认为，探测器进入了比预期低得多的轨道，最终在大气层中解体。项目损失约 1.25 亿美元。
>
> 直接原因听起来很小：地面软件计算推进器冲量时使用的单位是"磅力·秒"，而探测器软件期望的是"牛顿·秒"。两边的数值没有换算，导致轨道修正出现偏差。两边各自都"按自己的规格做对了"，但规格之间没有对齐。

**教师提问（先不解释）**

1. "这是'技术问题'还是'需求/沟通问题'？"
2. "如果需求文档和接口规格写清楚了单位、数据格式、假设，事故能不能避免？"
3. "为什么两个团队都'做对了'，系统却失败了？"

**学生讨论（3 分钟）**

- 小组快速讨论，派 1–2 组回答。

**教师归纳**

- 不是"谁写错了代码"，而是**接口契约、单位约定、跨团队验证**出了问题；
- 需求不只是"功能列表"，还包括**数据格式、单位、假设、约束、验收标准**；
- 需求阶段的"一句话没写清"，可能造成系统级的失败。

**过渡**

> "这就是需求工程要解决的问题：把'想要'变成'说清楚、可验证、能对齐'。"

---

### 环节2：需求是什么（15 分钟）

**教师讲授需求的三个组成部分**

| 类型 | 回答的问题 | 示例（图书借阅系统） |
|---|---|---|
| 功能需求 | 系统做什么 | 借书、还书、续借、查询、逾期罚款 |
| 非功能需求 | 做得怎么样 | 查询 < 1 秒；只有图书馆员能入库；数据每天备份 |
| 约束条件 | 外部限制 | 必须使用学校统一身份认证；部署在校园网内 |

**利益相关者**

- 学生、图书馆员、管理员、运维人员；
- 不同角色的目标可能冲突，需要平衡。

**想要的 vs 需要的**

- 想要：推荐算法、社交分享、积分商城；
- 需要：借还、查询、逾期处理、权限控制。

**需求不是界面**

> 用户说"我想要一个搜索框"，背后可能是"我想快速找到某本书"。搜索框是方案，快速找到是需求。

**强调**

> 需求是"用户需要解决的问题 + 系统必须满足的条件"，不是"用户提出的界面方案"。

---

### 环节3：需求获取方法（20 分钟）

**教师讲授五种方法**

| 方法 | 能补什么 | 图书借阅系统的例子 | 注意事项 |
|---|---|---|---|
| 用户访谈 | 业务规则、例外、优先级 | 问图书馆员：逾期怎么罚？丢书怎么赔？ | 开放式问题、追问"为什么" |
| 现场观察 | 实际操作习惯、隐性流程 | 看学生怎么借书、怎么找书 | 记录真实动作，不只看说法 |
| 问卷调查 | 大范围意见、频率 | 问学生最常用哪些功能 | 问题具体、避免引导 |
| 原型法 | 界面与交互需求 | 画一个借书页面的草图 | 原型是沟通工具，不是最终界面 |
| 文档分析 | 字段、约束、接口 | 看现有借阅规则、学生信息表 | 核对字段和约束 |

**提问技巧**

- 开放式："你平时怎么借书？"
- 追问："为什么？""然后呢？""如果……会怎样？"
- 避免引导："你是不是想要一个搜索框？"（会把答案带偏）

**课堂小练习（5 分钟）**

> "如果让你访谈图书馆员，写出 3 个开放式问题。"

**示例**

- 一天中什么时候最忙？
- 借书时最常遇到的问题是什么？
- 逾期罚款现在是怎么算的？

**强调**

- 没有一种方法能单独拿到完整需求；
- 访谈补规则，观察补实际操作，文档分析补字段和约束，原型补交互；
- 获取之后要**确认**：复述给用户听，避免理解偏差。

---

### 环节4：需求表达——用户故事与验收标准（20 分钟）

> **边界**：SRS 结构、INVEST 清单已放在课前讲义；课堂只练“把需求写成用户故事＋验收标准”，不展开讲模板。

**用户故事格式**

> 作为 **[角色]**，我想要 **[功能]**，以便 **[价值]**。

**好/坏对比**

- 坏："系统要能借书。"
- 好："作为学生，我想要通过学号借书，以便不用带借书证。"
- 验收标准：
  - 输入有效学号后，系统显示可借图书；
  - 无库存时提示"暂无可借"；
  - 超过借阅上限时拒绝并说明原因。

**写验收标准的三个检查**

1. 可验证：能用一个操作或数据判断通过/不通过；
2. 覆盖异常：无库存、超限、输入错；
3. 不写实现：写"系统应该怎样"，不写"用哪个函数"。

> **回扣火星案例**：单位、格式、字段含义这些"接口与数据约定"也要写进验收标准；它们是 SRS 讲义第 5 项，课堂不展开。

**课堂练习（10 分钟）**

> 把"还书"写成 1 条用户故事 + 2 条验收标准；写完后用讲义中的 INVEST 清单自查一遍（1 分钟）。

**示例**

> 作为图书馆员，我想要扫描图书条码完成还书，以便快速处理归还。
> 验收：扫描后显示借阅记录；逾期时显示罚款金额。

**互评（2 分钟）**

- 两人交换，按"角色 / 功能 / 价值 / 验收可验证"四项打勾；
- 不评价文采，只看能不能验收。

---

### 环节5：优先级与非功能需求（10 分钟）

**MoSCoW 示例（图书借阅系统）**

| 优先级 | 功能 |
|---|---|
| Must | 借书、还书、查询图书 |
| Should | 续借、逾期罚款 |
| Could | 预约、推荐 |
| Won't（本期） | 社交分享、积分商城 |

**非功能需求量化**

| 类别 | 模糊写法 | 可验证写法 |
|---|---|---|
| 性能 | 系统要快 | 查询响应 < 1 秒（1000 条数据） |
| 安全 | 系统要安全 | 只有图书馆员能入库；密码不明文存储 |
| 可用性 | 要好用 | 借书流程不超过 3 步；错误提示可理解 |
| 可维护性 | 代码要好 | 新增一个借阅规则不改动页面代码 |

**强调**

> 非功能需求不量化，就无法测试，也无法验收；接口约定不写清，就会出现"双方都做对、系统却失败"。

---

### 环节6：需求评审与变更（5 分钟）

**评审检查清单**

- [ ] 角色是否齐全？
- [ ] 主要流程是否覆盖？
- [ ] 每条用户故事是否有验收标准？
- [ ] 优先级是否有理由？
- [ ] 非功能需求是否可验证？
- [ ] 接口、单位、数据格式、假设是否写清？
- [ ] 术语、编号、字段名是否一致？

**需求变更**

- 变更不可避免；关键是**评估影响**：改需求 → 改设计 → 改代码 → 改测试；
- 建立变更记录：谁提出、为什么、影响哪些模块、何时完成。

**强调**

> 需求文档不是"写完就锁死"，而是"变更时有依据、有记录"。

---

### 环节7：小结与出口题（5 分钟）

**教师总结**

> 需求 = 功能 + 非功能 + 约束。
>
> 需求工程 = 获取（访谈/观察/问卷/原型/文档）+ 表达（用户故事/验收标准；SRS 结构见讲义）+ 取舍（MoSCoW）+ 验证（验收标准/评审）+ 变更管理。
>
> 需求是设计、编码、测试的输入；需求错误，是返工成本最高的错误。

**出口题（当场写，3 分钟）**

1. 用一句话说清"用户想要的"和"用户需要的"的区别。
2. 火星气候探测者号事故，应该在需求/接口规格里补上哪三项内容才能避免？
3. 为什么非功能需求必须量化？

**布置作业**

1. 复习讲义：SRS 结构模板、INVEST 清单，各写一句"哪一项最容易漏"。
2. 选一个你熟悉的系统（图书借阅、选课、点餐等），写出 3 个角色、5 条功能需求、3 条非功能需求、2 条约束。
3. 写 3 条用户故事，每条带验收标准，并用讲义中的 INVEST 清单自查。
4. 用 MoSCoW 给这 3 条故事排序，写明理由。
5. 预习课次3：duty 需求文档编写（回顾用户故事、验收标准与 MoSCoW，带纸笔/电脑）。

## 七、板书设计

```
需求 = 功能 + 非功能 + 约束
想要的 ≠ 需要的

获取：访谈 / 观察 / 问卷 / 原型 / 文档
表达：用户故事（作为…我想要…以便…）+ 验收标准；SRS 结构见讲义
检查：验收标准 + INVEST 清单（讲义）
取舍：MoSCoW
验证：评审 + 变更记录

接口约定：单位 / 格式 / 字段 / 假设 / 错误码
```
