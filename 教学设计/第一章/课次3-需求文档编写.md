| 项目 | 内容 |

| 主线案例 | 值班数据统计系统（duty） |
| 教学形态 | 角色扮演获取需求 + 模板填写 + 组间评审 + 当场落稿 |
| 与前序课次的关系 | 课次2 已讲需求分类、获取方法、用户故事、验收标准与 MoSCoW；本课次是"用方法"，不是"再讲一遍方法" |

## 二、教学目标

**知识与技能**

- 能说出需求文档的结构与各章节的写作要点。
- 能通过访谈与追问获取需求，区分"用户想要的"与"用户需要的"。
- 能把访谈记录整理成功能清单，并用 MoSCoW 排定优先级。
- 能按"作为—我想要—以便"的格式编写用户故事，并写出可验证的验收标准。
- 能用可度量的方式描述非功能需求与约束。
- 能按模板完成《duty 需求文档 v1》，并通过组间评审完成修订落稿。

**过程与方法**

- 经历"角色扮演获取需求 → 整理功能清单 → 编写用户故事 → 补充非功能需求 → 组间评审 → 修订落稿"的完整过程。
- 学会"先问清、再写清、后评清"：先把用户的话问明白，再写成开发能执行的需求，最后通过评审发现遗漏与矛盾。

**情感态度与价值观**

- 树立以用户为中心的需求观，认识到"需求写不清，后面全白干"。
- 养成规范、完整、一致的文档撰写习惯。
- 体会团队分工与评审协作的作用，强化保密意识与涉密信息脱敏的自觉。

## 三、教学内容

> 对应教学计划：专题一基本内容第 3 条"需求文档编写"。

1. **需求文档的结构与写作要点**：文档信息、项目背景与目标、用户角色与职责、功能需求、非功能需求、约束与假设、评审记录。
2. **duty 的业务背景与目标**：系统管什么、给谁用、解决什么问题、边界在哪里。
3. **用户角色与职责**：系统用户与业务人员的区别；管理员、普通用户、值班员、查班人员。
4. **需求获取的实施**：角色扮演、访谈提纲、开放式提问与追问；从原话中提取事实、痛点与业务规则。
5. **功能清单与 MoSCoW 优先级**：按"动词 + 对象"写功能；Must / Should / Could / Won't 的判定依据。
6. **用户故事与验收标准**：角色、功能、价值三要素；验收标准的"给定—当—则"写法；INVEST 自查。
7. **非功能需求与约束**：性能、安全与保密、可用性、兼容性、可靠性；约束与假设的写法。
8. **需求评审与修订落稿**：评审清单、评审意见的记录与处理、文档一致性检查。

## 四、重点与难点

**重点**

- 需求文档的结构与各章节写作要点。
- 功能清单的整理与 MoSCoW 优先级划分。
- 用户故事与可验证的验收标准。
- 需求评审与修订落稿。

**难点**

- 区分"用户想要的"与"用户需要的"，不被"给我加个按钮"带偏。
- 保证需求的完整性与一致性：角色、功能、流程、术语前后对得上。
- 把非功能需求写得可度量，而不是"要好用、要安全"。

## 五、学情分析与教学策略

课次2 已经讲过需求获取、用户故事、验收标准和 MoSCoW，学生"知道"这些名词，但没有完整写过一份需求文档。本课次的关键不是继续讲理论，而是**把方法用一遍、把文档写出来**。

策略：

- **模板驱动**：一开课就发需求文档模板，每个环节只填模板中的一块，学生始终知道"现在写到哪、还差什么"。
- **角色扮演**：一半人演值班业务骨干，一半人演开发人员，访谈 5 分钟后交换角色。让"问"和"记"都真实发生，避免凭空编需求。
- **先写后评**：不追求一次写对；先完成 v1，再通过组间评审发现问题、当场修订。
- **对照真实系统**：评审后用 duty 的真实模块与接口清单对照，检查"抓准了什么、漏了什么、多想了什么"，但不要求学生的文档与真实实现一一对应。
- **控制颗粒度**：只写"做什么、为什么做、做到什么程度算完成"，不写表结构、接口参数和页面布局。
- **时间不足时的取舍**：优先保证访谈、功能清单、用户故事与评审；非功能需求课上先写 2–3 条，其余课后补齐。

## 七、教学过程

### 环节1：任务说明与模板解读（8 分钟）

**教师说明**

> 今天的任务：以小组为单位，为 duty 写一份《duty 需求文档 v1》。
>
> 课次2 已经讲了怎么问、怎么写。今天不再讲方法，直接用：先访谈，再整理，最后按模板落稿。
>
> **今天不写模块划分、不写表结构、不写接口参数、不写页面布局**——这些是课次5 的内容。

**交付物**

每组提交一份《duty 需求文档 v1》，至少包含：

- 项目背景与目标；
- 用户角色与职责；
- 功能清单 + MoSCoW 优先级；
- 3–5 条用户故事 + 验收标准；
- 非功能需求与约束；
- 评审记录（评审意见及处理结果）。

**模板解读**

带学生逐节过一遍附录 A 的模板，说明每一节"写什么、写到什么程度算合格"：

| 章节 | 写什么 | 合格标准 |
|---|---|---|
| 背景与目标 | 系统解决什么问题、给谁用、不做什么 | 能说清系统边界 |
| 角色与职责 | 谁使用、谁被管理、各自能做什么 | 区分系统用户与业务人员 |
| 功能清单 | 动词 + 对象，按业务域分组 | 覆盖主要业务流程 |
| 优先级 | MoSCoW + 理由 | Must 不超过本期能完成的量 |
| 用户故事 | 角色、功能、价值 + 验收标准 | 验收标准可验证 |
| 非功能需求 | 性能、安全、可用性等 | 每条可度量 |
| 评审记录 | 意见 + 处理结果 | 有记录、有闭环 |

**分组**

- 每组 4–6 人，组内分"业务方"（2–3 人）和"开发方"（2–3 人）。
- 下一环节访谈 5 分钟后交换角色。

---

### 环节2：角色扮演获取需求（20 分钟）

**玩法**

1. 第一轮 5 分钟：业务方讲业务，开发方按访谈提纲提问并记录。
2. 第二轮 5 分钟：双方交换角色，换一个业务域再问一遍。
3. 用 10 分钟整理访谈记录：角色、业务流程、痛点、必须遵守的规则、数据敏感性。

**访谈提纲（开发方用）**

- 这个系统给谁用？他们每天/每周要做哪些事？
- 现在没有系统时，这些事怎么做？最麻烦的是哪一步？
- 哪些事必须按固定规则做？规则是什么？例外情况怎么处理？
- 哪些功能没有它系统就不能用？哪些可以以后再说？
- 数据从哪里来？谁能看、谁能改？哪些数据不能随便展示？
- 如果操作错了，希望系统怎么提示、怎么补救？

**教师巡视要点**

- 多问"为什么"和"现在怎么做"，少问"你想要什么功能"；
- 只记录用户的原话和事实，不急着替用户设计界面；
- 发现"用户说要一个按钮"时，追问"你点这个按钮想完成什么事"；
- 提醒业务方把"必须""一般""偶尔"说清楚，这是后面排优先级的依据。

**预期访谈记录（示例）**

| 项目 | 记录 |
|---|---|
| 角色 | 值班管理员、值班员、查班人员 |
| 主要流程 | 维护部门/人员/工位 → 排班并录入值班记录 → 查班 → 统计 |
| 痛点 | 手工排班容易冲突；查班记录分散；统计口径不一致 |
| 业务规则 | 同一人员同一时段不能重复值班；值班记录必须关联人员和工位 |
| 数据敏感性 | 人员联系方式、值班安排属于内部信息，需按角色控制查看范围 |

---

### 环节3：功能清单与 MoSCoW（15 分钟）

**从记录到功能清单**

把访谈记录中的"要做的事"改写成"动词 + 对象"的功能，按业务域分组：

| 业务域 | 功能（动词 + 对象） |
|---|---|
| 登录与账号 | 登录系统、退出登录、修改密码 |
| 部门 | 查询部门列表、新增部门、修改部门、删除部门 |
| 人员 | 查询人员列表、新增人员、修改人员、删除人员 |
| 工位 | 查询工位列表、维护工位 |
| 值班 | 新增值班记录、查询值班记录、修改值班记录、校验时间冲突 |
| 查班 | 新增查班记录、查询查班记录 |
| 统计 | 按年度统计值班次数、按时段统计值班分布 |

**MoSCoW 判定**

| 优先级 | 判定标准 | 示例 |
|---|---|---|
| Must | 没有它系统不能上线 | 登录、部门/人员/工位维护、值班记录新增与查询 |
| Should | 很重要，但首期可以先用替代办法 | 时间冲突自动校验、查班记录 |
| Could | 有更好，没有也能用 | 导入导出、部门树、图表美化 |
| Won't（本期） | 明确本期不做 | 移动端、消息推送、智能排班 |

**学生任务**

- 每组整理本组负责业务域的功能清单；
- 逐条标注 MoSCoW，并写一句理由；
- 自查：Must 是否过多？有没有把"页面"当"功能"？

**教师强调**

> Must 不是"我觉得重要"，而是"没有它，业务流程走不通"。如果一半功能都是 Must，等于没有排优先级。

---

### 环节4：用户故事与验收标准（15 分钟）

**用户故事格式**

> 作为 <角色>，我想要 <功能>，以便 <价值>。

**示例**

> US-01 按部门查询值班记录
>
> 作为值班管理员，我想要按部门和日期范围查询值班记录，以便核对值班安排是否落实。
>
> 验收标准：
> - [ ] 给定部门与起止日期，列表返回该范围内的值班记录；
> - [ ] 列表显示日期、时段、值班人员、工位；
> - [ ] 没有记录时显示"暂无数据"，不报错；
> - [ ] 起止日期颠倒时给出明确提示；
> - [ ] 只能查看本人权限范围内的部门数据。

**验收标准的写法**

- 用"给定—当—则"或可勾选的条件，写成能判断真假的一句话；
- 覆盖正常情况、边界情况、异常情况；
- 不写"界面美观""操作方便"这类无法验证的话。

**INVEST 自查（简版）**

- 独立（Independent）：一条故事不依赖另一条才能验收；
- 可协商（Negotiable）：细节可以再讨论，不是铁板一块；
- 有价值（Valuable）：对某个角色有明确价值；
- 可估算（Estimable）：开发能判断大概工作量；
- 小（Small）：一期能做完；
- 可测试（Testable）：有验收标准。

**学生任务**

- 每组为 3–5 个核心功能编写用户故事与验收标准；
- 组内互查：验收标准能不能判断"通过/不通过"。

---

### 环节5：非功能需求与文档组装（10 分钟）

**非功能需求的五个方面**

| 类别 | 要写什么 | 示例 |
|---|---|---|
| 性能 | 响应时间、数据量、并发 | 1000 条值班记录下列表查询 2 秒内返回 |
| 安全与保密 | 认证、授权、审计、脱敏 | 未登录不能访问；普通用户只能看本部门数据；联系方式脱敏展示 |
| 可用性 | 操作步骤、错误提示、学习成本 | 常用操作不超过 3 步；错误提示说明原因和处理办法 |
| 兼容性 | 浏览器、分辨率、网络环境 | 支持 Chrome/Edge 最新版；内网环境可离线部署 |
| 可靠性 | 数据备份、故障恢复 | 每日自动备份；异常退出后数据不丢失 |

**约束与假设**

- 约束：必须使用的技术栈、部署环境、时间与人员限制、必须遵守的规范；
- 假设：例如"部门与人员的基础数据由管理员提前维护"。

**文档组装**

- 按附录 A 模板把前面各环节的成果填进去；
- 检查术语一致：同一个角色、同一个业务对象，全文用同一个名称；
- 检查交叉引用：功能清单中的每项功能，是否都有对应的用户故事或说明；
- 补齐文档信息与修订记录。

---

### 环节6：组间评审（12 分钟）

**评审方式**

- 两组交换文档，按附录 B 评审清单逐项检查；
- 每条文档写 2 条优点 + 3 条改进建议；
- 评审意见要具体、可执行，不写"写得不错""再完善一下"。

**评审重点**

- 角色是否齐全？系统用户与业务人员是否区分？
- 功能是否覆盖主要业务流程？是否写成了页面清单？
- MoSCoW 是否合理？Must 是否过多？
- 用户故事是否有角色、价值、验收标准？验收标准是否可验证？
- 非功能需求是否可度量？
- 术语、角色名、功能名是否前后一致？
- 是否出现未脱敏的敏感信息？

**小组汇报**

- 选 2 组，各 2 分钟：我们访谈到了什么、文档中最关键的 3 条需求是什么、评审发现了什么问题。

---

### 环节7：修订落稿与小结（10 分钟）

**修订落稿**

- 各组根据评审意见，至少修订 3 处；
- 在"评审记录"中写明：评审意见、处理结果（采纳/不采纳及理由）；
- 提交《duty 需求文档 v1》。

**教师对照 duty 真实系统**

- 展示 duty 的模块目录与 `api说明.md`；
- 对照讨论：哪些需求抓准了、哪些漏了、哪些是多想的；
- 强调：需求文档不要求与真实实现一一对应，但要能说清"为什么需要、做到什么程度算完成"。

**教师总结**

> 课次3 解决"做什么、为什么做、做到什么程度算完成"；
> 课次5 解决"分几块、表怎么建、接口怎么定"。
>
> 今天交的是需求文档 v1，课次5 会把它转化为设计。

## 十、附录 B：评审清单

- [ ] 背景与目标说清了系统边界，能判断"什么不做"。
- [ ] 角色齐全，系统用户与业务人员区分清楚。
- [ ] 功能清单按"动词 + 对象"编写，覆盖主要业务流程，不是页面清单。
- [ ] MoSCoW 划分合理，Must 不超过本期能完成的量，每条有理由。
- [ ] 用户故事有明确的角色、功能与价值。
- [ ] 验收标准可验证，覆盖正常、边界、异常情况。
- [ ] 非功能需求可度量，不是"好用、安全"这类空话。
- [ ] 术语、角色名、功能名全文一致。
- [ ] 功能清单与用户故事能对应上，没有孤立的功能或故事。
- [ ] 已做涉密信息脱敏，未出现真实番号、姓名、驻地等敏感信息。
- [ ] 评审记录完整，意见有处理结果。

## 十一、附录 C：角色扮演任务卡与访谈提纲

**业务方任务卡（值班业务骨干）**

- 你是值班业务骨干，负责部门、人员、工位和值班安排。
- 你要说清楚：每天/每周做什么、按什么规则做、最容易出错的地方、哪些数据不能随便给人看。
- 不要直接说"给我做一个 XX 页面"，要说"我要完成什么事、现在卡在哪"。
- 当开发方问得太笼统时，用具体例子说明。

**开发方任务卡（需求分析人员）**

- 你的任务是问清楚业务，不是替用户设计界面。
- 按访谈提纲提问，追问"为什么""现在怎么做""例外怎么办"。
- 只记录事实与原话，把"必须/一般/偶尔"标记清楚。
- 访谈结束后，用 3 句话向业务方复述你理解的需求，请对方确认。

**访谈提纲**

1. 这个系统给谁用？他们每天/每周要做哪些事？
2. 现在没有系统时怎么做？最麻烦的是哪一步？
3. 哪些事必须按固定规则做？规则是什么？例外怎么处理？
4. 哪些功能没有它系统就不能用？哪些可以以后再说？
5. 数据从哪里来？谁能看、谁能改？哪些数据要脱敏？
6. 操作错了希望怎么提示、怎么补救？

**轮换规则**

- 5 分钟一轮，到点交换角色；
- 第二轮换一个业务域，避免两组问重复内容；
- 访谈记录随文档一起提交，作为过程性证据。

## 十二、附录 D：duty 业务模块速查（教师用）

> 用于评审时对照"需求是否覆盖主要业务"，不作为学生的标准答案提前发放。

| 业务域 | 典型需求 | 对应 duty 模块 |
|---|---|---|
| 登录与账号 | 登录、退出、修改密码、角色与权限 | `auth` / `user` |
| 部门 | 部门列表、新增、修改、删除 | `dept` |
| 人员 | 人员列表、新增、修改、删除、导入导出 | `personnel` |
| 工位 | 工位列表、新增、修改、删除 | `workstation` |
| 值班 | 值班记录新增、查询、修改、删除、时间冲突校验 | `duty_record` |
| 查班 | 查班记录新增、查询、评价 | `inspection_record`（扩展） |
| 统计 | 年度值班统计、时段分布统计 | `analytics` |

## 十四、评价与反馈

- 过程：角色扮演参与度、访谈问题的质量、组内分工与记录完整性。
- 成果：需求文档的完整性、一致性、规范性；用户故事与验收标准的质量；MoSCoW 的合理性。
- 互评：评审意见是否具体、可执行，是否形成"意见—处理"闭环。
- 反馈：下次课开头用 5 分钟点评 2 份文档，重点讲"想要的与需要的"和"验收标准要可验证"。

## 十五、无 AI 环境下的调整

- 本课次**不依赖 AI**，以角色扮演、小组讨论、模板填写和组间评审为主。
- 若环境允许，可用 AI 检查术语一致性、生成访谈问题清单或润色文档表述，但需求判断、优先级取舍和评审结论必须由学员完成。
- 若没有 AI，用组间评审、教师抽查和模板自查达到同样效果。
