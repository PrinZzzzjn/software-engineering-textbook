## 一、课次基本信息

| 项目 | 内容 |
|---|---|
| 所属专题 | 专题二：后端服务开发 |
| 学时 | 4 学时（实践，约 180 分钟） |

## 二、教学目标

**知识与技能**

- 能说清为什么写测试：改一处不坏三处、回归有保障。
- 能说出单元测试、接口测试、端到端测试的区别（只要求知道）。
- 能用 pytest 写 3 个测试：登录成功/失败、部门重复、执勤时间冲突。
- 能运行测试、看懂失败信息、定位问题。
- 能根据 422/400/401/500 快速判断问题出在哪。
- 能通过写测试发现教师故意留下的 bug。

**过程与方法**

- 经历"写测试 → 运行 → 失败 → 定位 → 修复 → 再运行"的循环。
- 学会用测试描述"系统应该怎么表现"。

**情感态度与价值观**

- 建立"测试是保险，不是负担"的意识。
- 养成"改代码前先跑测试、改完再跑一次"的习惯。

## 教学内容

> 对应教学计划：专题二基本内容第 10 条"模块测试与调试"。

1. **为什么测试**：回归、信心、可维护；改一处坏三处的代价。
2. **测试分类**：单元测试、接口测试、端到端测试的区别。
3. **pytest 基础**：`test_` 文件、`assert`、fixture。
4. **FastAPI 测试客户端**：`TestClient`、发请求、看状态码和响应。
5. **写 3 个测试**：登录成功/密码错 401；部门重复 400；执勤时间冲突 400。
6. **看懂失败**：断言失败、状态码不符、字段缺失。
7. **调试清单**：422/400/401/500 分别先查什么。
8. **找 bug 活动**：用测试暴露教师故意写坏的地方。

## 三、重点与难点

**重点**

- 用 `TestClient` 发请求、断言状态码。
- 写登录、部门、执勤记录三类测试。
- 看懂失败信息。

**难点**

- fixture 的作用（准备 client、token）。
- 测试数据准备（admin、人员、工位）。
- 区分"测试写错"和"代码有 bug"。

## 四、学情分析与教学策略

学生几乎零基础，没写过测试。本课次**不追求覆盖率**，只要求"会写 3 个测试、会看失败"。

策略：

- **测试模板**：教师提供 `conftest.py`（client、admin token、测试数据）；
- **先抄再改**：先抄一个测试跑通，再改参数写第二个；
- **一个测试只验一件事**：成功、失败分开写；
- **找 bug 活动**：让学生体会"测试能抓到问题"。

## 五、教学准备

- 课次7–12 的代码（学生自己那份）。
- 教师提供 `tests/conftest.py` 模板：`client`、`admin_headers`、测试数据。
- 3 个"故意写坏"的接口（找 bug 活动用）。
- 测试清单（见环节6）。

### 环节2：为什么测试与测试分类（15 分钟）

**教师讲授**

| 类型 | 测什么 | 例子 |
|---|---|---|
| 单元测试 | 一个函数/一段逻辑 | 时间重叠判断 |
| 接口测试 | 一个 HTTP 接口 | 登录返回 200/401 |
| 端到端测试 | 整条链路 | 登录 → 建部门 → 查列表 |

**为什么写测试**

- 改一处，能立刻知道有没有坏；
- 测试就是"可执行的说明书"；
- 不用每次手工点一遍。

**强调**

- 今天主要写**接口测试**；
- 不追求覆盖率，先写最有价值的 3 个。

### 环节3：pytest 基础（25 分钟）

**教师演示最小测试**

```python
# tests/test_login.py
def test_login_success(client):
    resp = client.post(
        "/api/v1/auth/login",
        json={"username": "admin", "password": "admin123"},
    )
    assert resp.status_code == 200
    assert "access_token" in resp.json()
```

**教师提供 `conftest.py`**

```python
import pytest
from fastapi.testclient import TestClient
from main import app

@pytest.fixture
def client():
    return TestClient(app)

@pytest.fixture
def admin_headers(client):
    resp = client.post(
        "/api/v1/auth/login",
        json={"username": "admin", "password": "admin123"},
    )
    token = resp.json()["access_token"]
    return {"Authorization": f"Bearer {token}"}
```

**讲清三件事**

1. `test_` 开头的函数会被 pytest 发现；
2. `assert` 不成立，测试就失败；
3. `fixture` 是"提前准备好的东西"（client、token）。

**学生任务**

- 复制模板，跑通第一个测试；
- 故意改错密码，看测试失败。

**运行**

```bash
pytest tests/ -v
```

### 环节4：写 3 个测试（50 分钟）

**测试 1：登录成功 / 失败**

```python
def test_login_success(client):
    resp = client.post("/api/v1/auth/login", json={"username": "admin", "password": "admin123"})
    assert resp.status_code == 200
    assert "access_token" in resp.json()

def test_login_wrong_password(client):
    resp = client.post("/api/v1/auth/login", json={"username": "admin", "password": "wrong"})
    assert resp.status_code == 401
```

**测试 2：新增部门 / 重复部门**

```python
def test_create_dept(client, admin_headers):
    payload = {"dept_code": "TEST001", "full_name": "测试部门"}
    resp = client.post("/api/v1/departments/", json=payload, headers=admin_headers)
    assert resp.status_code in (201, 400)  # 已存在也可以

def test_create_dept_duplicate(client, admin_headers):
    payload = {"dept_code": "TEST001", "full_name": "测试部门"}
    client.post("/api/v1/departments/", json=payload, headers=admin_headers)
    resp = client.post("/api/v1/departments/", json=payload, headers=admin_headers)
    assert resp.status_code == 400
```

**测试 3：执勤时间冲突（需要预置人员和工位）**

```python
def test_duty_record_conflict(client, admin_headers):
    payload = {
        "personnel_certificate_number": "ZHANG001",
        "workstation_id": "WS001",
        "start_time": "2026-01-01T08:00:00",
        "end_time": "2026-01-01T12:00:00",
    }
    client.post("/api/v1/duty-records", json=payload, headers=admin_headers)
    resp = client.post("/api/v1/duty-records", json=payload, headers=admin_headers)
    assert resp.status_code == 400
```

**学生任务**

- 先跑通登录测试；
- 再写部门测试；
- 最后写执勤冲突测试（用教师提供的测试数据）。

**提示**

- 一个测试只验一件事；
- 测试数据要可重复：用固定的编号/时间；
- 测试会写数据，建议用测试库，不要用正式库。

### 环节5：调试与排错（35 分钟）

**教师讲四类错误**

| 状态码 | 先查什么 |
|---|---|
| 422 | 请求体字段名、类型、必填 |
| 400 | 业务规则（重复、时间冲突、人员不存在） |
| 401 | 密码、token、请求头 |
| 500 | 看日志/堆栈：字段名、表名、空值 |

**读失败信息**

```
assert 400 == 201
```

- 第一个数是实际返回，第二个是期望；
- 先看实际返回的 `detail`，再看代码。

**学生任务**

- 故意改坏一个测试，观察失败信息；
- 故意改坏一个接口，看测试能不能抓到；
- 把"现象 → 原因 → 处理"记到问题卡。

---

### 环节6：找 bug 活动（30 分钟）

**教师准备 3 个"坏"接口**

1. 登录密码错也返回 200；
2. 部门重复也返回 201；
3. 用户列表没加管理员权限，普通用户也能访问。

**学生任务**

- 每个组选 1–2 个；
- 写一个测试，让它在"坏"代码上失败；
- 找到问题，说明应该改哪里；
- 教师公布答案。

**强调**

- 测试的价值是"让问题暴露"；
- 好的测试：失败时能直接指向问题；
- 测试不是写给老师看的，是给自己改代码用的。

### 环节7：小结与作业（15 分钟）

**教师总结**

> 测试 = 准备数据 + 发请求 + 断言结果。
>
> 三件事：一个测试只验一件事、先跑再改、失败先看状态码和 detail。

**布置作业**

1. 提交 3 个测试文件；
2. 交一张"测试失败 → 修复 → 通过"的截图；
3. 给课次11 的执勤记录再加 1 个测试（开始时间晚于结束时间 → 400）；
4. 预习课次14：代码质量与安全。

## 七、板书设计

