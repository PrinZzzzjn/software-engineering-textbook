## 二、教学目标

**知识与技能**

- 能读懂 `docker-compose.yml`：`services`、`build`、`ports`、`environment`、`volumes`、`healthcheck`、`depends_on`。
- 能用 `docker compose up -d --build` 一键启动前后端，用 `down` 停止。
- 能说清 `depends_on` + `condition: service_healthy` 如何控制启动顺序。
- 能用 `docker compose ps`、`logs`、`restart`、`exec` 管理服务。
- 能按"端口 → 网络 → 环境变量 → 日志 → 健康检查"的顺序排查部署问题。
- 能写出包含服务清单、端口、环境变量、数据与日志目录、备份与回滚的部署文档。

**过程与方法**

- 经历"手工部署 → 编排文件 → 一键启动 → 故障演练"的收敛过程。
- 学会从日志和健康检查反推部署问题。

**情感态度与价值观**

- 理解"部署上线不是终点，而是系统生命的起点"。
- 建立"配置即代码、文档随交付"的职业习惯。
- 树立部署安全与数据备份意识。

## 教学内容

> 对应教学计划：专题四基本内容第 4 条"部署调试与优化"。
> 项目答辩与终结性考核为课程考核环节，不占本课次学时。

1. **Compose 的作用与文件结构**：用一份文件描述多个服务。
2. **核心配置项**：`services`、`build`、`ports`、`environment`、`volumes`。
3. **健康检查与启动依赖**：`healthcheck`、`depends_on: condition: service_healthy`。
4. **Compose 常用命令**：`up`、`down`、`ps`、`logs`、`restart`、`exec`。
5. **日志与健康检查排障**：`logs/app.log`、`error.log`、`X-Process-Time`、`/health`。
6. **常见部署故障**：端口占用、网络不通、环境变量错误、数据库路径错误。
7. **部署文档与回滚**：环境变量清单、备份、版本回滚。
8. **综合验收与答辩准备**：交付物清单与成果展示要点。

## 三、重点与难点

**重点**

- Compose 文件的结构与常用配置。
- 健康检查与启动顺序。
- 日志排查与部署文档。

**难点**

- 服务名即网络地址：Compose 里的 `backend` 从哪来。
- 启动依赖：为什么前端要等后端健康。
- 故障定位顺序：先看哪一层，不先改代码。

## 四、学情分析与教学策略

课次25 已经手工打通两个容器，但命令多、参数多，学生容易"这次会、下次忘"。Compose 的价值正是把命令固化成文件。另一个薄弱点是部署文档：学生倾向只写"怎么启动"，不写环境变量、数据、备份与回滚。

策略：

- **先回顾手工命令，再读 Compose**：让学生看到一一对应关系；
- **一条命令对比**：昨天五六条，今天一条；
- **故障演练为主**：三个真实故障，学生按固定顺序排查；
- **文档给模板**：不让学生从空白页开始写；
- **明确答辩边界**：本课只整理材料，答辩另行安排。

## 六、教学过程

### 环节1：导入与任务说明（10 分钟）

**教师回顾课次25 的命令**

```bash
docker network create duty-net
docker run -d --name duty-backend --network duty-net --network-alias backend -p 8000:8000 ...
docker run -d --name duty-frontend --network duty-net -p 8501:8501 -e DUTY_API_BASE_URL=... ...
```

**提问**

> "换一台机器，这些命令你还记得全吗？参数少一个会怎样？"
>
> "如果团队里两个人部署得不一样，怎么保证一致？"

**任务**

1. 读懂 `docker-compose.yml`，说清每个配置项对应昨天的哪条命令；
2. 用一条命令启动整套系统；
3. 完成三个故障演练并记录；
4. 写出一页部署文档，完成验收。

**验收标准**

- `docker compose up -d --build` 后两个服务都启动；
- 浏览器能登录并看到部门列表；
- 能解释 `depends_on` 与 `healthcheck`；
- 部署文档包含环境变量、端口、数据与日志、备份与回滚。

### 环节2：读 `docker-compose.yml`（20 分钟）

**教师投影 `项目参考/docker-compose.yml`**

```yaml
name: duty-system

services:
  backend:
    build:
      context: ./duty
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: sqlite:///./duty.db
      SECRET_KEY: change-me-in-production
      ALGORITHM: HS256
      DEBUG: "False"
    volumes:
      - ./duty/logs:/app/logs
    healthcheck:
      test:
        - CMD
        - python
        - -c
        - "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 20s

  frontend:
    build:
      context: ./duty_frontend
    ports:
      - "8501:8501"
    environment:
      DUTY_API_BASE_URL: http://backend:8000
    depends_on:
      backend:
        condition: service_healthy
```

**逐项对应昨天的手工操作**

| Compose 配置 | 对应昨天的操作 |
|---|---|
| `services.backend` | `--name duty-backend` |
| `build.context: ./duty` | `docker build -t duty-backend:1.0 ./duty` |
| `ports: 8000:8000` | `-p 8000:8000` |
| `environment` | `-e KEY=VALUE` |
| `volumes: ./duty/logs:/app/logs` | `-v "$(pwd)/logs:/app/logs"` |
| `healthcheck` | 手工 `curl /health` |
| `frontend.environment.DUTY_API_BASE_URL` | `-e DUTY_API_BASE_URL=...` |
| `depends_on: condition: service_healthy` | 手工"先等后端起来，再起前端" |
| 服务名 `backend` / `frontend` | `--network-alias backend` |

**讲清三件事**

1. **服务名就是网络地址**：`frontend` 里写 `http://backend:8000`，Compose 自动创建网络并把 `backend` 解析到后端容器。
2. **healthcheck 是"活着"的标准**：每 10 秒访问一次 `/health`，连续失败 5 次判定不健康。
3. **depends_on 不等于"启动完成"**：默认只等容器启动；加了 `condition: service_healthy` 才等健康检查通过。

**强调**

> Compose 不是新东西，它把昨天的网络、端口、环境变量、挂载写进了一份文件。
> 文件进 Git，部署就变得可复现。

### 环节3：一键启动与验证（20 分钟）

**学生动手**

```bash
cd 项目参考
docker compose up -d --build
docker compose ps
```

**观察启动顺序**

```bash
docker compose logs -f backend
```

- 后端先起；
- healthcheck 通过后，前端才开始启动；
- 用 `Ctrl + C` 退出日志跟踪（不会停止服务）。

**验证**

1. 浏览器打开 `http://127.0.0.1:8000/docs`；
2. 浏览器打开 `http://127.0.0.1:8501`，用 `admin/admin123` 登录；
3. 进入部门管理页，确认有数据。

**常用命令**

| 命令 | 作用 |
|---|---|
| `docker compose up -d --build` | 构建并后台启动 |
| `docker compose ps` | 查看服务状态 |
| `docker compose logs -f 服务名` | 跟踪日志 |
| `docker compose restart 服务名` | 重启单个服务 |
| `docker compose exec 服务名 sh` | 进入容器 |
| `docker compose down` | 停止并删除容器与网络 |

**强调**

> `down` 删除容器，但不会删除镜像；本项目的数据库在容器层，`down` 后新建的数据会丢。
> 这正是下一步要发现并改进的问题（见环节5）。

---

### 环节4：故障演练（25 分钟）

**演练规则**：每组抽一个故障，按固定顺序排查，记录"现象—原因—修复"。

```text
docker compose ps → docker compose logs 服务名 → 容器内测网络 → 检查环境变量
```

**故障一：端口被占用**

```bash
# 先占用 8000（任选一种；离线环境推荐第一种）
python -m http.server 8000
# 或：docker run -d --name port-holder -p 8000:80 nginx

docker compose up -d
```

现象：`port is already allocated`，后端起不来。

修复：`Ctrl + C` 停掉本机服务（或 `docker rm -f port-holder`），再 `docker compose up -d`。

**故障二：环境变量写错**

把 `docker-compose.yml` 中前端的 `DUTY_API_BASE_URL` 改成：

```yaml
DUTY_API_BASE_URL: http://localhost:8000
```

现象：页面能打开，登录失败。

排查：

```bash
docker compose logs frontend
docker compose exec frontend sh
python -c "import urllib.request; print(urllib.request.urlopen('http://localhost:8000/health').read())"
```

原因：容器里的 `localhost` 是前端自己。

修复：改回 `http://backend:8000`，`docker compose up -d`。

**故障三：数据库路径错误**

把后端的 `DATABASE_URL` 改成：

```yaml
DATABASE_URL: sqlite:///./no_such_dir/duty.db
```

现象：后端容器反复重启或退出。

排查：

```bash
docker compose ps
docker compose logs backend
```

原因：目录不存在，SQLite 无法创建数据库文件。

修复：改回 `sqlite:///./duty.db`；若确实要放子目录，先确保目录存在并可写。

**强调**

> 三个故障分别对应三层：端口、网络与地址、文件与配置。
> 排查顺序固定，不要一上来就改代码。

---

### 环节5：日志、健康检查与交付（10 分钟）

**看三处证据**

| 证据 | 位置 | 说明 |
|---|---|---|
| 健康检查 | `GET /health` | 返回 `{"status":"healthy"}` |
| 响应时间 | 响应头 `X-Process-Time` | 后端中间件写入，判断慢请求 |
| 应用日志 | `duty/logs/app.log`、`error.log` | 挂载到宿主机，容器删了日志还在 |

**验证日志挂载**

```bash
ls duty/logs
tail -n 20 duty/logs/app.log
```

**讲清本编排的一个不足**

> 当前 `docker-compose.yml` 只挂载了日志，没有挂载数据库。
> 数据库文件在容器层，`docker compose down` 后新增数据会丢。
> 改进方式：给后端加数据目录挂载，并把 `DATABASE_URL` 指到挂载目录（可作课后选做）。

**部署文档要素**

| 章节 | 内容 |
|---|---|
| 服务清单 | backend / frontend，镜像与版本 |
| 端口 | 8000、8501，宿主机 → 容器 |
| 环境变量 | 名称、作用、是否敏感（`SECRET_KEY` 必须标注） |
| 数据与日志 | 宿主机目录 → 容器目录 |
| 启动与停止 | `up -d --build`、`down` |
| 健康检查 | `/health` 与 Compose healthcheck |
| 备份与回滚 | 备份数据库文件；回滚到上一个镜像版本 |
| 常见问题 | 端口占用、地址错误、数据目录权限 |

**强调**

> 部署文档不是"命令备忘录"，它要能让一个没参与开发的人把系统跑起来。

---

### 环节6：综合验收、小结与答辩准备（5 分钟）

**验收清单（逐项打勾）**

- [ ] `docker compose up -d --build` 一次成功；
- [ ] `docker compose ps` 两个服务都在运行；
- [ ] 登录成功，部门列表有数据；
- [ ] 能说出 `healthcheck` 与 `depends_on` 的作用；
- [ ] 完成一个故障演练并记录；
- [ ] 部署文档包含环境变量、数据与日志、备份与回滚；
- [ ] 能说出当前编排在数据持久化上的不足。

**教师总结**

> 从"手工敲命令"到"一份 Compose 文件"，部署变得可复现。
>
> 三句话：配置写进文件，健康检查兜底，日志和文档随交付。
>
> 部署上线不是终点，系统能不能稳定运行，才刚开始。

**答辩准备（课后）**

- 交付物：Dockerfile ×2、`.dockerignore` ×2、`docker-compose.yml`、部署文档、运行截图；
- 汇报结构：解决了什么问题 → 怎么部署 → 怎么验证 → 遇到什么故障 → 怎么改进；
- 答辩为考核环节，不占本课次学时，时间另行安排。

**布置作业**

1. 提交部署文档（按模板）与 `docker compose ps` 截图。
2. 提交一份故障演练记录（现象—原因—修复）。
3. 选做：给 Compose 增加数据库目录挂载，验证 `down` 后数据仍在。

## 七、板书设计

```text
一、Compose = 把命令写成文件
   services / build / ports / environment / volumes
   healthcheck / depends_on
   服务名 backend / frontend = 网络地址

二、启动顺序
   backend 启动 → /health 通过 → frontend 启动
   depends_on + condition: service_healthy

三、常用命令
   up -d --build / ps / logs -f / restart / exec / down

四、排错
   端口 → 网络 → 环境变量 → 日志 → 健康检查
   三个故障：端口占用 / localhost / 数据库路径

五、交付
   /health、X-Process-Time、logs/app.log
   部署文档：服务、端口、变量、数据、日志、备份、回滚
```
