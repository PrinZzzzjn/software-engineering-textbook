# 课次25：前后端服务部署——让两个容器互相找到

## 一、课次基本信息

| 项目 | 内容 |
|---|---|
| 所属专题 | 专题四：软件部署与系统交付 |
| 学时 | 4 学时（实践，约 180 分钟） |
| 教材对应 | 第19章 服务部署与编排（19.1–19.5） |
| 主线案例 | `duty` 后端容器 + `duty_frontend` 前端容器的联通部署 |
| 教学形态 | 复现问题 + 教师演示 + 学生部署 + 联调排错 |
| 教学定位 | **两个容器打通**：端口映射、容器网络、环境变量、数据持久化；**Compose 编排在课次26** |

## 二、教学目标

**知识与技能**

- 能解释 `-p 8000:8000` 中宿主机端口与容器端口的对应关系。
- 能用 `-e` 或 `--env-file` 注入 `DATABASE_URL`、`SECRET_KEY`、`ALGORITHM`、`DEBUG`。
- 能创建自定义 bridge 网络，让容器通过容器名或网络别名互访。
- 能把 `duty_frontend` 的 `DUTY_API_BASE_URL` 指向 `http://backend:8000`。
- 能用 `-v` 挂载数据库目录与日志目录，验证容器重建后数据仍在。
- 能说清敏感配置为什么不能写进镜像。
- 能完成部署后的登录与部门列表联调。

**过程与方法**

- 经历"现象 → 原因 → 修复 → 验证"的部署排错过程。
- 学会用 `docker exec`、`docker logs`、`env` 验证容器内部状态。

**情感态度与价值观**

- 树立"配置与代码分离"的意识。
- 建立"密钥不进镜像、不进仓库"的安全底线。

## 教学内容

> 对应教学计划：专题四基本内容第 3 条"服务部署"。

1. **部署拓扑与端口映射**：浏览器、宿主机、两个容器之间的访问路径。
2. **后端容器部署与环境变量**：`DATABASE_URL`、`SECRET_KEY`、`ALGORITHM`、`DEBUG`。
3. **数据持久化**：数据库文件与日志目录的挂载。
4. **容器网络**：默认 bridge 与自定义网络、容器名与网络别名。
5. **前端容器部署**：`DUTY_API_BASE_URL=http://backend:8000`。
6. **敏感配置管理**：密钥不进镜像、不进 Git，用环境变量注入。
7. **部署验证与排错**：登录、部门列表、401、日志与网络连通性。

## 三、重点与难点

**重点**

- 环境变量的注入与配置分离。
- 端口映射与容器网络。
- 前后端联通的配置。

**难点**

- 容器内的 `127.0.0.1` 指向容器自己。
- 自定义网络的 DNS 解析（容器名/别名）。
- 数据持久化的路径与权限。

## 四、学情分析与教学策略

课次24 已经能单独跑两个容器，但前端登录失败。学生容易认为"两个容器都在本机，为什么不能互相访问"——这是本课最核心的认知障碍。

策略：

- **先复现，再解释**：打开前端、登录失败、看日志，让问题先发生；
- **用"每台容器有自己的 localhost"解释**：一句话点破；
- **先网络、后配置**：先把两个容器放进同一网络，再改 `DUTY_API_BASE_URL`；
- **每步可验证**：`docker exec` 里 `curl /health`，成功后再打开浏览器；
- **手工部署为主**：Compose 放课次26，避免一上来被编排文件掩盖细节。

## 五、教学准备

- 课次24 构建好的 `duty-backend:1.0`、`duty-frontend:1.0`。
- `duty` 目录下有可用的 `duty.db`（含 `admin/admin123`）。
- 端口 8000、8501 空闲；自定义网络名 `duty-net`。
- `duty/.env.example` 投影。
- 联调清单、排错清单；数据目录 `data/`、日志目录 `logs/`。

## 六、教学过程

### 环节1：导入——复现"前端连不上后端"（10 分钟）

**教师演示**

```bash
docker ps
```

确认两个容器都在运行，打开 `http://127.0.0.1:8501`，用 `admin/admin123` 登录。

**现象**

登录失败，页面提示"无法连接后端服务"或类似信息。

**追问**

> "后端容器明明在跑，`/health` 也能访问，为什么前端说连不上？"

**让学生看配置**

```python
# duty_frontend/config.py
API_BASE_URL = os.getenv("DUTY_API_BASE_URL", "http://127.0.0.1:8000")
```

**教师点明**

> 前端容器里的 `127.0.0.1`，指的是前端容器自己。它在找"自己身上的 8000 端口"。
>
> 今天要解决三件事：找到后端、配置可替换、数据不丢。

---

### 环节2：部署拓扑与端口映射（20 分钟）

**教师画拓扑图**

```text
浏览器
  │
  ├─ http://127.0.0.1:8501 ──→ 宿主机:8501 ──→ duty-frontend 容器:8501
  └─ http://127.0.0.1:8000 ──→ 宿主机:8000 ──→ duty-backend 容器:8000

duty-frontend 容器 ──→ http://backend:8000 ──→ duty-backend 容器:8000
```

**讲清两种访问**

| 访问方 | 应该用 | 原因 |
|---|---|---|
| 浏览器 | `http://127.0.0.1:8501` / `:8000` | 走宿主机映射端口 |
| 前端容器访问后端 | `http://backend:8000` | 走容器网络，用容器端口 |

**强调**

- `-p 8000:8000`：左边宿主机，右边容器；
- 容器之间通信不使用宿主机的映射端口；
- `EXPOSE` 只是声明，不负责对外发布。

---

### 环节3：后端容器部署与环境变量（35 分钟）

**先清理旧容器**

```bash
docker rm -f duty-backend
```

**创建网络**

```bash
docker network create duty-net
```

**用环境变量启动后端**

```bash
cd duty

docker run -d --name duty-backend \
  --network duty-net \
  --network-alias backend \
  -p 8000:8000 \
  -e DATABASE_URL="sqlite:///./duty.db" \
  -e SECRET_KEY="classroom-demo-key" \
  -e ALGORITHM="HS256" \
  -e DEBUG="False" \
  duty-backend:1.0
```

**讲清每个参数**

| 参数 | 作用 |
|---|---|
| `--network duty-net` | 加入自定义网络 |
| `--network-alias backend` | 给容器起网络别名，前端可用 `backend` 访问 |
| `-p 8000:8000` | 宿主机 8000 → 容器 8000 |
| `-e KEY=VALUE` | 注入环境变量 |
| `SECRET_KEY` | JWT 签名密钥，不能写进镜像 |
| `DEBUG=False` | 生产/部署环境关闭调试 |

**验证环境变量**

```bash
docker exec duty-backend env | grep -E "DATABASE_URL|SECRET_KEY|DEBUG"
curl http://127.0.0.1:8000/health
```

**讲清"配置与代码分离"**

> 同一个镜像，开发环境可以 `DEBUG=True`、用本地数据库；
> 部署环境用 `DEBUG=False`、用部署目录的数据库。
> 镜像不变，变的只是启动时注入的环境变量。

**学生任务（15 分钟）**

- 用上面的命令启动后端；
- 用 `docker exec ... env` 确认四个变量都注入成功；
- 把 `DEBUG` 改成 `True` 重启，观察 `docker logs` 的日志级别变化，再改回。

---

### 环节4：数据持久化（25 分钟）

**提问**

> "如果我把容器删了，刚才建的部门还在吗？"

**演示容器层丢失**

```bash
docker rm -f duty-backend
docker run -d --name duty-backend -p 8000:8000 duty-backend:1.0
# 之前的数据不在了
```

**用挂载解决**

```bash
cd duty
mkdir -p data logs
cp duty.db data/duty.db

docker run -d --name duty-backend \
  --network duty-net \
  --network-alias backend \
  -p 8000:8000 \
  -v "$(pwd)/data:/app/data" \
  -v "$(pwd)/logs:/app/logs" \
  -e DATABASE_URL="sqlite:///./data/duty.db" \
  -e SECRET_KEY="classroom-demo-key" \
  -e ALGORITHM="HS256" \
  -e DEBUG="False" \
  duty-backend:1.0
```

> Windows PowerShell 中 `$(pwd)` 换成 `${PWD}`；cmd 中直接写绝对路径。

**讲清两种挂载**

| 方式 | 写法 | 特点 |
|---|---|---|
| 绑定挂载 bind mount | `-v 宿主机路径:容器路径` | 宿主机能直接看到文件，课堂推荐 |
| 数据卷 volume | `-v 卷名:容器路径` | 由 Docker 管理，便于迁移 |

**验证**

1. 在页面或 `/docs` 新建一个部门；
2. `docker rm -f duty-backend`；
3. 用同样命令重建容器；
4. 部门还在；`logs/app.log` 在宿主机能看到。

**强调**

- 数据库文件、日志不要打进镜像（`.dockerignore` 已排除 `*.sqlite3`、`*.log`）；
- 容器是"一次性的"，需要保留的东西必须放在卷里；
- 删除容器前先想清楚：数据在容器层还是卷里。

---

### 环节5：容器网络与前后端联通（40 分钟）

**先讲默认网络的问题**

> Docker 默认的 `bridge` 网络只提供 IP，不保证用容器名互相解析。
> 自定义网络自带 DNS：同一网络里的容器可以用容器名或网络别名访问。

**验证网络**

```bash
docker network inspect duty-net
```

**检查后端是否带别名**

```bash
docker inspect -f "{{json .NetworkSettings.Networks}}" duty-backend
```

**启动前端并指向后端**

```bash
docker rm -f duty-frontend

docker run -d --name duty-frontend \
  --network duty-net \
  -p 8501:8501 \
  -e DUTY_API_BASE_URL="http://backend:8000" \
  duty-frontend:1.0
```

**先在容器内验证网络，再打开浏览器**

```bash
docker exec -it duty-frontend sh

python -c "import urllib.request; print(urllib.request.urlopen('http://backend:8000/health').read())"
exit
```

**预期**

```text
b'{"status":"healthy"}'
```

**再打开浏览器**

`http://127.0.0.1:8501`，用 `admin/admin123` 登录，进入部门管理页。

**讲清三个地址**

| 写法 | 谁在用 | 结果 |
|---|---|---|
| `http://127.0.0.1:8000` | 前端容器内 | 指向前端自己，失败 |
| `http://duty-backend:8000` | 同一自定义网络内 | 用容器名解析，成功 |
| `http://backend:8000` | 同一自定义网络内 | 用网络别名解析，成功（与 Compose 一致） |

**强调**

- 容器之间用**容器端口**，不是宿主机映射端口；
- 别名 `backend` 是为课次26 的 Compose 做铺垫；
- 网络不通先 `docker exec` 进容器用 `python`/`curl` 测，不要只看浏览器。

**学生任务（15 分钟）**

- 完成前端容器启动与登录；
- 故意把 `DUTY_API_BASE_URL` 改成 `http://127.0.0.1:8000`，复现失败并记录日志；
- 改回正确地址，确认恢复。

---

### 环节6：联调验证与排错（30 分钟）

**验收清单**

- [ ] 浏览器能打开 8501；
- [ ] `admin/admin123` 能登录；
- [ ] 部门列表能显示数据；
- [ ] 新建一个部门后刷新仍在；
- [ ] 删除后端容器再重建，数据仍在；
- [ ] 未登录直接访问接口返回 401。

**排错顺序（固定四步）**

```text
docker ps → 容器是否在跑、端口是否映射
docker logs 服务名 → 启动是否报错
docker exec ... python/curl → 容器内网络是否通
环境变量 → 地址、数据库路径、密钥是否正确
```

**常见问题**

| 现象 | 先查什么 |
|---|---|
| 前端提示无法连接 | `DUTY_API_BASE_URL` 是否是 `http://backend:8000` |
| 连不上后端 | 两个容器是否在同一网络；后端别名是否存在 |
| 401 | 用户是否存在；`SECRET_KEY` 是否与签发时一致 |
| 数据库空 | `DATABASE_URL` 路径；`data/duty.db` 是否复制成功 |
| 容器重启后数据丢失 | 是否挂载了 `data/` |
| 端口被占用 | 本机是否有其他 duty / Streamlit 在运行 |

**强调**

> 排错不是"改代码试试"，而是按层确认：容器在不在 → 端口通不通 → 网络通不通 → 配置对不对。

### 环节7：敏感配置与部署清单（10 分钟）

**教师展示 `.env.example`**

```text
DATABASE_URL="sqlite:///./duty.db"
SECRET_KEY="your-secret-key"
ALGORITHM="HS256"
DEBUG=False
```

**讲清三条红线**

1. `SECRET_KEY` 不写进 Dockerfile、不提交到 Git；
2. 生产环境用安全的密钥注入方式，不用课堂示例值；
3. `.env` 文件本身也要加入 `.gitignore`。

**部署清单**

| 项目 | 内容 |
|---|---|
| 镜像 | 名称与版本号（`duty-backend:1.0`） |
| 端口 | 宿主机 → 容器（`8000:8000`、`8501:8501`） |
| 环境变量 | 名称、作用、是否敏感 |
| 数据目录 | 宿主机路径 → 容器路径 |
| 日志目录 | 宿主机路径 → 容器路径 |
| 健康检查 | `GET /health` |

## 七、板书设计

```text
一、拓扑
   浏览器 → 宿主机:8501/8000 → 容器
   前端容器 → http://backend:8000 → 后端容器

二、端口
   -p 宿主机:容器
   EXPOSE 只是声明

三、环境变量
   -e DATABASE_URL / SECRET_KEY / ALGORITHM / DEBUG
   同一镜像 + 不同变量 = 不同环境
   密钥不进镜像、不进 Git

四、网络
   默认 bridge：IP 可用，名字不保证
   自定义网络：容器名/别名可解析
   --network duty-net --network-alias backend

五、持久化
   -v 宿主机路径:容器路径
   data/ → /app/data；logs/ → /app/logs
   容器可删，卷要留

六、排错
   ps → logs → exec 测网络 → 环境变量
```
