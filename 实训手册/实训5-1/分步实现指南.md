# 实训 5-1 分步实现指南

> **定位**：演示从第 4 章实训产物到最小工程的逐步过程，每个阶段结束都有可执行的检查。以执勤电子年鉴中的“工位”为例。
> **与项目目录的关系**：[项目/](项目/) 是全部阶段完成后的最终状态，可直接启动；本指南说明它是怎么一步步长出来的。
> **与教材步骤的关系**：阶段 1–6 对应实训手册的操作步骤 1–6。
> **使用者**：教师课堂演示；学生对照自查。提交时须替换为自己选定的业务对象与模块名。

## 阶段 0：起点与目标

**起点**：第 4 章实训 4-1 的产物——设计文档、`main.py`、`schemas.py`、接口验证记录。此时项目只有两个代码文件，全部在根目录。

**目标**：一个可启动、可回溯、可复现的最小工程。

```text
duty/
├── main.py
├── requirements.txt
├── .env.example
├── .env                （本机创建，不进 Git）
├── .gitignore
├── README.md
└── app/
    ├── __init__.py
    └── modules/
        ├── __init__.py
        └── workstation/
            ├── __init__.py
            ├── controller.py
            └── schema.py
```

**为什么只有两个模块文件**：第 4 章 4.5 的六文件模板描述的是完整模块。`service`、`crud`、`model`、`param` 要到第 8 章第一次读写业务数据时才有内容；现在建空文件，学员要记住四个暂时无用的名字，却看不到它们的职责。因此本实训只建实际用到的两个文件，其余按“第一次需要”加入。

**一条原则**：每阶段只改变一件事，并在阶段末尾按“验证”确认。一次改太多，出错后无法判断是哪一步引入的。

## 阶段 1：建目录、迁移 4-1 的模型与接口

**目标**：把 4-1 的两个文件拆入工程目录：模型进入 `schema.py`，接口进入 `controller.py`，应用留给阶段 2 的根目录 `main.py`。

**做了什么**

1. 新建 `app/`、`app/modules/`、`app/modules/workstation/`，每个目录放一个空的 `__init__.py`。Git 不跟踪空目录，`__init__.py` 同时承担“让目录进入仓库”的作用。
2. 复制 4-1 的 `schemas.py` 内容到 `schema.py`，内容不变。
3. 把 4-1 `main.py` 中的接口移入 `controller.py`：删除 `app = FastAPI()`，只保留 `router` 与三个接口；前缀由 `/api/v1/workstations` 改为 `/workstations`；导入改为 `app.modules.workstation.schema`。

**app/modules/workstation/schema.py**

```python
"""工位模块的输入与输出模型（schema）：管什么能进、什么能出。

由第 4 章实训 4-1 的 schemas.py 迁入，内容不变，只是位置进入模块目录。
"""

from pydantic import BaseModel, Field


# 输入模型：新增时允许提交的字段与约束；校验失败由 Pydantic 返回 422。
class WorkstationCreate(BaseModel):
    workstation_id: str = Field(..., min_length=2, max_length=20)  # ... 表示必填
    workstation_name: str = Field(..., min_length=2, max_length=50)
    dept_code: str = Field(..., min_length=2, max_length=10)  # 外键：指向部门表
    # | None 表示可空；默认值 None 使其提交时可省略。
    category_code: str | None = None
    remark: str | None = None


# 输出模型：只声明允许出现在响应中的字段；接口声明 response_model 后按它过滤。
class WorkstationOut(BaseModel):
    workstation_id: str
    workstation_name: str
    dept_code: str
    category_code: str | None = None
    remark: str | None = None


# 列表输出：统一为 items 与 total，前端与后续分页都按这个结构取数。
class WorkstationListOut(BaseModel):
    items: list[WorkstationOut]
    total: int
```

**app/modules/workstation/controller.py**

```python
"""工位模块的接口层（controller）：接请求、取参数、返回响应。

由第 4 章实训 4-1 的 main.py 迁入：应用留在根目录 main.py，接口归本文件。
本文件只处理接口；业务规则与数据库读写在第 8 章加入 service.py 与 crud.py。
"""

from fastapi import APIRouter, HTTPException

from app.modules.workstation.schema import (
    WorkstationCreate,
    WorkstationListOut,
    WorkstationOut,
)

# 模块级路由：前缀只写本资源名，"/api/v1" 由根目录 main.py 的 include_router 提供。
router = APIRouter(prefix="/workstations", tags=["工位"])

# 内存数据演示“一张表”：第 8 章换成 model.py + crud.py + 真实数据库。
items = [
    {
        "workstation_id": "WS-001",
        "workstation_name": "一号值班台",
        "dept_code": "D01",
        "category_code": "C01",
        "remark": None,
    },
    {
        "workstation_id": "WS-002",
        "workstation_name": "二号值班台",
        "dept_code": "D02",
        "category_code": "C02",
        "remark": None,
    },
]


# 查询集合：成功状态码 200；response_model 会在返回前按输出模型过滤字段。
@router.get("/", response_model=WorkstationListOut)
def list_workstations():
    return {"items": items, "total": len(items)}


# 新增：成功状态码 201；请求体先由 WorkstationCreate 校验，不合法时框架在进入函数前返回 422。
@router.post("/", status_code=201, response_model=WorkstationOut)
def create_workstation(data: WorkstationCreate):
    items.append(data.model_dump())  # model_dump() 把模型转成字典，才能放进列表
    return data


# 查询单个：200 / 404；路径参数用于定位一条记录，找不到时由 HTTPException 拒绝。
@router.get("/{workstation_id}", response_model=WorkstationOut)
def get_workstation(workstation_id: str):
    for item in items:
        if item["workstation_id"] == workstation_id:
            return item
    raise HTTPException(status_code=404, detail="工位不存在")
```

**验证**（此时应用还不能启动，只验证模块可导入）

```bash
python -c "from app.modules.workstation import controller; print(controller.router.prefix)"
```

预期输出 `/workstations`。

**做错会看到什么**

- `ModuleNotFoundError: No module named 'app'`：缺 `__init__.py`，或不在项目根目录执行。
- `AttributeError: module ... has no attribute 'router'`：`controller.py` 仍是 4-1 的写法，或删掉了 `router = APIRouter(...)`。
- `ModuleNotFoundError: No module named 'schemas'`：导入未改为 `app.modules.workstation.schema`。

**本阶段检查点**

- [ ] `controller.py` 无 `app = FastAPI()`
- [ ] `schema.py` 只有模型
- [ ] `router.prefix` 为 `/workstations`

## 阶段 2：补齐配置并装配 main.py

**目标**：工程具备“装得上、排得掉、说得清”的三份文件；入口把模块挂到应用上，服务可启动。

**requirements.txt**

```text
fastapi
uvicorn[standard]
pydantic
```

**.gitignore**

```gitignore
venv/
__pycache__/
*.pyc
.env
*.db
logs/
.pytest_cache/
```

**.env.example**

```env
SECRET_KEY="change-me-in-env"
ALGORITHM="HS256"
ACCESS_TOKEN_EXPIRE_MINUTES=30
DEBUG=True
```

`.env.example` 进 Git，`.env` 不进。需要本机取值时复制一份为 `.env` 再改；本章只建文件，读取从第 6 章起（`os.getenv`）。

**README.md**

```markdown
# Duty API

## 启动

python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload

## 目录

- main.py：创建应用、挂路由
- app/modules/<模块>/：controller.py 与 schema.py
```

**main.py**

```python
"""Duty API 入口：只负责创建应用与挂载路由。

对应教材第 5 章 5.1：入口不写业务代码。
第 6 章会在这里补建表三行：导入 Base 与 engine、导入模型、调用 create_all。
"""

from fastapi import FastAPI

from app.modules.workstation import controller as workstation_controller

# 应用对象：所有路由最终都挂在它上面，/docs 页面也由它生成。
app = FastAPI(title="Duty API", version="0.1.0")


# 健康检查：不查数据库、不做业务，只回答“服务是否在运行”。部署后也是第一项可用性证据。
@app.get("/health")
def health():
    return {"status": "healthy"}


# 把模块路由挂到应用。模块 router 的前缀是 "/workstations"，这里再加 "/api/v1"，
# 两段相加才是完整路径 /api/v1/workstations/；缺一段就会出现 404。
app.include_router(workstation_controller.router, prefix="/api/v1")
```

本章不建数据库，因此没有 `create_all` 与模型导入；第 6 章建立用户表时再补三行。

**验证**

```bash
uvicorn main:app --reload
```

| 请求 | 预期 | 说明 |
| --- | --- | --- |
| `GET /health` | 200，`{"status": "healthy"}` | 应用已启动 |
| `GET /docs` | 200 | 文档页可打开 |
| `GET /api/v1/workstations/` | 200，`total` 为 2 | 两段前缀拼接正确 |
| `GET /api/v1/workstations/WS-999` | 404 | 业务规则生效 |

**做错会看到什么**

- `/docs` 404：启动的不是根目录 `main.py`，或 `include_router` 漏写 `prefix`。
- 接口返回 404、`/health` 正常：两段前缀只写了一段，或 `router` 前缀仍带 `/api/v1`，两段重复。
- `ModuleNotFoundError: app.core.database`：照抄了后续章节的代码；本章还没有该文件，删除导入。

**本阶段检查点**

- [ ] `python -c "import app"` 通过
- [ ] 三个接口路径完整、可调用
- [ ] `main.py` 只有创建应用、挂路由两件事

## 阶段 3：虚拟环境与依赖清单

**验证**

| 检查 | 命令 | 预期 |
| --- | --- | --- |
| 环境指向项目 | `python -c "import sys; print(sys.prefix)"` | 路径在项目下的 `venv` |

**本阶段检查点**

- [ ] `venv/` 未出现在 `git status` 中（阶段 4 验证）

## 阶段 4：Git 初始化与首次提交

**目标**：先建立排除规则，再把工程纳入版本控制。

**命令**

```bash
git init -b main
git add .gitignore
git commit -m "chore: add gitignore"
git status
git add .
git commit -m "chore: init fastapi project"
```

先单独提交 `.gitignore`，再执行 `git add .`，排除规则才生效。

**验证**

```bash
git log --oneline
git status
git ls-files | grep -E "venv/|\.env$|\.db$|logs/|__pycache__"
```

| 检查 | 预期 |
| --- | --- |
| 历史 | 两条提交：`chore: add gitignore`、`chore: init fastapi project` |
| 工作区 | `nothing to commit, working tree clean` |
| 排除项 | 无输出（Windows 用 `git ls-files \| findstr venv` 逐项查） |

**做错会看到什么**

- `git status` 出现 `venv/`：`.gitignore` 未生效；若已被跟踪，执行 `git rm -r --cached venv` 再提交。
- `.env` 已提交：`git rm --cached .env` 后提交移除；密钥泄露须更换。
- 提交为空：文件被忽略规则误伤，先看 `git status` 再判断。
- 提示 `Please tell me who you are`：先配置 `git config --global user.name` 与 `user.email`。

**本阶段检查点**

- [ ] 至少两次提交，信息可读
- [ ] `git ls-files` 中无 `venv/`、`.env`、`*.db`、`logs/`
- [ ] 工作区干净

## 阶段 5：分支开发与冲突合并

**目标**：在独立分支改一处，合并时处理一次冲突，留下可读历史。

**命令序列**

```bash
git switch -c feature/health-version
```

在分支上把 `/health` 改为：

```python
return {"status": "healthy", "version": "0.1.0"}
```

```bash
git add main.py
git commit -m "feat: add version to health check"
git switch main
```

在 `main` 上把同一行改为：

```python
return {"status": "ok"}
```

```bash
git add main.py
git commit -m "feat: simplify health status"
git merge feature/health-version
```

冲突文件出现三组标记：

```text
<<<<<<< HEAD
当前分支的内容
=======
要合并进来的内容
>>>>>>> feature/health-version
```

保留 `return {"status": "healthy", "version": "0.1.0"}`，删除三组标记，然后：

```bash
git add main.py
git commit -m "merge: combine health status and version"
```

**验证**

```bash
git log --oneline --graph
grep -nE "^(<<<<<<<|=======|>>>>>>>)" main.py
```

| 检查 | 预期 |
| --- | --- |
| 历史 | 能看到功能分支与一次合并提交 |
| 冲突标记 | 无输出 |
| 服务 | 重启后 `/health` 返回合并后的内容 |

**做错会看到什么**

- 提交提示 “You have not concluded your merge”：标记未删净或未 `git add`。
- 历史是一条直线、看不到分支：分支上没提交，合并成了空操作。
- `/health` 仍是旧值：改完未重启，或改在错误分支。

**本阶段检查点**

- [ ] 冲突标记为零
- [ ] 历史含分支与合并
- [ ] `/health` 为合并结果

## 阶段 6：最终验证与文档提交

**目标**：让磁盘目录、设计文档与服务状态三者一致，并留下最后一次提交。

**做什么**

1. 重新启动服务，验证 `/health`、`/docs` 与三个接口。
2. 填写 [验收记录.md](验收记录.md)。
3. 设计文档“模块目录”一节更新为实际目录；不一致处记录判定。
4. 提交文档：

```bash
git add -A
git status
git commit -m "docs: update project structure"
```

**验证**

| 检查 | 预期 |
| --- | --- |
| `/health`、`/docs` | 200 |
| `git log --oneline` | 至少 3 条，信息可读 |
| `git status` | 干净 |
| 设计文档目录 | 与磁盘一致，或差异已记录 |

**做错会看到什么**

- 文档与磁盘不一致：以实际目录改文档，并记录差异；不要默认任一方正确。
- `git add -A` 带入不应提交的文件：先看 `git status` 再提交。
- 提交信息写“update”：后续无法判断改动，重写为说明做了什么。

## 每阶段都要问的三个问题

1. 这一步新增了哪个文件？它解决什么问题，删掉会怎样？
2. 这一步改变了哪条路径或哪条命令？验证结果是否与预期一致？
3. 这一步的产物是否需要进入 Git？理由是什么？
