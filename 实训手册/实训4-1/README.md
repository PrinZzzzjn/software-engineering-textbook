## 二、学习目标与验收标志

### 2.1 本课结束后应能做到

课次 4 已讲过翻译链、表结构、模块划分、接口组与分层；课次 5 要求把这些内容变成能独立完成的能力。本手册按这五条组织，不覆盖教材之外的新知识。

| 编号 | 学习目标（能做什么） | 对应第 4 章目标 | 达标要点 |
| --- | --- | --- | --- |
| L1 | 说出需求到设计文档的翻译顺序，并为自选对象列出字段与主键 | 1、2 | 顺序为对象 → 表 → 模块 → 接口 → 目录；主键唯一且必填 |
| L2 | 写出一张表结构：字段、类型、主键；有一对多关系时说明外键位置 | 2 | 外键在“多”的一方，并能说出查询与修改的理由 |
| L3 | 写出五个标准接口的方法、URL、参数来源与成功状态码，并给出一条规则性失败 | 4 | URL 是名词、方法是动作、状态码表结果；能区分 422 与 400 |
| L4 | 按业务能力划出模块，用一句话写职责，画出六个文件的目录 | 3、5 | 一句话能说清职责；六个文件各就其位；能区分“六类职责”与“六层” |
| L5 | 用三个接口的最小实现验证设计中的状态码 | 6 | 200、201、404、422 各出现一次，且能指出实现位置 |

步骤与目标的对应：步骤 1–2 支撑 L1、L2；步骤 3 支撑 L3；步骤 4 支撑 L4；步骤 5–6 支撑 L5。下课前的出口检查见第十三节。

### 2.2 验收标志

| 目标 | 验收标志 |
| --- | --- |
| 表结构设计 | 字段、类型、主键清楚；有一对多关系时，外键放在“多”的一方并说明理由 |
| 模块模板 | 一句话说清模块职责；模块对应一个文件夹；按 4.5 的模块模板画出六个文件 |
| 接口组设计 | 五个标准动作的方法、URL、参数来源、成功状态码齐全；至少一条规则性失败的说明 |
| 最小实现可运行 | 最小 `main.py` 与 `schemas.py` 实现查询集合、新增、查询单个三个接口；`/docs` 可打开 |
| 状态码验证 | 200、201、404、422 至少各出现一次，并记录实际结果 |
| 设计文档 | 表结构、接口清单、模块目录三节齐全；两组一致性检查通过 |

验收标志衡量交付物，学习目标衡量能力；两者冲突时以学习目标为准。例如记录表填满，但说不出 422 为什么由模型而不是接口函数拒绝，L5 仍记为未达成。

## 六、操作步骤

每一步给出四项内容：做什么、预期输出、做错会看到什么、本步检查点。检查点未通过时不进入下一步。

### 步骤 1：选对象与写字段（10 分钟）

**做什么**

1. 确定业务对象，写出 3–5 个字段的候选清单。
2. 标出主键：哪一个字段能唯一标识一条记录。
3. 判断是否存在关联对象；有则记下关联的是哪张表。

**预期输出**：一条能说清“这个对象是什么、谁在用”的说明，以及字段清单。

**做错会看到什么**：对象选得太大，例如“管理系统”。此时字段无法列全，应缩到一个业务对象后继续。

**检查点**

- [ ] 对象是一个名词，不是一组页面或一个系统
- [ ] 主键字段已确定，且每条记录不会重复
- [ ] 字段数量在 3–5 个之间

### 步骤 2：设计表结构（20 分钟）

**做什么**

1. 为每个字段定名称、类型、是否必填。
2. 定主键；若存在关联对象，把外键放在“多”的一方，并写出理由。
3. 把结果填入设计文档模板第 1 节。

**预期输出**：一张表结构表，字段名与类型能直接用于建表。

下表以工位为例：工位属于部门，一个部门有多个工位，因此 `dept_code` 是外键，位于“多”的一方。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `workstation_id` | 文本 | 是 | 主键，工位编号 |
| `workstation_name` | 文本 | 是 | 工位名称 |
| `dept_code` | 文本 | 是 | 外键，所属部门内码 |
| `category_code` | 文本 | 否 | 工位类别内码 |
| `remark` | 文本 | 否 | 备注 |

**做错会看到什么**

- 将多个编号置于一行，例如在“一”方字段中存“人员编号列表”。
- 把“多”方字段放入“一”方，例如在部门表中存人员证件号列表。

出现上述情况时回到 4.2 的一对多判断：外键置于“多”的一方，每条“多”的记录只保存一个“一”的编号。

**检查点**

- [ ] 主键唯一且必填
- [ ] 每个字段有类型与是否必填
- [ ] 有一对多关系时，外键位置与理由均已写明；没有时写明“无”

### 步骤 3：设计接口组（20 分钟）

**做什么**

1. 按 4.4 的五动作表，写出列表、详情、新增、修改、删除的方法、URL、参数来源与成功状态码。
2. 为一条业务规则写出失败状态码与说明。
3. 填入设计文档模板第 2 节，并标出本次要实现的三个接口。

**预期输出**：一张接口清单，前端可据此直接调用。

| 方法 | URL | 参数来源 | 成功状态码 | 失败状态码与说明 |
| --- | --- | --- | ---: | --- |
| GET | `/api/v1/workstations/` | 查询参数 `page`、`page_size` | 200 | — |
| GET | `/api/v1/workstations/{workstation_id}` | 路径参数 | 200 | 404 工位编号不存在 |
| POST | `/api/v1/workstations/` | 请求体 | 201 | 400 工位编号已存在；422 字段不合法 |
| PUT | `/api/v1/workstations/{workstation_id}` | 路径参数 + 请求体 | 200 | 404 工位编号不存在；422 字段不合法 |
| DELETE | `/api/v1/workstations/{workstation_id}` | 路径参数 | 204 | 404 工位编号不存在 |

**做错会看到什么**

- 用 `GET` 删除，或用动作写进 URL，例如 `/workstations/delete/1`。
- 成功与失败都返回 `200`。
- 路径单复数混用，例如 `/workstation` 与 `/workstations/1` 并存。

出现上述情况时对照 4.4 的规则逐行修改：URL 表示资源，方法表示动作，状态码表示结果。

**检查点**

- [ ] 五个标准动作齐全，缺项须写明为什么不提供
- [ ] 每条接口写明参数来源：路径参数、查询参数或请求体
- [ ] 至少一条规则性失败，并说明由谁拒绝（模型校验还是业务规则）
- [ ] 已标出本次实现的三个接口

### 步骤 4：画模块目录（10 分钟）

**做什么**

1. 给模块起名，用一句话写职责。
2. 按 4.5 的模块模板画出 `app/modules/<模块>/` 下六个文件的目录树，每个文件一行注释。
3. 填入设计文档模板第 3 节。

**预期输出**：

```text
app/modules/workstation/
├── __init__.py
├── controller.py    # 接口
├── service.py       # 业务规则
├── crud.py          # 读写数据库
├── model.py         # 表结构
├── schema.py        # 输入输出模型
└── param.py         # 查询参数
```

**做错会看到什么**

- 模块按页面划分，例如“工位列表模块”“工位详情模块”。
- 一句话说不清职责，例如“负责工位相关的所有事情”。

两种情况都回到 4.3 的判据：模块按业务能力划分，一句话能说清职责即为合适的粒度。`app/core/` 与 `tests/` 不在本实训中建：前者在第 6 章加入，后者在第 12 章加入。

**检查点**

- [ ] 模块名与文件夹名一致
- [ ] 六个文件齐全，`__init__.py` 未遗漏
- [ ] 每个文件用一行注释写明职责，且不重复

### 步骤 5：实现最小后端（20 分钟）

**做什么**

1. 准备最小 `main.py` 与 `schemas.py`：`schemas.py` 写输入/输出模型。
2. `main.py` 用 `APIRouter` 实现三个接口：查询集合、新增、查询单个。
3. 启动服务，打开 `/docs`，确认出现对应分组。

**预期输出**：`/docs` 出现对应分组；查询 200、新增 201、查询不存在的编号 404。

**可以直接改写 [starter/](starter/)**：骨架已按教材 3.4–3.5 的写法搭好，可运行，但仅有列表接口完成；`main.py` 中的两处 TODO 对应本步骤。骨架使用执勤电子年鉴中的“工位”演示机制（字段取自 `项目参考/duty` 的工位表），**提交时须替换为自己选定的对象**，并同步修改设计文档中的表、接口与目录三节。若选择工位，字段与规则仍须自行设计，不得直接提交骨架。

实现范围以教材为准：查询集合、新增、查询单个为必做；`PUT` 与 `DELETE` 只设计、不实现，须在设计文档中注明。

需要看清每一步的代码变化时，按 [分步实现指南.md](分步实现指南.md) 的五个阶段推进：① 路由与空列表（200）→ ② 模型与输出过滤 → ③ 新增（201/422）→ ④ 查询单个（404）→ ⑤ 规则性失败（400，可选）。每个阶段结束都应能运行并验证一个状态码。

**做错会看到什么**

- 接口全 404：`APIRouter` 的 `prefix` 与 `include_router` 的 `prefix` 未都写，单复数不一致。
- 非法请求仍成功：接口参数未声明为模型类型，或字段约束没有写在模型里。
- 输出带出内部字段：未使用 `response_model` 过滤。

按第 3 章 3.4–3.5 的前缀、模型与 `response_model` 逐项排查。

**检查点**

- [ ] 服务能启动，`/docs` 可打开
- [ ] `/docs` 中分组名与模块 `tags` 一致
- [ ] 新增的记录能在查询集合中看到
- [ ] 查询不存在的编号返回 404，而不是 200 或 500

### 步骤 6：验证状态码与提交（10 分钟）

**做什么**

1. 在 `/docs` 中依次制造 200、201、404、422，每次记录实际状态码。
2. 填写 [记录表.md](记录表.md) 的「接口验证记录」。
3. 核对两组对应：表字段与接口返回字段；模块目录与六个文件。
4. 整理三项交付物并提交。

**预期输出**：四种状态码都出现；每组对应都能指出具体依据。

制造四种状态码的操作：

| 状态码 | 制造方式 | 责任方 |
| --- | --- | --- |
| 200 | 查询列表或查询单个已存在的记录 | 接口正常返回 |
| 201 | 新增一条合法记录 | 接口正常返回 |
| 404 | 查询不存在的编号 | `HTTPException(404)`，业务规则 |
| 422 | 提交缺少必填字段或类型不符的请求体 | Pydantic 在进入函数前拒绝 |

**做错会看到什么**：错误都返回 500 或 200。500 说明异常未被处理；200 说明失败分支没有拒绝请求。按第 3 章 3.2 的状态码责任表判断该由谁拒绝，再改代码。

**检查点**

- [ ] 四种状态码在记录表中各至少一行
- [ ] 每行的“实际状态码”与“预期状态码”一致，不一致的行有差异说明
- [ ] 两组对应各有具体依据，不写空结论
- [ ] 设计文档与代码不一致处已记录，未擅自以任一方为准

## 九、验收标准

按三项判定，建议权重如下：

## 十、排错清单

| 现象 | 先查什么 |
| --- | --- |
| 表字段与接口返回字段不一致 | 以设计文档为清单，逐字段对照 schema 与表设计 |
| 模块目录与模块清单不对应 | 每个模块一个文件夹；六文件是否齐 |
| 接口组缺动作 | 对照 4.4 的五动作表，补齐或说明为什么不提供 |
| 参数来源错误 | 定位单个资源用路径参数；筛选分页用查询参数；提交数据放请求体 |
| 设计文档与代码不一致 | 先记录差异，再判断改文档还是改代码；不要默认以任何一方为准 |
| 422 与 400 混用 | 输入不符合约定交 422（Pydantic）；业务规则不满足交 `HTTPException(400)` |
| 非法请求仍成功 | 接口参数是否声明为模型类型、字段约束是否写在模型里 |
| 输出带出内部字段 | 是否用 `response_model` 过滤字段 |
| `/docs` 打不开或接口全 404 | 服务是否启动、`include_router` 的两段前缀是否都写、单复数是否一致 |
| 端口已被占用 | 换端口启动：`uvicorn main:app --reload --port 8001` |
| `ModuleNotFoundError: fastapi` | 依赖未装到当前解释器；确认 `python -c "import fastapi"` 与启动命令使用同一 Python |
| 修改代码后页面无变化 | `--reload` 未生效或启动失败；查看终端最近一次报错 |
| 对照 `项目参考/duty` 后发现路径为单数、删除返回 200 | duty 为早期实现：前缀 `/api/v1/workstation`，`DELETE` 返回 200 与消息文本。本实训按第 4 章 4.4 的约定（复数资源名、删除 204）设计与判定；该差异记为“已知不同”，可在课后扩展中讨论两种取舍 |
| 返回 500 且终端有 `ResponseValidationError` | 返回值与 `response_model` 字段不匹配，检查字段名与是否缺字段 |

## 附录 B：状态码速查

| 状态码 | 含义 | 本实训中的来源 | 不得用于 |
| ---: | --- | --- | --- |
| 200 | 成功 | 查询成功 | 新增成功（应为 201） |
| 201 | 已创建 | 新增成功 | 查询与修改 |
| 204 | 成功且无内容 | 删除成功（本实训只设计） | 需要返回被删记录的场合 |
| 400 | 请求不合法（业务规则） | 工位编号重复（本实训只设计） | 字段缺失或类型错误（应为 422） |
| 404 | 资源不存在 | 按编号查询不到记录 | 参数格式错误 |
| 422 | 参数不符合约定 | Pydantic 校验失败 | 业务规则不满足（应为 400） |
| 500 | 服务器内部错误 | 未处理异常 | 任何可预期的失败 |

详细的责任划分见第 3 章 3.2。
